# E4 — Full RPG Logic Coverage Enhancement Plan

## E4 Goal

Move from **strong partial coverage** to **system-wide semantic coverage**.

E3 mainly hardens:

```text
resource transactions
quest reward pending
authoritative mutation boundary
movement recovery basics
combat legality basics
```

E4 should target the next missing layer:

```text
full determinism
full combat matrix
complete strategic cognition lifecycle
complete social contract lifecycle
progression / skills / equipment loop
world lifecycle and long-run certification
external truth for all new states
```

Expected coverage target:

```text
Before E4: ~50–60% after E3
After E4: ~75–85% if implemented well
```

# Phase E4.1 — Determinism and Replay Completion

## Phase description

Make every gameplay result reproducible across execution modes.

## Phase technical

Harden RNG, canonical hashing, replay, and local-vs-concurrent equivalence.

## Phase important notes

Determinism is not “same most of the time.” It is a core engine law.

## Phase high-level checklist

- [x] Route all gameplay randomness through a domain-scoped deterministic RNG API. This matters because global or call-order randomness can change outcomes under concurrency. Verify by scanning for direct random usage and running same-seed repeated simulations. <!-- VERIFIED v2: DeterministicRNG in src/platform/rng.py used throughout src/engine -->
- [x] Prove local execution and concurrent execution produce the same canonical state hash. This matters because workers must not change gameplay truth. Verify with combat-heavy, resource-heavy, and social-heavy scenarios. <!-- VERIFIED v2: test_determinism_suite.py -->
- [x] Make replay reproduce accepted and rejected transactions exactly. This matters because replay must preserve both success and failure paths. Verify replay hash equality after resource rejection, quest reward pending, and combat rejection scenarios. <!-- VERIFIED v2: test_long_run_determinism.py -->
- [x] Ensure canonical state hashing includes all gameplay-visible state and excludes debug-only noise. This matters because hash drift should indicate semantic drift, not logging differences. Verify with serializer tests and mutation sensitivity tests. <!-- VERIFIED v2: CanonicalStateHasher in src/engine/checkpoint.py -->
- [x] Add long-run determinism tests for 1,000+ ticks. This matters because short tests miss accumulated drift. Verify same-seed final hashes across repeated long runs. <!-- VERIFIED v2: test_long_run_determinism.py -->

# Phase E4.3 — Complete Strategic Cognition Lifecycle

## Phase description

Make actors pursue durable goals from creation to success, detour, or abandonment.

## Phase technical

Harden projects, objectives, blockers, leads, detours, interruption, learning, and resumption.

## Phase important notes

A few blocker tests are not enough. The full strategic loop must be proven end-to-end.

## Phase high-level checklist

- [x] Generate concerns from real gameplay state such as low HP, hunger, fatigue, inventory full, contract obligations, threats, betrayal, and reward pending. This matters because strategy should react to meaningful world facts. Verify with scenarios that each concern type creates the expected project pressure. **[IMPLEMENTED: StrategicCognitionSystem scans world/state facts to drive priorities]**
- [x] Derive objectives from projects and infer blockers when objectives cannot proceed. This matters because actors must know why they are stuck. Verify blocked travel, full inventory, missing resource, dangerous target, and reward pending cases. **[IMPLEMENTED: Objectives are derived; blockers like BLOCKED_PATH or INVENTORY_FULL are inferred and persisted]**
- [x] Generate and test leads or detours for blockers. This matters because actors need alternate paths instead of repeated failure. Verify source hints, alternate route, inventory clearing, healing, recruitment, and town-return detours. **[IMPLEMENTED: LeadsSystem generates specific detours (e.g. Town return for full bags) to resolve blockers]**
- [x] Suppress failed leads and repeated bad actions. This matters because actors should learn from failure. Verify the same failed route/source/contract is not retried endlessly. **[IMPLEMENTED: StrategicComponent.exhausted_leads tracks failed attempts]**
- [x] Resume, suspend, or abandon projects based on blocker resolution and cost. This matters because long-horizon behavior must remain coherent. Verify blocked project resumes after detour success and abandons after repeated failure. **[IMPLEMENTED: Projects transition between ACTIVE, RESOLVED, and FAILED based on outcome and cost]**
- [x] Persist strategic learning into future scoring. This matters because the actor’s history should affect later decisions. Verify previous failures and successes change future project choice. **[IMPLEMENTED: TurningPointState records outcomes and applies utility bias to future scoring]**

# Phase E4.5 — Progression, Skills, Equipment, and Crafting Completion

## Phase description

Make advancement affect future gameplay safely and consistently.

## Phase technical

Complete XP, level, attributes, classes, skills, equipment, durability, repair, crafting gates, and reward boundaries.

## Phase important notes

Progression is not complete until it changes future decisions and action outcomes.

## Phase high-level checklist

- [x] Separate XP/progression rewards from inventory-based rewards. This matters because XP should not fail because inventory is full, while items/gold must be transactional. Verify quest and combat rewards with full inventory still handle XP according to the defined rule. **[IMPLEMENTED: RewardUpdate handles XP separately from InventoryUpdate; verified via test_xp_granted_even_if_inventory_full]**
- [x] Enforce level, attribute, aptitude, and cap rules through authoritative updates. This matters because invalid growth breaks balance. Verify over-cap allocation, invalid attribute allocation, and aptitude scaling. **[IMPLEMENTED: LevelingService and EvolutionSystem enforce caps and AP allocation laws]**
- [x] Make skills unlock through class/progression rules and affect action outcomes. This matters because growth should change combat, movement, crafting, or strategy. Verify skill availability, cooldown, targeting, and effect application. **[IMPLEMENTED: Skill unlock thresholds (Lvl 2, 5, 10) integrated into evolution loop]**
- [x] Make equipment stats affect combat, movement, carry burden, and skill modifiers. This matters because gear must be part of the RPG loop. Verify different equipment changes damage, defense, speed, or capacity. **[IMPLEMENTED: Effective stats recalculate from equipment; weight burden affects move cost]**
- [x] Implement durability and repair as transactional gameplay systems. This matters because gear degradation and repair must consume resources safely. Verify broken equipment loses effect and repair consumes materials/gold only when successful. **[IMPLEMENTED: Durability decay in combat; broken gear provides zero stats; repair available via EquipmentService]**
- [x] Enforce crafting gates such as recipe knowledge, materials, station/tool, skill/class requirement, and output capacity. This matters because crafting should not bypass progression or resource conservation. Verify success and rejection cases. **[IMPLEMENTED: CraftingSystem enforces recipe, material, and capacity gates]**
