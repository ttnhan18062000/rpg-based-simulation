Where the Engine Sits in the Simulation Design Space

A pattern-by-pattern audit of this engine's actual, documented architecture against the general taxonomy of simulation-architecture design patterns used across games, robotics, physics engines, digital twins, and distributed simulation (108 named patterns, grouped into 12 concern categories).

The goal is threefold: give the patterns already in use here their established names (several are real, strong matches the engine docs never actually name), separate genuine architectural gaps from things that are simply out of scope for a single-authority, non-distributed, non-physics engine, and keep an honest record of what wasn't verified rather than guessing.

Implemented — Live and documented in the engine as it stands today. Partial — Real overlap with the pattern, but not a clean, full match. Planned gap — Documented as intended, wired for, or ticketed — not built yet. Architecture-enabled — Not built as this pattern, but a verified primitive elsewhere in the codebase would combine into it with real, modest new work. Not applicable — Out of scope for a single-authority, non-distributed, non-physics engine — not a defect. Unconfirmed — Plausible but not verified against docs in this pass — flagged for follow-up, not claimed.

The short version, before the detail. 108 patterns across 12 categories is a lot to read end to end — this table is the whole thing at a glance. Totals: 36 implemented, 14 partial, 1 planned gap, 4 architecture-enabled, 6 unconfirmed, 47 not applicable.

Determinism & Consistency

The load-bearing pillar everything else in this table is judged against.

2 implemented · 1 partial · 3 not applicable

Deterministic Simulation

Implemented

“same seed + same initial AuthoritativeState → same CanonicalStateHasher.get_hash()” — Pillar #1 of project_lawbook_m10.md, never traded away under load.

docs/engine/deterministic_execution.md

Causal Consistency

Partial

Revised after external review, verified independently: the underlying behavior is real and strong — the “Sliding State” rule means if Actor A kills Target T this tick, Actor B (later in the queue) sees T as dead and gets no kill reward. But “Causal Consistency” has a specific distributed-systems meaning (independent replicas observing causally-related updates in the same order) that doesn't strictly fit a single-authority system with no replicas at all. The more accurate name for what's actually built is Deterministic Sequential Resolution — canonically ordered (class priority, then local priority, then entity ID), applied one proposal at a time within Resolution, each seeing the effects of everything already applied ahead of it that tick.

docs/engine/authoritative_pipeline.md §Action Routing

Checkpointing / Snapshotting

Implemented

Revised after external review flagged the original citation as a hash, not a real checkpoint — correct on that distinction, but the conclusion (downgrade to unconfirmed) turned out wrong once the actual code was checked: ScenarioCheckpointer.save()/.restore() pickle the full AuthoritativeState plus tick and RNG checkpoint to a file and reconstruct a live, resumable Kernel from it — exposed via POST /api/v1/scenarios/{id}/checkpoint and /restore/{name}, and covered by tests. Scoped to ScenarioRuntimeService (certification/scenario contexts, INFRA-215/E31C), not the live API-served world. This is a genuinely different mechanism from the per-tick SHA-256 hash cited under Deterministic Replay below, which proves state identity but cannot reconstruct state on its own — the two were conflated in the first pass of this document.

Named in the taxonomy, unnamed in our own docs

Two patterns above are strong, deliberate matches for how the kernel actually works, but docs/architecture/kernel_concurrency_design_philosophy.md reconstructs the same reasoning from scratch each time rather than pointing at the established vocabulary:

Bulk-Synchronous Parallel (BSP) — Collection is a parallel superstep, future.result() is the global barrier, Resolution is the serial synchronization phase. This is the textbook BSP loop.

Functional Core / Imperative Shell — Collection computes against frozen, read-only snapshots (the functional core); only the AuthoritativeApplyPipeline in Resolution commits (the imperative shell).

Cross-referencing both terms in that doc costs one line each, gives future readers the established name for free, and changes no behavior.

The genuine gaps, separated from “not applicable”

Interest Management is the one pattern in this table the project's own docs already flag as planned-but-unbuilt — the WS wire format reserves a region_id field today, unpopulated, explicitly deferred to TCK-20260821-EPIC-LIVE-MAP-INTEREST-MANAGEMENT.

ECS and the Actor Model are real, named mismatches — not gaps to close, just worth being precise that this engine is neither of those things despite surface resemblance (entity-like objects; per-tick worker dispatch).

Event Sourcing and Command/Input Log are partial: the replay/hash trail is real and does its verification job well, but it proves and detects divergence rather than being the mechanism state is actually reconstructed from.

Everything marked Unconfirmed above (Behavior Trees, GOAP, Fault-Injection/Chaos testing, LOD, Time-Dilation) is a genuine open question for a future pass, not a claimed absence — the relevant docs simply weren't opened this session.

Results were mixed, which is the point of checking:

Right, and adopted: the review argued the per-tick SHA-256 hash cited for Checkpointing / Snapshotting proves state identity but can't reconstruct state, so it isn't really a checkpoint. That distinction is correct. Its suggested fix — downgrade the pattern to unconfirmed — was not adopted, because grepping the codebase for a real one instead of assuming it didn't exist turned up ScenarioCheckpointer (src/engine/scenario_checkpoint.py): it pickles the full AuthoritativeState plus tick and RNG checkpoint, restores a live resumable Kernel from that file, is exposed over REST (POST /api/v1/scenarios/{id}/checkpoint and /restore/{name}), and is covered by tests. The pattern stays Implemented, cited correctly now instead of conflated with the hash.

That same discovery validated the review's separate, more speculative claim that checkpointed branching is a natural extension of this architecture: restoring one checkpoint into multiple independent Kernel instances is a real, tested primitive, so Shadow, What-If, Branching, and Counterfactual Simulation moved from Not Applicable to a new Architecture-enabled status — the primitive exists, the orchestration on top of it doesn't.

Right on its own terms: the review's objection to calling the Sliding State rule “Causal Consistency” is a fair terminology correction — that term has a specific distributed-replicas meaning this single-authority engine doesn't have occasion to use. Downgraded to Partial with the more accurate name (Deterministic Sequential Resolution) noted in its card.

Prompted a closer look, revised more narrowly than proposed: the review questioned whether Record-and-Replay was really implemented. Checking replay_manager.py directly confirmed it has no restore/reconstruct path — its persisted events are for offline comparison, not reconstruction. But the review's framing implied nothing like real record-and-continue existed; ScenarioCheckpointer's save/restore/resume is exactly that, just via full-state snapshot rather than an input log. Downgraded to Partial, with the corrected mechanism cited.

Noted, not adopted into the grid: the review's broader reframings — naming the whole architecture Two-Phase Simulation / Intent-Resolution, elevating Single-Writer Principle as its own named invariant, an Amdahl's-law serial-fraction framing of the Resolution-phase bottleneck, and splitting Presentation LOD from Simulation LOD — are reasonable synthesis and worth a future pass, but they're this reviewer's interpretive framing rather than checkable facts about what's built, so they aren't reflected as verdicts above.
