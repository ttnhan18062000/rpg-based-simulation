Discussion Brief: The Layer Model Above Entity (City / Country / Clan / Race)
================================================================================

This is an open discussion, not a review or an ideation request. Nothing here
needs to be "fixed" or "added to" -- the goal is genuine back-and-forth about
whether this holds together and what it implies for other parts of the design.

Where to read it
-------------------
Everything referenced here lives in the engineering atlas:
https://claude.ai/code/artifact/23feda01-9857-4508-a014-3caa61bdbd07

Specifically: "The Layer Model" section near the top (the diagram and its
explanatory text), the "Clan Layer" and "Race Layer" sections, and Design
Ideas 35 through 37 (the wiring proposals). The rest of the atlas is there
for supporting context if useful, but these are the parts under discussion.

How this came about
----------------------
The project has an existing scale hierarchy: Entity -> Group -> Faction ->
Region -> World, taken directly from the actual simulation's own code
structure. After a long investigation into the Entity layer specifically
(covering how a character acts, who they are, how injury changes them, and
how they think), the question came up: is Entity "healthy" as a layer, using
a specific test -- does it have a complete lifecycle, a clear boundary, and a
coherent domain, and how far does its influence actually reach?

That test surfaced a mismatch: the person driving this project has an
intuitive mental model of scale that goes Entity -> City -> Country -> [a
membership-based tier, like a Clan] -> Race -> World, with Race being
described as "a significant force" bigger than a Country. That doesn't map
cleanly onto the existing Group/Faction/Region/World code structure, so a
direct investigation was done to find out what's actually real:

- Region turned out to already be roughly city-scale in practice (about 20
  buildings per region in realistic test scenarios, with real population,
  siege, and local-economy state) -- relabeled City rather than treated as
  a new layer.
- Faction turned out to already support many real, independent instances
  (16 distinct factions exist in the game's content today, each with its
  own territory, diplomacy, and military state) -- relabeled Country. This
  corrected an earlier wrong claim in the same conversation that Faction was
  hardcoded to exactly four instances.
- A real gap was found instead: a region's owning faction is tracked by two
  separate mechanisms that don't agree with each other, and conquest
  attribution collapses onto one hardcoded faction name regardless of which
  faction actually did the conquering.
- Clan and Race were both confirmed to have zero existing representation in
  the codebase -- not thin implementations, genuinely absent. Both were
  added as new layer-model tiers, explicitly linked to the others: City is
  contained in and owned by Country; Clan spans membership across multiple
  Cities and Countries rather than belonging to one; Race's population is
  distributed across multiple Countries the same way.
- Three wiring proposals were then written (Design Ideas 35-37), each
  reusing an existing mechanism rather than inventing a new one: unifying
  the split ownership-tracking system, giving Clan the same shape as
  Faction but with membership instead of territory, and wiring a new
  race-relations concept into hostility/targeting logic that already reads
  an entity's race today.

None of this is implemented. All of it is design work, evaluated the same
way -- checked against what's actually in the codebase before being written
down, not invented freely.

What's worth discussing
--------------------------
1. Does the layer model itself pass its own test? Apply the same standard
   used to evaluate Entity -- complete lifecycle, clear boundary, coherent
   domain -- to City, Country, Clan, and Race as now defined. Where does it
   hold up, and where does it feel thin or arbitrary?

2. The relationship types. Three different kinds of link were used:
   containment (City in Country), membership-spanning (Clan across
   Cities/Countries), and population-distribution (Race across Countries).
   Is that the right set, or is something being conflated that shouldn't
   be, or split that shouldn't be?

3. Implications for the reproduction/marriage/coming-of-age design (a
   separate, already-detailed part of the atlas, Design Ideas 32-34).
   That design was built before this layer-model revision. Now that City,
   Country, Clan, and Race exist as real concepts: should a marriage
   record which City/Country the couple belongs to? Does a City's own
   population health interact with reproduction's population-pressure
   gate, or are those meant to stay separate? Does Clan membership matter
   for who a family might arrange a marriage with? Does the new
   race-relations idea (37) have any bearing on the existing rule that
   marriage/reproduction require the same race -- for instance, could
   hostile race relations someday make even same-race pairings across
   certain political lines meaningfully harder, the way Country-level
   diplomacy already can?

4. What's the biggest thing this layer model doesn't address yet? Not "what
   feature is missing" -- more architecturally: is there a phenomenon at
   this scale (city, country, clan, or race level) that doesn't fit
   cleanly into any of the four link types described above?

How to respond
-----------------
Open-ended is fine. If something seems well-reasoned, say so and why. If
something seems shaky, say so and why. If a question above leads somewhere
interesting, follow it. This is meant to surface genuine perspective, not
produce a checklist of action items.
