RPG Schema Registry

Field-level schemas for the atlas's proposed ideas — not prose descriptions of target behavior, but the actual typed shape each feature needs, so ambiguity like "is City a kind of Region or does Region contain Cities?" gets caught before a ticket is written, not after.

Prompted directly by that exact ambiguity surfacing in idea 66, then expanded twice on direct request: first to cover all 30 proposed ideas that introduce new durable state (not just the highest-leverage 9), then to also track the existing live schemas — even the ones with no proposed change — so this is the one page to check for any RPG feature’s real current shape, plus what’s planned to change about it. A third dimension catalogues hardcoded values in the live codebase that behave like they should be schema-driven instead of Python literals. A fourth, added on direct request, specifies the expected runtime events each idea should emit — real event names, payloads, triggers, and SimQ pillar/scenario mapping — the layer between durable state and being actually gradeable, which neither M7 nor M9 pre-specifies. A fifth, its counterpart, distinguishes what should be real YAML config (catalog-shaped, multi-instance) from what belongs in Hardcoded Logic instead (single tunable scalars) — a real, code-confirmed dividing line, not an arbitrary split.

New — no equivalent exists in code today Reused — an existing real class/field, unchanged Extended — an existing field/enum gains a new value Open question — a real design decision not yet made

Expected Events

The third dimension this registry is missing until now: durable state (above) is what an idea persists; an event is the runtime signal SimQ actually counts to score it. Ownership split (2026-08-29, reconciled with docs/brainstorm/codex/2026-08-27-core-rpg-plan-brainstorm-update-request.md): each M2-M6 feature ticket owns defining its own real event type, payload, and trigger as part of its own Definition of Done, not M7 — M7 verifies completeness and calibrates the aggregate scoring rules afterward. M7 deliberately defers naming real event types until after M1-M6 ship ("speculating against code that hasn't been written"); M9 names which pillar each idea should register against but never the actual event name or payload. This section closes that gap ahead of implementation, the same way the State sections above closed it for durable fields — grounded directly in the real event system: every event is a SimulationEvent (src/observability/events.py), snake_case event_type, a fixed EventCategory enum, plus tick/entity_id/related_entity_ids/severity/source_system and event-specific typed fields; scoring reads a flat payload: dict via .get() (src/simulation_quality/score_record.py).

Do any of these need a genuinely new SimQ pillar, not just a new scenario within an existing one? Checked directly, not assumed: every one of the 32 ideas maps onto the existing 10 pillars (COMBAT, PROGRESSION, ECONOMY, FACTION, SOCIAL, INFORMATION, AGENCY&ACTION, COGNITION, WORLD DYNAMICS, NARRATIVE). Five need a genuinely new scenario entry within an existing pillar (SQ-25 through SQ-29, below) — none need an 11th pillar. The one idea that could plausibly have forced a new pillar — 63 (Belief/Religion) — is too underspecified to build one around responsibly; that's a door worth leaving open for later, once the idea itself has real shape, not forcing now on spec.
