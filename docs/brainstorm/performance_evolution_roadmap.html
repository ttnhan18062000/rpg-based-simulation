What's Actually Left to Optimize

An external AI, asked how it would optimize this engine's performance while preserving determinism, produced 20 concrete ideas (22 of them individually checked here). The premise of that note was sound — sacrifice freshness, fidelity-for-low-value-entities, and immediacy before ever touching determinism or the single-writer model. But checking each idea against the actual code turned up something the note couldn't have known without reading it: a large fraction of what it proposes building is already built.

This isn't a rubber stamp on that note, and it isn't a dismissal of it either — it's what's left standing after checking, plus my own read on what to actually do next.

Already built — Verified in production code today — proposing this as new work would be redundant. Partially built — A real mechanism exists and helps, but doesn't cover the full idea as proposed. Architecture-enabled — The safety precondition or building block is verified real; nothing built for this specific use yet. Genuinely open — Checked — this does not exist yet. A real, unclaimed opportunity. Correctly out of scope — Would solve a problem this single-authority engine doesn't have; agreed. Unconfirmed — Plausible but not verified this pass.

The headline number. Of 22 performance ideas checked: 8 are already built and running, 4 are partially covered by an existing mechanism, 2 have a verified enabling primitive but no feature built on it, 7 are genuinely open, and 1 are correctly out of scope by the review's own reasoning.

Already running in production

The single biggest finding of this pass: several of the review's proposals aren't proposals. They're already load-bearing, documented, tested mechanisms — checked directly against the code, not assumed from either document.

8 already built

Dirty / affected-set processing (idea #2)

Already built

The dirty-flag system's own doc calls it “the primary optimization layer in the tick pipeline.” CandidateSelector.entities() already returns only the relevant entity IDs per phase and skips clean ones — PERF-005 through PERF-015, with 10 causal expansion edges. Not a future direction; the current one.

docs/core/dirty_state_and_dependency.md; docs/engine/candidate_selection.md Tier 2

Deterministic multi-rate scheduling (idea #3)

Already built

DeterministicScheduler.select_work() already gates on tick % entity.strategic_cadence == 0. MovementCandidateSelector already throttles wandering entities on tick % wander_modulo == 0. Both are exactly the “tick % N == entity_phase” deterministic temporal partitioning the review proposed building.

docs/engine/candidate_selection.md Tiers 1 & 3

Deterministic simulation LOD (idea #5)

Already built

DeterministicScheduler.select_work() already carries an explicit LOD tier (A/B/C) that gates full vs. simplified work items by distance/priority. This one also corrects the design-taxonomy document itself, which had marked LOD Unconfirmed — fixed there too, same pass.

docs/engine/candidate_selection.md Tier 1

Readiness / demand-driven gating

Already built

Entities below entity.readiness >= 100 receive no work item at all this tick. The taxonomy document had marked Demand-Driven Simulation Not Applicable — also wrong, also fixed.

docs/engine/candidate_selection.md Tier 1

Frozen-snapshot caching (part of idea #9)

Already built

Collection-phase freezing is not a fresh deep-copy every tick: get_frozen() caches each frozen object keyed by Python id(), and only re-freezes when the underlying object's identity actually changed. The “if freezing means deep-copy the world” premise behind idea #9 doesn't hold as stated.

src/engine/executor.py (CORE-PERF-020)

Full-hash rate limiting (part of idea #14)

Already built

A full SHA-256 canonical hash is already rate-limited to a budget per 100-tick sliding window, falling back to a stale cached hash and logging a WARNING when the budget is exhausted — plus a separate guard that rejects FULL-hash calls outside sanctioned boundaries (start-of-run, shutdown, certification/audit/replay). The “hashing the whole world every tick is a hidden cost” framing undersells what's already there.

src/engine/checkpoint.py (BudgetedCanonicalHasher)

Type-batched Resolution (idea #15, structurally)

Already built

The 37 named phases (movement_routing, action_routing, resource_transactions, ...) already partition Resolution by intent type at the macro level — each phase touches only its own kind of proposal. The idea as “batch by type instead of one giant undifferentiated loop” is the existing shape of the pipeline, not a change to it.

docs/engine/authoritative_pipeline.md

Semantic vs. execution determinism (idea #17)

Already built

Already the documented philosophy, word for word in spirit: “same seed + same profile + same inputs => bit-identical state,” defined over the canonical sorted output, never over which thread executed which entity. This is the existing design rationale, not a new principle to adopt.

docs/architecture/kernel_concurrency_design_philosophy.md

Partially there — the idea is real, the coverage isn't complete

Verified mechanisms exist, but each stops short of the review's full proposal in a specific, checkable way.

4 partially built

Structural sharing across the whole world (idea #8/#9)

Partially built

The per-collection-object freeze cache (regions, resource_nodes, buildings, groups, corpses, ground_items, terrain) already avoids re-freezing unchanged objects. What's not confirmed: copy-on-write / persistent-tree structural sharing across the whole AuthoritativeState on every Resolution commit, which is what idea #8's generation-swap diagram actually describes.

src/engine/executor.py (CORE-PERF-020)

Reducing hashing's per-call cost (rest of idea #14)

Partially built

BudgetedCanonicalHasher controls how often a full hash runs, not how expensive each call is — CanonicalStateHasher.to_canonical_data() still walks and JSON-serializes every entity/region/node/building/corpse/item every time it does run. Hierarchical/Merkle-style incremental hashing (only rehash dirty leaves) is still a real, unclaimed idea for the calls that do happen.

src/engine/checkpoint.py

Precompute static tables (idea #19)

Partially built

ContentWarmupService.warmup() confirmed eager-loading all content singletons before tick 1, specifically to keep the tick hot path free of lazy loads. Whether every table the review lists (terrain movement costs, region adjacency, probability tables) is specifically precomputed wasn't checked item-by-item this pass.

docs/engine/kernel.md §Content Hot-Path Guard

Separate simulation rate from broadcast rate (idea #13)

Partially built

WS deltas are already suppressed entirely on quiet ticks (except a 20-tick heartbeat) — so broadcast frequency already diverges from simulation frequency when nothing changed. Per-client or per-distance broadcast-rate tiering (nearby entities at 12 Hz, far entities at 2 Hz) specifically is not confirmed.

docs/engine/contracts/api_protocol_contract.md §2

Architecture-enabled — the primitive is real, nothing is built on it yet

Same status tier introduced in the design-taxonomy document's own revision, for the same reason: a verified building block exists, but no feature was built from it.

2 architecture-enabled

Dynamic work-stealing among Collection workers (idea #16)

Architecture-enabled

The safety precondition the review names — worker completion order must never influence semantic application order — already holds today, verified: Resolution sorts every result by (class_priority, -local_priority, entity_id) before applying anything. But WorkerManager.execute_batch() currently slices packets into static contiguous chunks (packets[i:i+chunk_size]), not a work-stealing queue. Safe to build; not built.

src/engine/worker_manager.py; docs/architecture/kernel_concurrency_design_philosophy.md Part 3

Branch/checkpoint-based tooling (idea #12 in the review's priority table)

Architecture-enabled

Directly reuses the finding from the design-taxonomy document's external-review response: save()/restore() already round-trip full AuthoritativeState + tick + RNG through a live, resumable Kernel, over a tested REST API. What-if/branch/shadow-simulation tooling built on top of it doesn't exist yet — but for a performance roadmap specifically, the more immediate use is cheap, repeatable before/after benchmarking from a fixed checkpoint, which needs no new tooling to start doing today.

src/engine/scenario_checkpoint.py (ScenarioCheckpointer)

Genuinely open — checked, and these really are unclaimed

No existing mechanism found for any of these. Real opportunities, not restatements of what's already there.

7 genuinely open

Data-Oriented hot-path projections / SoA (idea #1 & #11 & #18)

Genuinely open

Entity state stays OO (EntityState objects) all the way through Collection — no SoA/array projection layer for hot fields (position, health, goal_id) was found. The review's own hedge (“you do not need to convert the whole engine to ECS”) is the right framing: a narrow, opt-in hot-view projection for Collection's tightest loops, not a rewrite.

src/entities/; src/engine/executor.py

Spatial domain decomposition as the parallelism unit (idea #6)

Genuinely open

Confirmed: chunk_size = max(1, len(packets) // max_workers), then packets[i:i+chunk_size] — a flat index-range split, not region-aware. Assigning whole regions to workers instead is a real, unclaimed change, and composes cleanly with the spatial grid that already exists for proximity queries.

src/engine/worker_manager.py

Hierarchical / aggregate simulation for distant regions (idea #4)

Genuinely open

Region/world layers exist conceptually (sovereignty, regional trauma) but nothing aggregates a whole region's population into a cheaper macro-model when it's not being observed. Highest ceiling of anything on this list; also the most invasive and the easiest to get wrong deterministically.

docs/mechanics/06_worldbuilding_foundation.md

Job / task-graph for independent subsystems (idea #7)

Genuinely open

The 37 phases run strictly sequentially today. Some are provably independent of each other's inputs within a tick (e.g. weather vs. shop pricing) and could run concurrently before their outputs merge — but nothing does this yet, and proving independence correctly is the hard part.

docs/engine/authoritative_pipeline.md

Deterministic memoization by input signature (idea #10)

Genuinely open

No evidence of a signature-keyed memoization layer for expensive pure functions (pathfinding, utility scoring, perception queries). Determinism makes this unusually safe to add — same input genuinely does mean same output here — but nothing does it yet.

Both are already built, which changes what actually belongs at the top of a real roadmap. This list only contains items confirmed Genuinely open or Architecture-enabled above — nothing that's already running made the cut twice.

Where I'd add to this

Two things beyond adjudicating the review's list:

Measure before you build DOD. The review calls hybrid Data-Oriented Design “probably one of your highest-value changes,” using a mental model of “10,000 entities” hitting Collection every tick. But the readiness/cadence/LOD gates already verified above mean the real per-tick working set is very likely far smaller than the full population — and DOD's payoff scales with how large and uniform that working set actually is. TickAudit already records phase costs; get the actually-processed-entity count out of it before committing to an SoA rewrite. It's possible the gates already did most of this optimization's job.

The review didn't know about ScenarioCheckpointer, and that changes its own recommendations. It correctly points out that measuring serial_fraction = (T_sort + T_resolution + T_hash) / T_tick matters more than worker count — but the tool to actually gather that number cheaply and repeatably already exists: checkpoint a running scenario, restore it, and benchmark from a fixed, reproducible starting point instead of a fresh cold-start every time. That's available today, with no new engineering, before any of the 8 items in the priority table above.
