§1

Executive recommendation

This system does not need more architecture. It needs the architecture it already has to be enforced instead of documented, bounded instead of unbounded, and measured instead of assumed. That diagnosis survives this deeper pass — but the deeper pass changes what counts as "next": not a flat priority list, but a small set of Committed changes that are genuinely ready to ticket today, a smaller set of Experiments designed to produce evidence rather than ship a feature, and a explicitly preserved set of Future Options that stay un-ticketed until their prerequisite evidence exists.

Nothing in the Committed set requires new infrastructure this repository doesn't already have the pieces for. The one genuine experiment — a filtered agent-evaluation replay — is deliberately sized small (20–40 tickets, not the full 1,099-ticket eligible pool) with a dev/validation/holdout split, because a small trusted benchmark beats a large untrusted one. And nothing that increases agent autonomy (model routing, one-click workflow resume, blocking security enforcement) is Committed — each is explicitly gated behind a named decision point, not a target date.

Configuration precedence invariant

Target rule: local configuration may specialize machine-specific behavior, but may not silently widen the centrally reviewed security envelope. Formally: effective local capability ⊆ approved capability envelope. This review found no confirmed mechanism in the current harness to enforce that inclusion automatically at runtime — stated as a limitation, not assumed away. The practical fallback: a versioned, reviewed capability-envelope baseline (bucket A, §8) plus an auditable comparison script that diffs the live settings.local.json against it. That script is a check a human or CI can run, not a proven runtime guarantee that a wider local permission can never take effect. What belongs in the version-controlled baseline: the approved envelope itself. What may stay machine-local: entries within that envelope. What requires review: any local entry the diff flags as outside it.

§85

Roadmap, as three separated outputs restructured

Per §85: Committed Changes, Experiments/Measurements, and Future Options are deliberately not one backlog. Readiness is not the same as timing — READY means the design is resolved enough to write a ticket; it does not by itself mean "start today." This proposal uses three states: Start now (bucket A, horizon H0 — begin immediately), Ready, schedule later (bucket A, horizon H1/H2 — ticket-writable now, sequenced later by dependency and capacity, not by any remaining design gap), and Experiment/measurement only (bucket B — do not ticket; run the investigation first, per §83). Bucket C receives no tickets at all until its named blocker clears.

Decision gates between horizons NEW

Horizon 0 → Horizon 1 gate

All four must hold before Horizon 1's "ready, schedule later" items begin in earnest (independent H1 items like tools.jsonl rotation may start in parallel — they don't depend on this gate):

① Per-agent capability policies deployed with zero critical workflow breakage over 2 weeks. ② The Bash secret-exposure advisory hook shows an acceptable false-positive rate in normal advisory operation. ③ Both converted guardrail hooks show zero recurrence of their target failure pattern across ≥2 subsequent weekly retros. ④ knowledge-gateway archived with zero renewed calls over 2 weeks.

① Repeatable scoring established — the same config scores the same on 2 independent runs. ② Sample quality accepted for the 2 target defect classes. ③ Replay contamination risk (shared sidecar, post-hoc knowledge leakage — see §11) is understood and demonstrably controlled in the pilot's own execution.

Model routing, phase-resume automation beyond shadow, and any further autonomy increase wait here — not on a calendar date.

§65–69

Evaluation design NEW

Three levels, not one global score — and two evaluation modes with their limitations named explicitly, not assumed away.

1Role-level — is this specific agent doing its job?

Available today (Level A data): done-checker's block rate — the DOD_BLOCKED share of runs.jsonl — is a directly observed metric available now. That is not the same as its false-block rate, which requires independent adjudication of whether each block was actually correct; no adjudicated labels exist yet for any role. Everything else in this level needs a baseline collected first.

2Workflow-level — did the engineering task succeed?

3System-level — is the platform improving delivery overall?

§65's own warning applies directly to any future model-routing pilot (bucket C, blocked on this eval work): judge it on Level 1 — done-checker's block rate today, its false-pass/false-block rate once adjudicated labels exist — never on system-level DONE-rate alone, which is too noisy to attribute to a single mechanical-agent change.

Safety vs. optimization split — worked example

done-checker routing pilot (bucket C, blocked until this eval work lands) — Primary: role-specific correctness for done-checker — today that means its directly observed block rate; a true false-pass/false-block rate needs adjudicated labels the eval pilot could eventually produce. Safety: overall DOD_BLOCKED+NEEDS_CHANGES rate must not exceed the 6.3% baseline. Efficiency: latency and cost_proxy_score for done-checker specifically. The pilot is not "successful" merely because global workflow failure stayed flat — the primary metric has to move, not just fail to regress.

Metric-strength terminology, used consistently

Directly observed: block rate, DONE rate, workflow duration, tool-call volume, NEEDS_HUMAN_INPUT rate — all read straight off runs.jsonl/tools.jsonl. Derived: first-pass success (computed from DONE without a prior NEEDS_CHANGES). Requires adjudication: false pass, false block, reviewer precision/recall, ticket-scoper accuracy — none of these exist yet; they need an independent judgment of correctness the repository doesn't currently produce. This proposal names each metric it uses by which of the three it is, rather than treating "observed" and "correct" as interchangeable.

Offline replay — contamination risks, named

①The referenced repo state has moved on since a historical ticket closed — code an old investigation.md cites may no longer match HEAD. ②Shared unscoped sidecar contamination if replay isn't strictly worktree-isolated. ③Newly named this revision: the search index/graph now contain information written after the original ticket closed — an agent replaying that ticket today may "solve" it using knowledge it wouldn't have had access to originally, inflating the score.

Online shadow mode — where it's recommended here

Not for the eval pilot (offline is sufficient and cheaper there). Recommended specifically for the model-diverse reviewer routing item: run the candidate model alongside the current one on the same diffs for several weeks, comparing finding rates, before it ever gates a real workflow — a genuinely new refinement this revision adds to that item.

Dataset hygiene & starting small

The 1,099-ticket filtered pool is the eligible set, not the pilot size. First batch: 20–40 tickets, stratified across tier, layer, and success/failure (the ~88 known-failed runs in runs.jsonl give a real "failed tasks" stratum). Split into development / validation / untouched holdout before any scoring rule is tuned. Add newer closed tickets periodically so the benchmark doesn't stagnate against a fixed 2026-era corpus.

Roles, not headcount: Agent Configuration Maintainer, Workflow Runtime Maintainer, Evaluation Maintainer, Agent Monitoring Maintainer, and Repository Intelligence Maintainer describe responsibility boundaries. If this repository currently has a single maintainer holding several of these roles, that is acceptable — the point is that each responsibility has a name, not that it has a dedicated person.

Resume semantics, not just resume mechanics (§76)

A checkpoint is reusable only if workflow_version matches, the input the phase consumed is unchanged (input_hash), and every artifact the phase produced still exists on disk. All three must hold, or the workflow restarts from the earliest invalidated phase — never a blind "checkpoint exists, so skip."

Complexity budget (§79) — the three genuinely new subsystems

Rotation infra: small new surface, justified — near-100% of the growth-bounding benefit for one script and one hook edit. Eval pilot tooling: justified at pilot scale (§69 keeps it small); a full platform (H3) must re-justify itself separately, not inherit the pilot's justification. Claim detection→lock: exactly why it starts as logging-only — paying the larger complexity cost only if evidence demands it.

AI-infrastructure maintenance cost (§80)

Add two lightweight trend lines to the existing weekly retro, using data already collected: the share of closed tickets tagged agent-infra/agent-monitoring/dashboard vs. product/simulation tags (via the existing tag registry), and the count of active agent/skill files over time (16 agents, 22 skills today). Early-warning signals only — §80 explicitly rejects an arbitrary target ratio, and so does this proposal.

Detection before prevention (§77)

Applied consistently across this revision: the Bash secret-exposure hook ships advisory before it ever blocks; the ticket-claim mechanism ships as logging before it ever locks. Both follow the same unknown-risk → detect → measure → decide → prevent-if-justified pattern, not parallel one-off designs.

Secret exposure ≠ command-risk policy

The Bash secret-exposure advisory hook detects secret-shaped values in a command string — nothing more. It is not a dangerous-command policy, and not command-injection detection. Destructive filesystem/Git commands, Docker host-wide operations, remote script execution, suspicious piping, privilege escalation, and network exfiltration remain entirely unaddressed by this proposal. Per §64's own instruction, that broader policy is not designed or committed here — it would need its own evidence-backed proposal if the repository's risk profile ever justifies it.

A harness-level capability, not something this repo can build for itself. Reconsider if: the harness itself ships sandboxed execution — adopt it, don't build a parallel one.

KEEP — the weekly retro cadence

It correctly surfaced the same 2 defects for 3+ consecutive weeks — detection works.

Why: the loop's failure is that findings don't automatically become shipped fixes, not that it fails to surface them. Fix the close (§10), not the detect.

KEEP — provider-neutral orchestration contract discipline

A static check already fails on the mere presence of a provider-specific field name.

Why: unusually rigorous forward design. Only change to add the conformance test the ADR already calls for.
