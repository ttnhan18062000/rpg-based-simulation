# Ticket-Creation Handoff — Provider-Agnostic Agent Orchestration

For: Claude Code ticket creation

Source plan: [idea_provider_agnostic_agent_orchestration.md](idea_provider_agnostic_agent_orchestration.md)

## Decision Already Made

Create **one parent `epic` ticket for gated discovery only**, plus its scoped
child discovery tickets. Do **not** create provider-runtime implementation
tickets yet.

The parent follows the repository's existing `epic` tier: it scopes and tracks
children but does not implement. Each child may use an ordinary scoped tier,
but every child must repeat this containment rule:

> It may create only isolated contract, replay, fixture, diagnostic, or
> decision-record work. It must not modify production Claude/Codex workflows,
> hooks, monitoring writers, live ticket artifacts, or the shared monitoring
> JSONL corpus.

No follow-on implementation epic may be scoped as ready until all five
Discovery-Epic Acceptance Criteria in the source plan are complete,
evidence-backed, and explicitly approved.

## Required Discovery Outputs

The discovery tickets collectively must produce these five outputs:

1. `.agents/` disposition report and approved active-location map.
2. Contract-format ADR: source ownership plus adapter-generation/conformance
   approach.
3. Execution-identity and portable monitoring-writer ADR, backed by
   portability/concurrency evidence.
4. Codex capability matrix, verified from current official documentation and
   provider fixture experiments.
5. Replay-fixture specification and proof that the initial Codex slice can run
   without ticket edits, production hooks, or monitoring writes.

## Suggested Parent and Child Sequence

Use the ticket IDs/names generated by normal project conventions; the labels

the containment rule. Ticket 4 must not make the final location/identity/writer
choices before its dependencies supply evidence. Ticket 5 is last.

## Monitoring-Specific Traps

Treat executable writers/readers and the full schema as authoritative over
compact summary prose.

- `agent-monitoring/README.md` is a compact overview and is stale in places;
  its status list and simplified run identity do not cover all live outcomes
  or the planned provider migration.
- `docs/agent-monitoring/schema.md` is more detailed but documents multiple
  historical schema generations. It must be read with `tools/agent-monitoring/
  validate.py`, `record_run.py`, `record_events.py`, `vocabulary.py`, and the
  hook scripts.
- Historical data already has missing events, incomplete runs, legacy
  timestamp shapes, ad hoc run IDs, and known pre-fix tool-count attribution
  gaps. Do not combine cleanup/backfill with provider enablement without a
  separate approved scope.
- `tools.jsonl` currently relies on POSIX `fcntl.flock`; this is the concrete
  portability/concurrency problem the writer-decision ticket must address.
- Monitoring writes are best-effort by policy: a logging failure must not fail
  a user workflow. The proposed writer design still needs diagnostics and
  recovery evidence.

## Ticket-Authoring Rules

Before creating the parent or children, follow the repository context scan in
`CLAUDE.md`: semantic search, Graphify, then targeted tickets/docs/artifacts
and code. Use the registered `ai` layer and only registered tags. Keep the
parent `epic` ticket scope-only; classify discovery children accurately rather
than labeling them hotfixes.

Every child ticket must include:

- the containment rule quoted above;
- explicit out-of-scope production paths;
- a deterministic evidence/test plan;
- dependency links to the parent and prerequisite children;
- the exact required decision artifact or replay proof;
- a closure condition stating that its output is input to the five-output
  discovery exit gate, not approval for implementation.
