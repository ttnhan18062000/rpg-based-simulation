# Investigation — TCK-20260811-CAPABILITY-CONFIDENCE-ADVENTURE-SCORING

## Current Behavior

### `AdventureRouteScorer.score()` — `src/domains/adventure/scoring.py:33-300`
Static method, signature `score(entity, route, resource_nodes=None, quest_registry=None, group=None, faction_directives=None, factions=None, progression_plan=None)`. Computes
`score = urgency + benefit + personality_bias + plan_advance_bonus + memory_adjustment + confidence_bonus - risk_penalty - blocker_penalty` (scoring.py:252).

The current `confidence_bonus` term (scoring.py:244):
```python
confidence_bonus = route.confidence * 0.15
```
`route.confidence` is a **generation-time** field set once per candidate by `AdventureRouteGenerator.generate()` / `AdventureRouteOption` construction — flat literals (`0.9`, `0.8`, `1.0`), a pass-through of `opp.confidence` (generator.py:83, itself always `1.0` in both live providers — `resources.py:92`, `services.py:69/81/97/110/123`), or `min(1.0, sociability + 0.3)` for `FORM_PARTY` (generator.py:153). None of these values derive from `CapabilityEstimateService` — confirmed zero references to `self_model.capabilities`, `CapabilityEstimateComponent`, or `capability_key` anywhere in `src/domains/adventure/*.py` (`grep`: no matches). `confidence_bonus` is capped at `0.15` (weight documented in `docs/mechanics/04_strategic_cognition.md:147` and `docs/parity_ledger/strategic_cognition.yaml` STRAT-227).

The module docstring (scoring.py:6-8) states the same information-opacity boundary the memory-informed sibling ticket already interpreted: "Reads only subjective self-model and cognition/memory aspects — the entity's own beliefs, never omniscient world truth." `CapabilityEstimateService.estimate()`'s inputs (`entity.combat`, `entity.stamina`, `entity.inventory`, `entity.equipment`, `entity.identity`) are all entity-owned fields, so calling it from inside `score()` is consistent with this boundary regardless of which resolution option is chosen.

### `AdventureRouteGenerator.generate()` — `src/domains/adventure/generator.py:24-181`
Route families actually emitted today, confirmed by reading every `opts.append(...)` call site and the `kind_map` (generator.py:38-45): `GATHER_RESOURCE`, `BUY_UPGRADE`, `CRAFT_UPGRADE`, `RECOVER` (from `repair_gear`/`rest_inn` opportunities, `services.py:72-82,113-124`), `ASK_INFORMATION`, `FORM_PARTY`, `DEFER_WITH_REASON`. **`HUNT_WEAK_ENEMY` and `SCOUT_LOCATION` are never emitted anywhere in `generator.py`** — `HUNT_WEAK_ENEMY` is independently confirmed dead code by `docs/simulation/domains/adventure_contract.md:160-166` (already surfaced and re-verified by the prior sibling ticket, `stored_artifacts/TCK-20260811-MEMORY-INFORMED-ROUTE-SCORING/investigation.md:25`) and `SCOUT_LOCATION` has zero generator call sites despite the doc's "Candidate sources" table (`adventure_contract.md:99`) claiming it comes from "Region exploration targets" — a second, previously-undocumented dead-route finding this ticket's own scope surfaced (see Docs Requiring Update).

Data actually available to `AdventureRouteOption`/`generate()`/`score()` per live family, relevant to constructing a `CapabilityContext`:
- **`GATHER_RESOURCE`**: `route.target_node_id` (generator.py:75-77,90) + the `resource_nodes: Dict[int, ResourceNodeState]` parameter `score()` already accepts (used today for the depletion-fraction multiplier, scoring.py:149-155). `ResourceNodeState.kind` (`src/core/state.py:911`) is the resource identifier already used as the `ResourceRegistry.get()` key (`resources.py:65`) — this is the same string that would key `CapabilityContext.gather_resources`/`gather.resource.<resource_id>` (`capability_estimate.py:174`). Confirmed by the existing test fixture `tests/unit/domains/adventure/test_depletion_scoring.py:36-44` (`_node(node_id, remaining, max_charges)` sets `kind="iron_ore"`).
- **`CRAFT_UPGRADE`**: routes sourced from `craft_item` opportunities carry `route.requirements = opp.requirements` (generator.py:86), and `services.py:53-59` populates that tuple with `Requirement(kind="recipe_known", subject=recipe_id)` plus `Requirement(kind="has_item", subject=m_id, quantity=m_qty)` per required material — i.e. the recipe id and its material requirements are already present on the route's own `requirements` tuple, reachable without any new parameter. `recipe.gold_cost` itself is not carried through, only the `has_gold` requirement's `quantity`.
- **`BUY_UPGRADE`, `RECOVER`, `ASK_INFORMATION`, `FORM_PARTY`, `DEFER_WITH_REASON`**: none of `CapabilityContext`'s four domains (`combat_enemies`, `travel_regions`, `gather_resources`, `craft_recipes`) has an obvious, evidence-backed mapping target for these families — `BUY_UPGRADE`/`RECOVER` opportunities key to a shop/service id (`services.py`), not an enemy/region/resource/recipe id in `CapabilityContext`'s vocabulary.
- **`HUNT_WEAK_ENEMY`** (→ `combat.enemy_type.<id>`) and **`SCOUT_LOCATION`** (→ `travel.region.<id>`) are the two capability domains with the most obvious semantic mapping, but both route families are dead code (never generated) — wiring either would be unit-testable but have zero live observable effect, mirroring the sibling memory ticket's identical `HUNT_WEAK_ENEMY` finding.

### No existing `RouteFamily` → capability-key mapping convention
Confirmed by repo-wide grep: no file anywhere maps a `RouteFamily` value to a `combat.enemy_type.*`/`travel.region.*`/`gather.resource.*`/`craft.recipe.*` capability key. This ticket must originate that mapping, not follow a precedent — and per the evidence above, the only two **live** families with an evidence-backed key source are `GATHER_RESOURCE` (via `resource_nodes[target_node_id].kind`) and `CRAFT_UPGRADE` (via `route.requirements`'s `recipe_known` entry).

## Mechanics / Engine Constraints

- **Route scoring formula** (`docs/mechanics/04_strategic_cognition.md` §6.4/§6.11, mirrored in `docs/parity_ledger/strategic_cognition.yaml` STRAT-227): `confidence_bonus` weight is `0.15`, currently defined purely as `route.confidence × 0.15`. Any capability-driven replacement/supplement must be documented as an explicit constant/formula change to this named term, not silently folded into `route.confidence` upstream.
- **Information opacity law** (scoring.py:6-8 docstring): capability reads must stay scoped to the entity's own state — satisfied by `CapabilityEstimateService.estimate()`'s existing input contract (entity-only fields, no world-truth scan) regardless of whether it's invoked via `SelfModelUpdatePhase` or ad-hoc from the scorer.
- **Capability estimation is caller-scoped, not world-scan** (`docs/cognition/capability_and_knowledge_contract.md` "Scoped estimation" section, `capability_estimate.py:9-10,85-104`): `CapabilityEstimateService.estimate()` is a `@staticmethod`, stateless, deterministic, and returns an empty component when `context is None` — nothing about its implementation requires it to be invoked only from `SelfModelUpdatePhase.run()`. It has no dependency on the dirty-check machinery in `run()` (`self_model_phase.py:143-161`) or on `entity.self_model.capabilities` being pre-populated; it takes `entity`/`state`/`context`/`tick` directly.
- **Durable-state / read-only rule** (CLAUDE.md): `AdventureRouteScorer.score()` is read-only; calling `CapabilityEstimateService.estimate()` ad-hoc inside it does not mutate `entity.self_model` (the result would be a throwaway local value used only for this tick's score, never written back) — this must be preserved by whichever option is chosen.
- **`RouteFamily` extension rule** (`docs/simulation/domains/adventure_contract.md` "Extension Rules"): modifying `confidence_bonus`'s formula for existing families does not require a new `RouteFamily` value or `RouteToProjectMapper` case.

### Option (a) vs. option (b) — evidence-backed recommendation: **option (b)**

- **Option (a) — populate a real `CapabilityContext` upstream of `SelfModelUpdatePhase.apply()`** would require: (i) deciding what world-scoped data `apply()` should feed into a context (which enemies/regions/resources/recipes are relevant to *this* entity this tick — `apply()` currently has no per-entity opportunity/enemy list computed anywhere in its own scope, that data lives in `src/world/providers/*` and is only assembled inside `AdventureGoalScorer.score()`/`AdventureRouteGenerator.generate()`, a different subsystem entirely); (ii) `apply()` runs once per entity per tick unconditionally for `ENABLE_SELF_MODEL_COGNITION`-gated entities regardless of whether they're `adventure`-eligible, so a generically-useful context would need scope broader than adventure's own needs — a materially larger cross-subsystem design question (which capabilities does *every* entity need estimated every tick, for what purpose) the ticket's own scope does not authorize deciding. This is consistent with the ticket's own "BLOCKED/larger-prerequisite" framing.
- **Option (b) — call `CapabilityEstimateService.estimate()` directly inside `AdventureRouteScorer.score()`** is architecturally clean because `CapabilityEstimateService.estimate()` has no dependency on being invoked from `SelfModelUpdatePhase` (see Mechanics/Engine Constraints above) — it is a plain stateless static method taking `(entity, state, context, tick)`. `score()` already receives `entity` and (optionally) `resource_nodes`; a scoped, per-route, ad-hoc `CapabilityContext` can be constructed with data already reachable from the route/route-generation context for the two live families that have an evidence-backed capability-key source: `GATHER_RESOURCE` (`resource_nodes[route.target_node_id].kind`) and `CRAFT_UPGRADE` (recipe id parsed from `route.requirements`'s `Requirement(kind="recipe_known", subject=recipe_id)`). This does not touch `self_model_phase.py`, `entity.self_model.capabilities`, or the pipeline at all, so it trivially satisfies AC3 ("existing isolated `CapabilityEstimateService` unit tests continue to pass unchanged" — those tests only exercise `capability_estimate.py` directly and this option makes zero edits to that file).
- **Recommendation: option (b), scoped to `GATHER_RESOURCE` and `CRAFT_UPGRADE` only.** Extending to `HUNT_WEAK_ENEMY`/`SCOUT_LOCATION` (the "obvious" combat/travel semantic mapping) is unit-testable but has zero live observable effect (both are dead-code route families) — Plan should decide explicitly whether to include them anyway (mirrors the sibling ticket's dead-route decision) or scope narrowly to the two live, evidence-backed families. The other live families (`BUY_UPGRADE`, `RECOVER`, `ASK_INFORMATION`, `FORM_PARTY`) have no capability-key mapping evidence at all and should stay on the flat `route.confidence × 0.15` term.

## Risks and Open Questions

1. **[BLOCKING for Plan] Exact `RouteFamily` → capability-key mapping scope is not fully determined by evidence.** `GATHER_RESOURCE` and `CRAFT_UPGRADE` have clean, evidence-backed key sources (see Current Behavior). `HUNT_WEAK_ENEMY`/`SCOUT_LOCATION` have the more "obvious" semantic mapping but are dead-code route families with zero live effect. Plan must decide explicitly whether to (a) scope to `GATHER_RESOURCE`+`CRAFT_UPGRADE` only (recommended — live, testable, evidence-backed), or (b) also wire the two dead families for completeness/unit-test coverage while disclosing the zero-live-effect caveat, mirroring the sibling ticket's identical decision for `HUNT_WEAK_ENEMY`.
2. **[Not blocking, must be disclosed] Option (b) does not fix `entity.self_model.capabilities.estimates` being empty in production — it bypasses the gap, not resolves it.** After this ticket, `entity.self_model.capabilities` is still empty at every real tick (the `apply()` → `run()` wiring gap remains). Plan must state this explicitly (as the memory-informed sibling did for `MemoryUpdatePhase`'s pipeline-registration gap) rather than let AC1's "resolved as part of this ticket's own scope" read as "the upstream field is now populated" — it isn't; only the scorer's own local read is resolved.
3. **Recipe-id extraction from `route.requirements` is a string/`Requirement`-shape dependency, not a typed field.** `AdventureRouteOption` has no dedicated `recipe_id`/`resource_id` field; recipe id must be parsed by finding `Requirement(kind="recipe_known", ...).subject` inside `route.requirements`. This is a real but indirect dependency on `services.py`'s opportunity-construction shape (services.py:55) — if that shape ever changes, the capability-key extraction silently breaks (no natural failure surface other than the key not resolving, which would just fall back to the flat `route.confidence × 0.15` term if implemented defensively). Plan should decide the exact fallback behavior when extraction fails (missing/malformed requirement) — recommended: silently fall back to the existing flat term, never raise, consistent with `score()`'s defensive `getattr(...)`-heavy style throughout.
4. **`gather.resource.<kind>` key convention assumes `ResourceNodeState.kind` is a stable, registry-backed resource id** — confirmed true today (`ResourceRegistry.get(node.kind)`, `resources.py:65`) but this is an implicit convention, not a documented contract between `capability_estimate.py` and `core/state.py`. Worth a one-line doc note if Plan wants to make this explicit rather than an inferred coincidence of naming.
5. **`recipe_data`/`resource_data` optional reference dicts on `CapabilityContext`** (`capability_estimate.py:44-47`) are not populated by an ad-hoc scorer-local context unless Plan decides to also thread `gold_cost` (from the route's `has_gold` requirement quantity) — without it, `CapabilityEstimateService.estimate()` for `craft.recipe.*` still works (falls back to the "unknown recipe" branch, `estimate=0.3, confidence=0.3`, if `recipe_data` isn't provided) but produces a less-informative estimate than if the full recipe_data dict were reconstructed from `route.requirements`. Plan should decide whether the extra reconstruction effort is worth it or whether the degraded-but-safe estimate is acceptable for a first pass.

- **Do not touch `AdventureGoalScorer`, `AdventureDecisionService.decide()`, `RouteToProjectMapper`, or `src/engine/pipeline.py`.** Per the recommended option (b), no new plumbing through the call chain or pipeline registration is needed or in scope.
- **Do not attempt option (a) (upstream `SelfModelUpdatePhase`/`apply()` wiring) without an explicit Plan decision** — it is a materially larger, cross-subsystem change (deciding what capabilities *every* `ENABLE_SELF_MODEL_COGNITION`-gated entity needs estimated every tick, not just adventure-eligible heroes) that the ticket's own Scope section frames as optional, not committed.
- **Do not silently claim `entity.self_model.capabilities.estimates` is now populated in production** — under option (b) it remains empty; only document what actually changed (a new local, throwaway capability read inside `score()`).
- **Do not extend the capability-key mapping to `HUNT_WEAK_ENEMY`/`SCOUT_LOCATION` without disclosing the dead-route-family caveat**, mirroring the sibling ticket's identical disclosure for `HUNT_WEAK_ENEMY` and `memory_adjustment`.

- **Do not modify `capability_estimate.py` itself** unless a genuinely new capability domain is required — AC3 depends on that file's existing unit tests passing unchanged, and no evidence gathered here shows a need to change `CapabilityEstimateService`'s internals for this ticket's scope.
- **Preserve the existing flat `route.confidence × 0.15` term for every family without a resolvable capability key** — this is an additive/conditional change, not a wholesale replacement of the formula.
