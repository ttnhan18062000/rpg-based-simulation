# Investigation: TCK-20260619-E42D-CONTRADICTION

## Existing Code Surveyed

### Lead Contradiction Infrastructure (already exists)
- `src/domains/information/contradiction.py` — `BeliefContradictionService.detect()` returns a `BeliefContradictionResult` with `contradiction_detected`, `lead_id`, `old_certainty`, `new_certainty`, `reason`. It handles `claim_failed_search` and `region_danger_seen` observations. However it only detects — it does NOT emit events, update provider reliability, or update LeadState in StateUpdate.
- `tests/unit/domains/information/test_phase5_belief_contradiction.py` — one existing test (`test_failed_search_contradicts_lead`) for `BeliefContradictionService.detect()`.

### Lead and Strategic State
- `src/core/strategic.py` — `LeadState` has `tested`, `test_outcome`, `failure_count`, `suppression_until_tick` fields. All frozen, updated via `StrategicUpdate.leads_add_or_update`.
- `StrategicUpdate` in `src/core/updates.py` has `leads_add_or_update`, `source_trust_updates`.

### InformationProviderState
- `src/domains/information/providers.py` — `InformationProviderState` is frozen. `reliability_score: float = 1.0`. No update record for providers exists in `StateUpdate`.
- `AuthoritativeState.information_providers: Dict[int, InformationProviderState]` — registered at world level.

### StateUpdate / Events
- `StateUpdate` has no `simulation_events` field. SimulationEvents flow through `EventRecorder` (kernel-level), not through `StateUpdate`.
- `StateUpdate` has `metric_counters: Dict[str, int]` which can be used to signal events to the kernel.
- The ticket spec says to emit `SimulationEvent(kind="belief_contradiction", ...)`. In the existing pipeline pattern, phases return `StateUpdate`. The SimulationEvents are generated by `EventExtractor` from state diffs OR by the kernel from violations/status changes.
- **Resolution**: The new pipeline phase will return a `(StateUpdate, List[SimulationEvent])` tuple so that the calling context (kernel or test) can record the events. For tests, we check the returned list directly.

### KnowledgeFact Staleness
- `src/core/self_model.py` — `KnowledgeFact` is frozen with `certainty` and `recorded_tick`. No staleness decay exists.
- The staleness formula from the ticket: `effective_certainty = fact.certainty * max(0.1, 1.0 - (current_tick - fact.recorded_tick) * DECAY_RATE)` with `DECAY_RATE = 0.0001`.
- This must be applied at read time without mutating `KnowledgeFact`. A utility function in `src/cognition/knowledge_model.py` or a new `src/engine/pipeline_phases/lead_contradiction.py` module is appropriate.

### Provider Reliability Update Path
- `StateUpdate` has no `information_providers_update` field. We need to add one or use an existing pattern.
- Closest pattern: `StateUpdate.world_updates` for world-level state. However, a cleaner approach is to add `information_providers_update: Dict[int, InformationProviderState]` to `StateUpdate` — but that requires changes to a core record.
- **Decision**: Add `information_providers_update: Dict[int, InformationProviderState]` to `StateUpdate` so provider reliability is updated authoritatively. This follows the existing pattern for other world-state updates.

### Test File Location
- Tests for E42A/B/C all live in `tests/unit/cognition/test_information_seeking.py`. The ticket specifies the same file for E42D tests.

## Gap Analysis

| Requirement | Gap | Resolution |
|---|---|---|
| Lead test outcome detection | `BeliefContradictionService.detect()` partially handles this | Extend to cover depleted resource nodes, dead person leads |
| Emit belief_contradiction event | No event emission in existing code | New pipeline phase returns `List[SimulationEvent]` |
| Provider reliability -= 0.1 | No update path for providers | Add `information_providers_update` to `StateUpdate` |
| LeadState.test_outcome = FAILURE | Not wired from contradiction detection | New phase applies result to StrategicUpdate |
| UnknownFact regeneration | Not implemented | New phase adds UnknownFact via `self_model_bundle_set` or knowledge component update |
| KnowledgeFact staleness decay | Not implemented | New utility function `effective_certainty()` in knowledge_model.py |

## Architecture Observations
- All durable changes must go through typed updates: `StrategicUpdate` for leads, `EntityUpdate.self_model_bundle_set` for knowledge (or a new self-model update type), `StateUpdate.information_providers_update` for provider reliability.
- KnowledgeFact is frozen — staleness is always computed at read time, never stored. This is correct per the ticket spec.
- The contradiction phase is a decision-only system (reads state, returns updates) — never writes directly.
