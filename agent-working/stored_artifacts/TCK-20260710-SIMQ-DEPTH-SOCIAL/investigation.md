# Investigation — TCK-20260710-SIMQ-DEPTH-SOCIAL

## Current Behavior

**Flag wiring (confirmed intact, no re-fix needed):**
- `src/engine/pipeline.py:158` — `run_phase("cooperation", update, lambda u: CooperationPhase.execute(state, u), "ENABLE_SOCIAL_COOPERATION")`. Gating happens **here**, via `ff_manager.get_flag_mode("ENABLE_SOCIAL_COOPERATION")` (`src/engine/pipeline.py:102-110`). If `FeatureMode.OFF`, `CooperationPhase.execute` is never called.
- `src/engine/pipeline.py:70` constructs `ff_manager = FeatureFlagManager()`; flags are set from `state.feature_flags` (populated by `tools/calibrate_simq.py::_run_engine` L222-226 via `dc_replace(state, feature_flags=combined_flag_overrides)`, itself fed by `_load_profile_feature_flags()` L44-64 reading the profile YAML's `feature_flags:` block, per `docs/guides/feature_flags.md`).
- `src/domains/cooperation/phase.py:40` — `flag = getattr(state, "social_cooperation_enabled", True)`. **This is a second, effectively dead gate** — `state.social_cooperation_enabled` is never set anywhere in `src/` (confirmed via repo-wide grep, only hit is this one `getattr` call), so it always defaults to `True` and never disables the phase. The ticket's own citation of this line as "the flag check" is correct as a *pointer* but the ticket should not assume this line does the real gating — the real gating is 100% at the `run_phase()` call site. Harmless (defaults permissive), but worth noting as a stale/vestigial internal check.

**Help-need + partner + decision pipeline** (`src/domains/cooperation/phase.py:34-141`):
1. `HelpNeedEvaluator.evaluate()` (`evaluators.py:22-106`) — **hard-gated on `entity.strategic.current_objective_id`**: line 34-35, `if not current_obj_id: return ()`. No objective → zero help needs, unconditionally, regardless of faction, HP, or combat state. This gate is *not* mentioned in `docs/simulation/domains/cooperation_contract.md`'s trigger table (see Anti-Drift Hazards — that doc is stale relative to live code).
2. If `current_objective_id` is set, four triggers apply: `combat_support_needed`/`healer_needed` (risk/HP), `guide_needed` (unexplored region), `carry_support_needed` (gold > 1000).
3. `PartnerCandidateProvider.get_candidates()` (`providers.py:29-111`) — same-faction filter (role-1 "Hireling" is the only cross-faction exception), `spatial_radius=15.0`, OR `trust_history > 0.7` fallback. Confirmed defaults: `trust_history.get(cand_id, 0.5)`, `familiarity_history.get(cand_id, 0.0)` — no pre-seeded content required, consistent with the ticket's claim.
4. `CooperationPhase.execute()` L76: `if not help_needs and entity.identity.group_id is None: continue` — entities **already in a group** are still evaluated even with zero help needs (falls through to `CooperationDecisionService.select()`, which returns `SOLO` with `trace={"reason": "No help needs detected."}`). Because `last_cooperation_decision` is set to the posture string unconditionally whenever this loop body executes (L138-139), **`cooperation_event` fires from `EventExtractor` (`src/observability/event_extractor.py:302`, `is not None` check on `last_cooperation_decision`) even for a bare `SOLO` decision**, as long as the entity has a `group_id`.
5. **This is not a cheap bypass**, however: `group_id` is never assigned at world-generation time (`V2EntityBuilder` defaults `group_id=None`, confirmed no assignment in `src/systems/world_systems/generator.py`). At runtime, `GroupSystem` (`src/systems/world_systems/groups.py:260-328`) only forms a group from an **already-ACTIVE contract** between two ungrouped entities within 10.0 units — explicitly documented in-code as `SOC-164: Proximity alone does not create a party`. So the group-membership bypass is *downstream* of a first successful cooperation cycle (help-need → partner → `REQUEST_HELP`/`HIRE_SUPPORT` contract → accepted → group formed), not an independent trigger path. The `current_objective_id` gate in step 1 is therefore the practical precondition for SOCIAL activation in any of these worlds.
6. `entity.strategic.current_objective_id` is set by the **baseline, unflagged** `StrategicIntelligenceSystem.fused_strategic_pass` (`src/systems/strategic_systems/intelligence.py:200`, wired at `src/engine/pipeline.py:320` with **no** feature-flag argument — runs every tick for every faction) via `ProjectState`/`ObjectiveState` machinery, and separately by `src/domains/adventure/phase.py:137` (adventure/quest routing, likely gated by the separate `ENABLE_ADVENTURE_ROUTING` flag, not requested by this ticket). Objective assignment is **not hero-faction-exclusive** in code — any faction's entities can accrue an objective through the baseline system.
