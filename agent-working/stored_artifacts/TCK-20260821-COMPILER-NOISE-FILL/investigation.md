## Current Behavior

### `WorldCompiler.compile()` region-painting loop (`src/worldbuilding/compiler.py`)
`compile()` is a `@staticmethod` (line 176). It constructs a **local, ephemeral** `rng = DeterministicRNG(seed)` at line 198 — never returned, never exposed to the caller; it is garbage-collected when `compile()` returns.

Corrected line numbers (the ticket's own text cites "around lines 202-219"; current lines, verified by direct read, are 211-221 for the actual per-tile write):
- Lines 202-205: base topology fill — every `(x, y)` in the full map gets `terrain[(x,y)] = "PLAIN"` before any region is painted.
- Lines 211-237: the region loop (`for r_spec in spec.regions:`).
- **Lines 214-221 — the exact flat-fill block this ticket must change:**
  ```python
  r_terrain = getattr(r_spec, "terrain", "GRASS")
  for x in range(min_x, max_x + 1):
      for y in range(min_y, max_y + 1):
          if 0 <= x < spec.topology.width and 0 <= y < spec.topology.height:
              terrain[(x, y)] = r_terrain
              if r_spec.type == "town":
                  town_tiles.add((x, y))
  ```
- Bounds-clamp: the `if 0 <= x < spec.topology.width and 0 <= y < spec.topology.height:` guard is the only bounds protection; it must continue to gate every terrain write (and any new noise-fill write) exactly as today.
- **`town_tiles` membership (verified, ticket's claim confirmed true):** driven solely by `r_spec.type == "town"` on line 220, inside the same `(x, y)` loop but **independent of the terrain string written on line 219**. The write order is terrain-then-town-check but town membership never reads `r_terrain`/`terrain[(x,y)]`. Likewise `RegionState.kind` (line 232, `r_spec.type.upper()`) and the later `town_entity_ids` gate (line 444, `if region.kind == "TOWN":`) are both keyed off `r_spec.type`, never off any terrain string. **Conclusion: replacing the flat `r_terrain` assignment with a per-tile noise-sampled value cannot affect town_tiles/town_entity_ids membership as long as the `if r_spec.type == "town":` line is left untouched and still executes for every tile in bounds.**
- `RegionState` itself (lines 228-237) carries no terrain field at all — `terrain` only ever lives in the flat `Dict[tuple[int,int], str]` on `AuthoritativeState.terrain`.

Steps 4-6 (resources, buildings, entities) all draw from `rng.get_int(Domain.WORLD, 0, <id>, ..., sub_id=<n>)` with an established sub_id convention: resources/buildings use sub_id 0 (x) / 1 (y); entities use sub_id 0 (x) / 1 (y) / 10 (greed) / 11 (bravery) / 12 (sociability) / 13 (industry) / 14 (class), plus reroll sub_ids ≥100 for `LAW-SPAWN-OCCUPANCY` collision resolution (`_resolve_entity_spawn_tile`, lines 110-154, added by `TCK-20260817-STANDARD-SPAWN-OCCUPANCY-COLLISION-RNG-ROOT-CAUSE`). All of Domain.WORLD's `entity_id` values used inside `compile()` are the real numeric IDs (`next_resource_id` from 10000, `next_building_id` from 20000, `next_entity_id` from 1) — a noise-fill draw that picked a colliding `(entity_id, sub_id)` pair under **the same** Domain.WORLD would not corrupt anything (see RNG statelessness below) but would be semantically confusing/statistically correlated with an unrelated real object's draw. This is the concrete, evidence-based reason a **separate Domain is the right call**, not merely "recommended."

### `DeterministicRNG` (`src/platform/rng.py`)
Confirmed: `get_float`/`get_int`/`choice`/`weighted_choice`/`sample` (lines 85-108) are all **stateless composite-key hashes** — each call computes `seed = _composite_seed(base_seed, domain, tick, entity_id, sub_id)` (lines 65-83) and constructs a **brand-new** `random.Random(seed)` for that single call only. None of these touch `self._rng_map` (the `_rng_map` dict is only ever read/written by the `DEPRECATED` `next_float`/`next_int` stateful methods, lines 46-52, which `compile()` never calls). This independently confirms ticket #1's investigation claim and the ticket's own framing: there is no sequential stream to "order" — only a key-namespace to keep collision-free.

`_composite_seed` bit layout (line 65-83): `seed ^= (domain.value << 48); seed ^= (tick << 32); seed ^= (entity_id << 16); seed ^= sub_id`. This is a **bit-partitioned XOR composition**, not just "very unlikely to collide":
- `domain.value` occupies bits 48+ (values 0-11 today, 4 bits needed).
- `tick` occupies bits 32-47 (`compile()` always passes literal `0` for every draw — verified by reading every `rng.get_*` call site in `compile()`).
- `entity_id` occupies bits 16-47 (32-bit range; string IDs are folded through a 32-bit hash first).
- `sub_id` occupies bits 0-15 (unshifted; every existing call site in `compile()` uses sub_id < 128).
Since `domain.value << 48` is the only term touching bits ≥48, and every existing/realistic `(tick, entity_id, sub_id)` combination inside `compile()` stays well below 2^48 (a 100×100 or even 10,000×10,000 tile-encoded ID is nowhere near 2^48 ≈ 2.8e14), **two different `Domain` values provably cannot produce the same composite seed** — this is a hard guarantee by construction, not a probabilistic one, as long as the noise-fill implementation keeps `entity_id`/`sub_id` within the existing realistic ranges (true for any sane tile-coordinate encoding).

### `Domain` enum (`src/core/enums.py`, line 168)
Full current membership: `DEFAULT=0, SPAWN=1, WORLD=2, CALAMITY=3, SOCIAL=4, STRATEGIC=5, TACTICAL=6, ECONOMY=7, QUEST=8, COMBAT=9 (reserved), LOOT=10 (future), INIT=11`. `Domain.INIT`'s own docstring comment already reads "World initialization / entity placement" — suggestive but, per direct grep, **not actually used for entity placement today**.

**Domain.INIT is NOT currently unused — this corrects the ticket's Assumption, which must be read carefully rather than taken as "confirmed no collision risk."** Grep of `Domain\.INIT` across `src/`, `tests/`, `data/` found exactly one production use: `src/engine/kernel.py:122`:
```python
if self._run_id is None:
    _run_suffix = self._rng.get_int(Domain.INIT, 0, 0, 1000, 9999)
    self._run_id = f"run_{int(time.time())}_{_run_suffix}"
```
This is `Kernel.__init__`, called **after** `WorldCompiler.compile()` has already run and returned in every real call path verified (`src/cli/entry.py:203-235`, `src/lab/orchestrator.py:196-215`: both construct a **separate** `DeterministicRNG(seed)` instance for the `Kernel(...)` call, distinct from `compile()`'s own internal, already-discarded `rng` local variable — though frequently the *same numeric seed value*). All other `Domain.INIT` hits are in `tests/integration/kernel/test_phase2_determinism.py`'s `TestCLIDeterminism` class, which is a synthetic exercise of the RNG API's general determinism property (comment says "monster positions" but it is not tied to any real production call site using entity_id 0-8 — no production code currently draws under `Domain.INIT` with those params) and `TestDomainEnum::test_init_domain_exists` (`assert Domain.INIT == 11`).

**Is this a real collision risk for this ticket?** No, for two independent, verified reasons — and the ticket's own stated reason ("compile()'s RNG instance is distinct from Kernel's own") is directionally correct but imprecisely reasoned; instance separation is not actually what makes this safe:
1. **Call-ordering**: `compile()` computes and returns `state_hash` (via `StateFingerprinter.get_fingerprint`, lines 598-599) *before* `Kernel` is ever constructed in every real call path. Nothing `Kernel.__init__`'s own `Domain.INIT` draw does can retroactively change a hash already computed and returned.
2. **Statelessness**: even if a noise-fill draw inside `compile()` used the exact same `(Domain.INIT, tick=0, entity_id=0, sub_id=0)` key as Kernel's run-suffix draw, both are pure functions of that key — each independently constructs its own `random.Random(seed)` and reads one value. This is not state corruption (no shared mutable RNG state is touched by either stateless call), only a coincidental value correlation between two logically unrelated consumers. It cannot affect `compile()`'s `state_hash`, Kernel's tick loop, or replay/checkpoint state.

As a hygiene recommendation for the implementer (not a correctness blocker): pick a tile-encoding scheme for the noise-fill's `entity_id`/`sub_id` that avoids `entity_id=0, sub_id=0` exactly (e.g. reserve `sub_id=0` for the terrain-variant weighted-choice draw but derive `entity_id` from `region_id` hash XOR tile offset rather than raw `x*height+y`, so tile `(0,0)` of the first-declared region never lands on `entity_id=0`) purely to avoid a confusing coincidental value match during debugging — this has zero effect on any test outcome.

**`scenario_checkpoint.py` note (tangential, not a blocker for this ticket):** `src/engine/scenario_checkpoint.py:100-108` passes `run_id=` explicitly into `Kernel(...)` "to suppress the Domain.INIT RNG draw... that would otherwise advance the stream by 1 after `set_state()` restores it, breaking the determinism AC." This comment's "advance the stream" language does not match the current `get_int()` implementation (stateless, does not touch `_rng_map`/the checkpointed stream at all) — possibly stale relative to an earlier stateful-RNG version of this code. This is **unrelated to and unaffected by this ticket**: checkpoint restore never touches `WorldCompiler.compile()`'s RNG instance (a different `DeterministicRNG(base_seed=0)` object entirely, restored via `set_state()`), and this ticket's new `Domain.INIT` draws live entirely inside `compile()`, which finishes before any `Kernel`/checkpoint code runs. Flagged for awareness only.

### Certification / golden-hash regression risk — the most important finding of this investigation
**There is no literal "golden hash" fixture corpus in this repo for `WorldCompiler.compile()`.** The phrase "certification corpus" in the ticket's own Request Summary and Acceptance Criteria does not correspond to an existing persisted-hash fixture anywhere (searched for `golden`, `CERTIFICATION_CORPUS`, and literal fixed hash-string assertions — none found tied to `compile()`). The actual regression coverage is:
- `tests/certification/test_world_compile_determinism.py` — **self-consistency** only: compile the same spec twice with the same seed → hashes/entity/resource coordinates must match; different seed → hash must differ. No fixed hash literal.
- `tests/unit/worldbuilding/test_world_compiler.py` — asserts concrete `region_count`/`entity_count`/faction/position-in-bounds values for specific fixture specs (including two real resolved worlds, `data/worlds/urban_political/resolved/world.resolved.yaml`), plus `isinstance(report["state_hash"], str)` (never a literal string).

**Critical, independently-verified gap: `state_hash` does not include terrain at all.** Read `src/replay/fingerprint.py::StateFingerprinter.get_fingerprint()` in full — the hashed `raw_data` string is built from `entity_ident` (id/kind/pos/hp/gold/project/objective/readiness/active/skills/items/bonds/reputation/strategic), `resource_ident` (global_resources), `node_ident` (resource node charges/cooldown), `region_ident` (**only** `rid`/`owner_faction_id`/`influence`/`hazard_level` — no terrain field), `scar_ident`, `group_ident`, `macro_ident`. **`state.terrain` (the `Dict[tuple[int,int], str]` this ticket modifies) is never read by `StateFingerprinter` at all.** Also checked `src/engine/checkpoint.py::CanonicalStateHasher.to_canonical_data()` (the repo's other state-hashing mechanism, used for replay/checkpoint, not by `compile()`) — it includes `town_tiles`/`blocked_tiles` (sorted tuple lists) but likewise never serializes `state.terrain`'s per-tile values.

**Consequence for this ticket's own Acceptance Criteria:** AC #1 ("bit-identical state_hash... verified against the certification corpus") is **necessary but not sufficient** — a broken terrain-painting change for non-declaring regions (e.g. an off-by-one, or accidentally painting the wrong region's terrain) would **not be caught by `state_hash` equality at all**, because `state_hash` is structurally blind to terrain content. Positive news: entity/resource/building spawn coordinates are computed from RNG draws that are entirely independent of terrain painting (terrain painting reads `r_spec.terrain`/`r_spec.terrain_variants`, a static schema field, not RNG output — see below), so state_hash equality does still validate that entity/resource placement logic is untouched, just not terrain content itself. **This ticket's own test plan must therefore add direct `state.terrain` dict-content assertions — hash equality alone is an incomplete regression guard for the actual behavior being changed.**

**Is a new, conditionally-gated RNG draw provably safe for non-declaring worlds regardless of Domain choice?** Yes, with concrete evidence: `get_float`/`get_int`/`choice` construct a fresh `random.Random(seed)` per call with zero shared mutable state across calls (see DeterministicRNG section above). Gating the new draw strictly behind `if r_spec.terrain_variants:` means the new code path is never even reached for a non-declaring region — but even if it were reached unconditionally, no other region's or object's RNG-derived value could change, because each draw's output depends only on its own `(domain, tick, entity_id, sub_id)` key, never on how many prior draws happened. This eliminates the "accidentally-unconditional draw silently reorders a sequential stream" risk class entirely, by construction of `DeterministicRNG` itself — there is no stream to reorder.

### Terrain string semantic risk (downstream consumers, informational — not blocking this ticket)
`src/engine/legality.py` reads `state.terrain` for real tactical effects: `"WALL"` blocks movement/line-of-sight (line ~401) and is treated as cover terrain (line ~486-491 with `"FOREST"`/`"MOUNTAIN"`); `"HILL"`/`"MOUNTAIN"` grant high ground (`check_high_ground`, lines 415-424). `WorldCompiler.compile()` itself does **not** check terrain type when placing entities/buildings/resources (only tile-occupancy, via `LAW-SPAWN-OCCUPANCY`) — so once a real content module (ticket #5) declares `terrain_variants` including a blocking/high-ground terrain string, noise-fill could place an entity on now-impassable terrain with no compile-time check to catch it. Flagged here since this ticket is what makes the mechanism live, but the actual gameplay exposure only materializes once real content declares variants (ticket #5's own scope, per SEQUENCE.md).

- **Open, not blocking**: exact tile→`entity_id` encoding scheme for the noise-fill draw (e.g. `region_id` hash XOR `(x << 8 | y)`, or similar) is an implementation-phase decision; any scheme that (a) stays within realistic bit ranges verified above and (b) is itself deterministic given `(region_id, x, y)` satisfies both determinism and collision-freedom. - **No blocking open question found** on the Domain-value choice itself — `Domain.INIT` is confirmed safe by the two independent arguments above (call-ordering + RNG statelessness), not merely "recommended pending confirmation" as the ticket's Assumptions section states. ## Anti-Drift Hazards
- **Do not gate the new draw on anything except `if r_spec.terrain_variants:` (or equivalent truthy/non-empty check).** Any broader condition (e.g. "if region type is X") risks silently changing behavior for regions that happen to match that condition but don't declare variants.
- **Do not touch the `if r_spec.type == "town": town_tiles.add((x, y))` line at all** — it must remain reachable and execute identically regardless of which terrain-fill branch (flat vs. noise) runs above it.
- **Do not let the noise-fill draw's `entity_id`/`sub_id` selection reuse `Domain.WORLD`'s existing conventions** (0/1 for position, 10-14 for personality/class, ≥100 for reroll) even by accident — this ticket's own investigation established `Domain.INIT` as the correct choice specifically to avoid needing to reason about this at all; reverting to `Domain.WORLD` "for consistency" would reintroduce the exact class of risk this ticket exists to eliminate.
- **Do not rely on `state_hash` equality as the sole proof of "no change for non-declaring worlds."** As established above, it cannot detect a terrain-painting regression at all. Any implementer or reviewer treating a passing `test_compiler_seeding_determinism` as sufficient proof of terrain correctness is trusting an incomplete signal.
- **Do not expand scope into validating terrain-type semantics against `legality.py`'s blocking/cover/high-ground vocabulary** — that's a real, identified risk but belongs to ticket #5 (real content migration) or a future ticket, not this one.
- **`TerrainVariantSpec.weight` must be used as a true relative sampling weight** (via `rng.weighted_choice`, already present and unused in `DeterministicRNG` — a perfect existing fit) — do not silently ignore `weight` and pick uniformly, and do not reinvent weighted sampling by hand when `DeterministicRNG.weighted_choice` already exists for exactly this.
