## Current Behavior

**`DemographicCycleService.process_demographics()`** (`src/domains/demographics/cohort.py:337-419`) runs every `COHORT_INTERVAL=200` ticks. For each region with non-empty `population_cohorts`, it computes `net = int(count*birth_rate) - int(count*mortality_rate)` per bracket, builds a full replacement `Dict[str, PopulationCohort]` (`new_cohorts = dict(region.population_cohorts)`, then `replace(cohort, count=new_count)` per changed bracket), and packages it into `WorldUpdate(region_id=..., population_cohorts_set=new_cohorts)`. It then runs `_check_migration()` (cohort.py:223-321), which does the same whole-dict-rebuild pattern for source and target regions of an emigration.

**`compute_regional_scarcity()`** (cohort.py:153-180) is a pure function: `1.0 - mean(remaining/max)` over resource nodes in the region's bounds, `1.0` if the region has no nodes/doesn't exist.

**`RegionalPressureModel.evaluate()`** (`src/domains/world_emergence/models.py:104-118`) computes `demand_multiplier = 1.0 + (compute_population_density(reg_state) * 0.5)` and folds it into `res_intensity` whenever there is harvest/depletion activity in the region. `compute_population_density()` (cohort.py:122-146) is `sum(cohort.count for cohort in region.population_cohorts.values()) / max(1, area)`.

## Mechanics / Engine Constraints

- **`docs/mechanics/05_world_evolution.md` §5, "Migration Law"** (line 207-208): `scarcity(region) > cohort.migration_threshold` (default 0.7) triggers 30% emigration — the eligibility gate all three paths already reuse verbatim; this ticket's nudge is additive to the *count*, not a re-derivation of this law.
- **§5, "Birth/Death Law"** (lines 153-158): `net_change = int(count*birth_rate) - int(count*mortality_rate)`; `new_count = max(0, count + net_change)`. This is the *aggregate* 200-tick cycle this ticket's individual-birth nudge sits alongside, per the ticket's explicit Out-of-Scope: "Any change to `DemographicCycleService`'s own 200-tick aggregate birth/death/migration cycle — this ticket only adds an additive nudge on top of it, not a replacement."
- **§5, "Population Density Demand Signal (E52D)"** (lines 217-229): `demand_multiplier = 1.0 + (population_density * 0.5)` is the exact mechanism AC#3 requires to "measurably respond" — since `compute_population_density()` sums all bracket counts, a `young` +1 nudge does move `demand_multiplier` by `0.5 / area` per birth, satisfying AC#3 as long as `area` is small enough in the test fixture for the effect to be measurable (the existing test pattern `test_high_population_region_higher_resource_demand` uses `count=2000` over a `100x100` region — a single +1 nudge is a ~0.05% density change and will need a comparably scaled fixture, or repeated births, to produce an assertable delta; do not silently scale up to a "recomputed total" to make the test pass more easily — see Anti-Drift Hazards).
- **`docs/core/state.py` immutability law**: `RegionState`/`PopulationCohort` are frozen dataclasses; the only legal path to a *durable* count change is a typed `WorldUpdate.population_cohorts_set` merged through `StateUpdate` and applied by `apply_plan.py` (`src/engine/apply_plan.py:124,139`) — confirmed: `pop_cohorts = r_upd.population_cohorts_set if r_upd.population_cohorts_set is not None else reg.population_cohorts` is a **whole-dict replace**, not a per-key merge. This is the binding constraint behind the single biggest risk below.

## Risks and Open Questions

1. **[BLOCKING — architecture gap, not a design choice] `WorldDynamicsSystem.resolve_dynamics()` silently drops `world_updates` from two of the three reproduction paths today.** At `src/engine/world_dynamics.py:174-182`, the explicit `update.replace(...)` call that folds in `camp_state_update` (from `CampService.process_camps()`) and `calamity_update` (from `CalamityService.process_world_dynamics()`) only pulls named fields (`maturity_set`, `last_calamity_tick_set`, `entities_add`, `camp_updates`) — **`camp_state_update.world_updates` and `calamity_update.world_updates` are never read anywhere in this function.** By contrast, `demo_update`, `seasonal_update`, `territory_update`, and `repro_update` (`HumanoidReproductionService`) are all correctly folded in via `update = update.merge(...)` (lines 184-207), which *does* pick up `world_updates`. **Concretely**: if the natural-creature or magical/demonic path is changed to return a `population_cohorts_set` `WorldUpdate` the same way `_check_migration` does, that update will be silently discarded before it ever reaches `apply_plan.py` — the nudge would appear to work in a unit test that calls `CampService.process_camps()`/`CalamityService.process_world_dynamics()` directly, then silently no-op in the real per-tick pipeline. Only the humanoid path's `world_updates` would actually flow through as-is today. Plan must explicitly fix `world_dynamics.py:174-182` (fold `camp_state_update`/`calamity_update` in via `.merge()`, taking care not to double-count `entities_add`/`camp_updates` which are already explicitly handled) as part of this ticket's implementation, not treat it as pre-existing/out-of-scope plumbing.
2. **[Correctness risk under the ticket's own "exactly +1" AC] `WorldUpdate.merge()`'s `population_cohorts_set` field is whole-dict-replace, "prefer other, non-None", not additive** (`src/core/updates.py:854`). Two independent nudges targeting the *same region* on the *same tick* — e.g. two camps in the same region both spawning natural-creature offspring in one `CampService.process_camps()` call, or (once fix #1 lands) a natural-creature nudge and a `DemographicCycleService` 200-tick cycle write landing on the same region on a tick that's a multiple of both `CAMP_SPAWN_INTERVAL` (30) and `COHORT_INTERVAL` (200) — will have the later-merged `WorldUpdate` silently clobber the earlier one's entire `population_cohorts` dict, not add to it. This is not hypothetical: `SystemCadence.reproduction_humanoid` is also 200 ticks, exactly equal to `DemographicCycleService.COHORT_INTERVAL`, so on every tick where both fire and target the same region, `update.merge(demo_update)` (world_dynamics.py:185) followed later by `update.merge(repro_update)` (world_dynamics.py:207) means the humanoid nudge's dict **replaces**, not adds to, whatever the demographic cycle just wrote for that region — silently discarding the aggregate cycle's own birth/death/migration changes for that region on that tick. AC#2's "exactly +1, not a recomputed total" test must specifically cover the *within-one-call* multi-birth case (e.g. two eligible camps, same region, same tick); the *cross-service same-tick* collision (reproduction cadence == cohort cadence == 200) is a genuine, currently-undecided design question for Plan: either each nudge site must read the *already-accumulated* `population_cohorts_set` from the `StateUpdate` under construction (not a fresh copy of `state.regions[...].population_cohorts`) as its increment baseline within a single call, and/or the merge order in `world_dynamics.py` needs an explicit accumulation step rather than relying on `WorldUpdate.merge()`'s last-write-wins semantics for this specific field. Do not assume this is fine because "additive-only" — the field itself is not additive at the merge layer; only the intent is.
3. **Missing `young` bracket at the birth region.** Per `WORLD-DEMO-006`, a region can have `population_cohorts == {}` (zero declared population) or a non-empty dict missing the `young` bracket specifically. The ticket's Scope literally says "nudge... `population_cohorts["young"].count` by +1", implying the bracket must exist — Plan must decide whether to (a) create a fresh `PopulationCohort(bracket="young", count=1)` with dataclass defaults when absent (mirroring `_check_migration`'s own "new bracket in target" branch, cohort.py:288-290), or (b) skip the nudge entirely when no `young` bracket is seeded (mirroring the eligibility gates' own skip-when-empty convention, but that convention is about *suppressing spawns*, not about *dropping a birth's aggregate signal* — the entity already exists either way). This is a real behavioral choice, not a formality; document whichever is chosen in the mechanics doc, since it changes whether a birth in an unseeded region silently vanishes from the aggregate signal forever.
4. **Whether the magical/demonic path participates in the nudge at all is unresolved**, inherited verbatim from `TCK-20260902-REPRODUCTION-MAGICAL-DEMONIC-PATH`'s own flagged open question and repeated in this ticket's own Assumptions/Open Questions. Arguments for excluding it: the shipped `WORLD-121` entry frames a calamity-driven spawn as "a world-threat escalation event, not a settlement/camp demographic signal" and deliberately carries no population-pressure *gate* — the same reasoning could argue it shouldn't feed the aggregate *signal* either, since it never reads it either. Arguments for including it: the ticket text says "on a successful individual birth from ANY of the three now-shipped reproduction paths" without carving out an exception, and idea 38's own framing is that *any* individual birth should nudge the aggregate. This ticket must not silently assume either answer — Plan should resolve it explicitly and record the decision (with rationale) in both the plan and the mechanics doc, mirroring how the magical/demonic ticket itself resolved its own "no population-pressure gate" question as an explicit numbered Decision.
5. Magical/demonic entities spawn without a guaranteed `region` object matching the eligibility-gate pattern the other two paths use — `target_region` there is always a real, already-selected `RegionState` from `state.regions.values()` (line 42-45 of calamity.py), so unlike the natural-creature path (`region` can be `None` if `LegalityServiceV2.get_region_for_position` finds nothing) this path always has a valid region to nudge if the answer to risk #4 is "yes, include it."

## Anti-Drift Hazards

- **Do not implement this as a single generic "scan `entities_add` for births" hook.** All entities from `spawn_monster()`/`spawn_goblin()` (existing garrison/raid spawns) and all entities from the three reproduction paths' own `spawn_*` methods flow through the same `entities_add` list, and `LifecycleComponent.birth_tick` defaults to `0` for every entity, not `None` — `spawn_monster()`/`spawn_goblin()` never call `.birth_record()` at all (confirmed: no `birth_record(` in either method), so `parent_a_entity_id`/`parent_b_entity_id` are also both `None` by default and cannot reliably distinguish "reproduction-path birth" from "no tracked parents because this is an ordinary garrison monster." A post-hoc entities_add scan is exactly the kind of "clever generalization" the ticket's own scope forbids (a full resync/recount is explicitly rejected); wire the nudge inside each of the three already-flag-gated call sites instead, where "this is a birth" is unambiguous by construction.
- **Do not let the nudge silently become a resync.** The three sibling tickets' own guard tests (`test_*_does_not_write_population_cohorts`) currently assert the *opposite* of what this ticket needs — they will legitimately fail/need rewriting to assert "+1 exactly", not deletion. Do not delete these tests wholesale; retarget them to assert the additive-only invariant (see test_plan.md).
- **Do not touch `DemographicCycleService.process_demographics()`'s own birth/death math** — explicitly Out of Scope. The nudge must be a separate, additive `WorldUpdate.population_cohorts_set` built from a copy of the *pre-nudge* cohort dict with only the `young` bracket's `count` incremented — never a call into or reimplementation of the 200-tick cycle's own net-birth formula.
- **Watch the whole-dict-replace trap when building the nudge's `population_cohorts_set`.** Because `WorldUpdate.merge()` prefers the "other" (later) `population_cohorts_set` wholesale, any nudge-building code that does `new_cohorts = dict(state.regions[region_id].population_cohorts)` and only reads from `state` (not from the in-progress `StateUpdate`/`world_updates` being built) will silently lose a sibling birth's nudge the moment two births land on the same region in the same call or the same tick (see Risk #2). This is the single highest-value thing a reviewer should check in the diff.
- **Do not widen scope to fix the pre-existing `EntityGenerator._last_id` id-collision quirk** flagged as an out-of-scope known-gap in the humanoid ticket's own Completion Summary — unrelated to this ticket even though the new tests will likely touch the same `EntityGenerator(seed=...)` test-construction pattern.
