# Investigation — TCK-20260811-MEMORY-INFORMED-ROUTE-SCORING

## Current Behavior

### `AdventureRouteScorer.score()` — `src/domains/adventure/scoring.py:26-279`
Static method, signature: `score(entity, route, resource_nodes=None, quest_registry=None, group=None, faction_directives=None, factions=None, progression_plan=None)`.
Computes `score = urgency + benefit + personality_bias + plan_advance_bonus + confidence_bonus - risk_penalty - blocker_penalty` (scoring.py:232). Confirmed **zero references** to `entity.cognition`, `entity.cognition.memory`, or `CausalMemoryEntry` anywhere in the file (`grep` across the file body: none).

The module docstring (scoring.py:6-7) states the exact documented boundary quoted by the ticket:
> "Implements subjective route scoring with imperfect decision personality bias. Reads only subjective self-model aspects to protect information opacity."

This is a real, load-bearing distinction, not loose wording: `EntityState` has **two separate fields** — `self_model: SelfModelBundle` (`src/core/state.py:689`) and `cognition: CognitionModel` (`src/core/state.py:690`). `scoring.py` and `generator.py` today read only `entity.self_model.needs`, `entity.self_model.self_awareness` — never `entity.cognition`. `entity.cognition.memory` (the field this ticket must read) is a *different* attribute than the one the docstring's literal noun phrase ("self-model") names. The docstring predates the `cognition`/`self_model` split-out and should be read as "reads only the entity's own subjective interior state, never omniscient world truth" — `entity.cognition.memory.causal` is still the entity's own private belief record (its own past causal attributions), so it is consistent with the *spirit* of the boundary (information opacity: entity acts on what it believes, not on ground truth), but Plan should decide whether to also update this docstring so "self-model" doesn't read as a literal, narrower promise than what the code will now do.

### `AdventureRouteGenerator.generate()` — `src/domains/adventure/generator.py:24-181`

### `CausalMemoryEntry` — `src/core/cognition.py:246-253`

class CausalMemoryEntry:
    event_id: str

`future_advice` is a `Tuple[str, ...]` — an entry can carry more than one advice string simultaneously (confirmed by `CausalAttributionService.attribute()` below, which always emits 2 advice strings for 3 of the 4 event kinds). Any AC test/implementation that assumes "one advice string per entry" is wrong; must iterate the tuple.

Storage path: `entity.cognition.memory.causal.entries` → `Tuple[CausalMemoryEntry, ...]`, via `CognitionModel.memory: MemoryModel` (`cognition.py:549`) → `MemoryModel.causal: CausalMemory` (`cognition.py:344`) → `CausalMemory.entries` (`cognition.py:259`, capacity 30, oldest evicted first).

## Mechanics / Engine Constraints

- **Route scoring formula** (`docs/mechanics/04_strategic_cognition.md` §6.4, mirrored in `docs/parity_ledger/strategic_cognition.yaml` STRAT-227): `score = urgency + benefit + personality_bias + confidence_bonus - risk_penalty - blocker_penalty`. A new memory term must be additive/multiplicative in a way consistent with this documented formula shape — Plan must decide which existing term family it belongs to (a new named additive term, like `plan_advance_bonus`, or a multiplier on `benefit`, like the depletion-fraction precedent) and document the exact constant.
- **Information opacity law** (scoring.py:6-7 docstring, echoed in `docs/simulation/domains/adventure_contract.md` "Purpose" — "subjective route selection"): scoring may only read the entity's own subjective belief, never omniscient/hidden world truth. `entity.cognition.memory.causal` satisfies this (it is the entity's own private causal belief record), but see the self-model/cognition field-naming nuance flagged above.
- **`RouteFamily` extension rule** (`docs/simulation/domains/adventure_contract.md` "Extension Rules", generator.py/scoring.py file headers): adding a new scoring term for existing families does not require a new `RouteFamily` enum value or a new `RouteToProjectMapper` case — the memory term modifies existing families' scores, not introduces a new family. In scope, but must not silently violate the "Extension Rules" pattern of documenting where changes were made.
- **Durable-state / authoritative-mutation rule** (`CLAUDE.md`): `AdventureRouteScorer.score()` is read-only and must remain so — the memory term must not mutate `entity.cognition.memory` from inside the scoring path (only `MemoryUpdatePhase` may do that, and even that is currently unwired — see above). Confirmed the current file performs no mutation; new code must preserve this.

## Risks and Open Questions

1. **[BLOCKING for Plan] `future_advice` → `RouteFamily` mapping is genuinely ambiguous and must be decided explicitly, not assumed.** Candidate mappings per event_kind:
   - `avoid_enemy` (combat_loss fallback) → the obvious target is `HUNT_WEAK_ENEMY`, but that family is **dead code in `generator.py`** (never generated) — suppressing it has zero live effect even though it is directly unit-testable. Plan must decide: suppress `HUNT_WEAK_ENEMY` anyway (satisfies AC literally, honest about the dead-code caveat in docs), or pick a different, live family (e.g. suppress routes with the highest `expected_risk`, which is a `risk_penalty`-shaped change, not a `RouteFamily`-shaped one — a bigger design shift the ticket's Scope doesn't obviously authorize).
   - `heal_first` / `rest_often` / `repair_weapon` (combat_loss non-fallback) → plausibly promote `RECOVER`, but these three are **not** in the ticket's own AC-listed example set and are easy to scope-creep into.
   - `seek_trusted_guide` / `verify_intel` (failed_search) → plausibly `ASK_INFORMATION` and/or `SCOUT_LOCATION` — ambiguous which, or both.
   - `acquire_mats` / `train_blacksmith` (failed_craft) → plausibly `GATHER_RESOURCE`/`CRAFT_UPGRADE` and `TRAIN_SKILL` respectively — two advice strings mapping to two different families from one entry.
   - `boost_party_trust` / `realign_directive` (party_abandoned) → `boost_party_trust` could mean *promote* `FORM_PARTY` (seek a new, better-vetted party) or *suppress* it (caution after abandonment) — directionally ambiguous, must be decided, not assumed. `realign_directive` doesn't obviously map to any of the 16 current `RouteFamily` values at all.
   The ticket's own AC1 only commits to 2 of these 8 possible advice strings (`avoid_enemy`, `boost_party_trust`) as required-measurable; Plan should scope the mapping table narrowly to what AC1 actually requires and treat the rest as explicitly out of scope for this pass, or decide to cover all 8 — this is a real scope decision, not a detail to leave implicit.
