# Investigation — TCK-20260811-RELATIONSHIP-AWARE-FORM-PARTY

## Current Behavior

### `PartyCompositionScorer.score()` — `src/systems/social_systems/party_composition.py:104-118`
Static/classmethod, signature `score(cls, entities: List[EntityState]) -> float`. Reads the whole file (31-119) —
confirmed **zero references** to `trust_history`, `bonds`, `.social`, or any counterparty-specific lookup anywhere
in the file (`grep`-equivalent full read: none). The class combines two pure-static sub-scores:
- `score_role_diversity()` (68-76): fraction of the 4 `PartyRole` values (TANK/HEALER/DPS/SUPPORT) represented
  among the candidate pool, weight `0.6`.
- `score_ocean_compatibility()` (79-102): bravery/sociability variance across the pool, weight `0.4`.

Both sub-scores are computed purely from each candidate's own `identity.personality` (bravery, sociability) and
`kind` — **never from the perspective of the entity forming the party**. The ticket's claim that
`PartyCompositionScorer.score()` "never reads `trust_history`/`bonds` for the specific candidates being
considered" is **confirmed true**. Note also: `score()` has no parameter for the *acting* (party-forming) entity
at all — only the candidate pool. Since `trust_history`/`bonds` are subjective/directed (keyed by counterparty id,
stored on the *viewer's* `SocialComponent` — see below), any trust-aware version of this method needs a new way to
know *whose* trust perspective to read from, which the current signature has no slot for.

### `SocialComponent` — `src/core/models/social.py:22-48`
Confirmed exact shapes (frozen dataclass, slots):
- `trust_history: Dict[int, float]` — **EntityID → trust score**, clamped to `[-1.0, 1.0]` by `RelationshipService.process_update()` (`relationships.py:31-33`).
- `bonds: Dict[int, SocialBond]` — **EntityID → `SocialBond`**, where `SocialBond` (models/social.py:6-11) is `{target_id: int, familiarity: float (0.0-1.0), sentiment: float (-1.0-1.0), last_interaction_tick: int}`.
Both are keyed by the **counterparty's** entity id and live on the **viewer's own** `SocialComponent` (`entity.social`, confirmed field name via `EntityState` dataclass body in `src/core/state.py`) — i.e. "does entity A trust entity B" is read as `A.social.trust_history.get(B.id, 0.0)` / `A.social.bonds.get(B.id)`, never a global/omniscient lookup. This is directly compatible with the information-opacity boundary `scoring.py`'s docstring documents.

## Mechanics / Engine Constraints

- **Personality-bias formula** (`docs/mechanics/04_strategic_cognition.md` §6.4, lines 225-242): `FORM_PARTY | sociability | 0.40`. AC4 requires this row to stay bit-identical — confirmed the current code (scoring.py:220-221) matches this table exactly today.
- **Route scoring formula** (§6.1-6.2, mirrored in `docs/parity_ledger/strategic_cognition.yaml` STRAT-227): `score = urgency + benefit + personality_bias + plan_advance_bonus + memory_adjustment + confidence_bonus - risk_penalty - blocker_penalty`. Any new scoring.py-level term must slot into this documented shape as a new named additive term (mirroring `memory_adjustment`'s precedent, §6.11) — not silently folded into an existing term.
- **Information opacity law** (scoring.py:6-13 docstring, mirrored in `docs/simulation/domains/adventure_contract.md`): scoring may only read the entity's own subjective belief, never omniscient world truth. `entity.social.trust_history`/`bonds` satisfy this — they are the *viewer's own* directed relationship state, exactly analogous to how `entity.cognition.memory.causal` was judged compliant for the memory-informed sibling ticket.
- **Durable-state / read-only rule** (CLAUDE.md): both `PartyCompositionScorer.score()` and `AdventureRouteScorer.score()` are pure/read-only today (confirmed: no `dataclasses.replace`/`EntityUpdate` construction in either file's scoring path). A trust/bonds read must stay a throwaway local value, never written back to `entity.social`.
- **`RouteFamily` extension rule** (`docs/simulation/domains/adventure_contract.md` "Extension Rules"): this is a same-family enrichment, not a new `RouteFamily` — no new enum value or `RouteToProjectMapper` case needed.

## Risks and Open Questions

1. **[BLOCKING for Plan] No architectural slot exists for "the specific candidate under consideration" at the `AdventureRouteScorer.score()` layer.** `FORM_PARTY` is generated once per acting entity as a pool-aggregate (`comp_score` over up to 8 candidates, collapsed to one float before reaching the route), and `AdventureRouteOption` has no candidate-id field (confirmed, schema.py). AC1 ("FORM_PARTY confidence/benefit for a specific candidate incorporates that candidate's real trust_history/bonds value") and AC2 ("two pools differing only in one candidate's trust_history value produce different comp_score/confidence for that candidate") are each satisfiable **at the `PartyCompositionScorer.score()` layer** (which iterates real candidates and can look up each one's trust value individually before aggregating) but **not literally satisfiable as a single-candidate value exposed at the `scoring.py`/`AdventureRouteOption` layer** without inventing a new field — the same class of gap the design doc already flagged for `HUNT_WEAK_ENEMY`/`SCOUT_LOCATION`. Plan must decide and explicitly disclose one of:
   - **(a)** Trust/bonds only enters via `PartyCompositionScorer.score()` (new optional param carrying the acting entity or its `SocialComponent`/trust dict, default `None` for full backward compatibility with every existing `score(entities)` call site) → flows into `route.expected_benefit`/`route.confidence` through the *already-existing* `comp_score`/`sociability+0.3` computations in `generator.py`. Under this shape, `scoring.py`'s FORM_PARTY branch (personality_bias, confidence_bonus) is **not touched at all**, trivially satisfying AC4's bit-identical requirement, and AC2's test is satisfied directly (comp_score differs). AC1's "confidence... incorporates trust/bonds" would need `route.confidence`'s generation-time formula in `generator.py` to also blend in a trust-derived term (separate from `comp_score`/benefit), which is a second, related decision.
   - **(b)** A genuinely new additive term inside `scoring.py`'s FORM_PARTY branch (mirroring `memory_adjustment`'s shape) — requires either (i) a new `AdventureRouteOption` field populated by `generator.py` from the same pool-level `comp_score`-style computation (still not literally single-candidate at this layer, just relabeled), or (ii) `AdventureRouteScorer.score()` reading `entity.social` directly for some aggregate/best-of measure across the *whole* pool the entity is generally sociable toward (not the specific route's candidates at all, since scoring.py never receives them) — a materially different, weaker interpretation of "specific candidate."
   The ticket's Scope section explicitly names both `party_composition.py:105` **and** `scoring.py` lines as needing changes, suggesting the ticket author intended both layers touched — but the *specific-candidate* framing is only literally true at the `PartyCompositionScorer.score()` layer. Plan must state plainly which layer(s) change and, if `scoring.py` changes too, exactly what pool-level-vs-candidate-level value it consumes and why that still satisfies AC1's wording in spirit.
2. **[BLOCKING for Plan] Exact trust/bonds → score formula and magnitude is undecided.** Neither the ticket nor any prior art in this repo specifies how `trust_history` (a `[-1.0, 1.0]` float) and `bonds` (`SocialBond.sentiment ∈ [-1.0, 1.0]`, `familiarity ∈ [0.0, 1.0]`) should combine into a bounded contribution to `comp_score` (already `[0.0, 1.0]`, weighted 0.6/0.4 role/OCEAN) or a `personality_bias`-style additive term (existing terms are `0.25`-`0.50` magnitude). A defensible default (mirroring `E11C`'s calibration precedent in §6.4) would be a small additive term (e.g. mean trust across candidates × some weight ≤ 0.15, similar magnitude to `confidence_bonus`) — but this is a real design decision Plan must make and document with a rationale, not something Investigate should assume.
3. **[Not blocking, must be disclosed] `RelationshipService` has no read/lookup method** — any new code must do raw `entity.social.trust_history.get(candidate.id, 0.0)` / `entity.social.bonds.get(candidate.id)` dict access, following every existing test's pattern. Do not add a new method to `RelationshipService` (an authoritative-mutation-only service) unless Plan explicitly decides a shared helper is warranted — a local, scorer-side helper function is lower-risk and matches this file's own style (e.g. `get_trait()` closures already used in `scoring.py`).
4. **[Not blocking, must be disclosed] Pre-existing SOC-231/SOC-232 ID collision** (see Parity Ledger Overlap) means `party_composition.py`'s own docstring citation is misleading. Do not propagate the wrong IDs into the new parity entry — mint a fresh ID or extend an existing correctly-scoped entry, and optionally (not required by this ticket's scope) flag the docstring's stale citation for a future cleanup ticket.
5. Sequencing risk with the wrapper migration (ticket's own Assumptions) is **resolved/moot** — confirmed via the two sibling investigations' re-verification that the migration (`TCK-20260811-ADVENTURE-GOAL-SCORER`, `TCK-20260811-DELETE-ADVENTURE-DECISION-PHASE`) is done and committed, and `generator.py`/`scoring.py` remain the live, unmodified-by-migration call targets.

## Anti-Drift Hazards

- **Do not touch `AdventureGoalScorer`, `AdventureDecisionService.decide()`, or `RouteToProjectMapper`.** `entity` already reaches both `PartyCompositionScorer.score()`'s caller (`generator.py`) and `AdventureRouteScorer.score()` unmodified; no new plumbing through that chain is needed.
- **Do not silently invent a per-candidate value at the `scoring.py` layer and claim it's "the specific candidate's" score** when the architecture only supports pool-level aggregation at that layer (see Risk 1) — disclose which layer any new value is actually computed at.
- **Do not touch the existing `personality_bias += sociability * 0.40` line (scoring.py:221) or `ROLE_DIVERSITY_WEIGHT`/`OCEAN_COMPAT_WEIGHT` constants (party_composition.py:38-39)** — AC4 requires bit-identical preservation of the existing weighted terms; any new trust/bonds contribution must be a separate, additive quantity.
- **Do not add a read/lookup method to `RelationshipService`** without an explicit Plan decision — it is an authoritative-mutation-only service today; raw dict access is the established read pattern.
- **Do not cite SOC-231/SOC-232 as the parity-ledger home for this change** — they are real, unrelated, already-used IDs (Grief urgency / Nemesis relation). Mint a new entry.
- **Do not conflate this ticket's trust/bonds term with SOC-232's nemesis-blocker mechanism** even though both live in the same `generator.py` code region — they are separate mechanisms (hard block vs. continuous score contribution) and should get separate parity-ledger treatment.
- **Do not mutate `entity.social` from inside either scorer** — both must remain read-only; any trust/bonds read is a local, throwaway value for this tick's score only.
- **Preserve backward compatibility of `PartyCompositionScorer.score()`'s signature** — every existing call site (`generator.py:139`, and 3 direct calls in `test_party_composition.py`) passes only the candidate list positionally; any new parameter must be optional/keyword-only with a default that reproduces today's exact behavior.
