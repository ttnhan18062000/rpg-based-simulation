# Implementation Plan — TCK-20260713-MONITORING-VALIDATE-INDEX-MIGRATE

## Summary

The ticket's own Request Summary/Scope text is imprecise about what "migrate" means (see Anti-Drift Notes item 1) and its AC3 is not literally achievable (item 2). This plan corrects both explicitly rather than implementing the ticket's literal wording. The actual migration is: swap `validate.py`'s `main()` from loading `runs`/`events`/`tools` via `load_jsonl(RUNS_FILE|EVENTS_FILE|TOOLS_FILE)` to loading the same three lists from the SQLite index (`agent-monitoring-index/monitoring.db`, built by `build_index.py`), via new helper functions that mirror `query.py`'s precedented `open_index`/`load_runs_from_index`/`load_events_from_index` shape (plus one genuinely new `load_tools_from_index`, since `query.py` never touched `tools.jsonl`). Because `compute_drift_report`, `compute_tool_count_drift_report`, and `compute_multi_invocation_collision_report` are pure functions that take plain lists and are never changed themselves, swapping `main()`'s single data-loading step automatically migrates all three at once — this is how `compute_multi_invocation_collision_report` gets folded in with no dedicated code change, only a dedicated parity test. `LEGACY_COMPLETION_FIELDS`/`LEGACY_TERMINAL_STATUS_VALUES` are untouched: neither of the two functions named in Scope ever referenced them, so there is nothing to reduce (AC3 resolved as satisfied-by-inaction, documented not silently applied). `validate.py` gains the same hard index-existence precondition `query.py` already established (actionable stderr message + `sys.exit(1)` if the db is missing), a deliberate behavior change from today's zero-precondition standalone run, stated explicitly rather than assumed.

## Steps

### Step 1 — Add SQLite index-loading helpers to validate.py
**Files:** `tools/agent-monitoring/validate.py`
**Change:** Add, near the top of the file (after the `LOG_FILE`/`MONITORING_START` constants, before `_record_is_complete`):
- `DEFAULT_DB_PATH = Path("agent-monitoring-index/monitoring.db")`
- `open_index(db_path: Path) -> sqlite3.Connection` — byte-identical logic to `query.py`'s `open_index` (query.py:29-36): if `not db_path.exists()`, print the same actionable message shape to stderr (`f"No agent-monitoring index found at {db_path} — run \`make agent-monitoring-index\` first."`) and `sys.exit(1)`; otherwise `sqlite3.connect(str(db_path))`. Do not special-case a corrupt db — let a native `sqlite3` exception propagate unmasked, matching `query.py`'s documented/tested precedent (`test_corrupt_db_does_not_print_missing_index_message`).
- `load_runs_from_index(conn) -> list` — `SELECT raw_json FROM runs ORDER BY id`, `json.loads()` each row, return plain dicts. **Do not** inject `_resolved_status` the way `query.py`'s version does — `compute_drift_report` only reads raw fields (`workflow`, `tier`, `final_status`) directly off the dict, and injecting an extra key that didn't exist pre-migration is an unrequested behavior surface, however harmless it looks.
- `load_events_from_index(conn) -> list` — `SELECT raw_json FROM events ORDER BY id`, `json.loads()` each row. Byte-identical to `query.py`'s version (query.py:49-51).
- `load_tools_from_index(conn) -> list` — new, no precedent: `SELECT raw_json FROM tools ORDER BY id`, `json.loads()` each row.
- Add `import sqlite3` to the existing import block.
- These four helpers are new, freestanding additions in `validate.py` — **do not import them from `query.py`**. `validate.py` and `query.py` are sibling CLI scripts with no existing cross-import relationship (only `build_index.py` imports *from* `validate.py`, never the reverse or sideways); introducing a `validate.py → query.py` import would be an unrequested new dependency edge. Mirror the shape/wording, don't share the code.
**Do NOT touch:** `query.py` itself (read-only reference for shape only), `build_index.py`'s schema, `LEGACY_COMPLETION_FIELDS`/`LEGACY_TERMINAL_STATUS_VALUES`, `_record_is_complete`, `load_jsonl`.
**Verify:** No standalone test for these helpers in isolation is required by test_plan.md — they are exercised indirectly by Step 2's and Step 3's tests (test_plan.md items 1–3, 5–7). Manually confirm `python3 -c "..."` importability is not needed; proceed to Step 2 where they're wired in and testable end-to-end.

### Step 2 — Wire main() to source runs/events/tools from the index
**Files:** `tools/agent-monitoring/validate.py`
**Change:**
- Remove the module-level `RUNS_FILE`, `EVENTS_FILE`, `TOOLS_FILE` constants (validate.py:24-26). Confirmed nothing outside `validate.py` imports these three names (only `LEGACY_COMPLETION_FIELDS`, `LEGACY_TERMINAL_STATUS_VALUES`, `_record_is_complete`, `load_jsonl` are imported elsewhere — by `build_index.py`, `legacy_reader.py`, `src/api/agent_ops_dashboard/ingest.py`).  
  ```
  runs = load_jsonl(RUNS_FILE)
  events = load_jsonl(EVENTS_FILE)
  tools = load_jsonl(TOOLS_FILE)
  ```
  with:
  ```
  conn = open_index(Path(args.db_path))
  runs = load_runs_from_index(conn)
  events = load_events_from_index(conn)
  tools = load_tools_from_index(conn)
  conn.close()
  ```
  placed after `args = parser.parse_args(argv)`, before the existing `runs_by_id = {...}` line. Everything downstream in `main()` (the incomplete-run check, the no-events check, the working_log cross-check, and the three `print(compute_*_report(...))` calls) is otherwise **untouched** — same variable names, same call sites, same order, same control flow.

**Do NOT touch:** the bodies of `compute_drift_report`, `compute_tool_count_drift_report`, `compute_multi_invocation_collision_report`, `_record_is_complete`, or `load_jsonl` (must remain fully defined and unmodified — `legacy_reader.py` and `src/api/agent_ops_dashboard/ingest.py` call `validate.load_jsonl`/`validate._record_is_complete` directly). **Do NOT touch:** `Makefile`'s `agent-monitoring-validate` target (Makefile:266-267). It stays `python3 tools/agent-monitoring/validate.py` with no arguments and no auto-build-index dependency, exactly mirroring `agent-monitoring-query`'s target, which also does not auto-build the index before running `query.py` despite `query.py` already hard-requiring it. Consistency with the established precedent, not a gap to fix here.
**Verify:** test_plan.md items 1–3 (`test_main_loads_runs_from_index_not_direct_jsonl`, `test_main_loads_events_from_index_not_direct_jsonl`, `test_main_loads_tools_from_index_not_direct_jsonl`) and item 4 (`test_validate_py_has_no_direct_jsonl_reads`).

## Anti-Drift Notes

1. **Ticket premise correction (stated, not silently redefined):** Neither `compute_drift_report()` nor `compute_tool_count_drift_report()` ever referenced `LEGACY_COMPLETION_FIELDS`/`LEGACY_TERMINAL_STATUS_VALUES` — confirmed by direct read (validate.py:61-167). The real duplication this ticket targets, per the idea doc's own migration-target table, is the hand-rolled `Counter`-over-`load_jsonl()`-loaded-lists pattern, which this plan migrates to `Counter`-over-index-loaded-lists. The ticket's Request Summary and Scope bullets describing "LEGACY_* allowlist duplication" are imprecise; this plan implements the idea doc's actual intent, not the ticket's literal (inaccurate) wording.
2. **AC3 is resolved as inapplicable/satisfied-by-inaction for the two named functions**, not implemented literally. `legacy_reader.py` and `build_index.py` both import `LEGACY_COMPLETION_FIELDS`/`LEGACY_TERMINAL_STATUS_VALUES` directly from `validate.py`; deleting them breaks both (out of scope to touch). `validate.py` is already the canonical upstream definer — there is no "index normalization" to point back at without inverting the import direction, which would be a materially larger, unrequested architectural change. Do not attempt to "fix" this later by inverting the import direction or duplicating the constants into the index/build_index.py.
3. **`compute_multi_invocation_collision_report()` is folded into this migration**, per the ticket's own Assumptions section anticipating and endorsing this, and per investigation's recommendation: its fields (`run_id`, `seq`, `phase`) are already typed/indexed columns on `events` (`idx_events_run_id_seq`), it follows the identical read-only/non-gating/hand-rolled-`Counter`-over-raw-`events` shape as the other two, folding it in requires zero `build_index.py` schema changes, and leaving it out would keep `events` sourced from two different paths (JSONL for this function, SQLite for the other two) inside the same `main()` run — reintroducing exactly the duplication this ticket exists to remove. No dedicated code change is needed for this function itself (Step 2's data-source swap covers it automatically); only its dedicated parity test (Step 3) is new work.
4. **`events.workflow` (typed column) is never used as a substitute for `infer_workflow(run_id)`.** `build_index.py`'s `_ingest_events` sets `workflow = record.get("workflow") or infer_workflow(run_id)` (raw-field-preferred), while `compute_drift_report` (validate.py:76) always calls `infer_workflow(e.get("run_id") or "")` directly on the `run_id` extracted from the raw dict, ignoring any `workflow` field. Because this plan reads `raw_json` and `json.loads()`s it back into the exact same dict shape (not the typed `workflow` column), `compute_drift_report`'s body is completely untouched and this divergence risk never materializes — Step 3's parity test is the proof, not an assumption.
5. **Index-existence precondition is a deliberate, stated behavior change.** `validate.py` currently runs standalone with zero index dependency; post-migration it hard-requires `agent-monitoring-index/monitoring.db` to exist, exiting 1 with the same actionable "run `make agent-monitoring-index` first" message `query.py` established, rather than falling back to the old JSONL path (a silent fallback would defeat the point of migrating — two live data-loading paths for the same file is the exact duplication problem this ticket removes). Anyone running `make agent-monitoring-validate` on a fresh checkout without having built the index first will now see this actionable failure instead of a report. This is intentional and matches `query.py`'s precedent exactly; it is not a bug to "fix" with an auto-build fallback.
6. **Parity ID is provisional.** INFRA-290 was confirmed as the next free ID at Plan time (INFRA-289 is the current max, added by the sibling `query.py` migration ticket in this same session), but Step 6 explicitly requires re-verifying the max ID immediately before writing the entry in case a concurrent process claimed it first.
7. **`main()`'s incomplete-run check is a side effect, not a target.** Do not read this plan's Step 2 as "migrating the incomplete-run check" in the sense the ticket's Out-of-Scope language warns against. That check's logic (`_record_is_complete`, both `LEGACY_*` allowlists) is byte-for-byte unchanged; only the origin of the `runs` list it iterates over changes, as an unavoidable consequence of `main()` now loading all three lists from one source instead of three separate `load_jsonl()` calls. If a future reviewer flags this as scope creep, point them to this note — splitting `runs` into two different sources (index for `compute_drift_report`, JSONL for the incomplete-run check) inside the same `main()` invocation is a worse outcome, not a safer one.

## Deviations

All 6 steps were implemented as specified, with one addition beyond the plan's explicit scope and one finding surfaced during implementation that the plan did not anticipate:

1. **Addition (not a deviation, but not explicitly called for): a documenting/pinning test for a real-corpus output divergence.** The plan's Step 3 scoped regression-parity tests to "the same corpus `test_query.py`'s parity test used" (the curated `shape1..shape6*.jsonl` + `events_jsonl_*` fixtures, plus the two `tools_jsonl_*` fixtures for the tools-dependent report). Manual end-to-end verification against the live `agent-monitoring/tools.jsonl` corpus (run *after* Step 6 was explicitly deferred, as an extra confidence check beyond what Step 3/4/5's Verify sections required) surfaced a real output divergence between `load_jsonl()`-direct and index-sourced input for `compute_tool_count_drift_report`, specifically: a `tools.jsonl` row with a valid `run_id`+`seq` but no `tool` field is counted by `compute_tool_count_drift_report`'s `actual_counts` loop (which only checks `run_id`+`seq` presence) but structurally excluded by `build_index.py`'s `_ingest_tools()` (which additionally requires `isinstance(record.get("tool"), str)`). This shape is not present in any of the plan's named curated fixture files, so none of Step 3's parity tests caught it. A new test, `test_tools_row_missing_tool_field_is_a_known_bounded_divergence`, was added to `TestRegressionParity` in `tests/tools/test_validate_agent_monitoring.py` to pin and document this exact shape, using a synthetic minimal repro rather than the real corpus's specific `run_id` (to keep the test isolated from live-data churn).
2. **This divergence is not fixed, by design, within this ticket's stated scope guards.** Fixing it would require either (a) relaxing `build_index.py`'s tools-ingestion rule to accept rows without a `tool` field — out of scope (`build_index.py`'s schema/ingestion logic is the sibling `TCK-20260713-MONITORING-SQLITE-INDEX` ticket's territory, and this plan's own Scope Guards explicitly forbid touching it), or (b) tightening `compute_tool_count_drift_report`'s body to also require a `tool` field — forbidden by this plan's own explicit instruction that the three `compute_*` function bodies stay unchanged. The divergence is non-gating (never changes `validate.py`'s exit code) and already surfaced loudly at build time via `build_index.py`'s own `WARNING: tools.jsonl record skipped` stderr line for the one known live-corpus record that triggers it. Documented in `tickets/inprogress/TCK-20260713-MONITORING-VALIDATE-INDEX-MIGRATE.md`'s Implementation Notes rather than silently absorbed.
3. **Step 6 (parity ledger) was explicitly deferred**, as instructed by the orchestrating agent for this implementation session — not a deviation from the plan's own content, but noted here since the plan's Dependency Map framed Step 6 as part of this same implementation pass ("Step 6 depends on Steps 1–5 being complete and tests green"). The INFRA-290 entry (with the divergence above noted in its `divergence_note`/`v2_evidence` if the Parity phase judges it material) is left for that later pipeline phase to write, including its own required re-verification of the current max `INFRA-*` ID.
