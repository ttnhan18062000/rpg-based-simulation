# Investigation — TCK-20260702-OBSISO-ISOLATION-PROOF

## Current Behavior

### Kernel wiring for the three benchmark configs (`src/engine/kernel.py:227-269`)
- `build_feed_from_env()` (`src/simulation_quality/feed.py:128-142`) reads `QUALITY_SCORING_DISABLED` first (returns `None` if `"1"`), then `QUALITY_FEED_MODE` (`inprocess` default / `broker`).
- If `_feed is None` (mode a, disabled): the whole hub-construction block (`kernel.py:234-260`) is skipped, `_quality_fn` stays `None`.
- If `_feed` is `InProcessQualityFeed` (mode b): hub + `build_all_scorers(weights)` (10 pillars) are built in-engine, `_quality_fn = _hub.on_envelope`, injected into `EventRecorder`'s single `QueueDrainWorker`.
- If `_feed` is `BrokerQualityFeed` (mode c): `if not isinstance(_feed, BrokerQualityFeed):` guard (G3 fix, `INFRA-318`) means **zero** `QualityHub` is built in-engine; `self._quality_feed = _feed` is still set (hoisted out of the conditional) but its `.start()` call is guarded by `self._quality_hub is not None` (`kernel.py:268`), which is `False` in broker mode — so nothing starts in-engine. The engine only produces events; scoring happens entirely in the external `QualityWorker` process.
- **Important nuance not spelled out in the ticket**: mode (a) `QUALITY_SCORING_DISABLED=1` is *not* the same as `ObservabilityMode.OFF` (used by the pre-existing `tests/perf/test_production_observatory_overhead.py`). `EventRecorder` is still constructed with `enabled=(obs_mode != ObservabilityMode.OFF)` regardless of `QUALITY_SCORING_DISABLED` — JSONL writes, stream publish, and the queue/drain-worker all keep running in mode (a); only the `quality_fn` callback inside the shared `QueueDrainWorker._run()` loop (`src/observability/queue.py:144-149`) is skipped. Mode (a) isolates SimQ's own incremental per-envelope cost on top of an already-running observability pipeline, not "observability off." Do not conflate this with `ObservabilityConfig.set_override_mode(OFF)`.
- A second, independent `QueueDrainWorker` exists for `DecisionTraceWriter` (`src/observability/cognition/decision_trace_writer.py:79-80`, landed by TRACE-ASYNC), gated by `ObservabilityConfig.is_decision_trace_enabled()` (`src/observability/config.py:292-293`), which is `True` by default in most runtime profiles and `False` only in one. This thread's presence is **orthogonal** to `QUALITY_FEED_MODE`/`QUALITY_SCORING_DISABLED` — it runs identically in all three benchmark configs as long as the same runtime profile is used for all three. It is not a confound *if* the harness holds the profile constant across the three runs, but the benchmark script must say explicitly which profile (and therefore which `OBS_DECISION_TRACE` value) it used, since this second background thread's own GIL contention is baked into every config's numbers.

### Queue-size test injection — no existing lever (gap vs. AC #3)
`EventRecorder.__init__` (`event_recorder.py:99`) builds `self.queue = BoundedObservabilityQueue(max_size=self.max_events)`, and `Kernel.__init__` calls `EventRecorder(run_dir=..., max_events=5000, ...)` with **`5000` hardcoded as a literal** (`kernel.py:263`) — no flag, env var, or profile field controls it. This is a *different* queue from the global singleton `get_observability_queue()` (`src/observability/queue.py:164-170`), which *does* honor `SIM_MAX_QUEUE_SIZE`/`RPG_MAX_QUEUE_SIZE` (`src/observability/config.py:341-343`) but is only consumed by `decision_trace_writer.py` and `stream/factory.py` — never by `EventRecorder`. There is therefore no environment-variable path today to force the SimQ-relevant queue small for AC #3's "test-injected small queue size" run. Two viable approaches, no code precedent picks one for us:
  (a) add a Kernel constructor flag/env override for `EventRecorder`'s `max_events` (production code change, also usable for a real ops runbook), or
  (b) test-only post-construction mutation of `kernel.event_recorder.queue.max_size` before the tick loop starts (no production code change; same technique `tests/unit/observability/test_obs_backpressure.py::_set_queue_fill` already uses on a different attribute of the same class).
  This needs a Plan-phase decision — flagged as an open question below, not assumed.

### `tools/calibrate_simq.py` — exact call site for a drop guard
`_run_engine()` (`calibrate_simq.py:152-264`) builds the `Kernel`, loops `kernel.tick_once()` (line 246-247), records wall-clock `elapsed = time.perf_counter() - start` (line 248, already a working precedent for timing), then `kernel.shutdown()` (line 252). **No code anywhere in this file touches `dropped_count`, `pressure_report()`, or `observability_status()`.** The guard belongs immediately after the tick loop and before/around `shutdown()`, reading `kernel.event_recorder.observability_status()` / `.queue.dropped_count` while the recorder is still alive (recorder is not guaranteed to survive `shutdown()` — needs verification during implementation whether `EventRecorder.shutdown()` (kernel.py:1065-1066) clears the queue before the counters are readable, since `queue.dropped_count` is a persistent counter not reset by `drain()`, so this should be safe, but must be checked against `EventRecorder.shutdown()`'s actual body, which this investigation did not read).

- **Hardware-class doc conflict discovered**: `docs/performance/perf_baseline_policy.md` §2.2 defines `CLASS_B` = "4 Dedicated Cores, 8GB RAM" and `CLASS_C` = "2 Cores, 2GB RAM" (this machine: 4 cores but only 5.8GB RAM — fits neither cleanly). `docs/engine/contracts/certification_contract.md` §3 ("Proof-Stable", binary AND rule) defines `CLASS_B` = "≥4 Logical Cores AND ≥8GB Total RAM", `CLASS_C` = "all other systems" — under this rule, 5.8GB < 8GB means this machine is unambiguously `CLASS_C` despite its 4 cores. - **Open**: the ticket's default preference ("hard-fail for `calibrate_simq.py`, warn for ad-hoc evaluation") is stated as a default in the ticket's own Assumptions/Open Questions, not yet confirmed by a maintainer — carried forward, not re-litigated here.
- Swap is nearly saturated in this session (920Ki free of 4.0Gi) — a real noise risk for CPU-time measurement; the benchmark run should be executed in a fresh session/close other processes, or the resulting numbers should be treated as indicative rather than final, and re-measured before locking the regression-guard threshold.

## Anti-Drift Hazards
- Do not measure `ObservabilityConfig.set_override_mode(OFF)` and report it as this ticket's mode (a) — mode (a) is `QUALITY_SCORING_DISABLED=1` with `EventRecorder` still fully enabled; conflating the two would produce a benchmark that doesn't answer R1's actual question (SimQ's own incremental cost) and would silently contradict `tests/perf/test_production_observatory_overhead.py`'s existing numbers if compared.
- Do not let the second (`DecisionTraceWriter`) `QueueDrainWorker` thread vary between the three mode runs — it's controlled by a separate flag (`OBS_DECISION_TRACE`, profile-dependent) and must be held constant, or the 3-way comparison picks up noise unrelated to `QUALITY_FEED_MODE`.
- Do not silently pick a hardware-class label without noting the `perf_baseline_policy.md` vs `certification_contract.md` conflict — a future reader auditing the results table needs to know which table was used and why.
- Do not add a `docs/guidelines/intentional_divergences.md` entry for this ticket unless the regression-guard threshold itself represents an accepted behavior change from a documented mechanics expectation — this ticket is a measurement + tooling-guard ticket, not a mechanics change; an entry there is very likely *not* required, but Plan should make that call explicitly rather than by omission.
- Do not let the queue-drop guard's implementation quietly regress `calibrate_simq.py`'s existing exit-0-on-success contract for scenarios that have zero drops — every existing calibration/anchor-based test (`test_grade_regression.py` etc.) depends on `calibrate_simq.py` continuing to succeed normally when there's no overflow.
