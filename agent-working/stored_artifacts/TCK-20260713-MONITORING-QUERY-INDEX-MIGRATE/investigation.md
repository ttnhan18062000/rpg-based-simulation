# Investigation — TCK-20260713-MONITORING-QUERY-INDEX-MIGRATE

## Current Behavior

**`tools/agent-monitoring/query.py`** (121 lines, unmodified since 2026-06-08 per `ls -la`) — a pure argparse CLI with zero test coverage (`tests/tools/test_query.py` does not exist; confirmed via `ls tests/tools/`).

- `load_jsonl()` (24-27): reads `RUNS_FILE`/`EVENTS_FILE` (`agent-monitoring/runs.jsonl`, `agent-monitoring/events.jsonl` — module-level `Path` constants at lines 19-20), returns `[]` if the file doesn't exist, else `[json.loads(l) for l in ...]` with no malformed-line handling (unlike `validate.py::load_jsonl()`, which wraps each line in `try/except json.JSONDecodeError` and warns to stderr — see Anti-Drift Hazards).
- `main()` (80-120): builds an `argparse.ArgumentParser` with 7 flags — `--agent`, `--status`, `--phase`, `--run-id`, `--days`, `--summary-contains`, `--runs` (store_true) — then branches on `args.runs`:
  - `--runs` branch (93-101): loads `runs.jsonl`, filters by `run_id` (exact), `final_status` (exact — **line 98 reads `r.get("final_status")` with no fallback to legacy `status`**, so `--status` silently misses every legacy-schema run record that only has a bare `status` field), then a `start_ts >= cutoff` days filter.
  - events branch (102-116): loads `events.jsonl`, filters by `agent`, `status`, `phase`, `run_id` (all exact match), `summary_contains` (case-insensitive substring), then a `ts >= cutoff` days filter.
- `cutoff_ts()` (35-38): `--days N` → ISO cutoff = `now(UTC) - N days`.
- `print_events()`/`print_runs()` (41-77): fixed-width table printers, no JSON output mode.
- No error handling anywhere for missing/corrupt index — not applicable today since it reads JSONL directly; this is exactly the gap AC4 (actionable "index missing" error) targets once the read path moves to SQLite.

**`tools/agent-monitoring/build_index.py`** (211 lines, just shipped by sibling ticket `TCK-20260713-MONITORING-SQLITE-INDEX`, now in `tickets/done/`) — the dependency this ticket migrates onto:
- DB path: `DEFAULT_DB_PATH = Path("agent-monitoring-index/monitoring.db")` (line 45), overridable via `--db-path`.
- Make target: `agent-monitoring-index:` (`Makefile:278-280`), invokes `tools/agent-monitoring/build_index.py` via the same interpreter-fallback shell chain as `knowledge-index:`. Not wired into `test:`/`ci:`/`all:` (on-demand only). `.gitignore:266-267` ignores the whole `agent-monitoring-index/` directory.
- Schema (`_create_schema()`, lines 52-96):
  - `runs(id, run_id, workflow, tier, start_ts, resolved_status, is_complete, raw_json)`, index on `run_id`.
  - `events(id, run_id, seq, workflow, phase, agent, raw_json)`, non-unique index on `(run_id, seq)` (deliberately non-unique — historical duplicate `(run_id, seq)` pairs exist from the pause/resume seq-collision bug, `TCK-20260728-MONITORING-PAUSE-RESUME-SEQ-COLLISION`).
  - `tools(id, run_id, seq, workflow, tool, raw_json)`, non-unique index on `(run_id, seq)`.
  - **No `agent`/`status`/`ts`/`summary`/`tool_call_count`/`cost_proxy_score`/`reason_code` columns on `events`, and no `final_status`/`agent_count`/`duration_s` columns on `runs`, and no `input_summary`/`status`/`duration_ms` columns on `tools`.** Every field query.py currently filters/prints beyond `run_id`/`seq`/`phase`/`agent`/`workflow`/`tier`/`start_ts`/`resolved_status` is **only available inside the `raw_json TEXT` column**, not as a queryable SQL column. This directly affects how the migrated query.py must be implemented: either `json.loads(row["raw_json"])` per row after a SQL fetch (Python-side filtering, closer to today's shape) or `json_extract(raw_json, '$.status')` in the `WHERE` clause (real SQL filtering). Neither is decided by the sibling ticket — it is this ticket's call.
  - `resolved_status` (via `generate_retro.py::_resolve_status()`) already fixes query.py's legacy `--status`-on-runs gap noted above (`r.get("final_status") or r.get("status")`), for free, once query.py reads `resolved_status` instead of re-deriving `final_status` itself.
  - `is_complete` (via `validate.py::_record_is_complete()`) is available but not something query.py's current flags expose — out of scope to add new flags (see Open Questions).
- `build()` (169-194): unconditional delete-and-recreate of the db file (`if db_path.exists(): db_path.unlink()`), full rebuild only, no incremental mode, prints a one-line summary, returns 0.

## Risks and Open Questions

1. **Scope ambiguity on provider/execution_id filtering — blocks a clean implementation plan until resolved.** The ticket's own Scope/Acceptance-Criteria sections (`tickets/inprogress/TCK-20260713-MONITORING-QUERY-INDEX-MIGRATE.md`) list only the 7 pre-existing flags (`--agent`, `--status`, `--phase`, `--run-id`, `--days`, `--summary-contains`, `--runs`) — no `--provider`/`--execution-id`/`--ticket-id` flag is named anywhere in Scope or Acceptance Criteria. But the Related Tickets note and `SEQUENCE.md`'s 2026-07-22 addendum both describe this ticket as consuming WRITER-UNIFICATION's fields for a "provider/execution_id-aware read migration." Live data shows zero `runs.jsonl` records currently carry these fields, and `build_index.py`'s schema has no dedicated columns for them (only reachable via `raw_json`, if present). **Do not assume which is correct** — flag for Plan/human decision: (a) migrate exactly the 7 existing flags only (literal Scope/AC reading), leaving provider/execution_id filtering to a future ticket once real data exists, or (b) also add `--provider`/`--execution-id` flags now, filtering via `raw_json` extraction since no column exists. Given CLAUDE.md's Clarification Rule ("ask only if it changes outcomes... unclear acceptance criteria"), this qualifies — it changes both the CLI surface and the SQL query shape.
2. **`raw_json`-only fields vs. dedicated columns.** Every filter/print field this ticket must migrate (`agent`, `status`/`final_status`, `summary`, `start_ts` for runs' days-cutoff, `ts` for events' days-cutoff, `agent_count`, `duration_s`) is absent from `build_index.py`'s typed columns and only available via `raw_json`. The migration must either (a) `SELECT run_id, ..., raw_json FROM runs` then filter/format in Python after `json.loads(raw_json)` (minimal SQL, closest to a drop-in replacement for `load_jsonl()`), or (b) push filters into SQL via `json_extract(raw_json, '$.status')` predicates. Approach (a) is lower-risk and easier to guarantee field-for-field output parity (AC2) since it reuses the exact same dict-based filter/print logic that exists today, only swapping the data source; approach (b) is more "real" index usage but riskier for the parity test. Recommend (a) for Plan to confirm — flagging as an open question rather than assuming.
3. **AC3 ("query.py performs zero direct reads of runs.jsonl/events.jsonl once migrated") is a testable architecture guard** — should be enforced the same way `test_build_index.py`'s `test_build_index_never_touches_write_path_modules` enforces its own file-path guard: a source-text/AST check that `query.py` no longer references `RUNS_FILE`/`EVENTS_FILE` `Path("agent-monitoring/...")` literals or `load_jsonl()`.
4. **AC4's "clear, actionable error" needs a concrete message contract.** No existing precedent phrase like "run `make X` first" exists elsewhere in `tools/`/`src/` (grep returned zero hits) — `knowledge_search.py::cmd_build_incremental()` handles a missing index by silently falling back to a full build (lines 753-756), a different UX than what this ticket's AC4 wants (a hard, actionable error, not a silent fallback). This ticket should not reuse that fallback pattern; it should mint its own message (e.g. `"No agent-monitoring index found at {db_path} — run \`make agent-monitoring-index\` first."`) and needs to also define "stale" — no staleness/mtime check exists anywhere in `build_index.py` today (it has no timestamp/version metadata table), so "stale" detection either needs a new mechanism (e.g. compare db file mtime to the 3 source JSONL mtimes) or AC4's "stale" language should be read as aspirational/future and this ticket implements only the "missing" half. Flag for Plan.
5. **Regression-parity test fixture scope.** AC2 requires "pre-migration in-memory-scan output vs post-migration index-backed output field-for-field identical on fixed fixtures." This requires either (a) keeping a copy of the pre-migration `query.py` logic (e.g. via `git show` of the pre-migration file, or a frozen helper function) to diff against, since the migration overwrites `query.py` in place, or (b) writing the parity test *before* the migration lands and snapshotting its output as literal expected strings. Given the ticket's own Open Question ("tests before migration, or same diff") leans toward sequencing as lower-risk per the idea doc, recommend capturing this diff at Plan time as an explicit two-step (tests first against current code, then migrate, then re-run same tests against migrated code) rather than assuming same-diff.
6. **`build_index.py`'s legacy-shape coverage gap.** The sibling investigation confirmed 60 distinct top-level key-sets in live `runs.jsonl` reduce to a small number of terminal-status vocabularies already handled by `resolved_status`/`is_complete`. Query.py's regression-parity fixtures should include at least the `TCK-20260623-TYPE-CHECKER` 6th-shape record (`resolved_status` legitimately `NULL`) to confirm the migrated `--status` filter doesn't crash or silently misbehave on it — this is a "permanently accepted exception," not a bug to fix (per `docs/agent-monitoring/schema.md`'s Known Limitations and `build_index.py`'s own docstring).

## Anti-Drift Hazards

- **Do not modify `build_index.py` or its schema.** Explicitly out of scope, owned by the already-shipped sibling ticket. If the migration needs a column `build_index.py` doesn't provide (see Risk #2), the answer is Python-side `json.loads(raw_json)` filtering, not "add a column" — that would be scope creep into a closed ticket's territory.
- **Do not touch `validate.py` or `generate_retro.py`** beyond importing already-existing functions (`_resolve_status`, `_record_is_complete` if needed) — their own migrations are separate, explicitly sequenced-after tickets (`TCK-20260713-MONITORING-VALIDATE-INDEX-MIGRATE`, `TCK-20260713-MONITORING-RETRO-INDEX-MIGRATE`) per `SEQUENCE.md`.
- **Do not change the JSONL write path** (`writer.py`, `post_tool_hook.py`, `record_run.py`, `record_events.py`) — explicitly out of scope and covered by CLAUDE.md's hard rule.
- **Do not silently reintroduce the legacy `--status`-on-runs bug** (line 98's `final_status`-only check with no `status` fallback) by naively porting the same filter logic onto `raw_json`-extracted dicts — the migration should filter on `resolved_status` (the SQL column, already fixed) for the `--runs --status` path, not re-derive `final_status` from `raw_json` and reintroduce the original gap.
- **Do not add new CLI flags speculatively** (e.g. `--provider`) without resolving Open Question #1 first — adding them without a clear AC would itself be undocumented scope creep, and *not* adding them if that's what the batch's cross-batch dependency note actually intended would silently leave the ticket's real intent unmet. This is exactly the kind of ambiguity CLAUDE.md's Uncertainty Rule says to leave vague rather than collapse into an assumed answer.
- **Do not assume SQLite output ordering matches JSONL append order.** `load_jsonl()` today preserves file order (append order = read order). A `SELECT ... FROM events` with no `ORDER BY` clause has undefined row order in SQLite — the migration must add an explicit `ORDER BY id` (or `ORDER BY seq`) to preserve today's implicit ordering, or the regression-parity test (AC2) will spuriously fail/flake on ordering alone, not on real content divergence.
- **Do not let the "actionable error" (AC4) swallow or mask a genuine SQLite error** (e.g. a corrupt db file, a permissions issue) under the same "index missing" message — those are a different failure class from "never built" and conflating them would make debugging a real corruption harder, not easier.
