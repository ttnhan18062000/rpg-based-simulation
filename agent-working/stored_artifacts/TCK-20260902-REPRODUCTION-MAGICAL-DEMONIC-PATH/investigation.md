# Investigation — TCK-20260902-REPRODUCTION-MAGICAL-DEMONIC-PATH

## Current Behavior

**`CalamityService.process_world_dynamics`** (`src/world/calamity.py:22-59`) is the direct
integration point named in this ticket's Related Code Areas:
- Maturity advancement: `state.tick % MATURITY_INTERVAL(1000) == 0` → `maturity_set = state.maturity + 1` (lines 30-31).
- Calamity spawn check (lines 33-58): `should_spawn` is true when `state.tick - state.last_calamity_tick >= CALAMITY_MIN_INTERVAL (2000)` AND `state.tick % CALAMITY_FORCE_INTERVAL (5000) == 0`. When true, it filters `state.regions` for `calamity_intensity > 0.3` (`CALAMITY_RANDOM_CHANCE` at line 19 is declared but never read anywhere in this method — dead constant, not touched by this ticket), picks the region with the max intensity, and spawns via `generator.spawn_monster(state=state, kind="world_boss", pos=target_region.center, difficulty_tier=4)`. Returns `StateUpdate(entities_add=[boss], last_calamity_tick_set=state.tick)`.
- **This is the exact trigger pattern the ticket's Scope references** ("following its existing intensity/trigger pattern") — `CALAMITY_MIN_INTERVAL`, `CALAMITY_FORCE_INTERVAL`, and the `calamity_intensity > 0.3` region filter are the "existing trigger threshold" constants an implementation should reuse, not reinvent.

**`CalamityService.apply_calamity_consequences`** (`calamity.py:61-82`): increases a region's `calamity_intensity` by `+0.05` (capped 1.0) when a `kind=="hero"` entity dies in a region with `hazard_level > 0.5`. Unrelated to the spawn trigger; not touched by this ticket.

**`CalamityPressurePropagator.propagate_seasonal`** (`calamity.py:85-146`): spreads `calamity_intensity` between adjacent regions every 500 ticks. Unrelated; not touched.

**Call site** — `src/engine/world_dynamics.py:127-199` (`WorldDynamicsSystem.resolve_dynamics`): `CalamityService.process_world_dynamics(state, generator)` is called **unconditionally** at line 133 (no feature-flag gate today), and its `entities_add`/`maturity_set`/`last_calamity_tick_set` are folded into the composite `update` at lines 174-182. Contrast with `CreatureTerritoryService` (lines 193-199), which is gated by `flags.get("ENABLE_CREATURE_TERRITORY_LIFECYCLE", "OFF") == "ON"` **at the world_dynamics.py call site**, versus `CampService.process_camps()` (sibling ticket TCK-...-NATURAL-CREATURE-PATH), which reads `getattr(state, "feature_flags", None) or {}` **inside the service itself**. Two valid precedents exist for where to put the flag check; see Anti-Drift Hazards.

**`EntityGenerator.spawn_monster`** (`src/systems/world_systems/generator.py:59-83`, the method the existing boss-spawn call above uses): builds via `V2EntityBuilder`, does **not** call `.identity(life_stage=...)` and does **not** call `.birth_record(...)` — today's world-boss spawn has no birth-record fields at all (both default via `LifecycleComponent`'s own defaults: `parent_a_entity_id=None`, `parent_b_entity_id=None`, `birth_tick=0`).

**`IdentityComponent.life_stage`** defaults to `LifeStage.ADULT` (`src/core/state.py:512`, `LifeStage` enum at `state.py:433-437` has `CHILD`/`ADULT`/`ELDER`). This means the ticket's "spawn directly as ADULT, no maturation clock" requirement is satisfied simply by **not** passing `life_stage=LifeStage.CHILD` and **not** pre-seeding a reduced `age_ticks` — the opposite of the sibling natural-creature path, which explicitly sets `life_stage=LifeStage.CHILD` plus `age_ticks=3000-CAMP_SPAWN_INTERVAL` to engineer a short maturation clock (`src/systems/world_systems/generator.py:85-...`, per `stored_artifacts/TCK-20260902-REPRODUCTION-NATURAL-CREATURE-PATH/plan.md` Decision 1).

**`V2EntityBuilder.birth_record()`** (`src/core/builder.py:619-...`, shipped by TCK-20260902-REPRODUCTION-BIRTH-RECORD-SCHEMA): signature `birth_record(*, parent_a_entity_id=None, parent_b_entity_id=None, birth_tick=0, birth_city_id=None, seed_familiarity=0.8, seed_sentiment=0.8)`. Wraps `.lifecycle(...)` for the four birth-record fields and `.social(bonds=...)` to seed a `SocialBond` toward each non-`None` parent — with both parent ids `None` (this ticket's Scope), no `SocialBond` is seeded, exactly matching the natural-creature path's already-proven parentless usage.

**`LegalityServiceV2.get_region_for_position`** (`src/engine/legality.py:44-46`): `Optional[RegionState]` lookup by position, already used by `CalamityService.apply_calamity_consequences` (line 69) and by the sibling `CampService` (Step 3 of its plan) for the same "which region is this event's origin" purpose — the natural precedent for resolving "the calamity's origin location" the ticket's AC references.

## Mechanics / Engine Constraints

- **`docs/mechanics/05_world_evolution.md` §6 "Calamities & World Threats"**: documents Boss Spawns / Raids / Threat Evolution at the chapter level, and already carries two precedent subsections for exactly this kind of addition — "Creature Territory Lifecycle" and "Natural-Creature Reproduction" — both structured as: flag name/default, trigger (citing existing named constants, "not new authored numbers"), birth-record population, and any maturation-clock or population-pressure-gate behavior. This ticket's new subsection must follow the same structure, explicitly stating the "no childhood" rule as its own bullet (per AC6).

This ticket's own Out of Scope section flags whether this law applies to the magical/demonic path as an **open Plan-phase question** — the atlas's population-pressure gate language is authored primarily with natural/human reproduction in mind, and a calamity-intensity-driven spawn is conceptually a different trigger family (world-threat escalation, not settlement demographics).
- **Authoritative pipeline (CLAUDE.md Durable State Rule / Authoritative Mutation Pipeline Contract)**: the spawn must be represented as `StateUpdate.entities_add` (a typed `EntityState` built via `V2EntityBuilder`), applied via the standard `AuthoritativeApplyPipeline`/`ApplyPath.apply_generation()` — identical to how the existing world-boss spawn and the sibling natural-creature spawn both already work. No direct mutation permitted.

## Risks and Open Questions

- **Population-pressure gate applicability is unresolved** — the ticket's own Out of Scope/Assumptions sections flag this explicitly as a Plan-phase decision, not assumed here. Do not default to reusing `compute_regional_scarcity()`/`migration_threshold` without an explicit Plan decision; a calamity-intensity-driven spawn is conceptually distinct from settlement/camp demographics.
- **Exact trigger relationship to the existing world-boss spawn is unresolved**: does the magical/demonic entity spawn *alongside* the world_boss on the same `should_spawn` tick/region (additive to the existing branch), or on a separate/independent condition (e.g., a distinct calamity-intensity threshold representing an escalation beyond a plain boss)? The ticket's Scope text ("at or above its trigger threshold... following its existing intensity/trigger pattern") suggests reusing `CALAMITY_MIN_INTERVAL`/`CALAMITY_FORCE_INTERVAL`/the `0.3` intensity filter verbatim (no new authored magic number, matching the sibling ticket's own precedent), but whether it is the *same* trigger evaluation as the boss spawn or a parallel one is a genuine open question for Plan — flag, do not assume.
- **Flag-gating location** (in-service inside `CalamityService.process_world_dynamics`, matching `CampService`'s idiom, vs. a new call site in `world_dynamics.py`, matching `CreatureTerritoryService`'s idiom) is a real architectural choice with two live precedents in this codebase; Plan must pick one and justify it, not default silently.
- **`birth_city_id`**: `LifecycleComponent.birth_city_id` is `Optional[int]` while `RegionState.id` is `str` — there is no numeric city id available from a calamity's origin region, matching the sibling natural-creature path's own resolution (leave `None`, satisfy the AC's "or the calamity's origin location if no city applies" via the entity's spawned `position` falling inside the target region's bounds, not a stored field). Not a gap — an already-established pattern.
- **No existing "magical"/"demonic" `kind` string or `Faction`/`EntityRole` value**: grepped `generator.py`/`spawn_config.py` — no demon/magical-being content-catalog entry exists today. Plan must decide the `kind=` string and whether `faction=Faction.MONSTER_HORDE` (used by both `spawn_monster` and `spawn_natural_creature_offspring`) is appropriate for a magical/demonic being, or whether a distinct faction is warranted — not specified by the ticket, must not be invented silently at Implement time without a Plan-phase decision.
- **`CALAMITY_RANDOM_CHANCE = 0.005`** (`calamity.py:19`) is declared but never referenced anywhere in `process_world_dynamics` — a pre-existing dead constant, unrelated to this ticket; flagging only so it is not mistaken for part of the "existing trigger threshold" the AC references.

## Anti-Drift Hazards

- **Do not modify `spawn_monster()`'s signature** — confirmed (via the sibling ticket's own grep, reused here) 7+ call sites across `camp.py`, `spawn.py`, `creature_territory.py`, `certification/scenarios.py`, `boss.py`, `calamity.py` itself, `raid.py`, plus an integration test. Add a new `EntityGenerator` method instead, mirroring `spawn_natural_creature_offspring()`'s precedent of being fully additive.
- **Do not touch the existing boss-spawn branch's `should_spawn`/`high_intensity_regions`/`target_region` logic** (`calamity.py:33-58`) — `WORLD-025`–`WORLD-028` (P0) describe this exact code; any new branch must be additive, not a refactor of the existing trigger evaluation.
- **Do not pre-seed `age_ticks` or pass `life_stage=LifeStage.CHILD`** — the natural-creature sibling's maturation-clock trick is the *opposite* of what this ticket requires. `IdentityComponent.life_stage` already defaults to `ADULT` (`state.py:512`); simply omitting both kwargs satisfies AC2's "no CHILD→ADULT transition or maturation clock" requirement. Copy-pasting the sibling's `spawn_natural_creature_offspring()` body without deleting the CHILD/age_ticks lines would be a direct AC violation.
- **Do not add any `GeneticsSystem`/`GeneticProfile` reference** — confirmed absent from `calamity.py`/`builder.py`'s birth-record path today; this ticket's Out of Scope explicitly excludes genetics. Follow the sibling's behavioral-form guard-test precedent (`test_..._does_not_reference_genetics`).
- **Do not write `population_cohorts_set`** under any circumstance in this ticket, even if Plan decides the population-pressure gate applies — the gate, if adopted, is read-only (`compute_regional_scarcity()`), matching the natural-creature path and the Migration Law's own write-path ownership (`DemographicCycleService`/`_check_migration` only).
- **Do not gate the existing maturity-advancement (`calamity.py:30-31`) or boss-spawn logic behind the new flag** — those must remain unconditional exactly as today, matching the sibling's explicit Anti-Drift Note ("flag is checked once, wrapping only the new block").
- **Flag naming**: register `ENABLE_REPRODUCTION_MAGICAL_DEMONIC_PATH`, default `FeatureMode.OFF`, DEV-002-style comment, appended after `ENABLE_REPRODUCTION_NATURAL_CREATURE_PATH` in `feature_flags.py` (`src/domains/optimization/feature_flags.py:146`) — a brand-new, ticket-owned flag, never reusing or renaming the sibling flag (per that ticket's own explicit Decision 3 convention: "each is its own per-ticket flag").
- **Do not conflate this new spawn branch with `apply_calamity_consequences()` or `CalamityPressurePropagator.propagate_seasonal()`** — both are separate, unrelated methods in the same file; neither should be touched.
