# TCK-20261004-DATA-RUNS-CLEAN-NOT-SESSION-SCOPED

## Title
`clean_data_runs_early` deletes other sessions' run data (mtime gate, no ownership marker)

## Status
OPEN

## Tier
standard

## Type
bug

## Priority
P2

## Request Summary
Reported by `rpg-feature-planning`: the post-Test cleanup removed 3684 files across 14 distinct PID suffixes, not just its own session's. Nothing in flight was lost, by luck: of the 14 suffixes only one matched a live process, and that was a GNOME daemon that had recycled a dead session's PID.

Verified here from `tools/gate_checks/done_checker_static.py`: `_find_flagged_data_run_files` flags every file under `data/runs/` and `reports/release_proof/` with `mtime >= start_ts`, and `clean_data_runs_early` unlinks all of them. Its own docstring concedes it does not protect against a concurrent session and calls this an accepted, not mitigated, tradeoff. With ~15 Claude processes live on this machine the window is open on every pipeline run. Blast radius is untracked run data (both directories are gitignored; confirmed), not source, but another session's in-flight evidence can vanish.

The peer's second point stands: the obvious fix "clean by PID suffix" is incomplete, because a PID liveness check can return a false LIVE after PID reuse, exactly as it did here. Ownership must come from a session identifier or an ownership marker, not a PID.

## Scope
- Find what writes into `data/runs/` and `reports/release_proof/` (run-directory naming, the PID suffix) and decide the ownership marker: a per-session subdirectory or a small `.owner` file written at run start containing the session id (role-aware session id once M2b exists, otherwise the pipeline's own run id) and start time.
- `clean_data_runs_early` and `check_data_runs_clean` delete or flag only paths whose marker names this session; unmarked or unknown-owner files are reported, never deleted. Both keep sharing `_find_flagged_data_run_files` (single definition, per its docstring).
- Missing or unparsable `start_ts` keeps today's fail-closed flagging for the **report**, but no longer permits deletion of unowned files.
- Update the docstring's "accepted residual risk" paragraph and the Anti-Drift note to the new behaviour; `CLAUDE.md`'s cleanup line (`rm -rf data/runs/* reports/release_proof/*`) is a governing-file item: report it to the owner, do not edit it here.

## Out of Scope
- PID-liveness-based ownership; changing where run data is written for unrelated reasons; CLAUDE.md edits.

## Acceptance Criteria
1. Two simulated sessions with overlapping mtimes and different owner markers: cleaning as session A removes only A's files; B's files survive (positive control: the old behaviour deletes both).
2. A file with no marker is reported and kept by `clean_data_runs_early`; `check_data_runs_clean` still reports it so the Verify backstop is not weakened.
3. A recycled PID (a marker naming a PID-shaped id that belongs to an unrelated live process) never causes a deletion of that owner's files, since ownership is by marker, not liveness.
4. Existing tests for `check_data_runs_clean`, INDETERMINATE and CLEANED/FAIL results stay green and unchanged in meaning; the implement-ticket.js call site works unchanged.
5. Docs and `docs/REGISTRY.yaml` regenerated.
