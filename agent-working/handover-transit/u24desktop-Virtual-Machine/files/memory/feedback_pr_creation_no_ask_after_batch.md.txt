**CURRENT RULE, 2026-09-19: work until a batch is complete, then create the PR.** Not per ticket,
and not never — accumulate several tickets on one branch and open a single PR when the batch is
done.

This settled in two steps the same day. First: *"don't open PR on your own"* — after several PRs a
day appeared, including a `CLAUDE.md` proposal (#221) the user never asked for. Then, clarifying:
*"you can continue until complete a batch, then create PR."*

So the objection was never to PR creation itself; it was to **one PR per ticket**. The user has
asked for fewer, larger batches throughout, and this is that preference applied to PR granularity.

**How to apply:** keep closing tickets on the same branch. When the batch is genuinely complete —
not when one ticket finishes — create the PR and report it. Folding into an already-open PR still
beats opening a second; see [[feedback_push_to_open_pr_not_new_stacked_pr]]. Merging remains the
user's call, always.

**History, kept because the reasoning only reads against it:**

**What changed:** the standing authorization below was given (2026-09-13) when work arrived as one
ticket, one branch, one PR. By 2026-09-19 a single session was producing several PRs a day, some
opened on my instruction rather than the user's — including a `CLAUDE.md` guidance proposal (#221)
the user had not asked for. Volume turned a convenience into noise, and PRs the user did not
request started appearing in their queue.

**How to apply now:** push and report; ask before opening. Folding work into an already-open PR is
still preferred over opening a new one — see [[feedback_push_to_open_pr_not_new_stacked_pr]] — and
the user has repeatedly asked for *fewer, larger* batches, so the usual right answer is to add to
an existing PR rather than ask about a new one.

**Original guidance, 2026-09-13 (no longer in force):**

Don't ask the user for confirmation before creating a PR once a ticket in a batch is fully closed
(Verify passed, Finalize done, pushed). Create the PR directly, update its description as needed,
and ask the reviewing peer session (e.g. agent-working-design) to review — no need to loop the user
in for each individual PR-creation decision.

**Why:** User said explicitly, mid-turn, while I was drafting a PR body and about to ask via
AskUserQuestion (2026-09-13): "you can always create PR after a batch, update PR description and
ask peer to review, don't need to ask me." This directly overrides the more conservative pattern
demonstrated earlier in the same session (asking before every single PR creation, even when a peer
had already relayed authorization) — that earlier pattern was appropriate for establishing trust,
but the user has now given standing authorization for the PR-creation step specifically.

**How to apply:** Applies to PR creation for a ticket that has already gone through the full
implement-ticket pipeline (Review approved, Verify/done-checker passed) and whose branch is already
pushed — i.e., the point where CLAUDE.md's own "require explicit user opt-in" table would otherwise
call for asking. Still confirm before other irreversible/visible actions this instruction doesn't
cover: merging a PR, force-pushing, or any destructive git operation — those remain gated as before.
Does not relax [[feedback_push_to_open_pr_not_new_stacked_pr]]'s "one open PR at a time" preference,
or the underlying Gate Integrity rule about honestly reporting gate failures.

**Reconfirmed 2026-10-03:** after a complete batch, push and open the PR without asking first ("after a batch you always need to push and open PR"). Don't ask "shall I push?" — render with `pr_render`, push, open, `--check`. Merge stays the user's call.
