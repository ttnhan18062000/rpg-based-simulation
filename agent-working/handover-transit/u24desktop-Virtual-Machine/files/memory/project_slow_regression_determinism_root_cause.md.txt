Root cause confirmed (2026-08-26) for the long-run determinism/certification test failures
investigated under `TCK-20260822-STANDARD-SLOW-REGRESSION-CI-JOB-EXIT-CODE-2` (still OPEN in
`tickets/todos/`, not yet fixed — user said "let it sit, don't do slow regression now").

**The bug:** `Kernel.tick_once()` (`src/engine/kernel.py:585-596`, also a softer check at line 435)
checks real wall-clock elapsed time (`time.perf_counter_ns()`) mid-tick, every 10 processed entity
results. If elapsed exceeds `profile.max_tick_budget_ms` **and `self._audit_mode` is False**
(the default — only `True` if `Kernel(..., flags={"audit_mode": True})` is passed explicitly), it
silently drops the remaining unprocessed entity results for that tick (`record_dropped_work`) and
forces the governor into `DEGRADED` mode. None of the three affected test files
(`tests/integration/kernel/test_long_run_determinism.py`,
`tests/certification/test_cert_long_run_stability.py`,
`tests/simulation_quality/test_grade_regression.py`) set `audit_mode=True` — confirmed via grep.

Since real per-tick wall-clock timing is subject to host CPU scheduling noise (GC pauses, thread
contention, thermal throttling — not seeded or reproducible), two runs from the identical seed can
diverge in real timing purely by machine luck, causing one run to drop entity updates the other
processes normally — producing genuinely different final entity states and thus different
`CanonicalStateHasher` hashes.

**Directly proven, not just theorized**: ran `test_1000_tick_determinism` twice in a row, identical
command (`--resource-budget large`, matching real CI), same machine, same seed — attempt 1 FAILED
(watchdog trip at tick 627, `governance_ecology` phase spiked to 36ms vs normal ~0.01-0.15ms),
attempt 2 PASSED cleanly. Matches the real CI history (4/7 push-to-main runs failed with exit 2,
most recent one passed) — same non-determinism, different runner load each time.

**Why:** Do not act without validating context — this took an actual back-to-back repro to confirm,
not just code reading; the watchdog-trip phase that spikes varies run to run (persistence one run,
governance_ecology another), consistent with real scheduling jitter rather than a fixed logic bug.

**Recommended fix (not yet applied):** narrow, test-only change — construct the `Kernel` in the
three affected long-run test files with `flags={"audit_mode": True}` so wall-clock throttling is
disabled during determinism verification, matching `audit_mode`'s existing sanctioned purpose
elsewhere in the file (bypassing real-time-dependent shortcuts for audits/certification). No
production behavior change implied.

**How to apply:** When asked to resume work on this ticket, this write-up is the investigation
artifact — skip re-deriving root cause, go straight to filing/implementing the fix (add
`audit_mode=True` to Kernel construction in the 3 test files) unless the user indicates otherwise.
