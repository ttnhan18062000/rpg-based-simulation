When work surfaces a concern that implies a decision — "should this get formalized into the doc," "should we fix this now or later," "is this scope creep" — present it as multiple explicit options, each with what it trades off, and name a recommendation. Don't collapse it into a single yes/no ask ("want me to add X, or is this a discussion for now?") or just silently pick one path and proceed.

**Why:** In the rpg-based-simulation brainstorming session (2026-08-22), after a self-assessment turn where I named real limitations in a Cross-Cutting Risk investigation, I asked "want me to add a short note... or is this more a discussion for now?" — a binary check-in, not real options. The user's correction: "next time give options and recommendations when you face a concern decisions." The pattern to avoid is defaulting to a single proposed action phrased as a question; the fix is laying out the actual alternatives (e.g., "fix now inline / file as a follow-up / leave as a known gap and move on") with a stated recommendation among them, even when one option is obviously best.

**How to apply:** Whenever a concern surfaces mid-task (a risk, an inconsistency, a scope question, a limitation just discovered), pause and frame it as: (1) the concern itself, stated plainly; (2) 2-4 concrete options for handling it — not just "do it" vs. "don't"; (3) a recommendation among them with the reason. This applies whether the concern is about documentation (this session's context), code, architecture, or process. Use `AskUserQuestion` for concerns that are genuinely blocking and need a real choice; for smaller in-flow decisions, this structure can just be written out in the response text before proceeding. Related: [[feedback_no_forced_routes_for_simq]] is a narrower, earlier instance of the same underlying instinct — don't collapse a real decision into a single default action.

**Explicitly extended to hard blocking (2026-08-26, rpg-based-simulation, hand-orchestrated implement-epic):** when a pipeline gate hard-stops (e.g. `NEEDS_HUMAN_INPUT` from a plan-phase check, `DOD_BLOCKED`, `NEEDS_CHANGES`), don't just describe the block and dangle a single "tell me to re-run" ask — lay out the concrete options for resolving it (e.g. "re-run the sub-agent to genuinely fix its own artifact" / "orchestrator patches the artifact directly" / "abandon and pick different work") with a recommendation and *why*, same as any other concern. The user's correction: "when you face hard blocking, give me options and your recommendation." This does not relax the Gate Integrity rule (never silently edit an artifact to dodge a check) — it's about how the stop is *reported*: present the real remediation paths and which one you'd pick, don't leave a bare status report.

**Explicitly extended to peer-session requests (2026-09-23, `world-rule-catalog-design` session, told to stand idle until `rpg-feature-planning` sends a design-vision request):** the user's standing instruction — "open discussion with me (options and recommendation) if you face a hard decision from request from the peer rpg-feature-planning" — means an inbound `SendMessage` from a peer session is not itself authorization to just execute a hard call unilaterally. If a peer's request implies a real decision (scope tradeoff, architectural direction, conflicting priority), route it back to the user with the same options-plus-recommendation structure before acting on the peer's behalf, even though the peer is another trusted agent session rather than a human. Routine, non-decisional peer requests (a straightforward lookup, a well-scoped task with one obvious answer) don't need this — it's specifically for the hard-decision case.
