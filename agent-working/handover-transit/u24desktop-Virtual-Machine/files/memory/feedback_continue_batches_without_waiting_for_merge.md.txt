Once a batch PR is green and I've reviewed it, tell the implementer to continue straight to the
next batch. Do not wait for the user to merge. PRs may sit open and unmerged while work continues.

Stated by the user 2026-09-13, from the batch after PR #180.

**Why:** merging is the user's call and their availability shouldn't gate implementation throughput.
Review is the quality gate, not merge.

**How to apply:**
- Review the green PR, give the merge verdict to the user, then dispatch the next batch in the same
  turn rather than holding.
- **Branch the next batch off the previous batch's branch, not main, whenever the new work depends
  on the unmerged work.** Branching off main would silently omit the dependency — which on a
  dependency chain means building against code that isn't there.
- When reviewing a stacked PR, review only its own new commits; the parent batch's commits will
  appear in the diff against main and were already reviewed.
- Expect rebases: when the user merges an earlier PR, later stacked branches may need updating.

Related: [[feedback-push-to-open-pr-not-new-stacked-pr]] governs follow-up commits to an *open* PR's
own work; this covers starting genuinely new work while an earlier PR is unmerged.
