On 2026-10-03 the shared `/` filled while I extracted a whole `git archive` tree into `/tmp`. A hook write to
`agent-working/agent-monitoring/data/<week>/<branch>.tools.jsonl` was cut off mid-record (`..."seq":n`) and the next
record was appended on the same line with no newline. Later, `record_hand_orchestrated_closure.py` crashed in
`record_events.compute_tool_stats` with a raw `JSONDecodeError ... line 1 column 74`, which looks like a bad
`--events` argument but is not (a bad `--events` prints a clean `ERROR: Invalid JSON in --events`).

**Why:** the shard is read back by the closure tool, so one corrupt line blocks every closure on that branch.

**How to apply:** (1) when that traceback appears, find the bad line first (parse each line, print line numbers), do
not retry the command. (2) Repair only when the line is a truncated fragment followed by one complete record: drop the
fragment, keep the record, check the kept part parses and the fragment does not, re-verify the whole shard, and tell
the reviewer. Do it while the shard is still untracked, so nothing committed changes. (3) Prevent it: never extract a
full tree into `/tmp` (use `git show <ref>:<file>` into an untracked file inside the worktree, then delete it); check
`df -h /` before any large scratch work; when the disk is full, Bash output is lost, so redirect output to a file in
the worktree and Read it. An empty untracked `.writer_health.jsonl` appears in the shard dir after such an episode:
do not commit it.
