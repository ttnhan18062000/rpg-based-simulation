**Also 2026-09-25: the implementer owns CI checking and triage entirely** — polling, diagnosis,
log/annotation fetching, re-runs. The design session does not poll CI or reproduce CI failures
locally. This is the recurring drift: after being told to review approach only, this session polled
CI, ran local repros of the failing job, and began reconstructing CI's merge ref — all work the
implementer was already doing, and one of those local repros pointed at the wrong test entirely.
Hand over leads and hypotheses; let them run the experiment; review the conclusion.

Set 2026-09-25. On a branch an `agent-working-implementer` peer is working, the design/review
session (`agent-working-design`) **does not commit or push**. It scopes, reviews and verifies, then
**hands ticket content to the implementer** to commit and push. One writer per branch.

**Why:** two sessions committing to one branch generates non-fast-forward races and merge tax. This
was confirmed live on the `github-delivery-process-epic` branch: a ticket push was rejected
non-fast-forward because the implementer had pushed underneath it, requiring fetch → discard a
regenerated `docs/REGISTRY.yaml` timestamp → merge → re-push. The shared-worktree monitoring-shard
race ([[project_worktree_verification_traps]]) compounds it, since every tool call re-dirties
`agent-monitoring/data/YYYY-Www/tools.jsonl` between git commands.

**How to apply:** write the ticket draft (or the finding), then send it to the implementer via
`SendMessage` for them to commit. Keep handing off the *verification detail* that would otherwise be
lost — baseline values with their SHAs, bisection evidence, what was ruled out and how — because the
implementer cannot re-derive it and will otherwise reconstruct it wrongly
([[feedback_push_ticket_before_dispatching]] is the older, superseded-in-part pattern: it assumed
the design session pushes the ticket itself, which no longer applies to a branch the implementer
holds).

Still the design session's own job: reviewing, running tests independently to verify claims, and
getting **direct user confirmation on governing-file edits**
([[feedback_verify_governing_file_edits_directly]]) — that is not delegated.

**2026-09-29, the same hazard in a second shape: a branch with a `Workflow` running on it.** The rule
isn't only "a branch a peer session holds" — it is **any branch an implementer is mid-workflow on**.
After dispatching `/implement-epic` over `systemic-world-first-wave-tickets`, this session committed
an unrelated ticket-status fix straight onto that branch while the epic was still running. Caught
before pushing; nothing broke.

**How to recover cleanly** (the whole point of recording this): don't reset and lose the work.
`git branch <topic-name> <the-commit>` to park it, then `git reset --hard <origin-sha>` to restore the
shared branch to exactly what was pushed. Verify with `git rev-parse HEAD origin/<branch>` printing
two identical SHAs. Later, once the workflow reports done, `git merge --ff-only origin/<branch>` then
`git cherry-pick` the parked commit — and if the branch is squash-merged, confirm the fix landed by
**content** (`git show origin/main:<path> | grep <the change>`), not by `git merge-base --is-ancestor`,
which is always false after a squash.

The tell that you are about to do this: you are about to `git add` in a worktree whose current branch
you handed to an implementer earlier in the same session. Check `git log origin/<branch>` first.
