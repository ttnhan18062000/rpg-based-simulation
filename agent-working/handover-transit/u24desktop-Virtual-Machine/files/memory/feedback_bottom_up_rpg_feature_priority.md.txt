When sequencing RPG feature repairs, go **bottom to top**. Lower/core layers before higher ones:
movement, combat, and interaction sit *below* party/group, which sits below cognition/knowledge.

Rank by two signals, both pointing the same way:
- **Execution frequency** — something running every tick outranks something running occasionally.
- **Dependency-by-other-count** — the more features that depend on it, the higher its priority.

Stated by the user 2026-09-13, after a batch that mixed layers (group linkage, progression,
world-assembly) and after I scoped a cognition-layer initiative (knowledge/investigation) ahead of
lower-layer defects.

**Why:** a defect in a low, high-frequency layer corrupts or blocks everything built on it, so
fixing upper layers first means building on unverified ground — and the upper-layer fix may be
re-done once the layer beneath it changes.

**How to apply:** before sequencing a batch or gating one ticket behind another, check the
dependency direction is real and not assumed. Specifically re-check any gate where a *lower*-layer
item was made to wait on a *higher*-layer decision — that's the shape this rule forbids. See
[[project-worktree-verification-traps]] for the related habit of verifying rather than asserting.
