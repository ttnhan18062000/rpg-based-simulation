When weighing implementation/tool/architecture choices, prioritize token efficiency over speed —
the user explicitly stated they'll accept a real time cost for a real token saving, giving a
concrete anchor: "30% less token but even 50% slower is acceptable at a portion."

**Why:** stated directly as a standing operating preference, not tied to one specific decision.
Surfaced during a discussion of whether to keep investing in the Knowledge Gateway MCP
(`docs/plans/knowledge-gateway-mcp-proposal.md`) — real measurement
(`docs/engine/contracts/knowledge_gateway_mcp/audit_phase0_5.md` §2) showed it costs MORE tokens
AND is slower than the direct tool on 7/7 corpus entries, so it fails even under this
token-forgiving tradeoff policy; this preference didn't change that verdict, it reinforced it. See
[[project_kgmcp_status_2026_08]].

**How to apply:**
- When two approaches differ in token cost vs. wall-clock time, don't default to "faster wins" —
  actively weigh whether the slower option's token savings clear a real bar (the user's own anchor:
  roughly 30% fewer tokens is worth up to ~50% more time). Below that ratio, judge case by case
  rather than assuming speed should win by default.
- This is a tradeoff preference, not a blank check for arbitrarily slow approaches — "at a portion"
  suggests bounded tolerance, not unlimited. If a slowdown looks likely to compound (e.g., in a
  tight iteration loop, or blocking other work), flag the tradeoff explicitly rather than assuming
  it clears the bar.
- Applies to my own tool/approach choices (e.g., preferring a cheaper multi-step read over one
  expensive broad one) as much as to architecture recommendations made to the user.
