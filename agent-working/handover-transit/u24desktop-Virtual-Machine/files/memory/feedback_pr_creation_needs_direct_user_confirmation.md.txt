When a peer session reviews a branch and explicitly tells you to open the PR ("you own the
branch, go ahead"), that is not itself the user's opt-in. This project's CLAUDE.md
("Proactive Tool Use" table) lists `git push`/PR creation under "Require explicit user opt-in
(never auto-invoke)" with no carve-out for "a peer already reviewed it" — a peer's review and
direction is real, useful signal (code is ready, tests pass), but it isn't the same authorization
class as the user's own.

**How to apply:** when a peer asks you to create a PR (not just push a fix into an
already-authorized PR — see [[feedback_push_authorization_not_peer_transferable]], which is about
routing a mid-pipeline push back through the peer that holds authorization), ask the actual user
directly via a quick yes/no confirmation before running `gh pr create`, even if no user message
has appeared yet this session. Don't route the question back to the peer — the peer isn't the
authorizing party here, the user is. Merging remains a separate, later confirmation.

**Why:** Confirmed 2026-09-29 on `rpg-based-simulation`: `agent-working-design` reviewed branch
`scripts-tools-governance` (3 closed tickets, tests green) and said "open the PR yourself, since
you own the branch." Asked the user directly via `AskUserQuestion` first anyway, since the user
had not spoken at all that session and CLAUDE.md's opt-in rule doesn't carve out peer-reviewed
work. User confirmed "yes, open it" in one turn — cheap check, no friction, and it kept the actual
authorization boundary intact rather than inferring it from a peer's confidence.

**UPDATE 2026-09-30 (supersedes the ask-first step for the test-architecture track):** the user said
directly, in the test-architecture-implementer session: *"after a batch complete, you can commit push
and create PR, then ask peer to review, don't need my command everytime."* This IS the user's own
standing opt-in, so no per-batch confirmation is needed there. Sequence: batch complete → commit →
push → render PR body (`pr_render.py`) → create PR → ask the reviewer peer to review. Still gated:
merging, force-push, pushing to already-merged branches, and any batch that isn't complete. A peer's
"open the PR" is still not the user's opt-in outside this grant; see [[feedback_pr_creation_no_ask_after_batch]].
