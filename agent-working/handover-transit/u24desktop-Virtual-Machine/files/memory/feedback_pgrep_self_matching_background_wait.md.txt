Found 2026-09-30 (TCK-20260929-CREATE-TICKETS-WORKFLOW-RUNTIME-PILOT session): 13 background bash
processes had been stuck for up to ~11 hours, all shaped like `until ! pgrep -f "pytest
tests/tools" > /dev/null; do sleep N; done`. `pgrep -f` matches against a process's *full command
line* — since the literal string `"pytest tests/tools"` appears inside the wrapper's own `eval`
argument (not just in the target process it's meant to detect), each loop matched itself and could
never see "not found," so it spun forever even after the real target process had long since exited.

**How to apply:** when writing a `pgrep -f "<pattern>"`-based polling/wait loop, never use a
pattern that is also a substring of the wrapper command's own text. Anchor on something only the
*target* process has and the polling loop's own source text does not — a PID file the target
writes, a sentinel the target creates on exit, or a pattern specific enough (e.g. including a
flag combination or full path only the real target uses) that the wrapper's own invocation text
can't accidentally contain it. When in doubt, write the target's PID to a file at launch and poll
`[ -e /path/to/pidfile ]` or `kill -0 "$PID"` instead of `pgrep -f` on a loose substring.

**Why this is easy to miss:** the loop looks correct in isolation and works fine the first time
you read it, since the bug only manifests once the wrapper's own command line happens to contain
the same string it's searching for — an interaction between the polling pattern and the wrapper's
own boilerplate, not a bug in the polling logic itself.
