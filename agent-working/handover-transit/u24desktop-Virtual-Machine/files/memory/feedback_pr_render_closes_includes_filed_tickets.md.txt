`tools/delivery/pr_render.py` treats "ticket file touched by the branch" as "ticket closed by the
branch", so a PR that closes work **and files a follow-up** lists the follow-up in `Closes:`.
`pr_render --check` **passes anyway** — it does not catch this. Remedy is
`pr_render --exclude-ticket <ID>` with a reason.

Seen twice: PR #276 (wrongly closed an epic the PR filed) and PR #279 (wrongly closed
`TCK-20261001-SPAWN-AND-DERIVATION-HOLD-INCOMPATIBLE-DERIVED-STAT-MODELS`, which sat in
`tickets/todos/`). Both caught only by reading the body; in #279 the body even contradicted itself
(`Tests: (none yet)` for the "closed" ticket).

**FIXED IN #280, merged 2026-10-01.** `agent-working-design`/`agent-working-implementer` landed: a
ticket that is only *cited* is left out of `Closes:` automatically (keyed on the changed ticket **file**
in `git diff --name-only base..HEAD`, not on the commit subject — so a genuine close, which moves its
file into `done/`, is still listed); a ticketless branch renders via `--theme`/`--scope`/`--why` ending in
`Closes: (none)`, and `--check` parses that; and `pr_render` now warns on a ticket under `inprogress/`.
**VERIFIED ON A LIVE PR, 2026-10-02: PR #284** (`goal-dispatch-objective-kind`, a planning-only batch).
Both fixed behaviours held. The branch touched 7 ticket files, all open, and `pr_render` left **every
one** out of `Closes:` with a per-ticket warning naming the actual directory (`inprogress/` vs `todos/`),
plus one `cited, not closed` for a ticket named in two commit subjects whose file the branch never
touched. It then rendered the ticketless body from `--theme`/`--scope`/`--why` ending in
`Closes: (none)`. No `--exclude-ticket` was needed. The earlier concern that the round-trip test used a
fake `gh` runner is **discharged** — this was a real `gh pr create`.
The history below is kept because the failure shapes are what to check for, not because the tool still has
them.

**Third variant, 2026-10-02 — a ticketless branch cannot be PR'd at all (NOW FIXED, see above).** On a docs-only /
record-only branch (changes no ticket file), `pr_render` reconstructs a body from the *commit
subject's* ticket ID, per the repo's own commit convention — so it emitted the whole already-merged
#279 body plus `Closes:` for a ticket already in `tickets/done/`. Adding `--exclude-ticket` then
yields `no tickets discovered` / `TITLE: None`. Wrong body or no body, no third path, and bodies must
be rendered not hand-written — so such a branch has no legal PR. **Fold it into the next batch that
does touch a ticket file.** Every follow-up commit to a closed ticket trips this.

**Why:** most good batches file follow-ups, so this fires often, and it silently makes a false claim
that an open ticket is done. Nothing in CI or `--check` flags it.

**How to apply:** before recommending a merge, read the `Closes:` line and check each ID's physical
directory — a ticket in `todos/`, or in `inprogress/` without `phase: done`, cannot be closed by that
PR. Reported to `agent-working-design` as a tool gap (delivery tooling is theirs) rather than patched
around; see [[feedback_file_tickets_for_workflow_gaps]] and
[[feedback_pr_body_must_be_rendered_not_written]]. Note the ticket's location already encodes the
answer, the same signal `validate_frontmatter.py::check_ticket_location_consistency()` uses.
