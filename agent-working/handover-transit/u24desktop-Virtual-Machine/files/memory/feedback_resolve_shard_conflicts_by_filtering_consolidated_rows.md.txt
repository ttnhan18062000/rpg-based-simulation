When a per-batch monitoring shard (`agent-monitoring/data/<week>/<batch-id>.tools.jsonl`) conflicts on
a merge or blocks a branch switch — typically `modify/delete`, because consolidation deleted it
remotely while hooks appended to it locally — **neither taking nor dropping the whole file is correct**:

- dropping it loses rows appended since the last consolidation;
- keeping it re-adds already-consolidated rows, which the next consolidation folds into the canonical
  file a second time.

**How to apply:** compare row-by-row against the canonical file, keying on each row's own `ts`, and keep
only rows whose `ts` is absent from it; delete the shard if none remain. Same method for a branch switch
blocked by local changes — copy the working-tree file aside first, `git checkout -- <file>` to clean, switch,
then restore the filtered rows. Confirmed twice on 2026-09-29: one cherry-pick where 14 of 25 rows were
already consolidated and 11 were not, and one branch switch carrying 18 rows forward.

**Why:** these shards exist to give every writer a disjoint file (`TCK-20260924-MONITORING-SHARD-SQUASH-MERGE-CONFLICT-AVOIDANCE`),
so a conflict means the same batch was written from two places, not that one side is stale. Never resolve one
with `git checkout HEAD -- <shard>` without saving the working copy first — the hook appends, so that
permanently deletes every row written since the last commit, including other sessions' in a shared worktree.

Also: a per-batch shard belongs only on the branch whose work produced it. When cherry-picking a
commit to another branch, drop the other branch's shard from the pick rather than carrying it across.
Relates to [[feedback_working_log_row_lives_in_pending_shard]], which is the same pending-then-consolidated
design applied to `tickets/working_log.csv`.
