When a sub-agent, reviewer or peer session hands over a finding, **verify the load-bearing claims before
relaying them onward as fact.** Relay unverified claims explicitly marked as that agent's inference.

**Why:** on 2026-10-01 I relayed an `architecture-reviewer` claim that removing `combat.py:136` made
former-`HERO` entities "lethally killable through `resolve_attack` for the first time", so "mortality
moves corpus-wide". It reached the implementer, a roadmap draft and a PR disclosure before a measurement
showed **zero `COMBAT` deaths in 900 tick-world-runs** — no `KILL` fired at all, because that path is
starved, so the change had no measurable effect. The claim was plausible, structural, and false.

**How to apply:**
- Verifying usually costs one `grep`/`git show`/short run. I verified the same reviewer's *other* claims
  (no deserializer exists; `COMB-311` is P1 on the reduced tuple) and all held — so this is cheap
  filtering, not distrust.
- The pattern in my own errors: **most confident where I reasoned from structure instead of reading the
  code or the rule.** Treat a conclusion reached without opening the file as a hypothesis.
- **Measure your own claims when a measurement is cheap.** A 6-run, ~2-minute base-vs-head probe
  falsified both my framing *and* half the rule owner's hypothesis, and surfaced a mechanism neither of
  us predicted (mortality scaling with succession dispatch volume). It caught errors *before* anyone had
  to argue with me — the only one of ~8 that day to do so.
- State hypotheses as hypotheses in artifacts ("Readings (hypotheses, not conclusions)"), and name the
  discriminating test rather than letting a lead harden into a finding.
