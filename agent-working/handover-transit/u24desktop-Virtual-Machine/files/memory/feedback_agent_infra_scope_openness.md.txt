When scoping fixes to `.claude/skills/`, `.claude/agents/`, or `.claude/workflows/*.js` (the agent-orchestration layer itself, not simulation code), the user has explicitly authorized going beyond minimal patches: introducing a new skill, a new pipeline phase, or a new agent is on the table if it's genuinely warranted — and so is updating or removing an existing one that isn't working.

**Why:** stated directly after a data-mining audit (agent-monitoring-driven) found real gaps in `planner.md`, `implementer.md`, and `create-tickets/SKILL.md`. The user's instruction was "you can introduce new skills, new phases, new agent, if it worth and well data-managed to see if it worked, you also can update or remove one" — i.e., don't default to the smallest possible diff out of caution; the real constraint is *observability*, not *change size*.

**How to apply:** Before picking a fix's shape (prompt-text patch vs. new phase vs. new agent vs. removal), ask: (1) is there already an agent-monitoring metric that would show whether this fix worked (e.g. Review/Verify failure rate trend in `generate_retro.py`'s existing gate-outcome computation) — if yes, a targeted patch verified against that existing metric is usually sufficient and simplest; (2) if the gap genuinely can't be measured with existing instrumentation, that's a signal the fix may need new instrumentation alongside it (new event field, new retro section) before or as part of the structural change — per this repo's "never a fabricated or silent number" convention (see `[[project_environments]]`-adjacent conventions in `retrieval_baseline_metrics.py`/`retrieval_events.py`). Don't invent a new phase/agent just because a problem seems structurally bigger than a prompt tweak — invent it when the existing metrics can't see the problem without it, or when a prompt-only fix has already been tried and the metric shows it didn't move.
