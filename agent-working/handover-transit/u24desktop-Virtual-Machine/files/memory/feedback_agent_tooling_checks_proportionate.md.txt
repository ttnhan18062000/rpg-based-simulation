Checks over agent-working tooling (agent-monitoring data, working_log, retro reports, sidecar
attribution) must be **proportionate, not strict**. The user's framing, 2026-09-16: *"we don't need
to make the test too strictly for agent working, since it's just the side effect, not the core
simulation feature."*

**Why:** this telemetry records *how work happened*, not what the simulation does. Its values move
with working style — pipeline vs hand-orchestrated, how many sessions run concurrently, what time
of week it is — none of which is a defect. A strict gate over it fires on legitimate activity,
which makes it an *inverted* signal: it goes red **because** work is happening. Core simulation
behaviour (mechanics, parity, determinism) is what deserves hard gating; monitoring exhaust is not.

**Concrete case that produced this:** `ATTRIBUTION_RATE_FLOOR` in
`tools/gate_checks/sidecar_attribution_coverage_check.py` was a blocking ratchet on a rolling
14-day attribution percentage. Daily rates measured 2026-09-16: 09-10 was 100%, then 54.8%, 30.6%,
38.1%, 30.2% — the drop begins exactly when a hand-orchestrated batch started, not when any code
regressed. The constant was re-pinned 75.3 → 74.0 → (73.0, reverted) inside two days, never once
caught a regression, and left `main` and every PR red. An absolute-count variant fails the same
way: the raw unattributed count swung 0 → 1,492 → 2,044 → 595 day to day, tracking working style.

**Resolved 2026-09-16: the gate was deleted**, not lowered or re-pinned — `main` and every red PR
go green without weakening any threshold or guard. The full daily series adds the pre-drop baseline:
09-08 98.0%, 09-09 99.2%, 09-10 100.0%, then 54.8% on 09-11, the first day of the hand-orchestrated
batch. Three consecutive days near-perfect, then a cliff on a date with no code change, is what made
deletion defensible rather than merely convenient — without that date, removing a guard under CI
pressure is indistinguishable from the gate-gaming the guard existed to prevent.

**How to apply:**

- For agent-working/monitoring signals, prefer **reported numbers in the retro** over blocking gates.
- If a detector is genuinely wanted, scope it to a population where the property is *expected to
  hold* — e.g. pipeline runs that opened a `run_id` whose tool rows lack one (should be zero, so
  any nonzero is a real defect) — rather than a corpus-wide rate diluted by legitimate work.
- Ratchets remain right for *corpus debt that only grows on a real mistake* (duplicate rows,
  malformed records). They are wrong for anything that moves with time or working style.
- A gate that needs re-pinning to keep passing is not a ratchet; it is churn. See
  [[project_graphify_out_stays_local]] for the adjacent case of not over-engineering local tooling.
