Runtime measurement is the right instrument for a reachability or absence claim — and a probe is
itself an instrument that can be wrong. Give every probe a **positive control**, and scrutinise a
contradicting measurement as hard as the claim it contradicts.

**Both failure directions happened on 2026-09-30, hours apart.**

*False positive.* A peer's probe reported "30 `POPULATION_BIRTH`/`POPULATION_DEATH` events in 6 of
21 worlds", apparently disproving my ticket. Its filter matched any category *containing*
`POPULATION`, so all 30 were `POPULATION_MIGRATION`. Re-run with exact names: **0 and 0**.

*False negative risk.* My own probe monkeypatched `get_effective_stats` and counted 0 calls over
600 ticks. A zero from a monkeypatch is meaningless if the patch never took effect, so the probe
asserted a positive control first — call through the *consumer's own resolved name*
(`apply_mod.SkillScalingService is rpg_depth.SkillScalingService`, then invoke it) and require the
counter to increment by exactly 1 before the run. It did, which is the only reason the 0 was
reportable.

**What caught the false positive was an invariant, not suspicion.** `process_demographics` computes
`net = int(births - deaths)` with `birth_rate 0.02 > mortality_rate 0.01`, so `net >= 0` always and
the rates are never overridden anywhere in `src/`. A reported *decrease* was therefore impossible
from that service. Checking one arithmetic invariant against the reported data located the filter
bug.

**The second mistake, which cost a commit to undo:** I conceded the *entire* premise, then appended
the invariant objection. The right order is the reverse — lead with what cannot be true, and
concede only the part actually contradicted. My ticket had two claims ("never emits an event" and
"counts frozen"); only the second was false, and I withdrew both, then had to restore the first
(`da5172170` → `e60b6af71`).

**How to apply:**
- Before reporting a count, especially a zero: add a positive control that proves the instrument
  fires. Say in the write-up that it passed.
- Prefer exact matching over substring/prefix matching in any event or category filter, and state
  which you used.
- Use the *production* entry point — see [[project_worktree_verification_traps]]; loading a world
  via a non-production loader measures a different world.
- When a measurement contradicts you, check it against an invariant of the code before conceding.
  Then concede precisely the contradicted claim and restate what survives.
- State the bounds every time: how many worlds, which seed, how many ticks. A 3-world zero is
  strong; a 1-world zero is the overgeneralisation that got a whole pattern document retired the
  same day.

**2026-10-04 — the check that never ran at all.** A new instance with a different mechanism: in a
chained `cmd_a && grep -c X && cmd_b && grep Y`, the `grep -c` returned `0` — which is **exit status
1** — so the `&&` chain short-circuited and `grep Y` silently never ran. I read the empty output as
"the second check found nothing" and concluded four ticket files were untracked and invisible to a
peer implementer. They were committed all along. So: a probe can be wrong, *and* a probe can be
absent while still producing output that looks like a negative result.

**How to apply:** never put a counting command (`grep -c`, `wc -l`-style tests, anything that exits
non-zero on a legitimate zero) in the middle of an `&&` chain — use `;` between independent checks,
or print an explicit sentinel after each one. When a chained check yields nothing, confirm the
command ran before interpreting the silence.

**Third instance, same day, same root cause — an exit code treated as "try again later".** A
`Monitor` poll loop built on `s=$(gh pr checks <n> --json ...) || { sleep 30; continue; }` emitted
**zero events for 30 minutes** while three checks were already failing. Cause: **`gh pr checks`
exits 1 when any check fails** (verified: exit code 1), so every iteration took the retry branch and
never reached the emit. The silence was indistinguishable from "checks still pending" — the exact
"silence is not success" trap the Monitor tool documents.

**How to apply:** before using a command's exit code as a liveness/retry signal, check what it
returns on the *condition you are watching for* — many CLIs (`gh pr checks`, `grep -c`, `diff`,
`pytest`) exit non-zero on a legitimate, informative result. Treat only a genuinely absent/garbled
response as transient, e.g. test for empty output instead (`[ -z "$s" ]`). And when a watch reports
no events, verify the watcher ran rather than concluding nothing happened.

**Fourth instance, same day — the search's SHAPE decided the answer.** I grepped
`"def test_.*determinism"` over a test directory, found two matches in other classes, and told an
implementer there was **no** test asserting same-seed→same-content for a generator. There was:
`TestDeterminism::test_two_calls_produce_identical_output`, which `pop`s
`generation_provenance.generated_at` and compares the rest. My pattern looked for the concept in
**function** names; this codebase carried it in the **class** name. The implementer corrected me and
the correction verified.

**How to apply:** when concluding a test or behaviour does **not** exist, the claim rests on the
search pattern, so state the pattern and widen it before asserting absence — search the concept in
class names, file names, docstrings and assertion text, not just `def` lines. "I did not find it"
is reportable; "it does not exist" needs a search you would defend. Sharpest version of the day: I
asserted this gap *in the same message where I was telling someone else their test filter was too
narrow.*
