When folding a finding from a PR-under-review into a ticket that runs on a *different* branch, check
that the target branch actually contains the cited code before handing over the scope item:
`git merge-base --is-ancestor <pr-commit> <target-branch>`, or just grep the symbol on
`origin/main` and on the target branch.

**Why:** on 2026-09-24 I reviewed PR #245 and folded a defect in `_COMPARISON_TEXT`
(`generate_territory_control_view.py:203-238`) into `TCK-20260924-REGIONAL-SOVEREIGNTY-THRESHOLD-DISAGREEMENT`,
citing line numbers taken from #245's own version of the file. That branch had been cut from `main`
before M4 merged, so the function did not exist there at all — 5 occurrences on the M4 branch, 0 on
`origin/main`, 0 on the sovereignty branch. The implementer's architecture review caught it before
writing code; it cost a round-trip and left two steps of a ticket blocked on an unrelated merge.

**How to apply:** a review finding is anchored to the branch it was found on, not to the repo. When
scoping it elsewhere, either confirm ancestry first or state the dependency explicitly ("blocked
until #N lands") so it is scheduled rather than discovered. Line numbers read out of a PR diff are
the least portable thing to hand another agent — prefer the symbol name plus the branch it lives on.
Related: [[project_worktree_verification_traps]], [[feedback_push_ticket_before_dispatching]].

**Same trap, second shape — a TOOL's output is anchored to the branch too (2026-09-30).** I ran
`tools/gate_checks/done_checker_static.py`, read four FAILs, and reported them to
`agent-working-design` as a live gap in the gate. They asked me to check ancestry first:
`git merge-base --is-ancestor 833b60306 791e6bf6b` → not an ancestor. `origin/main` had moved to
#261, which *already fixed* all four; my branch was still on #260. After merging `origin/main` the
four FAILs were gone and the real gap was **one** condition, not four-plus-three. A stale checkout
does not just make you cite wrong line numbers — it makes the tools you run report already-fixed
problems, and those reports are more convincing because they look like fresh evidence.

**So: before reporting any gate/validator/test failure as an unfixed gap, `git fetch` and confirm
your base contains current `origin/main`.** Re-run on a current base, and report what that run
says. Especially when the finding is about the tooling itself — that is exactly the code most
likely to have just been fixed by someone else.
