Feature flags belong on **isolated, unique, or extended** features only — not on core mechanisms.

Stated by the user 2026-09-14, after the `ENABLE_COMBAT_ENGAGEMENT` work.

**Why:** a flag creates two branches of behaviour, enabled and disabled, and only one of them
actually runs. The other is carried, tested in isolation, and unexercised — so it rots. Flagging a
*core* mechanism means the simulation has two versions of its own laws, and the version most people
observe is the one where the mechanic doesn't exist.

**The evidence from this repo (2026-09):** `combat_engagement` — pre-combat threat assessment,
learning from fights, fight-or-flee judgement — is core simulation behaviour and sat behind a
default-OFF flag for months. Enabling it immediately exposed four real defects: silent
cognition-memory loss, an O(n²) scan hidden behind a dead optimisation check, a dead local variable,
and a documented-but-unimplemented `FLED` branch. All had passing tests. See also: 18 of 27 flags
default OFF, and 9 of them cited a SHADOW validation that was itself broken — held behind a gate
nobody could pass. A feature permanently off is indistinguishable from one never built.

**How to apply:**
- Core simulation laws (combat resolution, perception, movement, economy rules) ship unflagged.
- Use a flag for: genuinely optional/extended features, experiments, or a *temporary* rollout of a
  risky change — with a removal plan, not indefinitely.
- Treat a long-lived flag on core behaviour as a design smell to retire, not a permanent control.

problem seen from two angles.
