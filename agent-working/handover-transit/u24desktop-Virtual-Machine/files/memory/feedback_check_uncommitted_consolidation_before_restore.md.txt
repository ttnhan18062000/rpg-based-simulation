When a peer's commit appears to delete hook-written rows from a per-batch monitoring shard, check that peer's working tree for the canonical `agent-monitoring/data/<week>/tools.jsonl` (and runs/events) before asking for a restore. `monitoring_consolidation` moves shard rows into the canonical file and truncates the shard. If the canonical file isn't committed yet, the committed tree looks like data loss.

**Why:** 2026-09-28, PR #253. `0d28d5fea` truncated the batch shard, and a `git grep` of the committed head found the 25 rows nowhere. I asked for a restore. The rows were already in the implementer's uncommitted canonical file, so the restore commit (`0f46089db`) double-counted all 25, which inflates `compute_tool_stats`, since it reads both files.

**How to apply:** Before reporting monitoring rows as lost, grep exact lines in (a) every file at the committed ref and (b) the owning worktree's canonical files on disk. Only request a restore if both come back empty. Instruct "each line exactly once across all week files" as the acceptance check. Related: [[feedback_verify_peer_commits_via_shared_object_store]], [[project_worktree_corpus_measurement_staleness]].

**Reconfirmed 2026-09-30, as the one who made the mistake this time** (TCK-20260929-CREATE-TICKETS-WORKFLOW-RUNTIME-PILOT batch, PR #261): restored 10 accidentally-deleted per-branch shards via `git checkout -- <path>` without first diffing the canonical files against origin/main, so the already-folded rows got double-counted (~3,300 rows). `agent-working-design` caught it by exactly the method this memory prescribes. Two escalations beyond the original incident:
1. **The check must be re-run before every commit, not just once** — a single test suite run can re-trigger the fold mid-session, silently reintroducing duplication between an earlier "clean" check and the next commit. A one-shot verification is not enough once any test in the session can call `consolidate_all()`.
2. **`tickets/working_log.csv` shards are a different, worse case than `tools/events/runs.jsonl` shards.** The JSONL canonical files can be safely de-duplicated after the fact (filter canonical rows against every currently-present shard, keep only what's absent — see [[feedback_resolve_shard_conflicts_by_filtering_consolidated_rows]]), so restoring a stale shard there is recoverable. `working_log.csv` has no equivalent per-shard dedup check anywhere in the repo's tooling — if a `<branch>.working_log.jsonl` shard's rows are already correctly, exactly-once present in canonical (confirmed by grep), restoring that specific shard and letting it get re-consolidated on the next fold reintroduces the exact same duplicate rows every time. The fix that actually stuck: leave an already-fully-consolidated `working_log.jsonl` shard deleted rather than restoring it, once its content is confirmed safe in canonical — do not apply the "always restore, they're not branch defects" default to this one file type uncritically.
