Don't send plan-only or spec-only PRs for work that is understood. Implement the logic and fold
any plan document into the same PR as the code.

Stated 2026-09-15, after a doc-only PR was opened for the execution-census plan when the initiative
had already been scoped.

**Why:** a separate planning PR is review overhead without delivery, and it splits one piece of work
across two merges. Compounds with the standing fewer-larger-PRs preference.

**The line to hold:** spec-before-code is still right for **new gameplay design**, where the design
itself can be wrong — it caught the power formula reading every entity as identical (all level 1)
and the faction importance signal being structurally capped at 2x. Those specs went into
`docs/mechanics/` and were reviewed before code, correctly.

It is **not** right for tooling, repairs, or work already scoped in an initiative doc. There, build
it and include the doc in the same PR.

**Deferred work rides along, it does not get its own PR.** When a plan, initiative doc, or
follow-up ticket is created that is *not* meant for immediate implementation — low-priority
follow-ups, findings recorded for later, scoping for a future batch — push it inside whichever
implementation PR is already open for the current batch. Never open a standalone PR for it, and
never force implementing it now just because it exists. Stated by the user 2026-09-15.

**Ticket-only PRs are the same anti-pattern, and deferral exceptions are the user's call.** Stated
2026-09-19 on PR #221, which carried two tickets and no implementation: *"since I want to use single
PR don't need to merge the PR creating ticket, then another PR implement them."* When the user wants
the ticketed work done, implement it in that same PR. Don't merge the tickets first and open a second
PR for the work.

This does **not** relax deferral. The user called those two tickets an explicit *exception*: "don't
violate the rule of defer minor affect tickets." A deferred minor-effect ticket still rides along
unimplemented by default (the paragraph above). Only the user turns one into same-PR implementation,
per ticket, explicitly. Don't infer an exception from a loose "implement these": on 2026-09-19 that
phrase was ambiguous about a twice-deferred ticket, and flagging it instead of assuming was right.
The user then made the exception explicit.
