This repo runs many concurrent worktrees (`git worktree list` typically shows 8+). Two traps
confirmed live on 2026-09-13, both producing confident false claims:

**1. A repo-wide grep from a worktree is only valid for that worktree's branch.** I claimed two
tickets "exist nowhere in the repository" based on a grep run from a worktree ~20 commits behind
main; both were real and open, landed in a PR my branch predated. For existence, provenance, or
"has this already been filed" questions, use `git ls-tree origin/main` (after `git fetch`), never a
local grep.

**2. Local branch refs are shared across every worktree, so a branch appears in yours regardless of
who created it.** A peer session saw `agent-process-findings` locally and claimed it as theirs; it
was mine. A branch being visible locally says nothing about authorship — check `git log --format=%an`
before claiming or acting on one.

**3. `origin/main` answers "did this land", NOT "does this exist".** Confirmed 2026-09-17: I checked
`git ls-tree origin/main` for two tickets, got nothing, and told the implementer "NEITHER IS FILED"
— they had filed both hours earlier, in a commit on a branch whose PR was still **open**. Work in an
open PR exists and has not landed; those are different questions and `origin/main` only answers the
second. This is rule 1's own fix producing the same class of false claim from the other direction.

Before claiming something does not exist, check open PR branches too — `gh pr list` then
`git ls-tree origin/<branch>`, or `git log --all --oneline -- <path>`. In a repo where a peer session
is pushing continuously, `origin/main` is behind reality by however long the current PR has been open.

**4. This repo squash-merges, so `git log origin/main..<branch>` lists EVERY commit as unmerged even
after the PR has merged.** Confirmed 2026-10-01: after PR #276 merged, that command showed 10 of my
commits as "unmerged" and I nearly concluded work was lost before cleaning up a worktree. **Verify a
merge by content, not ancestry**: `git ls-tree -r --name-only origin/main -- <paths>` for added files,
and `git show origin/main:<file> | grep <the-edit>` for modified ones. Especially important for
anything pushed *after* a peer's last merge of your branch. Cheapest correct check (2026-10-04): the
branch tip equals the PR's final head SHA (`gh api pulls/N --jq .head.sha` vs `git worktree list`), which says
nothing was added after what merged. Reproduced the same near-miss on 2026-10-04 (17, 9 and 9 "unmerged" commits
on three squash-merged branches).

**5. Never inspect or delete another session's worktree, even when asked.** Same day, a peer asked me
to remove `baseline-pre`/`baseline-post` as "your measurement worktrees" — they were not mine (mine were
under `/tmp`), and they predated my session. A peer's cleanup request can carry a misattribution, and the
user's approval of it does not transfer. The session-isolation Bash guard also refuses `git` aimed at
another worktree, which is the system enforcing this. Report sizes and let the owner act.

All of these are the same root shape: a local check that silently answers a narrower question than the
one asked. Related: [[feedback-worktree-by-default]], [[project-sidecar-cross-session-contamination]],
[[feedback_attribute_relayed_findings_to_source]],
[[feedback_verify_a_peer_finding_before_relaying_it_as_fact]].

**Why:** these produce assertions that look verified and aren't, and in one case nearly caused
well-evidenced tickets to be closed and replaced with thinner duplicates.

**How to apply:** before asserting what exists in the repo, verify against `origin/main`, not the
working tree. Before acting on a branch, check its commit author.
