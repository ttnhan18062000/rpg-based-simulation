`docs/REGISTRY.yaml` and the append-only `agent-working/agent-monitoring/**.jsonl` shards are merged by
**local-only** mechanisms — the `registry-regen` merge driver (`merge.registry-regen.driver=true` in git
config) and `merge=union` from `.gitattributes`. GitHub's server-side merge-ref computation applies
neither. CLAUDE.md documents the conflict; these are the two consequences it does **not** say:

1. **A CONFLICTING PR runs no CI at all.** `test.yml` is `on: pull_request:` with no path filter, so
   checks are due — but GitHub never creates the merge ref, so zero workflows start. "No checks
   reported" is then a *symptom of the conflict*, not a green PR and not a missing-CI bug. Confirmed on
   #328, 2026-10-04: zero runs until the branch was synced locally and pushed, then 15 jobs started.
2. **It comes back on every `main` advance.** Each merge to main re-conflicts those same files, so the
   PR flips CONFLICTING again. On a day with five PRs landing, the sync→merge window is minutes. Do
   **sync → push → merge back-to-back**; do not sync, then go do something else.

**How to diagnose it in one step** (and distinguish it from a real conflict): simulate GitHub's
driver-less merge with attributes disabled —

    git --attr-source=4b825dc642cb6eb9a060e54bf8d69288fbee4904 \
        merge-tree --write-tree --name-only origin/main <pr-head-sha>

Exit 1 + only `docs/REGISTRY.yaml` and/or `*.jsonl` shard paths ⇒ driver-only, no real conflict, fix is a
local merge. Run the same command **with** attributes to confirm it is otherwise clean, and
**positive-control the instrument** on a pair you know conflicts before trusting a clean result.

**Two probe traps hit while diagnosing this:** merge-tree against the *local* branch rather than the PR
head measures a different commit (a peer's unpushed shard commit was on top); and the REST API's
`.base.sha` always lags, so it is not evidence that GitHub's verdict is stale. See
[[feedback_a_probe_is_an_instrument_that_can_be_wrong]].

Note `gh api --method PUT .../pulls/<n>/update-branch` returns **422 "merge conflict between base and
head"** here rather than fixing it — it cannot resolve what it has no driver for. The local merge is the
only path. Branch protection is **disabled** on `main`, so nothing mechanically requires green CI; not
merging red is a discipline, not a gate.
