# M0 spike notes (draft, class-1 probes) — Claude Code 2.1.286, 2026-10-03
Method: disposable `claude -p --model haiku --setting-sources project` sessions in a scratch git repo (scratchpad/m0), project
settings with logging hooks (hooks/log.py writes raw stdin + CLAUDE*/SESSION* env). Probes run as child sessions of the
design session (env CLAUDE_CODE_CHILD_SESSION set). Raw logs: scratchpad/m0/logs/*.json(l). Positive control for every
tool-blocking probe: a run with no hook decision executes the command (side effect file), a run with `allow` also does.

## Verified
- **o/j/a/k (signals, payloads).** SessionStart payload keys: cwd, hook_event_name, session_id, session_title, source
  ("startup"), transcript_path. `--name X` appears as `session_title` in SessionStart and UserPromptSubmit but NOT in
  PreToolUse, Stop or SessionEnd payloads. UserPromptSubmit carries `prompt`, `prompt_id`, `permission_mode`, `session_title`
  (item j: usable for the headline metric). PreToolUse carries session_id, tool_name, tool_input, tool_use_id, prompt_id,
  permission_mode, transcript_path, cwd. Hook env has CLAUDE_CODE_SESSION_ID, CLAUDE_PID (harness pid), CLAUDE_PROJECT_DIR,
  CLAUDE_CODE_MESSAGING_SOCKET (inbox socket, item q), no SESSION_ROLE unless set by the launcher.
- **b.** `--agent session-probe` (tools: Read, Glob) applies the allowlist to the MAIN session: the model had no Bash and said
  so. `agent_type: "session-probe"` appears in SessionStart, UserPromptSubmit, Stop and SessionEnd payloads, and
  env CLAUDE_CODE_AGENT is set. Not yet tested: agent_type in a PreToolUse payload.
- **d.** An agent file `.claude/agents/session-probe.md` DOES appear in the Agent-tool roster of a plain session (roster seen:
  claude, Explore, general-purpose, Plan, session-probe, statusline-setup). Whether the model would spawn it is untested.
  Implication for plan 5: generated `session-*.md` files pollute the roster; needs a description or location that avoids it.
- **n (decision semantics, positive controls pass).** PreToolUse hook outcomes for a Bash tool call:
  none or `allow` -> executed; JSON `deny` -> blocked; exit code 2 (stderr) -> blocked; JSON `ask` in `-p` (no UI) -> blocked
  (not executed); unparseable stdout with exit 0 -> EXECUTED (fails open); exit code 1 -> EXECUTED (fails open).
  Implication for plan 10: a guardrail may only rely on exit 2 or a well-formed JSON deny; a crashing or malformed hook does
  not block. Deny reason reached the model verbatim.

## Round 2 (all positive-controlled where a negative claim is made; Claude Code 2.1.286)
- **e.** `PreToolUse` payload for Write has `tool_input.file_path`, for Bash `tool_input.command`; it carries `agent_type` when the
  session was started with `--agent`, and env `CLAUDE_CODE_AGENT`; it does NOT carry `session_title`. A path- or command-matching
  guardrail can therefore key on `agent_type`/env, not on the session name.
- **f/p (resume).** `claude -p --resume <id>` works from a different cwd, keeps the same `session_id`, `session_title`, and
  `source: "resume"`. Caveat (positive control: the file at the payload path does not exist): the `transcript_path` in that
  SessionStart payload points into the NEW cwd's project directory, but the harness keeps writing the original file in the
  ORIGINAL project directory (mtime advanced there). Recovery must find a transcript by `session_id` (glob
  `~/.claude/projects/*/<id>.jsonl`), not trust the hook's path after a cross-cwd resume.
- **h (fork).** `--resume <id> --fork-session` gives a NEW `session_id`, `source: "fork"`, and the SAME `session_title`; its
  transcript lands in the cwd's project directory. A fork therefore creates a duplicate name.
- **m (duplicate names).** Resume by name is scoped to the cwd's project directory (from another cwd it picked only the session
  stored there). Two sessions with the same name in one project directory: `--resume <name>` ERRORS, listing both ids with
  modification times and asking for an id; it never picks silently.
- **p (title persistence).** The title is stored in the transcript as `"customTitle":"<name>"`; it survived resume and fork.
- **q/r (liveness, kill).** A live `claude -p` (stdin held open) has `CLAUDE_PID` alive in /proc and a socket file
  `/run/user/<uid>/cc-socks/<pid>.sock`. After `kill -9`: the pid is gone, the socket FILE REMAINS (stale), no `SessionEnd` hook fired,
  the transcript is intact (29 lines unchanged), and `--resume <id>` of the killed session works and the model recalled its reply.
  Liveness must test the pid in /proc (and its cmdline), not the socket file's existence.
- **o/i (signal precedence, partial).** Session started with `--agent session-probe2` and `SESSION_ROLE=rpg-x`, resumed with
  neither: SessionStart(resume) shows `agent_type=None`, env CLAUDE_CODE_AGENT unset, SESSION_ROLE unset, title kept;
  UserPromptSubmit of the same resumed session still shows `agent_type=session-probe2`; and the tool allowlist of the agent
  STILL applies (positive control: an explicit `--agent session-probe` start had no Bash; the resumed session without the flag had no
  Bash either). So the agent persists in the transcript, but `SessionStart`'s `agent_type` and the process env are NOT reliable on
  resume; `SESSION_ROLE` is a per-process env var and is not persisted.
