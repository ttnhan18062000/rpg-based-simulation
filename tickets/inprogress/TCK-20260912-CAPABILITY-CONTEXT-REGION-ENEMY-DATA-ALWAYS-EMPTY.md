# TCK-20260912-CAPABILITY-CONTEXT-REGION-ENEMY-DATA-ALWAYS-EMPTY

## Title
`CapabilityContext.region_data`/`.enemy_data` are read at capability-estimation decision time but
populated by nothing, from any source — an always-empty decision input

## Status
BLOCKED — **still not built, re-confirmed 2026-09-13 after this batch's two blocking tickets
landed.** Chain 1 (the guild-lead-belief path) is now genuinely reachable, which changed the
question from "is there a live belief source" to "does that source actually feed either field" —
and the answer for each field is different and independently disqualifying. See Completion Summary
for the full, corrected picture: `enemy_data` has no real belief-derivable source anywhere in the
codebase (a deeper, newly-filed gap, not this ticket's own wiring problem); `region_data` has a
real derivation path but its one real consumer, `travel_regions`, has no live caller — and the one
route family that would naturally provide one, `RouteFamily.SCOUT_LOCATION`, is itself never
generated by any real code path. Declined to invent a caller placement nobody declared.

standard

bug

## Request Summary
Found during `TCK-20260911-KNOWLEDGE-FACT-STORE-NO-DECISION-TIME-READER-INVESTIGATION`'s own
search for a real, concrete consumer that `KnowledgeFact`'s `"danger_rating"` fact type looked
plausibly shaped to feed. That investigation explicitly declined to build any connection between
the two (no design-doc declaration states one should feed the other), but the underlying structural
defect it surfaced along the way stands on its own, independent of `KnowledgeFact` entirely:

`CapabilityContext` (`src/cognition/capability_estimate.py:44-45`) declares two fields explicitly
typed for exactly this shape:
```python
enemy_data: Dict[str, Any] = field(default_factory=dict)     # {enemy_id: {level, danger_rating}}
region_data: Dict[str, Any] = field(default_factory=dict)    # {region_id: {danger_rating}}
```
Both are read at real decision time (`capability_estimate.py:124` — `enemy_info =
context.enemy_data.get(enemy_id, {})`; line 154 — `region_info = context.region_data.get(region_id,
{})`) to scale a capability confidence estimate.

**Confirmed, not assumed, that nothing anywhere populates either field with real content.** Grepped
every real `CapabilityContext` construction site in `src/`:
- `src/domains/adventure/scoring.py:394` — constructs `CapabilityContext(gather_resources=...,
  resource_data=...)`, a *different* field pair (`gather_resources`/`resource_data`), never
  `region_data`/`enemy_data`.
- `src/domains/adventure/scoring.py:416` — constructs with `craft_recipes`/`recipe_data`, same
  pattern, different fields again.
- `src/engine/tactical.py:405` — `CapabilityContext.for_combat(enemy_ids=[h.kind])`.
  `for_combat()`'s own signature accepts an optional `enemy_data` parameter, but this real call
  site never passes it, so it defaults to `{}`.

No other real construction site exists. `context.enemy_data.get(enemy_id, {})` and
`context.region_data.get(region_id, {})` therefore always return `{}` in every real code path,
meaning every real capability-confidence estimate that consults enemy- or region-level danger
scaling consults an empty dict, every time, regardless of what the entity has actually encountered,
learned, or observed about that enemy or region.

## Scope

  standard practice for this whole audit arc, do not trust the citing ticket's own claim as final).

**Re-investigated 2026-09-13, same day, after `TCK-20260913-FEATURE-FLAG-DEFAULT-DOES-NOT-
PROPAGATE-TO-STATE-FEATURE-FLAGS` and `TCK-20260913-LEADSTATE-DETAIL-LOCATION-KIND-CONTRACT-
MISMATCH` both landed and `TCK-20260912-KNOWLEDGE-INVESTIGATION-LAYER-INERT-NO-FACTS-NO-LEADS`
closed `DONE` on real evidence.** Chain 1 is genuinely reachable now — but reachable is not the
same as "feeds either field," and checking that changed the answer for both fields, in opposite
directions from what was expected walking in.

**`enemy_data` — deeper problem than "blocked," not just unreached.** Grepped every real (non-test)
`BeliefEntry` construction site in the codebase — exactly 3: `belief.py:148` (rumor), `belief.py:181`
(observation, Chain 1's own producer), `phase.py:68` (`combat_risk`, Chain 2). **None of the three
captures a per-enemy-kind identifier anywhere.** Chain 1's own belief `subject` is the guild lead's
own subject (`"iron_ore"`, the one real producer), never an enemy type string. This isn't "the
connecting call was never written" — it's that no producer of this data exists at all, on either
side. Filed `TCK-20260913-NO-MECHANISM-RECORDS-PER-ENEMY-KIND-DANGER`, framed as the real gameplay
gap it is (per peer review): nothing in the simulation lets an entity learn that one kind of
creature is more dangerous than another, which is why every capability estimate falls back to the
same hardcoded `_ENEMY_DANGER` table regardless of what that entity has actually fought.
`KnowledgeFact`'s own `"danger_rating"` shape would fit exactly (real candidate, not a redesign),
cross-referenced there — but it's independently confirmed at zero real writes, so not reachable
either without that separate gap resolving first.

**`region_data` — more tractable than expected, but still blocked, for a corrected reason.** A
Chain-1 belief's `claim` carries real coordinates, and `LegalityServiceV2.get_region_for_position()`
(`src/engine/legality.py:44`) is real, existing, widely-used machinery that resolves coordinates to
a real `region_id` — a genuine derivation path exists. Applied the declared-intent test before
building a caller for `travel_regions` (still zero real construction sites, re-confirmed): **does
an existing route family or decision point already have "going somewhere" as its whole point?**
`RouteFamily.SCOUT_LOCATION` (`src/domains/adventure/schema.py:27`) is exactly that shape, and
`mapper.py:41` maps it to `ObjectiveKind.REACH_LOCATION` — but grepping every real construction site
of `AdventureRouteOption` (`generator.py`, `service.py`) confirms `SCOUT_LOCATION` is **never
actually generated by any real code path** — it exists only in mapping/scoring/impact-tracking
tables, the same "declared but unbuilt" shape this whole arc keeps finding elsewhere. The one place
that would provide a natural, already-declared caller for `travel_regions` is itself dead. Building
a caller into `SCOUT_LOCATION` would wire two never-reached mechanisms together and call it done;
building one into `GATHER_RESOURCE`/`CRAFT_UPGRADE` (the two real route families that do consult
`CapabilityEstimateService` today) or `DetourSuggestionSystem` would invent a placement nobody
declared. Declined both, per explicit instruction: a populated, tested, unread field is precisely
the shape this ticket exists to eliminate, and a plausible-looking placement would be worse than
none — it would look wired and encode a gameplay decision nobody made.

**Disposition: stays `BLOCKED`, on two independently-confirmed, corrected chains.** Neither field
gets wired. `enemy_data`'s own gap is filed as a real, standalone gameplay finding. `region_data`'s
own gap is the same `travel_regions`-has-no-caller finding as before, now with the added evidence
that the one route family that would supply one doesn't exist in practice either.
