# TCK-20260520-SIM-OBS-M37

## Title

Live Anomaly Worker Service

## Status

DONE

## Request Summary

Turn the Phase 6 external anomaly worker into a standalone live worker service that consumes events from a stream backend (e.g. Redis Stream or in-process queue), manages a rolling in-memory tick window, executes lightweight live anomaly detection rules, publishes detected anomaly notifications, and updates live status files.

## Scope

- Implement a comprehensive `LiveAnomalyWorker` that supports running either asynchronously or via a standard poll-based loop.
- Support consuming events from `RedisStreamConsumer` or `LiveEventPublisher` depending on the configured `stream_backend`.
- Implement a rolling event tick window tracking system (`RollingEventWindow`) to store only the last `window_ticks` ticks of events, ensuring bounded memory footprint.
- Implement 5 lightweight live anomaly rules:
  1. `HardLawViolationLive`: Checks for `InvariantViolation` events.
  2. `NavigationStuckLive`: Checks if an active entity's position is frozen over a window of ticks.
  3. `EventDropRateHigh`: Checks if there is a high rate of dropped events.
  4. `GovernorDegradedLive`: Checks if the governor is in a degraded or survival mode.
  5. `CriticalEventObserved`: Checks if any CRITICAL severity event is observed.
- Integrate an alert/anomaly deduplication mechanism inside the live worker to prevent flooding duplicate anomalies continuously.
- Support publishing detected anomalies to:
  1. Local JSONL file (e.g. `anomaly_events.jsonl` under the worker's run directory).
  2. Live anomaly counters/Prometheus metrics.
  3. Optional Redis channel / stream if configured.
- Write/update a live status JSON (`data/runs/workers/{worker_id}.json`) tracking heartbeat, health, stream lag, memory estimate, processed events count, and emitted anomaly count.

## Out of Scope

- Modifying the core authoritative execution loop or mutating the simulation's state from the anomaly worker (strict boundary separation).
- Building the full visualization web dashboard interface (covered in subsequent milestones).

## Acceptance Criteria

- The `LiveAnomalyWorker` correctly validates config schemas and boots up successfully.
- It consumes events from the stream backend, processes them, and acknowledges them successfully.
- It maintains a rolling window of events by tick, evicting expired events, keeping memory bounded.
- The 5 target live rules execute correctly and detect anomalies under simulated test scenarios.
- Deduplication prevents repetitive duplicate anomaly spamming.
- The worker updates its status JSON file regularly with correct health and performance properties.
- Full unit and integration test suite verifies the functionality, achieving high test coverage.

- Supported both thread-safe `in_process` callback queue polling and out-of-process Redis Streams reading.
- Integrated `psutil` inside health auditing checks to ensure RSS does not exceed configured limits.
