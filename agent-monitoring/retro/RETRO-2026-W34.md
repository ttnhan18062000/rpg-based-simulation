## Notes

Deep-dive requested by the user specifically to answer: does the agent-working pipeline itself
need fixing, based on this week's real, heavy usage (39 runs, hand-orchestrated end-to-end since
the Workflow tool was unavailable all session).

### 1. What failed most — and it's mostly a good sign, not a problem

Only 2 real gate failures this week, both `BLOCKED` (not `FAILED`), and both are the pipeline
working exactly as designed:
- `TCK-20260817-STANDARD-SIMQ-NARRATIVE-EVENT-EMISSION-REGRESSION-FRONTIER` — a sub-agent was
  explicitly told a "missing merge()" hypothesis was the likely root cause, independently
  investigated it, found the hypothesis was **wrong**, and refused to fabricate a source fix for
  a bug that didn't exist. Reported BLOCKED with full evidence instead.
- `TCK-20260818-STANDARD-QUEUEDRAINWORKER-CI-THREAD-LEAK-BISECTION` — a sub-agent could not
  reproduce a real CI-observed thread leak locally after exhaustive attempts, and correctly
  refused to fabricate a fix for a defect with no local repro, per CLAUDE.md's Hard Rule against
  editing artifacts to make gates pass. Reported BLOCKED with disclosed open hypotheses instead.

`done-checker` shows a 30% "failed" rate (3/10 calls) — this reads as the gate catching real,
minor issues before they shipped (e.g. one run's done-checker flagged a test-count inaccuracy in
a ticket's own Test Summary, 14 vs actual 12, corrected before commit) rather than a broken gate.
Worth periodically re-checking if this rate climbs, but not actionable now.

### 2. What was slow — a real, now-fixed pipeline gap

The single most concrete, actionable finding this week: **3 independent `general-purpose`
sub-agent dispatches spawned their own `run_in_background` commands and then stopped their turn
to "wait for a notification"** — but a dispatched sub-agent has no mechanism to receive that
notification the way the top-level orchestrator does, so each one silently stalled and required
a manual `SendMessage` resumption (one needed two resumptions). This cost real wall-clock time
across the week's slowest runs (`TCK-20260818-STANDARD-LONGRUN-DETERMINISM-WATCHDOG-AUDITMODE` at
90 min, `TCK-20260817-STANDARD-SIMQ-NARRATIVE-EVENT-EMISSION-REGRESSION-FRONTIER` at 70 min BLOCKED).

Root cause: this exact lesson was already learned and encoded — but only in 2 of 15 project agent
definitions (`implementer.md`, `test-scoper.md`). The other 13, plus the built-in `general-purpose`
type (which has no project-level file to carry the warning at all), had no such guidance. **Fixed
this session**: added the same warning as a new Hard Rule in `CLAUDE.md` itself, since that's the
one place loaded into every agent's context regardless of role or whether a project file exists
for it.

Caveat on duration numbers generally: since the Workflow tool was unavailable all session, every
ticket this week was hand-orchestrated with manually-written monitoring records (approximate
start/end timestamps, not automation-measured). Two hotfix runs show an identical, suspiciously
round `900s` duration (3.5x the hotfix median) — almost certainly a `-15 minutes` timestamp
approximation artifact from hand-orchestration, not a real duration signal. Treat this week's
timing data as directionally useful, not precise.

  confirmation bias, vs. one continuously-context-accumulating session investigating its own

  — flagging for whoever has visibility into it, not a ticket this repo can self-resolve.
- The `Parity` phase shows 18/19 calls "skipped" — likely mostly benign (most of this week's
  tickets were test recalibrations with no mechanics/formula changes, correctly not needing a

  even when parity was considered inline. Not clearly actionable without automation-measured data
  to compare against; worth re-checking once the Workflow tool is available again.

### 4. What worked — confirmed patterns to keep

- **Gate integrity held under real pressure, twice, this week** — both BLOCKED outcomes above
  happened on genuinely hard problems (a plausible-sounding but wrong root-cause hypothesis; a
  real CI-only leak with no local repro) where fabricating a fix would have been easy to
  rationalize. Neither agent took the shortcut. This is the pipeline's most important property
  working exactly as intended — keep reinforcing it, don't weaken it for convenience.
- **Real-evidence-only recalibration discipline held across ~10 SimQ anchor/tolerance tickets**
  this week (grep for "recalibrat" in this week's `working_log.csv` entries) — every changed
  anchor value traces to a specific measured trial or a same-commit fixture, never a guessed
  number to make a test pass. Same standard should apply to any future calibration work.
- **Parallel investigation-agent batching was effective once the stalling issue was worked
  around** — dispatching 3-5 agents in parallel to investigate independent hypotheses (e.g. the
  original 10-test slow-suite triage, and this week's determinism/perf/thread-leak triage)
  produced real, differentiated findings faster than sequential investigation would have, and each
  agent correctly stayed in its own file/topic lane per its dispatch instructions — no observed
  cross-agent file collisions in a shared working tree this week, despite heavy concurrent use.
- **Isolated `git worktree` bisection was used correctly and repeatedly** this week to get real
  causal evidence (ruling the spawn-collision fix in or out as a cause) instead of guessing —
  including recovering cleanly from an early mistake (bisecting against the wrong commit hash
  because this repo's branch history is squash-merged from a more granular source) by re-deriving
  the correct ancestor rather than reporting a false conclusion.
