## Notes

### 1. What failed most?

`done-checker`/Verify dominates gate friction: 92 calls, only 67 clean `ok` (73%), 19 `failed` +
6 `blocked`. `dod_condition_failed` is the single largest reason code this week (12 occurrences),
well ahead of `plan_needs_changes` (3) and `conflicts_detected` (2).

Drilled into the raw events (not just the aggregate table) for two specific patterns flagged for
this retro:

- **Empty `staging_artifacts/` leftover on hotfix tickets — 2/2 occurrences this week, both from
  this session's own two hotfix tickets** (`TCK-20260823-LIVE-TEST-API-KEY-AUTH`,
  `TCK-20260823-HOTFIX-PRESCAN-DRAFT-TEST-SHALLOW-CLONE-FALSE-POSITIVE`). Root cause is a
  self-inflicted Scope→Verify contradiction: the Scope phase's own instructions ("Create the
  staging directory... hotfix tier doesn't require artifacts inside it, but create the dir for
  consistency") unconditionally create `staging_artifacts/{tid}/` even for hotfix tickets that
  will never populate it, and `done-checker`'s repo-state-consistency condition then correctly
  flags that same empty directory as a leftover. Both instances cost a full extra Verify
  round-trip (BLOCKED → `rmdir` → re-verify) to fix. This is 100% reproducible on every hotfix
  ticket as currently scripted, not incidental.
- **`CONFLICTS_DETECTED` — 2/2 occurrences this week, both from this session's own two hotfix
  tickets, same two runs.** In both cases the ticket-scoper's `conflicts` array held genuinely
  non-blocking disclosure ("a related prior ticket exists but this isn't duplicate work," "the
  ticket that caused this bug already references the same file") rather than a real scope
  conflict — but the workflow gate treats any non-empty `conflicts` array as an unconditional hard
  stop, forcing a full Scope-resume round-trip (separate `CONFLICTS_DETECTED` monitoring write,
  new sidecar/seq, second `ticket-scoper` dispatch) for something that was never actually
  blocking. Also 100% reproducible whenever a scoping agent correctly surfaces related-but-not-
  duplicate context in good faith.

Also worth surfacing even though it predates this week's runs: `Review`/architecture-reviewer sits
at only 58% clean `ok` (36/62, with 13 `failed` + 7 `blocked`) — the second-heaviest gate after
Verify.

### 2. What was slow?

Avg duration (46 min/run) is high, pulled up by a long tail: 4 runs over 4 hours
(`TCK-20260817-DOC-CONCURRENCY-LIMIT-RATIONALE` 470 min, `TCK-20260819-STANDARD-PARITY-LEDGER-
HYGIENE-SWEEP` 434 min, `TCK-20260817-RUNTIMEMODE-BENCH-SCOPING` 314 min, `TCK-20260817-STATE-
DESIGN-PRIORITY-ORDER` 264 min) — all 3x+ their tier's own median duration per the Outliers table,
not just slow in absolute terms. Not diagnosed further here (out of scope for this retro pass),
but worth a dedicated look given the size of the gap from the rest of the distribution. By
cost-proxy-score, `Implement`/`implementer` is overwhelmingly the most expensive phase/agent
combination — it dominates the outliers table by a wide margin, which is expected (it's where the
actual work happens) but confirms `Implement` is the right place to focus any future per-phase
budget tuning.

### 3. What to change?

1. **Fix the Scope/Verify staging-dir contradiction for hotfix tier** — either stop creating
   `staging_artifacts/{tid}/` in Scope when tier is hotfix, or have `done-checker`'s repo-state
   check explicitly tolerate an empty staging dir on hotfix tier. Pick one, not both, to avoid
   the same fight recurring from the other direction.
2. **Split ticket-scoper's `conflicts` field semantics** — reserve it for genuine blocking
   duplicate/contradictory work; route informational disclosure ("related ticket exists, not a
   duplicate") into `summary` or a new non-gating field instead, so good-faith disclosure doesn't
   force an unnecessary Scope-resume round-trip.
3. **KGMCP cache coverage is very low: 1.4%** (6 cache events against 422 real `search_docs`/
   `graphify` calls this period) — the overwhelming majority of retrieval work bypasses the cache
   path entirely, which makes the 33% reuse-rate figure on the few events that do reach it a
   near-meaningless signal on its own. Worth a follow-up investigation into why cache writes are
   so rare relative to real search volume, separate from the reuse-rate number itself.
4. **Search-before-grep compliance sits at 72.4%** (21/29 Investigate-phase calls) — below what
   the Hard Rule expects. Worth a closer per-run audit of the 8 non-compliant calls to distinguish
   genuine rule violations from an attribution/measurement artifact before deciding whether this
   needs a prompt fix or just better instrumentation.

### 4. What worked?

- Static-script-backed gate checks (`run_static_precheck`, `doc_staleness_check`,
  `clean_data_runs_early`, etc.) continue to catch real, fixable gaps before ticket close rather
  than after — both of this week's `staging_artifacts` `BLOCKED` verdicts were caught and fixed
  within the same session, never shipped stale.
- `Document-Update` has a 100% clean `ok` rate this week (48/48 calls) — the `doc-updater` agent's
  judgment calls (including correctly declining out-of-scope doc edits, and correctly finding and
  fixing genuine staleness in adjacent docs) are holding up well and not producing gate friction.
- `Implement` and `Test` phases are both clean this week (94/94 and 83/83 respectively excluding
  the one skipped Test call) — the failure surface is concentrated in `Review`/`Verify`, not in
  the phases that write and validate code.
