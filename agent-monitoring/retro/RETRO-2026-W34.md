## Notes

Scope of this period: 29 runs, almost entirely a single hand-orchestrated `implement-ticket`
batch (the Workflow tool was unavailable) fixing a real CI investigation — 2 originally-failing
GitHub Actions jobs (Integration, API/tools/logging) traced to 26+ distinct root causes across 17
tickets, plus 4 more follow-up tickets closed same-day. Retro focuses on how that hand-orchestrated
pipeline actually behaved at this volume, not on individual code changes.

**1. What failed most?** `done-checker` (Verify phase, 7 ok / 3 failed) and `architecture-reviewer`
(Review phase, 2 ok / 1 failed) are the only agents with any failures this period — but both trace
to exactly 2 understood, one-off incidents, not a systemic gate problem:
- The 3 `done-checker` failures were one blast radius: a dispatched Verify subagent ran an
  unscoped `git stash` mid-verification, sweeping 3 concurrent sibling tickets' uncommitted work
  off the shared working tree at once. Fully recovered (stash popped, monitoring logs
  reconciled via common-baseline-plus-tail concatenation, all files independently re-confirmed) —
  no data loss, but the mitigation (explicit "no unscoped destructive git" instructions in every
  subsequent subagent dispatch prompt) should become a standing default for any future
  concurrent-Verify dispatch, not something re-derived from scratch next time.
- The 1 `architecture-reviewer` failure was the gate working exactly as designed: it caught that a
  bare `@pytest.mark.slow` marker addition wouldn't actually satisfy its own ticket's acceptance
  criteria (`--resource-budget large` raises timeout/memory ceilings, not compute speed — both CI
  lanes run identical hardware), forcing a real threshold fix before the plan was approved on a
  2nd pass. This is a genuine "gate caught a bug before it shipped" data point, not friction to
  remove.

**2. What was slow?** Only 1 run exceeded the 30-min slow-run threshold
(`STANDARD-HUNGER-STARVED-BY-RESOLVE-BLOCKER-FLAT-UTILITY`, 35 min) — legitimately deep work (a
real strategic-cognition blocker-lifecycle design fix, not padding). More interesting: 2
**hotfix-tier** runs are 4-5x their tier's own duration median
(`CI-FAST-LANE-EXTRA-SLOW-FILTER-INCONSISTENCY` 900s, `WEBSOCKET-API-TESTS-ASYNCIO-MARKER-AND-HEARTBEAT-DRAIN`
720s, vs. a 180s hotfix median). Both had genuinely tiny diffs (a few lines) but needed real
cross-environment verification work beyond a typical hotfix's scope — dev-server/production-build
checks for the echarts fix, `--collect-only` comparisons across 7 CI jobs for the filter fix. The
diff size stayed hotfix-appropriate; the *verification* cost didn't. Worth watching for: if a
"hotfix" investigation turns out to need this much cross-environment re-verification regularly,
that's a signal the tier-routing heuristic (diff size) is missing a real cost driver (verification
breadth), not that these two runs were mis-scoped.

**3. What to change?** One concrete action: when a Verify/done-checker subagent's own methodology
requires any git working-tree inspection, its dispatch prompt should default to forbidding
unscoped `git stash`/`git reset --hard`/`git checkout .`/`git clean` and steering it toward
`git show <commit>:<path>` (read-only) — proven this period as the actual fix, not a one-off
workaround. Consider adding this as a standing line in the `done-checker`/`architecture-reviewer`
agent definitions themselves (`.claude/agents/`) rather than re-adding it to every dispatch prompt
by hand next time this pattern recurs.

**4. What worked?** 100% DONE rate across 29 runs, 0 empty/truncated/legacy-format summaries, and
every real gate failure traced to a fully-understood, fully-recovered cause — this is a clean
bookkeeping trail for a genuinely large, hand-orchestrated batch (Workflow tool unavailable the
whole period). Two patterns worth keeping: (a) re-verifying a ticket's Investigate findings against
the *actual downloaded CI log* rather than trusting a summarized description caught real gaps a
generic re-read would have missed (e.g. the `agents.md`/`authoritative_pipeline.md` phase-count
ticket, where the "obvious" fix — bump 32→31 — would have shipped a doc that was *already* wrong at
31, only surfaced by counting real `run_phase()` call sites in source); (b) running a fix's exact
CI-job invocation locally (not just the specific files touched) before closing a ticket caught
2 additional real bugs (`test_ws_protocol.py`'s stale `@pytest.mark.asyncio` marker,
`test_observability_websocket.py`'s event-flood-vulnerable heartbeat read) that a scoped-diff-only
verification would have missed entirely — worth keeping as a standing Test-phase habit for
CI-investigation-shaped tickets specifically, not just this one.
