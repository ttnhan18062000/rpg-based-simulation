## Notes

**1. What failed most?** `DOD_BLOCKED` via `dod_condition_failed` (8 events, all 3 gate failures this week). `done-checker` has the worst first-pass rate of any agent this week: 28 calls, 8 failed (28.6%). Directly observed the root cause in this week's `context-retrieval-phase3` epic batch: 3 of its 4 child tickets (`DETERMINISTIC-CODE-INDEX`, `HYBRID-RETRIEVAL-FUSION`, `RETRIEVAL-CACHE-LEVELS`) were blocked at Verify for the *identical* reason — the Implement phase filled in `## Completion Summary`/`## Test Summary`/`## Files Changed` but left the ticket's `## Status` body field at `OPEN`, tripping done-checker's ticket-metadata-consistency condition every time. The 4th ticket avoided this only because the orchestrator pre-emptively edited `## Status` before running Verify, once the pattern was clear.

**2. What was slow?** This week's slowest run was `FOLDER-tickets-todos-context-retrieval-phase3` at 231 min (today's epic batch) — the slowest of the week by a wide margin. `Implement` has the highest per-call spend-proxy average of any phase (100.3, next highest is `Test` at 53.5), consistent with this batch: several Implement calls built genuinely new modules from scratch (`tools/hybrid_retrieval.py`, `tools/retrieval_cache.py`, `tools/context_packet_assembler.py`) with 15–65 new tests each. Separately, `TCK-20260728-MONITORING-PAUSE-RESUME-SEQ-COLLISION`'s Test-phase call is an 18.9x cost-proxy outlier (531.985 vs. phase median 28.2) — worth a one-off look, but isolated to that run, not a pattern.

**3. What to change?** Move the `## Status → INPROGRESS` update out of implicit implementer-prompt-text and into an explicit, deterministic step. Two options: (a) add an explicit line to the Implement-phase prompt in `implement-ticket.js` telling the implementer agent to set `## Status` to `INPROGRESS` in the same pass where it fills in Completion Summary/Test Summary/Files Changed, or (b) have the orchestrator set it deterministically via `bash`/`Edit` right after the Implement phase returns — mirroring how doc-staleness and other checks were already moved from agent-prompt-text into orchestrator-run steps for reliability (see `implement-ticket.js`'s own comments on that pattern). Option (b) is more reliable since it removes a 3rd LLM-compliance dependency from a condition that failed 75% of the time this batch (3/4 tickets) it would otherwise have applied to. Worth its own ticket rather than an inline tweak, since it touches a shared orchestration file.

**4. What worked?** The two-pass Review + Architecture-Verify design caught a real, non-cosmetic issue this week: `RETRIEVAL-CACHE-LEVELS`'s pre-Implement plan was correctly sent back `NEEDS_CHANGES` for missing a lifecycle/prune mechanism on its new SQLite cache tables (an actual unbounded-durable-store risk, not a false positive) — confirms the gate is doing real work, not just adding latency. Parity's skip-eligibility optimization is also earning its keep: 12 of 22 `parity-updater` calls were skipped this week (no `src/` change + `behavior_changed=false`), avoiding a full agent call in over half of eligible cases without weakening the P0 safeguard scan that still runs in that branch.
