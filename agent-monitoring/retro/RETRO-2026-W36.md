**2. Root cause for both is the same deliberate choice, not waste: this ticket removed a field from a live dataclass, so Test ran a much broader cross-cutting regression sweep (3010 tests) than an additive-field ticket needs, and Verify then independently re-ran/re-triaged all 3 resulting failures via git-stash comparisons rather than trusting the Test phase's own triage. Worth the cost here (a deletion has a wider blast radius than an addition) — not a pattern to trim.

**3. What to change?** Parity Ledger Write-Safety shows 5/5 `parity_index.py build` calls this period logged as "unsafe" (not co-occurring in the same run with the YAML edit) — this is a detector artifact of this session's own convention, not a real safety gap: every parity-updater agent in this batch was explicitly instructed to run the index build "as a separate visible Bash call" after the YAML edit, for auditability. If this pattern continues into future batches, the detector's co-occurrence window may need widening, or the instruction should be adjusted — flagging for whoever next tunes this gate check, not acting on it now.

**4. What worked?** The "independently re-verify triage claims before trusting them" pattern (git-stash comparisons for pre-existing-failure claims, full-repo greps for orphaned-reference claims, re-running cited tests directly rather than trusting a phase's self-report) caught a real regression once and confirmed 3 separate non-blocking triage claims correctly across this period — keep this as standard practice for the remaining 10 tickets in the batch, not just when something looks suspicious.
