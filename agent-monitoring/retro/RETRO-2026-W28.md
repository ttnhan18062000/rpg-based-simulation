## Notes

**1. What failed most?**

`done-checker` (16 failed / 43 calls, 37%) — but this is not a broken gate, it's the gate
*working*. All 16 failures carry `reason_code: dod_condition_failed` (matches the Reason Codes
table exactly, 16/16), meaning every failure was a genuine, correctly-caught DoD violation, not a
schema/parsing bug. Direct evidence from this week's own session: `TCK-20260709-REGISTRY-REGEN-ON-CLOSE`
was correctly `DOD_BLOCKED` when the ticket's Implementation Notes claimed the parity ledger was
"left unedited" but a new `INFRA-263` entry had actually been added by a later Parity-phase run —
Verify caught the doc/reality mismatch, it was fixed, and re-Verify passed clean. `architecture-reviewer`
had the second-highest raw failure count (7/65) but 0 in this session's own 6 tickets — likely
concentrated in other work earlier in the week, not something this retro can attribute further
without a deeper `query.py` pull.

**2. What was slow?**

Unmeasurable as reported — **"Avg duration: 0 min" and an empty "Slow Runs" section are both
artifacts of a real data gap, not evidence that runs are fast.** `docs/agent-monitoring/schema.md`
marks `duration_s` as a *required* run-record field (line 43: "Wall-clock seconds from start to
end... `null` for crashed runs"), but `tools/agent-monitoring/record_run.py`'s `REQUIRED` set
(`run_id, start_ts, workflow, tier, final_status`) never includes it, never computes it from
`start_ts`/`end_ts`, and no caller — not `implement-ticket.js`, not `implement-epic.js`, not
`create-tickets.js`, not the manual `record_run.py --data` calls made directly this session —
ever passes it. Spot-checking this session's own runs.jsonl entries against their actual
`start_ts`/`end_ts`: `TCK-20260709-REGISTRY-REGEN-ON-CLOSE` ran ~3h9m (04:00:19Z→07:09:54Z,
inflated by a mid-run human-facing Q&A gap, not pure compute), and a tight hotfix like
`TCK-20260709-DOCSITE-TICKETS-FRONTMATTER-BACKFILL` still ran ~11 min (03:29:14Z→03:40:10Z) — a
real, non-trivial duration that the report currently has no way to see or flag as slow.

**3. What to change?**

Fix `duration_s` at the source, not per-caller: add a `duration_s = end_ts_seconds - start_ts_epoch`
computation directly inside `record_run.py`'s `main()` (derived from the record's own `start_ts` and
either a `end_ts` field already in `--data` or the current time if absent), rather than relying on
every JS workflow's `writeMonitoring()` block to remember to compute and pass it. This is a small,
single-file fix that would make "Avg duration" and "Slow Runs" meaningful for every future retro
without touching any workflow call site. Candidate for a `TCK-*-AGENT-MONITORING-DURATION` hotfix
ticket.
