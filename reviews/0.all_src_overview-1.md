Here is the blunt review, top to bottom.

Your codebase has real strengths: there is an actual engine shape, a recognizable simulation loop, explicit actions, a goal-based AI layer, and a push toward deterministic execution. This is not amateur spaghetti. But the implementation keeps sabotaging its own architecture with backward-compatibility shims, cross-layer leakage, and feature accretion without hard boundaries. The result is a system that looks modular on paper and behaves like a tightly coupled monolith in practice.

## 1. Top-level layout and project direction

The overall folder structure is decent. You have separations for `actions`, `ai`, `core`, `engine`, `systems`, `api`, and `utils`, which is exactly what a simulation backend should aim for. The problem is that this separation is cosmetic more often than real. Data and logic leak across those boundaries constantly, especially between `core.entities`, `core.aspects`, `actions`, and `ai`.

The biggest strategic issue is this: you are trying to support too many architectural styles at once.

You have:

- aspect-oriented entities
- legacy stats compatibility
- proxy-based effective stats
- deterministic simulation claims
- RabbitMQ distributed AI workers
- API serialization directly from domain objects
- system-manager orchestration
- action handlers that also contain gameplay and narrative side effects

That is not one architecture. That is several partially merged architectures. The cost is that no single boundary is trustworthy anymore.

## 2. Entry point and bootstrap

`src.__main__` is readable enough and the CLI/server split is practical. It makes local experimentation easy. But `_run_cli()` is doing far too much orchestration inline: world setup, town painting, sanctuary painting, camp generation, hero creation, building registration, mob spawning, worker creation, resolver creation, recorder creation, and loop startup all live there. That is bootstrap bloat.

The immediate consequence is not style ugliness. It is testability loss. You cannot easily:

- construct a world fixture
- test one scenario without replaying all bootstrap logic
- evolve initialization rules without breaking startup

### Fix

Create explicit bootstrap services:

- `WorldBootstrapper`
- `TownBuilder`
- `InitialPopulationBuilder`
- `SimulationFactory`

Then `_run_cli()` should assemble those components, not perform the whole setup itself.

## 3. Configuration

`SimulationConfig` is one of the cleaner pieces. It centralizes defaults, includes AI thresholds, subsystem rates, worker timeout, and world settings. That is good.

But there are two problems.

First, config is becoming a dumping ground for both:

- game design constants
- operational/infrastructure tuning

Those should not be mixed indefinitely. `worker_timeout_seconds` and `chaos_drop_rate` do not belong in the same conceptual bucket as `town_aura_damage` and `hero_heal_per_tick`.

Second, your formulas and rules are not consistently anchored to config. Some gameplay numbers live in config, some are hardcoded in actions and AI.

Examples:

- flee thresholds are partly config-driven and partly modified in scorers
- combat damage uses config variance but many reward and mood effects are hardcoded in `CombatAction.apply`
- repair cost and effect are hardcoded in `RepairAction`

### Fix

Split config into:

- `EngineConfig`
- `WorldConfig`
- `CombatConfig`
- `AIConfig`
- `EconomyConfig`

Then stop hardcoding design constants inside action handlers.

## 4. Core entity model

This is one of your worst layers.

Your `Entity` is presented as an aspect-oriented container with an `aspects: dict[str, Any]`, but then it re-exports a huge amount of state via property shims, performs backward-compatibility mapping in `model_post_init`, handles serialization to API schemas, exposes a `StatsProxy`, and implements custom copy behavior.

That means `Entity` is simultaneously:

- domain model
- compatibility adapter
- lifecycle coordinator
- API mapper
- snapshot copy helper

That is a boundary failure.

The worst design choice is the string-keyed aspect registry:
`aspects: dict[str, Any]`

This destroys structural clarity. A typo becomes runtime behavior. Missing core aspects become hidden failures. The design claims composition but actually depends on magic string lookups everywhere.

### What is wrong logically

You say you moved away from a god object, but then re-expose everything through `entity.pos`, `entity.faction`, `entity.attributes`, `entity.quests`, `entity.home_storage`, `entity.stats`, and many more. So the object is still a god object, just via delegation.

### Fix

Replace the registry with explicit fields:

- `identity: IdentityAspect`
- `spatial: SpatialAspect`
- `combat: CombatAspect`
- `progression: ProgressionAspect`
- `mind: MindAspect`
- `inventory: InventoryAspect | None`

Then remove most property shims. Force code to say `entity.combat.hp` instead of pretending the structure does not exist.

## 5. Aspect model

Your aspect idea is valid in principle. The implementation is not.

`CombatAspect` contains combat stats, but also vision, loot bonus, trade bonus, interaction speed, rest efficiency, and cooldown reduction. Then it proxies progression state like `level`, `xp`, `gold`, `stamina`, and even mind state like `chase_ticks` and `engaged_ticks`.

That means `CombatAspect` is not a combat aspect. It is a stats warehouse with cross-system tentacles.

`MindAspect` has the same disease. It mixes:

- FSM state
- goals
- threat table
- memory
- terrain memory
- entity memory
- narrative memory
- emotional state
- grudges
- region fatigue
- action style
- boredom multipliers
- cooldowns
- diagnostics

That is not a single responsibility. That is a whole AI subsystem crushed into one object.

### Fix

Split `MindAspect` into nested typed models:

- `DecisionState`
- `PerceptionMemory`
- `EmotionState`
- `NavigationCache`
- `NarrativeMemory`

And stop using `Any`, `list[dict]`, and raw `dict[str, Any]` for behavior-critical data. Those are not temporary shortcuts anymore. They are architecture rot.

## 6. Stats and proxy model

The old `Stats` dataclass is simple and coherent. The new `StatsProxy` exists mainly to preserve legacy access while reading from aspects. That is a transition mechanism, not a stable architecture.

Right now you effectively have:

- raw aspect data
- old `Stats`
- `StatsProxy`
- convenience shims on `Entity`
- compatibility shims on `CombatAspect`

That is too many representations of the same truth.

### Consequence

When bugs happen, you will waste time answering:

- Is this the base stat?
- effective stat?
- proxied stat?
- post-effect stat?
- compat shim value?

### Fix

Pick one model:

- aspects hold authoritative raw state
- a separate pure calculator computes effective state
- old `Stats` becomes a migration-only artifact and then dies

Do not keep four access paths alive.

## 7. World state

`WorldState` is structurally reasonable. It owns the authoritative mutable state: entities, grid, spatial index, ground items, buildings, regions, corpse nodes, resource nodes, aggression, war state, and world progression counters. That is appropriate for a simulation core.

Still, there are issues.

First, it is growing into another god object. It already contains:

- spatial data
- economy state
- combat aftermath state
- faction war state
- calamity history
- event bus handle

Second, many subsystems mutate it directly from many locations, which weakens invariants.

### Fix

Keep `WorldState` authoritative, but narrow the mutation surface:

- add domain methods for specific transitions
- stop letting every action/system mutate internal collections casually
- introduce small manager services for buildings, corpse nodes, region control, and ground items

## 8. Engine and determinism

This is your highest-risk area.

The code describes `WorldLoop` as authoritative, tick-based, and four-phase. That is the correct shape. The `ConflictResolver` then sorts proposals deterministically and applies them sequentially. That is also directionally correct.

But your determinism claim is weakened by the distributed worker model.

`WorkerPool` sends pickled snapshots over RabbitMQ, publishes a batch task, and then synchronously waits for a result batch with a timeout. If timeout hits, results are partial or absent, and stale messages are skipped by tick. That means the engine behavior depends on infrastructure timing, not just seed and world state.

That is not fully deterministic simulation. It is “best-effort deterministic unless message timing interferes.”

You even have chaos mode that deliberately drops AI results, which is fine for resilience testing, but it proves the architecture is already modeling result loss as a normal execution branch.

### Hard truth

If you care about reproducibility, distributed AI workers must be optional infrastructure around a proven local deterministic core, not part of the definition of normal execution.

### Fix

Make local deterministic inline execution the reference engine.
Treat RabbitMQ mode as experimental or deployment optimization, with explicit loss of strict replay guarantees unless all results are collected.

## 9. Conflict resolution

`ConflictResolver` is cleanly scoped compared with other modules. That is a positive. It sorts, validates, tracks occupied positions, and applies actions.

But there are still design problems.

The sort key uses `(p.verb.value, next_act_at, p.actor_id)`. That means verb enum order affects initiative. Unless that enum ordering is explicitly designed as combat policy, this is an implicit gameplay rule hidden in implementation detail.

Also, some verbs are “validated and applied later in WorldLoop,” which splits action semantics between resolver and loop. That is another boundary leak.

### Fix

Define an explicit action priority table in one place.
Either the resolver owns action application policy or the world loop does. Not both.

## 10. Actions layer

This layer has the right outer shape: proposals are the currency, handlers validate and apply. `ActionProposal` as a frozen dataclass is solid.

But the implementation quality varies a lot.

`MoveAction` is fairly contained. `RestAction` is still okay. `RepairAction` is simple but hardcoded. Then `CombatAction` becomes an uncontrolled god-method.

`CombatAction.apply` currently handles:

- building sabotage
- evasion
- damage type resolution
- damage calculation
- elemental scaling
- crit
- event emission
- mood changes
- grudge accumulation
- memory log entries
- threat generation
- stamina costs
- attribute training
- veterancy progression
- near-death bonuses
- XP rewards
- region death statistics
- corpse creation
- loot transfer
- evolution hooks
- quest completion
- title rewards

That is absurd concentration of responsibility.

### Consequence

Combat is now the hidden integration center for half your simulation. Any change to combat risks breaking progression, AI, economy, history, and lifecycle.

### Fix

Split `CombatAction.apply` into services:

- `DamageResolutionService`
- `CombatAftermathService`
- `ThreatService`
- `KillRewardService`
- `DeathConsequencesService`
- `QuestCombatHook`
- `NarrativeCombatHook`

The action handler should orchestrate, not own every consequence.

## 11. Damage model

The strategy pattern in `actions.damage` is one of the cleaner decisions. `DamageCalculator` with physical/magical implementations is extensible and understandable.

But even here the system is not fully honest. Effective damage is still partially defined in calculators and partially in `CombatAction.apply`. So the strategy pattern only solves input extraction, not complete damage resolution.

### Fix

Make one pipeline object own damage resolution end-to-end. Calculators can provide stat sources, but the full sequence should be centralized.

## 12. AI brain

`AIBrain` is conceptually ambitious and better than average in structure. It has explicit phases:

- sensory/perception
- memory/appraisal
- deliberation/tactics
- finalization/proposal

That is a real architecture, not random if/else code.

But the implementation crosses a dangerous line: the brain is “stateless” by docstring while directly mutating the actor’s mind, mood, attention pool, boredom, memory, goal commitment, and even age-related death inside its phases. That is not stateless.

This matters because your workers operate on snapshots. If AI mutates snapshot actors during thinking, you are relying on those mutations being throwaway local decision-state, not authoritative world state. That may be acceptable, but then it must be explicit and limited. Right now it is broad and conceptually muddy.

### Fix

Separate:

- ephemeral decision-time scratch state
- persistent post-tick state updates

The brain should read world state and produce a proposal plus decision deltas. The main thread should decide what deltas become authoritative.

## 13. Goal system

The goal plugin system is a good idea. `GoalScorer`, `GoalEvaluator`, `GoalScore`, and modifier pipeline are understandable.

But the number of modifiers and cross-cutting influences is already too high:

- boredom
- life stage
- personality
- emotional
- hysteresis
- cooldown
- memory
- stuck
- skirmish
- ambition
- fatigue

This is tuning hell. It is hard to reason about combined effects, hard to debug why a choice happened, and easy to create accidental dominance or dead goals.

You are also using many string goal names and soft-typed memory/emotion structures, which compounds the opacity.

### Fix

Reduce the active modifier set to the minimum that changes behavior meaningfully:

- hysteresis
- emotional
- boredom
- one personality layer

Everything else should be introduced only after instrumentation proves it matters.

## 14. Goal scorers

The scorers are readable, but they encode a huge amount of game design in scattered heuristics. `CombatGoal`, `FleeGoal`, `TradeGoal`, `RestGoal`, and others each inject local rules, while modifiers inject more global rules. This creates policy fragmentation.

A specific logic bug stands out in `GuardGoal`: it computes `dist_home` in an `elif` branch and then does nothing with it before returning `base`. That is unfinished logic surviving in production code.

That one bug matters because it reveals a pattern: lots of ambitious behavior, not enough tightening and pruning.

### Fix

For each goal, write down:

- inputs
- hard blockers
- core score formula
- allowed modifiers

Then keep the scorer small and move reusable logic into helpers.

## 15. AI states and handlers

The handler architecture is decent: registry, `AIContext`, and specialized handlers are the right direction.

But again the codebase keeps cheating. Helpers are re-exported for backward compatibility, context is allowed to accumulate tactical hints loosely, and state handlers sometimes directly mutate snapshot-owned objects in ways that blur decision versus authoritative update. The corpse-run handler even mutates `snapshot.corpse_nodes`, which is conceptually wrong for an immutable decision snapshot.

### Fix

Treat `Snapshot` as read-only in a hard, enforced sense.
Handlers should only emit proposals and perhaps sidecar intent metadata.

## 16. Pathfinding and flow fields

The pathfinding direction is good. Terrain-aware A\* plus flow fields for shared destinations is exactly the kind of optimization that actually makes sense in a simulation.

The risk here is not cleanliness. It is uncontrolled complexity growth. Once you have:

- A\*
- movement costs
- occupied tiles
- cached paths
- flow fields
- tactical hints
- line of sight

you need very disciplined ownership. Right now navigation concerns are spread through pathfinding, handlers, `MindAspect`, `MoveAction`, and combat range checks.

### Fix

Create a navigation subsystem boundary:

- path computation
- path caching
- shared destination fields
- line-of-sight helpers
- movement cost registry

Do not keep smearing navigation into AI, combat, and aspects.

## 17. API layer

The API app factory is clean enough. Lifecycle wiring, OpenAPI metadata, and engine manager startup are straightforward.

But the domain/API separation is weak. Entity objects serialize themselves into API schemas, and the websocket path rebuilds client payloads by re-encoding snapshots and event logs in the API layer. That is functional, but domain objects should not know API schema shapes.

### Fix

Move mapping to dedicated serializers:

- `EntityPresenter`
- `WorldStatePresenter`
- `EventPresenter`

The API layer should depend on presenters, not on domain objects that render themselves.

## 18. Replay and observability

Replay recording is simple and fine as a first pass. Event log ring buffer is also reasonable. Metrics and logging coverage are extensive.

The problem is that observability is mixed into business logic everywhere. Metrics and event publishing appear inside low-level action code, AI exception handling, worker dispatch, and lifecycle logic. The result is noise and more coupling.

### Fix

Centralize instrumentation hooks where possible. Not every gameplay branch should inline metrics logic.

## 19. Style and code hygiene

Some style issues are not superficial here. They are signals of structural loss of control.

You have:

- `Any` in important state
- duplicate and legacy shims
- long god-methods
- hardcoded constants buried in action logic
- mixed enum and raw string state
- direct imports inside functions everywhere
- compatibility comments that never ended

These are not isolated code smells. They point to a codebase that keeps postponing hard cleanup.

## 20. What is actually strong

Do not ignore these, because they are the parts worth preserving:

The four-phase engine concept is sound. The action proposal model is good. The goal scorer architecture is directionally strong. The flow-field optimization is intelligent. `WorldState` as authoritative mutable state is the right idea. The project has enough structure that it can be saved without a rewrite.

## 21. Engine core: `WorldLoop`

This is the spine of the project, and the design intent is strong. `WorldLoop` is clearly meant to be the authoritative four-phase engine, and the code shows that intent: snapshot creation, dispatch, proposal collection, conflict resolution, system updates, telemetry, replay, and external publishing all revolve around it. That is the right place for central orchestration.

The problem is that `WorldLoop` is turning into an orchestration sink.

It imports and coordinates:

- worker pool
- conflict resolver
- action queue
- system manager
- multiple systems across gameplay, lifecycle, calamity, telemetry, environment, economy
- replay
- Kafka publishing
- direct event and snapshot serialization

That means the loop is doing both:

- simulation sequencing
- infrastructure integration

Those two concerns should not keep expanding in the same class.

### What is wrong logically

The loop is supposed to define “when” things happen.
It is not supposed to absorb every detail of “how every subsystem works.”

Once it starts owning both, every new feature wants a hook in the world loop. That is how engines become unmaintainable.

### Fix

Refactor `WorldLoop` into:

- `TickScheduler`
- `DecisionPhase`
- `ResolutionPhase`
- `PostTickPhase`
- `SimulationPublishers`

Keep one thin `WorldLoop.run_tick()` that calls those components in order.

That gives you one place for phase order, but not one god-class for all engine work.

## 22. Engine determinism is still weaker than you think

The project claims determinism, but the implementation still leaks nondeterminism through the worker architecture and timeout behavior.

The worker pool publishes AI batches, polls a result queue, ignores stale results, may partially drop results under chaos mode, and times out per tick. That means proposal availability is a function of infrastructure timing, not just world state and RNG seed.

This is the key uncomfortable truth:

- deterministic RNG does not make a distributed system deterministic
- deterministic sorting of received proposals does not fix missing or delayed proposals

Your engine is only truly deterministic in inline/local execution mode. The distributed mode is, at best, reproducible under stable conditions. That is not the same thing.

### Fix

Make the rule explicit in code and docs:

- inline mode = authoritative deterministic reference
- worker-dispatch mode = scalable execution mode with weaker replay guarantees unless all results arrive before the tick deadline

Then add a deterministic replay test harness that compares:

- same seed, same config, inline run A vs inline run B
- same seed, same config, worker run A vs worker run B
- inline vs worker final world hashes

Right now you are asserting determinism more than proving it.

## 23. Action queue and proposal handling

`ActionQueue` is one of the cleanest modules in the codebase. It is small, honest, and does one thing. That matters because it shows you _can_ write clean infrastructure code when you do not try to be overly clever.

The lesson is not “good job.”
The lesson is: small isolated interfaces are where your code quality is strongest.

You should use that as a model elsewhere.

## 24. `ConflictResolver` is decent, but it hides policy in implementation detail

`ConflictResolver` is structurally okay. It sorts, builds occupied sets, validates, and dispatches to action handlers. That is the right job.

But there is one design mistake you should not ignore:
`_sort()` uses `p.verb.value` as part of the deterministic order. That means enum ordering becomes gameplay priority. If someone reorders `ActionType`, they might silently change combat or movement fairness.

That is a hidden rule.

### Fix

Define an explicit action priority map:

```python
ACTION_PRIORITY = {
    ActionType.USE_ITEM: 10,
    ActionType.USE_SKILL: 20,
    ActionType.ATTACK: 30,
    ActionType.MOVE: 40,
    ActionType.REST: 50,
}
```

Then use that. Never let enum declaration order become game logic by accident.

There is also split authority here: some actions are fully handled by the resolver, while others are apparently validated/applied elsewhere. That weakens the layer.

### Fix

Resolver should own action application routing completely, or not at all.

## 25. `WorldState` is your best candidate for a durable core, but it is already bloating

`WorldState` is conceptually right. It is the mutable authoritative store with entities, grid, spatial index, buildings, ground items, corpse nodes, regions, aggression, war status, history, and progression counters. That is appropriate.

But it is starting to absorb too many unrelated state families:

- tactical simulation state
- world progression state
- economy state
- narrative history
- war/conquest state
- observability/event state

That is fine if all it does is store them.
It is not fine if more and more business logic starts accumulating there.

At the moment it is still mostly a data holder with helper methods like `add_entity`, `remove_entity`, `move_entity`, `drop_items`, `pickup_items`, and resource-node management. That is good.

### The actual weakness

The helper methods are too thin to protect invariants. For example:

- `add_entity` inserts into `entities` and spatial index, but there is no central validation of duplicate IDs
- `move_entity` updates both entity position and spatial index, but there is no domain-level movement guard
- `resource_at` linearly scans all resource nodes by position, which will get worse with scale

### Fix

Keep `WorldState` authoritative, but strengthen it with invariant-preserving APIs:

- `spawn_entity(...)`
- `despawn_entity(...)`
- `move_entity_checked(...)`
- `create_corpse_node(...)`
- `transfer_ground_items(...)`
- `find_resource_node_at(...)` backed by a position index, not a scan

That way, the rest of the code stops treating world state like a bag of mutable containers.

## 26. Snapshot discipline is currently weak

The biggest logic violation I saw in the AI stack is that decision code still mutates snapshot-backed state in places where it should not.

The worst example is `CorpseRunHandler`, which:

- adds gold/items directly to the actor during handler execution
- mutates `snapshot.corpse_nodes` by popping the recovered node

That is conceptually wrong.

A decision handler should say:

- “I want to recover corpse node X”

It should not:

- mutate the snapshot
- mutate inventory/gold directly inside decision generation

The moment handlers start doing that, your snapshot is no longer just read-model input. It becomes a shadow mutable world. That breaks the mental model of the engine.

### Fix

Introduce an explicit `RECOVER_CORPSE` or `LOOT_CORPSE` action proposal and apply it only in the authoritative resolution/application phase.

Do the same audit for every handler that increments counters or mutates inventory-like state during AI evaluation.

## 27. AI context and state handlers: good shell, sloppy contents

`AIContext` is a good concept. It gives handlers a common interface, and its lazy `visible` property plus helper methods like `nearest_enemy()` and `nearest_ally()` are practical.

But again you undermine the clean shell by making it too permissive and too magical.

Problems:

- `tactical_hints` is an untyped dict
- context helper logic depends on mutable actor state like grudges and threat table
- selection logic sometimes reaches into snapshot, sometimes actor memory, sometimes faction rules

That means the context is not just “information for handlers.” It is quietly a decision engine in its own right.

### Fix

Make `AIContext` stricter:

- replace `dict[str, Any]` tactical hints with a typed `TacticalHints` model
- keep helper methods simple and side-effect free
- avoid mixing long-term memory resolution rules directly into the context object

The context should package data, not become a second brain.

## 28. AI handlers have too much inline gameplay logic

The handler model itself is reasonable. `IdleHandler`, `WanderHandler`, `CombatHandler`, `FleeHandler`, `AlertHandler`, town interaction handlers, harvesting, corpse run—this is a good decomposition on paper.

But the code still leaks too much behavior into handler bodies. Handlers:

- query memory
- reset counters
- make tactical choices
- increment loot progress
- mutate actor counters
- sometimes perform pseudo-application rather than just proposing actions

That means your “state machine” is not just a proposer. It is also a partial executor.

### Fix

A handler should ideally do only three things:

- read context
- choose next state
- emit proposal

Everything else should either be:

- authoritative application logic
- post-tick update logic
- reusable helper/service logic

If a handler needs to update a channel/progress value, return it as a proposed state delta instead of mutating the actor directly during thinking.

## 29. Your backward-compatibility strategy is actively hurting the codebase

This is one of the clearest recurring pathologies.

You keep re-exporting helpers “for backward compatibility,” proxying old names, and layering shims instead of forcing a clean migration. The AI states package does this explicitly by re-exporting helpers from several submodules, and the entity/stat system does the same in a deeper way.

Backward compatibility is not free. Every shim:

- increases surface area
- preserves old mistakes
- confuses ownership
- lets inconsistent styles coexist

### Hard truth

At your current project stage, backward compatibility is mostly a self-inflicted drag. You are not maintaining a public ecosystem. You are freezing your own mess in amber.

### Fix

Start deleting compatibility layers on purpose.
Create a migration branch if needed.
Break imports.
Fix the call sites.
Move forward.

You will lose less time doing that than preserving three interfaces to the same concept.

## 30. `StatsProxy` proves the migration is incomplete

`StatsProxy` is polished in the sense that it gives legacy access to effective stats partitioned by combat and progression. But that is the problem. It is too polished for a thing that should be temporary.

It is not just a bridge anymore. It is now part of the architecture.

The evidence is obvious:

- top-level stat shims
- progression shims
- setters
- combat/progression partitioning
- entity still exposes `stats` as a first-class property

That means you have not migrated away from the old stats model. You have built a second model around it.

### Fix

Pick a deadline and deprecate it internally:

- stop adding new code that uses `entity.stats`
- update all hot paths to use explicit aspects or an effective-stat service
- leave `StatsProxy` only where migration is unavoidable
- then delete it

## 31. Specific logic bugs and fragility points

Here are concrete high-risk problems I would fix early.

### `CorpseRunHandler` mutates snapshot and actor state during decision generation

This is a real architectural bug, not a style complaint.

### `GuardGoal` has dead/incomplete logic

It computes `dist_home` and then returns `base` without using it. That is unfinished code surviving in a core scorer.

### Resource lookup is linear by position

### Bootstrap logic is too custom and inline

### Multiple mutation points for AI-ish state

## 32. The top-down refactor map

Here is the order I would actually execute, not the fantasy order where everything becomes beautiful at once.

### Step 1: freeze features

No new mechanics. No new traits. No new AI layers. No new buildings.

### Step 2: force ownership boundaries

Refactor the entity and aspect system until data ownership is explicit:

- combat owns combat state
- progression owns progression state
- mind owns AI state
- inventory owns inventory
- entity stops pretending it is flat

### Step 3: stop AI from mutating world-like state during thinking

Handlers and brain become read-only over snapshot + local scratch.
Application moves to authoritative phase only.

### Step 4: explode `CombatAction.apply`

Turn it into a coordinator over domain services.
This one move will cut a huge amount of hidden coupling.

### Step 5: centralize formulas

One module per formula family:

- action delay
- damage
- xp
- flee thresholds
- repair economics

No scattered mini-formulas in handlers and actions.

### Step 6: remove shims

Delete:

- old helper re-exports where possible
- compatibility properties in aspects
- `entity.stats` usage in new code
- API mapping methods from domain entities

### Step 7: add invariant tests

Not just unit tests. Invariant tests:

- same seed inline run is identical
- dead entities are never scheduled
- spatial index and entity positions never diverge
- snapshot handlers never mutate authoritative world state
- every applied proposal respects action preconditions

## 33. What to measure while refactoring

Do not trust “it feels cleaner.”
Measure things that expose architectural quality.

Track:

- number of `Any` types in core simulation modules
- number of cross-aspect/proxy properties
- number of domain objects with API serialization logic
- average lines per action handler
- number of direct world mutations outside authoritative phases
- deterministic replay equality across same-seed runs

If those numbers do not go down, your cleanup is cosmetic.

## 34. The actual strategic diagnosis

Your codebase is not failing because you lack ideas. It is failing because you do not kill old interfaces aggressively enough after introducing new ones.

That is the repeated pattern:

- introduce aspect system
- keep old flat entity access
- add stats proxy
- keep old stats shape
- introduce handler registry
- re-export old helper access
- introduce plugin goals
- keep stringly typed glue and mutable mind buckets

You are stacking abstractions instead of replacing them.

That feels safe. It is not. It compounds confusion.

## Priority Plan

What you must change in mindset or assumptions
Stop believing that preserving flexibility and backward compatibility is a virtue at this stage. In your project, it is the main source of architectural decay. Every time you avoid breaking an old interface, you make the real design less clear.

What actions you must take immediately
Audit the engine and AI path for illegal mutations during decision-making. Refactor `WorldLoop` into phase components. Replace enum-order action priority with explicit priority. Remove `CorpseRunHandler` snapshot mutation. Start deleting compatibility shims in entity, stats, and AI states.

What you must stop or eliminate
Stop letting handlers mutate domain state during proposal generation. Stop using read-model snapshots as writable scratchpads. Stop layering proxies and re-exports instead of migrating call sites. Stop hiding gameplay rules in enum order or helper side effects.

The consequences and opportunity cost if you fail to change
If you do not clean this now, every subsystem will continue to depend on accidental behavior. Replay and determinism will stay questionable, AI bugs will be harder to reproduce, and your next 10 features will cost more than the previous 20 combined because the core contracts will remain vague. That is where ambitious simulation projects stall and die.
