This plan is focused only on what to change in code, in what order, and what constraints to follow while implementing it. It is grounded in the current code structure and the architectural problems already identified in the entity/aspect layer, AI state handling, combat flow, and engine orchestration.

---

# Core Architecture Stabilization — Implementation Plan for AI Agent

## Objective

Refactor the simulation core so that:

- ownership of state is explicit
- mutation paths are reduced
- snapshot-based decision logic is read-only
- combat resolution is decomposed
- engine phases are clearer
- hidden compatibility layers are removed or minimized

The implementation must prioritize structural clarity over preserving every old access pattern.

---

# Global coding rules

## 1. Do not add features

Do not introduce new:

- traits
- goals
- buildings
- mechanics
- events
- balancing rules
- agent behaviors

Only refactor and stabilize what already exists.

## 2. Do not widen abstractions

Do not introduce generic “manager,” “registry,” or “adapter” layers unless they solve a concrete boundary problem already present in the code.

## 3. Reduce compatibility shims

If a module is touched and a compatibility shim is only there to preserve old access patterns, prefer removing it and updating call sites instead of preserving it.

## 4. Prefer explicit ownership

Use direct owner access:

- `entity.combat.hp`
- `entity.progression.level`
- `entity.spatial.pos`
- `entity.mind.decision.last_goal`

Do not keep flattening everything back onto `Entity`.

## 5. Snapshot inputs are read-only

Any decision-time code must treat snapshot-owned state as immutable. No handler may mutate snapshot-owned collections or authoritative-like world data.

## 6. Minimize `Any`

Do not add new `Any` in core simulation code. Replace existing `Any` where you touch it.

## 7. Keep behavior stable unless the current behavior is structurally invalid

Behavior may change only when:

- the current code violates the intended authoritative/snapshot model
- the current code hides ownership incorrectly
- the current code is clearly incomplete or logically broken

# 1. Refactor `Entity` into explicit composition

## Current problem

`Entity` currently uses `aspects: dict[str, Any]` and then rebuilds a flattened god-object through property shims, compatibility mapping, API serialization methods, and copy logic. That preserves ambiguity instead of removing it.

## Implementation steps

### 1.1 Replace the dynamic aspect registry

Refactor `Entity` so its primary structure is explicit typed fields, not a string-keyed registry.

Target shape:

- `identity: IdentityAspect`
- `spatial: SpatialAspect`
- `combat: CombatAspect`
- `progression: ProgressionAspect`
- `mind: MindAspect`
- `inventory: InventoryAspect | None`

Do not keep `aspects: dict[str, Any]` as the authoritative structure.

### 1.2 Remove broad property flattening

Delete property shims that simply re-expose nested aspect fields at entity top level.

Examples to remove or stop relying on:

- `entity.level`
- `entity.pos`
- `entity.faction`
- `entity.attributes`
- `entity.quests`
- `entity.home_storage`
- `entity.boredom_multipliers`

Keep only the absolute minimum temporary accessors if removing them immediately would break too much code in one pass.

### 1.3 Remove API serialization from `Entity`

Move:

- `to_slim_schema`
- `to_full_schema`
- `_serialize_attrs`
- `_serialize_caps`
- `_serialize_hero_class`

into dedicated presenter modules in the API layer.

`Entity` must stop importing API schema classes directly.

### 1.4 Simplify entity initialization

Remove backward-compatible constructor complexity that supports too many forms unless truly necessary.

Use explicit typed construction and validators instead of magic coercion and `__pydantic_extra__` remapping.

### 1.5 Move entity copy/cloning behavior out if needed

If snapshot generation still needs special copying logic, move that logic into a cloning/snapshot utility rather than keeping heavy copy behavior in `Entity`.

## Result expected

After this step, `Entity` must read like a real composite root, not like a compatibility facade.

# 2. Clean combat/progression ownership boundaries

## Current problem

`CombatAspect` contains combat data plus non-combat fields and legacy proxy access into progression and mind. This destroys aspect isolation.

## Implementation steps

### 2.1 Restrict `CombatAspect` to combat ownership only

Keep only fields that are truly combat-owned or directly required for combat resolution.

Expected to remain:

- hp
- max_hp
- atk
- def\_
- spd
- luck
- crit_rate
- crit_dmg
- evasion
- matk
- mdef
- elem_vuln
- effects
- combat_target_id

Evaluate fields like:

- `vision_range`
- `loot_bonus`
- `trade_bonus`
- `interaction_speed`
- `rest_efficiency`
- `cooldown_reduction`

Either move them to a better owner or define a clearly named derived/service-level container if they truly span multiple systems.

### 2.2 Remove cross-aspect proxy properties from `CombatAspect`

Delete compatibility properties that access progression or mind indirectly:

- `level`
- `xp`
- `xp_to_next`
- `gold`
- `stamina`
- `max_stamina`
- `fame`
- `chase_ticks`
- `engaged_ticks`

All call sites should be updated to use explicit owners:

- `entity.progression.level`
- `entity.mind.decision.engaged_ticks`
- `entity.progression.stamina`

### 2.3 Reduce reliance on `StatsProxy`

Do not expand `StatsProxy`. Refactor touched call sites to use:

- direct aspect access
- or a read-only effective-stat calculation service

`StatsProxy` can remain temporarily only as a migration bridge, not as a growing core abstraction.

### 2.4 Introduce effective stat helpers only where necessary

If multiple places need “effective” values after equipment/effects/territory scaling, create explicit pure helpers or calculators instead of hiding those through proxy chains.

## Result expected

`CombatAspect` becomes an actual combat aspect instead of a cross-system adapter.

# 3. Decompose `MindAspect` into typed submodels

## Current problem

`MindAspect` is a flat container for decision state, perception, threat, emotional state, navigation cache, memory, and diagnostics. It has no internal boundaries.

## Implementation steps

### 3.1 Split `MindAspect` into nested models

Create nested typed components inside `MindAspect`, for example:

### DecisionState

Owns:

- ai_state
- last_goal
- goal_committed_at
- goal_cooldowns
- goal_switch_count
- boredom_multipliers
- consecutive_idle_ticks
- chase_ticks
- engaged_ticks

### PerceptionMemory

Owns:

- terrain_memory
- entity_memory
- attention_pool
- hero_familiarity
- threat_table

### EmotionState

Owns:

- mood
- emotional_state
- grudges

### NavigationState

Owns:

- cached_path
- cached_path_target
- pos_history

### NarrativeMemory

Owns:

- memory_log
- memory_locations
- region_fatigue
- life_directive

The exact names may differ, but the split must be explicit and typed.

### 3.2 Replace vague containers

Replace structures like:

- `memory: dict[int, Any]`
- `entity_memory: list[dict]`
- `memory_log: list[dict[str, Any]]`
- `bonuses: dict[str, Any]`

with typed models or typed dictionaries where possible.

At minimum, introduce models for:

- seen entity memory records
- narrative memory entries
- tactical hint containers
- region sentiment/fatigue records if necessary

### 3.3 Add invariants

Enforce:

- `mood` between `0.0` and `1.0`
- non-negative counters
- bounded familiarity values if intended
- bounded fatigue/sentiment if intended
- attention pool length not exceeding max slots

### 3.4 Remove the generic `memory` bucket if it overlaps other memory stores

Do not keep both a vague catch-all memory structure and several specialized memory structures unless the distinction is explicit and enforced.

## Result expected

`MindAspect` becomes a root for structured AI state instead of a dumping ground.

# 4. Make AI decision logic read-only over snapshots

## Current problem

The AI layer claims statelessness but mutates actor and snapshot-backed state during decision generation. This breaks the authoritative simulation model.

## Implementation steps

### 4.1 Define strict allowed behavior during decision generation

Decision-time code may:

- read snapshot
- compute scores
- generate local scratch values
- return `ActionProposal`
- optionally return a small, explicit set of decision metadata

Decision-time code may not:

- mutate snapshot collections
- mutate buildings, corpse nodes, ground items, world collections
- directly transfer gold/items
- perform authoritative progression mutations
- persist long-lived world state as if it were already resolved

### 4.2 Refactor `AIBrain.decide`

`AIBrain.decide()` must become conceptually pure with respect to authoritative state.

It may still build a context and derive tactical hints, but it must stop directly performing durable state mutations as part of the decision process.

### 4.3 Fix `CorpseRunHandler`

This is mandatory.

The current corpse recovery logic must be changed so the handler proposes an action instead of:

- mutating snapshot corpse collections
- directly adding items/gold during decision generation

Create a real proposal/action path for corpse recovery.

### 4.4 Audit all handlers for illegal mutations

Check each handler for:

- direct world structure mutation
- direct item/gold transfer
- direct corpse/building/ground item removal
- progression updates that should happen only after authoritative action application

Move those effects to the action/application layer.

### 4.5 Replace loose tactical hint dicts

Where `AIContext` uses generic tactical hint dictionaries, replace them with a typed `TacticalHints` model.

## Result expected

The AI layer decides. It does not apply.

# 5. Decompose `CombatAction.apply`

## Current problem

`CombatAction.apply` is one of the most overloaded methods in the project. It contains damage calculation, narrative updates, threat, XP, corpse creation, loot transfer, veterancy, quest progression, and more. That is a central structural failure.

## Implementation steps

### 5.1 Extract a damage resolution service

Create a dedicated service responsible for:

- evasion check
- damage type selection
- raw damage computation
- variance
- elemental modifier
- crit
- final damage result

This service should return a typed result object.

### 5.2 Extract combat aftermath service

Create a service for post-hit but pre-death consequences:

- threat generation
- mood/grudge updates
- combat memory entries
- stamina cost
- attribute training
- veterancy point updates
- non-lethal post-hit effects

### 5.3 Extract kill/death consequence service

Create a service for death-only handling:

- XP and gold reward
- corpse node creation
- loot transfer
- death-region tracking
- title reward logic
- quest kill progression
- evolution/nemesis death hooks

### 5.4 Keep `CombatAction.apply` as a coordinator

After refactor, `CombatAction.apply` should:

- validate participants
- call damage resolution
- apply core hp change
- publish combat event if needed
- delegate aftermath
- delegate kill/death consequences
- update action delay

It should not contain dozens of independent rules inline.

### 5.5 Keep behavior stable where possible

Do not rebalance formulas during this decomposition unless the current logic is clearly invalid or contradictory.

## Result expected

Combat becomes inspectable and testable in pieces instead of being fused into one method.

# 6. Make action priority explicit

## Current problem

Conflict resolution currently hides gameplay ordering inside implementation details like enum value ordering. That is fragile and unclear.

## Implementation steps

### 6.1 Define an explicit action priority map

Create one explicit map for all actionable verbs.

### 6.2 Update resolver sorting to use that map

Do not rely on enum numeric values.

### 6.3 Keep deterministic ordering explicit

Sorting should remain deterministic using:

- action priority
- next act time
- entity id
- any other explicitly documented tie-breakers

## Result expected

Action ordering becomes reviewable policy, not a side effect of enum declaration order.

# 7. Extract `WorldLoop` into visible phases

## Current problem

`WorldLoop` is carrying too much sequencing and too much subsystem/infrastructure detail in one place.

## Implementation steps

### 7.1 Split the loop into phase-oriented collaborators

Extract explicit modules or classes for:

- scheduling/snapshot phase
- AI decision collection phase
- proposal resolution/application phase
- post-tick systems phase
- publishing/telemetry phase

### 7.2 Keep `WorldLoop` as the top-level conductor

`WorldLoop` should define phase order and top-level control flow, not own all implementation details.

### 7.3 Move infrastructure publishing out of core simulation sequencing

Kafka/Redis/event publication logic should sit behind dedicated publisher interfaces or a publish phase.

### 7.4 Document phase invariants in code

Each phase should clearly define:

- what it reads
- what it mutates
- what outputs it produces
- what invariants must hold before/after

## Result expected

The engine becomes phase-driven and easier to reason about.

# 8. Separate domain objects from API serialization

## Current problem

Domain entities currently know how to serialize themselves into API schemas, which mixes domain and presentation concerns.

## Implementation steps

### 8.1 Create presenter modules

Add dedicated presenter modules for:

- entity presentation
- world state presentation
- event presentation

### 8.2 Move all schema mapping out of domain models

Domain models must stop importing or constructing API schema classes directly.

### 8.3 Update API entry points to use presenters

Ensure endpoints and streaming layers call presenters instead of domain objects serializing themselves.

## Result expected

Domain code becomes independent from API schema shape.

# 9. Tighten deterministic inline execution

## Current problem

The project claims determinism broadly, but distributed worker timing weakens that guarantee. Inline mode should be treated as the authoritative deterministic mode.

## Implementation steps

### 9.1 Add a deterministic world-state hash helper

Implement a helper that computes a stable hash from key world state:

- tick
- sorted entities and core owned fields
- buildings
- ground items
- corpse nodes
- other authoritative counters if relevant

### 9.2 Use the helper in tests

Validate that inline mode with the same seed/config produces the same hash after a fixed number of ticks.

### 9.3 Do not rewrite worker mode in this milestone

Only stop over-claiming determinism in code comments or developer documentation where worker timeout and partial-result behavior clearly weaken it.

## Result expected

Inline determinism becomes something testable, not just claimed.

---

# 10. Reduce backward-compatibility re-exports and fake modularity

## Current problem

The codebase repeatedly re-exports helpers and preserves older interfaces instead of forcing a real migration. That keeps multiple abstractions alive at once.

## Implementation steps

### 10.1 Remove helper re-export layers where touched

If a module is already being refactored, do not keep old convenience imports unless absolutely necessary.

### 10.2 Update direct imports to the true owner module

Callers should import the real source, not a compatibility re-export.

### 10.3 Do not add new migration shims unless there is a hard blocker

If a call site breaks, fix the call site.

## Result expected

The codebase begins converging toward one interface per concept.

# Implementation order

Follow this order in code changes:

1. Refactor `Entity` to explicit aspects
2. Strip `CombatAspect` ownership back to combat only
3. Decompose `MindAspect` into nested typed submodels
4. Update callers away from broad property shims and cross-aspect proxy access
5. Move entity/API serialization into presenters
6. Refactor AI decision code to be read-only over snapshots
7. Fix corpse recovery to be proposal/application based
8. Decompose `CombatAction.apply`
9. Make conflict resolver use explicit action priority
10. Extract `WorldLoop` phases
11. Add deterministic inline validation helper and tests

Do not start with `WorldLoop` first. That would be premature and sloppy. The entity/aspect boundary must be fixed before the engine orchestration becomes cleaner.

# Acceptance conditions for each major code area

## Entity layer is acceptable when:

- explicit typed aspect fields exist
- the dynamic aspect dict is gone or no longer authoritative
- API serialization is removed
- broad shims are drastically reduced

## Combat ownership is acceptable when:

- `CombatAspect` no longer proxies progression or mind
- callers use true owners explicitly

## Mind layer is acceptable when:

- major categories of AI state are represented as typed submodels
- vague `Any`/list-of-dict memory structures are reduced or removed

## AI layer is acceptable when:

- handlers propose actions instead of mutating snapshot/world state
- corpse recovery is no longer applied during decision generation

## Combat flow is acceptable when:

- `CombatAction.apply` is primarily coordination
- damage, aftermath, and kill consequences are split into dedicated services

## Engine layer is acceptable when:

- world loop phases are explicit
- action priority is explicit
- deterministic inline behavior is verifiable

# Priority Plan

What must change in mindset or assumptions
Stop assuming refactoring means preserving every old access path. In this milestone, preserving old access paths is one of the main sources of structural dishonesty.

What actions must be taken immediately
Start by making `Entity` explicit, then strip `CombatAspect`, then decompose `MindAspect`, then make AI decisions read-only over snapshots, then split `CombatAction.apply`, then thin `WorldLoop`.

What must stop or be eliminated
Stop adding compatibility layers, stop using `Any` in core state, stop letting handlers mutate world-like data during decision generation, and stop mixing API presentation with domain models.

The consequences and opportunity cost if this is not followed
If the agent keeps layering instead of replacing, the milestone will look busy but accomplish almost nothing. The architecture will stay muddy, debugging costs will continue rising, and future features will keep getting more expensive to add.
