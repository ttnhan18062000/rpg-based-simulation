# Why logs are not enough

Logs are:

- linear
- verbose
- hard to query
- poor for state comparison
- bad for visual explanation
- bad for “what is true right now?”

Logs answer:

- “what happened?”

But your rendering/debugging needs also require:

- “what is currently true?”
- “why did that number happen?”
- “what is the effective value after all modifiers?”
- “who acts next and why?”
- “what changed this tick?”
- “what target is the AI committed to?”
- “what hidden effect is shaping combat?”

That means you need structured runtime data, not just text output.

# What architecture should support this

Do **not** put rendering logic into core engine classes.

Do **not** make frontend recompute engine logic.

Do this instead:

## 1. Create a presentation/introspection layer

Examples:

- `CombatInspector`
- `EntityInspector`
- `TurnOrderInspector`
- `AIExplanationPresenter`
- `StatBreakdownBuilder`

These read authoritative state and build render/debug payloads.

## 2. Add structured breakdown objects

Examples:

- `CombatBreakdown`
- `StatBreakdown`
- `GoalScoreBreakdown`
- `TurnOrderEntry`
- `EffectBreakdown`

## 3. Emit fine-grained runtime events only where useful

Not every tiny thing needs event spam.
But combat and AI decisions should have structured optional detail channels.

## 4. Separate “cheap live state” from “expensive debug detail”

This matters for performance.

You likely want:

### Always available

- entity current state
- effects
- next act
- target
- effective stats
- turn queue summary

### Debug mode / focused inspection

- full combat breakdown
- full AI score breakdown
- formula traces
- roll-by-roll detail

That way you do not drown the system in payload cost all the time.

# Priority Plan

What you must change in mindset or assumptions
Stop thinking “UI later.” For this kind of backend, renderability and explainability are core engineering requirements, not optional presentation work. If numbers remain silent inside the engine, tuning and debugging will become a nightmare.

What actions you must take immediately
Design a dedicated introspection layer between simulation and frontend. Start with three things: entity inspection model, combat breakdown model, and turn-order/scheduler view. Then add AI explanation as the fourth.

What you must stop or eliminate
Stop relying on logs as the primary way to understand runtime behavior. Stop letting the frontend infer hidden engine logic. Stop keeping effective stats and combat reasoning implicit.

The consequences and opportunity cost if you fail to change
If you do not build this layer, your future UI will stay shallow, combat will remain hard to validate, AI will be hard to tune, and every debugging session will depend on reading raw code or logs instead of inspecting live state. That will slow every future feature you add.
