Yes. And the performance angle changes the plan a lot.

You should **not** bolt rich rendering data onto the current `/state`, SSE, and WebSocket payloads indiscriminately. The current API is already split into three useful transport shapes: a polling-style full `/state` endpoint with optional selected entity details, an SSE delta stream carrying slim entity changes plus events, and a WebSocket path that negotiates JSON vs MessagePack and “rich” vs “compact” modes. That is a good base, because it already separates static map/metadata from live state and has a delta stream for the map view. But it is also already showing stress points: the SSE path computes slim diffs by rebuilding slim schemas, and the WebSocket path may re-encode from the latest snapshot rather than reusing a precomputed stream payload, which will get expensive as you add richer rendering views.

So the right plan is not “add more fields to state.” The right plan is to split the API into **view-specific introspection channels** with strict payload budgets.

# Core design goal

Build a rendering/introspection API that can expose rich runtime details for combat, entity inspection, and AI reasoning **without making the main map stream heavy**. The default live stream must stay small and cheap. Rich details must be opt-in, focused, and queryable by entity/combat/encounter.

# What is already good in the current API

The current API already has the correct broad separation:

- `/map` returns static grid data once, RLE-encoded, so the frontend does not keep paying for terrain repeatedly.
- `/metadata/*` exposes game definitions so the frontend can stay data-driven instead of hardcoding enums, traits, classes, and protocol maps.
- `/state` returns a slim entity list plus a single selected entity in full detail, which is exactly the right direction for “overview vs focus” rendering.
- SSE publishes delta payloads with `changed`, `removed`, and `events`, which is good for the world map and entity markers.
- WebSocket already negotiates transport format and supports a compact encoding path, which is the correct place for high-frequency rendering.

That means you do **not** need a new API philosophy. You need a stricter one.

# Current performance risks in the API

The biggest risks are these.

First, `/state` is doing too much for a single endpoint. It walks all entities, builds slim schemas for all living entities, and optionally builds a full selected entity schema in the same request. As the entity inspector gets richer, that endpoint will become progressively more expensive and more tempting to overuse.

Second, the SSE delta pipeline is currently based on converting snapshots into slim schema dicts and diffing them every publish. That is okay for a map-friendly “slim entity” view, but it is not the right place to push full combat or inspect traces. The more detail you add to slim schemas, the more expensive both diffing and serialization become.

Third, the WebSocket path currently may rebuild payloads from the latest snapshot and event log rather than just forwarding a precomputed transport payload. That means richer “rendering features” can accidentally increase server CPU per connected client, which is exactly the wrong scaling shape.

Fourth, your event log is a ring buffer of generic `SimEvent`s, which is useful for a timeline but not enough for rich combat rendering on its own. If you start shoving full breakdowns into that same generic event feed, you will either bloat the stream or turn the event log into a query anti-pattern.

# Implementation plan

## 1. Freeze the main world stream contract

Do not let the map stream become your universal rendering stream.

Keep the main SSE/WS world stream limited to:

- tick
- changed slim entities
- removed entity ids
- lightweight recent events
- optionally coarse world overlay updates like building damage or resource availability, but only in compact form.

The slim entity contract should stay close to what `EntitySlimSchema` already contains: identity, position, HP, state, level/tier, target, and a few rendering markers. Do not add deep combat, AI, or inventory detail there.

### Coding steps

Create a rule in code comments and presenter code: `EntitySlimSchema` is for map rendering only. Any new field must justify itself as map-critical. Put everything else in focused inspector/breakdown endpoints.

## 2. Split “overview” from “focused inspection” at the API level

Right now `/state?selected=...` mixes both. Keep that temporarily, but move toward separate endpoints.

Create dedicated read models and routes:

- `GET /api/v1/entity/{id}` for full entity inspection
- `GET /api/v1/entity/{id}/stats` for effective stat breakdown
- `GET /api/v1/entity/{id}/ai` for goal state / reasoning summary
- `GET /api/v1/entity/{id}/timeline` for recent related events
- `GET /api/v1/combat/{encounter_id}` or `GET /api/v1/entity/{id}/combat` for recent combat breakdowns
- `GET /api/v1/turn_order` for scheduler/next actors overview

Do not put all of that back into `WorldStateResponse`. The selected-entity option on `/state` should become a compatibility convenience, not the long-term home for rich details.

### Why

Focused inspection scales because the frontend only asks for heavy payloads when the user is looking at one entity or one encounter.

## 3. Introduce a dedicated introspection/query layer

Do not have routes build complex rendering payloads by spelunking through snapshots ad hoc.

Create a query/presenter layer, for example:

- `EntityInspectorService`
- `CombatInspectorService`
- `TurnOrderInspectorService`
- `AIExplanationService`

These should read the latest snapshot, event log, and any new breakdown stores, then return API-specific schemas. This prevents route handlers from becoming logic-heavy and lets you cache or batch internally later. The current API already leans on `EngineManager` as the state access point, so this is a natural extension.

### Coding steps

Add a new package like `src/api/introspection/` or `src/api/presenters/` and move heavy render-model construction there. Keep routes thin.

## 4. Build explicit render models, not just bigger entity schemas

You need new schemas rather than endlessly expanding `EntitySchema`.

Create:

- `EntityInspectSchema`
- `StatBreakdownSchema`
- `EffectBreakdownSchema`
- `TurnOrderEntrySchema`
- `AIReasoningSchema`
- `CombatBreakdownSchema`
- `CombatModifierSchema`
- `EncounterSummarySchema`

Your current `EntitySchema` is already large and mixes current state with some derived values, but it still is not a true explanation model. Keep it for general inspection compatibility, but do not keep stuffing more and more explanation detail into it.

### Example split

`EntityInspectSchema` can contain:

- identity
- current position/state
- current/effective stats
- active effects
- inventory/equipment
- progression summary

`StatBreakdownSchema` should contain:

- stat name
- base
- attribute contribution
- equipment contribution
- effect contribution
- terrain/territory contribution
- final value

`CombatBreakdownSchema` should contain:

- tick
- attacker/defender ids
- action/skill
- damage type
- element
- roll values
- modifier chain
- final damage
- result HP
- triggered side effects

## 5. Add a combat breakdown store separate from the generic event log

The existing `EventLog` is a capped ring buffer of generic `SimEvent`s and is fine for lightweight recent history. It is not enough for rich combat rendering by itself.

Create a dedicated in-memory ring buffer for rich combat breakdowns:

- keyed by tick and optionally by entity id / encounter id
- small retention window, for example recent N ticks or recent M breakdowns
- cheap append in authoritative application phase
- queryable by entity or encounter

Do not serialize this by default to SSE/WS world streams.

### Coding steps

Add something like:

- `CombatTraceStore`
- `EncounterIndex`
- `RecentBreakdownIndexByEntity`

Write to it in the authoritative combat application path, after you refactor combat into a structured resolution pipeline.

## 6. Make combat rendering demand-driven

For future real-time combat panels, do **not** stream every combat breakdown to every client.

Use one of these patterns:

- polling/fetch on inspect
- WebSocket subscription by entity id / encounter id
- on-demand recent breakdown replay when a user opens a combat panel

The current WS handshake already supports mode negotiation. Extend that idea to subscriptions:

```json
{ "type": "subscribe", "topics": ["entity:42", "combat:encounter_9"] }
```

The server should then push richer data only for those subscriptions. The default connection should still receive only the world overview stream. This is the single biggest performance safeguard.

## 7. Keep the delta stream cheap by using view-specific projections

Right now `EngineManager._publish_snapshot_and_events()` builds slim dicts, diffs them, and publishes a JSON payload to Redis. That is acceptable for the world map. Do not contaminate that path with detailed projections.

Instead, maintain separate projections:

- `world_overview_projection`
- `entity_inspect_projection` created on demand
- `combat_breakdown_projection` created on event/write
- `turn_order_projection` created periodically or on request

The rule should be:

- high-frequency projections must be tiny and precomputed
- rich projections must be on-demand or narrowly subscribed

## 8. Precompute compact payloads once, not per client

The current WS implementation comments already admit the problem: for JSON/MessagePack mode differences, it may rebuild from the latest snapshot for each client, and notes that in production both should be pre-published. That is exactly right.

Implement that.

At publish time per tick:

- build one JSON overview delta
- build one compact/msgpack overview payload
- store both in Redis stream or an in-memory recent payload cache

Then WS clients should forward the prebuilt format when possible, not re-encode per connection. This matters much more once you add more rendering features.

### Coding steps

Extend `EngineManager._publish_snapshot_and_events()` to produce:

- `overview_json`
- `overview_msgpack`
- maybe `overview_compact_json` if needed

Then store transport-ready payloads, not only a single JSON delta string.

## 9. Move selected-entity heavy detail out of `/state`

`GET /state` currently returns:

- slim entities for all alive entities
- optional `selected_entity`
- recent events
- ground items
- building states
- resource node states
- treasure chest states
- regions

That endpoint is already broad. As inspection deepens, it should not grow further.

Refactor toward:

- `/state` = world overview only
- `/entity/{id}` = focused inspect
- `/entity/{id}/stats`
- `/entity/{id}/ai`
- `/entity/{id}/events`
- `/entity/{id}/combat`
- `/turn_order`

This will reduce repeated heavy serialization when the frontend only needs the map.

## 10. Add “detail levels” explicitly

For every renderable domain, support levels of detail.

### World stream levels

- `compact`: map only / binary-friendly / minimal fields
- `standard`: current slim JSON fields
- `debug`: optional only in dev; never default

### Entity inspection levels

- `summary`
- `full`
- `full_with_breakdowns`

### Combat detail levels

- `summary`: hit, damage, crit, death, effect names
- `trace`: full modifier chain and rolls

This prevents you from forcing the most expensive data shape all the time.

## 11. Build a scheduler/turn-order projection without scanning everything per frame

You want turn orders rendered in real time. Do not make the frontend sort every entity itself every update.

Add a server-side `TurnOrderInspectorService` that returns the next N actors by `next_act_at`, including:

- entity id
- name/kind
- current state
- next act at
- delay until act
- optionally last action and delay reason if available

This can be built from the latest snapshot on demand. It does not need to be streamed every tick to everyone unless the UI is currently showing the turn panel. Since `next_act_at` already lives in entities and scheduling is a core engine concept, this is a natural focused view.

## 12. Add stat breakdown computation as a separate presenter, not inside entities

You want “almost no silent numbers.” That means every major stat should be explainable. Do not compute those breakdowns in the frontend, and do not bloat the main world stream with them.

Create a stat breakdown builder that returns, for each stat:

- base
- components
- final effective value

Compute it when:

- the user inspects an entity
- the frontend asks for combat detail involving that entity
- optionally cache for the current tick

Given the current state of `EntitySchema`, this is the right next step rather than adding twenty more flat fields there.

## 13. Add AI explanation as a separate debug/inspect view

Do not stream AI goal scores to everyone.

Provide:

- current goal/state
- last selected goal
- top scored candidate goals
- lock/cooldown state
- maybe a few key modifiers

This should be a separate endpoint or subscription topic, likely dev/debug oriented first. The current AI system already computes goal scores and uses modifiers and goal locks, so the information exists conceptually even if it is not yet exposed cleanly.

## 14. Use the existing event bus and event log, but separate “event feed” from “explanation stores”

The synchronous `EventBus` and `TelemetryBridge` are fine for coarse domain events and legacy API ring-buffer entries. Keep them for:

- timeline feed
- notifications
- recent world events

But do not force them to become the storage mechanism for every rich explanation payload. Use:

- event log for timeline
- combat trace store for detailed exchanges
- inspector services for current truth
- overview stream for map updates

Different use cases need different stores.

## 15. Cache by tick, not by request

The latest snapshot is already tick-based. Use that.

For expensive render models:

- cache entity inspect payloads per `(tick, entity_id, detail_level)`
- cache turn-order view per tick
- cache stat breakdowns per `(tick, entity_id)`
- cache combat summaries per `(tick, encounter_id)` if encounter modeling exists

This prevents repeated recomputation when the UI opens and closes panels within the same tick.

## 16. Keep static data static

You already did the right thing with `/map` and `/metadata`. Continue that principle.

Do not duplicate:

- material names
- class data
- item templates
- skill definitions
- protocol maps

inside live streams. The frontend should fetch static metadata once and join it with dynamic state client-side where appropriate.

## 17. Add performance budgets per channel

This is the part most teams skip.

Define budgets such as:

- world overview SSE/WS payload per tick should remain small and bounded
- entity inspect should be acceptable for one-off requests, not high-frequency polling
- combat trace topic should only exist for subscribed/focused clients
- AI explanation should be dev-mode or opt-in only

Without explicit budgets, every rendering feature will quietly leak into the main stream.

## 18. Recommended endpoint and channel layout

### Keep

- `GET /api/v1/map`
- `GET /api/v1/metadata/*`
- `GET /api/v1/state` as overview compatibility
- `GET /api/v1/stream`
- `WS /api/v1/ws`

### Add

- `GET /api/v1/entity/{id}`
- `GET /api/v1/entity/{id}/stats`
- `GET /api/v1/entity/{id}/ai`
- `GET /api/v1/entity/{id}/events`
- `GET /api/v1/entity/{id}/combat`
- `GET /api/v1/turn_order`
- optional `GET /api/v1/encounter/{id}`

### WS topics / subscription concepts

- `world.overview`
- `entity.{id}`
- `combat.{encounter_id}` or `combat.entity.{id}`
- `turn_order`
- `debug.ai.{id}`

Do not send all of those by default on connect.

# Concrete coding sequence

First, keep the existing overview API stable and define that it is “map-grade” only.

Second, move entity full-detail building out of entities and into presenter/introspection services, because rich rendering will otherwise keep inflating domain serialization.

Third, add a combat breakdown result model in the combat application path and write it into a dedicated recent trace store rather than the generic ring buffer.

Fourth, add focused REST endpoints for entity inspection, stat breakdown, and recent combat traces.

Fifth, upgrade the WebSocket handshake to support topic subscriptions and detail levels, while keeping world overview as the default topic only.

Sixth, precompute overview payloads once per tick in `EngineManager` for all supported transport formats, instead of re-encoding from latest snapshot per client.

Seventh, add per-tick caches for expensive inspector payloads.

Eighth, only after that, add richer frontend panels.

# What not to do

Do not:

- add full combat details into `EntitySlimSchema`
- make `/state` return everything for every entity
- push stat breakdowns to all stream consumers
- compute full render payloads separately for every WebSocket client
- treat the generic event log as the only data source for rich combat rendering

Those choices will crush performance for very little gain.

# Final recommendation

Your next API milestone should be named something like:

**Runtime Introspection and Renderable Views**

And its principle should be:

> cheap world stream, expensive focused views, no silent numbers, no duplicated engine logic in frontend.

That is the performance-safe way to make this simulation actually observable.

## Priority Plan

What must change in mindset or assumptions
Stop thinking of “rendering” as a single bigger state payload. The correct model is multiple view-specific projections with different cost profiles.

What actions must be taken immediately
Freeze the overview stream contract, add focused inspection endpoints, create dedicated combat and stat breakdown models, and precompute transport payloads once per tick instead of re-encoding per client.

What must stop or be eliminated
Stop expanding `/state` and the slim stream into all-purpose debug channels. Stop planning to send rich combat details to every client by default. Stop putting explanation data into generic event feeds only.

The consequences and opportunity cost if this is not followed
If you keep adding rendering data to the main live stream, you will increase CPU, bandwidth, and serialization cost exactly where the system is hottest. That will make the UI feel heavier, the backend scale worse with each new panel, and future introspection work much harder to control.
