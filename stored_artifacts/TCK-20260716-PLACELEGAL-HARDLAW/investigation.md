# Investigation — TCK-20260716-PLACELEGAL-HARDLAW

## Current Behavior

**`src/observability/hard_law_monitor.py`** — `HardLawMonitor` is a stateless class of `@staticmethod`s. `check(state, dirty_set)` (L46-59) orchestrates two sub-checks: `check_entities()` (L61-135, 5 laws: `LAW-HP-NONNEGATIVE`, `LAW-READINESS-NONNEGATIVE`, `LAW-GOLD-NONNEGATIVE`, `LAW-STAMINA-NONNEGATIVE`, `LAW-POSITION-FINITE`) and `check_occupancy()` (L137-188, 1 law: `LAW-OCCUPANCY-COLLISION`). **All 6 existing laws use `severity="ERROR"` exclusively** — confirmed by reading every `HardLawViolation(...)` construction call in the file; `WARNING` is declared in the dataclass docstring comment (L22) but never instantiated. `check_occupancy()` (L143) returns `[]` immediately `if not dirty_set or not dirty_set.movement_entities` — it is unconditionally gated on a non-empty `DirtySet.movement_entities`, i.e. entities that moved *this specific tick*. It rebuilds indexes via `Kernel.get_world_indexes(state, dirty_set)` (L154) and only checks entity-vs-entity tile occupancy via `indexes.entities_by_tile`, using a `reported_tiles` set to dedupe per-tile reporting.

`HardLawViolation` (L15-24) is a frozen dataclass: `law_id: str`, `entity_id: int` (**required, non-optional**), `severity: str`, `message: str`, `details: Dict[str, Any] = field(default_factory=dict)`. This matches the ticket's architecture-constraint claim exactly — no schema change is needed since `entity_id` can hold any of the three now-confirmed-disjoint ID spaces (below), disambiguated via `details["object_kind"]`.

**`src/worldbuilding/compiler.py`** — direct grep for `walkable`, `LegalityService`, `occupancy` returns **zero hits**, confirming the ticket's central claim. ID-space assignment, confirmed by direct read: `next_resource_id = 10000` (L206, incremented per node), `next_building_id = 20000` (L235, incremented per building), `next_entity_id = 1` (L264, incremented per entity). All three counters only increment upward from their respective bases and are never reset mid-compile, so the three spaces are disjoint for any world with fewer than 9999 resource nodes and fewer than 9999 buildings — true for all real content, not formally bounded in code but not a currently exploitable gap.

**`src/engine/kernel.py`** — `Kernel.__init__` line numbers verified by direct read, all match the ticket's citations:
- `self._run_id = run_id` at L120, with the fallback RNG-suffixed assignment at L121-123 — matches "~120-123" exactly.
- `self._artifact_repo = None` is actually assigned at L125 (not L180), but L180 is the first `self._artifact_repo`-dependent statement after the `create_run`/`update_manifest` calls (L175-176) — by L180 a fully populated `self._artifact_repo` (when `obs_mode != OFF`) or `None` (when `OFF`) is settled and usable. The ticket's phrasing "available by kernel.py:180" is accurate; the assignment itself starts three lines earlier than "180" alone would suggest.
- `self.validate(flags)` is at L311; the `ContentWarmupService.warmup()` try/except block (with its `WORLD-CAT-004` comment tag) spans L313-319 exactly, matching the "~311-319" citation (comment starts at 313, not 311, but 311 is `self.validate(flags)`, the other cited anchor). This is the last statement block in `__init__` — nothing follows it before the method ends. It is the correct and only sane insertion point for a new one-time init-time check.
- `_run_hard_law_checks(self, dirty_set)` spans exactly **L738-804** (confirmed: `def` at 738, last statement `logger.warning(...)` inside the `elif mode == ObservabilityMode.LIGHT:` block at L804; L806 begins the next method `_phase_observability`). Its shape: mode-gate (L742-744, return early if `OFF`), run checks (L753), early-return if no violations (L755-756), accumulate onto `self._status.hard_law_violations`/`cumulative_violations` (L758-767), write JSONL via `self._artifact_repo.resolve_path(self._run_id, "violations")` with a `tick` field from `self._state.tick` (L770-788), route through `AlertsManager.get_router().route(...)` (L790-798), and finally mode-branch: raise `HardLawViolationError` in `DEBUG`/`CERTIFICATION` (L800-801), log-only in `LIGHT` (L802-804). **Note a pre-existing quirk not part of this ticket's scope**: `LONG_RUN` mode falls through this if/elif chain with no log and no raise — `_run_hard_law_checks` only explicitly handles `LIGHT` for logging. This is an existing gap in the reused template, not something this ticket should silently fix or silently inherit without noting — the new method should decide explicitly whether it needs the same `LONG_RUN` blind spot or should log unconditionally in all non-fail-fast modes (leaning toward matching the existing template exactly, per the ticket's own "reuse this shape" instruction, but flagging the inherited quirk).

`Kernel.get_world_indexes(state, dirty)` (L1114-1122) is a thin wrapper that just delegates to `WorldIndexService.get_indexes(state, dirty)`. **Implementation-relevant finding not spelled out in the ticket**: `WorldIndexService._build_entity_index()` (`src/engine/world_index.py` L136-145) is *already* a full-population scan over `state.entities.items()` — it is not itself dirty-filtered; `CacheInvalidationPolicy.should_invalidate(...)` only decides whether to reuse a cached `WorldIndexes` object (keyed by `state.tick`) or rebuild fresh. At `Kernel.__init__` time no `state.world_indexes` attribute exists yet, so `Kernel.get_world_indexes(state, None)` will always rebuild fresh and full — the entity half of the occupancy problem is already naturally full-population, no synthetic `DirtySet` needed for that part. However, `active_resource_nodes` (`_build_resource_index`, 20-unit spatial buckets, not tile-keyed) and `buildings_by_kind` (keyed by kind string, not by tile) are **not** in the tile-keyed shape `check_occupancy()`'s `entities_by_tile` uses — a new `check_initial_placement()` cannot reuse `indexes.entities_by_tile` alone to catch entity-vs-building or building-vs-resource-node overlaps; it needs to build its own tile-position map spanning `state.entities`, `state.buildings`, and `state.resource_nodes` together (the prototype script `experiments/placement_integrity/prototype/check_placement.py`'s `by_pos` dict, L53-57, is exactly this shape and a reasonable model to follow).

**`src/engine/legality.py`** — `LegalityServiceV2.verify_occupancy(pos, state_or_context, ignore_entity_id=None)` (L54-114+) confirmed to implement the full 5-part rule the ticket describes: (1) `WALL` terrain via `state.terrain` (L72-73), (2) `blocked_tiles` membership (L75-77), (3) `building_tiles` (O(1) map) or a linear `buildings` scan fallback (L81-89), (4) `transient_claims` (L91-94), (5) dynamic entity occupancy via `occupancy_snapshot` or `SpatialQueryService.get_occupancy_map` or a raw `entities` scan fallback (L96-114). Returns `Tuple[bool, ReasonCode]`. This function is generic over `state_or_context` (uses `getattr(...)` throughout, never assumes a live `Kernel`), so it is directly callable against a freshly-compiled `AuthoritativeState` at `Kernel.__init__` time with no adaptation needed.
