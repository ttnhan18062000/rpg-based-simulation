# Implementation Plan — TCK-20260904-CAPABILITY-ENVELOPE-BASELINE

## Summary

Build one new module, `tools/capability_envelope_baseline.py`, backing a new
append-only-uniqueness JSONL registry (`registries/capability_envelope_registry.jsonl`) that
records the approved capability envelope for `.claude/settings.local.json`'s full schema
(`permissions.allow` entries plus the 3 MCP fields), and a `diff` CLI subcommand in that same
module comparing the live file against the registry. One module (not two) is used deliberately —
see "Resolved Design Question 1" below — mirroring `tools/tag_registry.py`'s own shape (registry
I/O + CLI in one file), which the ticket's own Scope section already names as the convention to
follow. The baseline is seeded, in Step 5, as a one-time snapshot of the real live 114-entry
`settings.local.json` (main checkout) — see "Resolved Design Question 2" below — so day-one drift
detection is meaningful (new additions after this ticket lands are what get flagged), not a
grandfather-everything-forever no-op wrapped in false rigor, and not noise generated by diffing
against an unrelated, differently-scoped file.

### Resolved Design Question 1 — Baseline shape: registry-style, not snapshot-style

**Decision: registry-style, mirroring `tools/tag_registry.py`/`tools/layer_registry.py` exactly**
(JSONL, one entry per line, unique-key, `add_entry()` refuses to re-add an existing key,
`load_registry()` raises on a duplicate key found on disk).

Reasoning:
- The ticket's own Scope section (not just investigation.md's musing) is explicit: "following the
  tag_registry.py/layer_registry.py registry convention (documented lifecycle, stable location,
  script-enforced)" — this already names the convention; it is not an open question the ticket
  left blank.
- `tools/agent-monitoring/manifest.py`'s snapshot+prefix-preservation pattern
  (`assert_prefix_preserved`, `manifest.py:120-128`, read in full) is purpose-built for a
  continuously-appended, never-rewritten *log* (`agent-monitoring/data/*/tools.jsonl`) where old
  lines must never be edited because they are an immutable historical record of what already
  happened. A capability envelope is the opposite kind of artifact: it is a live, occasionally
  *intentionally revised* statement of what's currently approved (a maintainer may deliberately
  narrow it later, in a separate governance ticket) — forcing every revision through
  `manifest.py`'s hash+prefix-preservation gate would fight that, not support it.
  `tag_registry.py`/`layer_registry.py`'s simpler "each key added exactly once, no update/delete
  command; a rare manual correction happens via direct file edit + git history, same as any other
  registry" model already tolerates this without extra machinery.
- Cardinality also fits: each `permissions.allow` string and each MCP server name is naturally an
  independent, individually-addable unit — the same granularity `tag_registry.py:199-245`'s
  `add_tag()` already uses for one tag at a time.

### Resolved Design Question 2 — Seed source: live `settings.local.json` (114 entries), not `.claude/settings.json` (48 entries)

**Decision: seed the baseline from a one-time snapshot of the real, live main-checkout
`.claude/settings.local.json` (114 `permissions.allow` entries + 3 MCP fields, confirmed live by
`investigation.md`'s Current Behavior section), not from `.claude/settings.json`'s 48-entry list.**

Reasoning:
- `.claude/settings.json` and `.claude/settings.local.json` are two structurally different,
  intentionally-coexisting config surfaces (confirmed by `docs/ai/skills.md:170`'s
  `/update-config` skill documentation, cited in investigation.md's Docs Requiring Update section
  — that skill already documents editing both files for different scopes: shared/committed vs.
  personal/local). Seeding this ticket's *local-envelope* baseline from the *shared* file's
  unrelated 48-entry list would compare two different things and immediately flag ~66+ everyday,
  legitimate local permissions (`git`, `grep`, `pytest`, etc. — none of which are unusual or
  suspicious) purely because they live in the other file, not because they represent real
  permission creep. That is pure noise on day one and would undermine trust in the tool before its
  first real use.
  the tool's own audit purpose (this ticket exists to catch capability creep, not to rubber-stamp
  an already-current state). This is a real, disclosed tradeoff, not something this ticket resolves
  through a security review: the baseline's per-entry `note` field will say explicitly
  "grandfathered baseline snapshot as of TCK-20260904-CAPABILITY-ENVELOPE-BASELINE — not
  individually security-reviewed; establishes the drift-detection floor going forward," so nobody
  reading the registry later mistakes "in the baseline" for "individually vetted."
- This keeps the ticket's actual scope (commit a baseline + a diff script) separate from a
  never-scoped manual security review of 114 permission strings, which is explicitly not an
  acceptance criterion here and would be its own future governance ticket if wanted.
- This does not conflict with the ticket's own AC2, which requires the diff script to run against
  the real `settings.local.json` and produce "a real, non-stub report" — a report whose live-vs-
  baseline counts are both real, live-computed 114s (not zeros, not a placeholder) satisfies that
  wording even when nothing is flagged on day one, because baseline and live are the same snapshot
  at seed time. AC4's positive/negative control cases (a synthetic clean fixture and a synthetic
  out-of-envelope fixture) are deliberately exercised against **synthetic** fixtures, not the real
  corpus — see Step 6 — so the "does the flagging logic actually fire" proof does not depend on the
  real file ever containing a violation.

## Steps

### Step 1 — Registry core: schema, load, single-entry add
**Files:** `tools/capability_envelope_baseline.py` (new)
**Change:**
- `REPO_ROOT = Path(__file__).resolve().parent.parent`, `REGISTRY_REL_PATH =
  Path("registries/capability_envelope_registry.jsonl")`, `registry_path(root=None) -> Path`
  (mirrors `tools/tag_registry.py:145-153` exactly).
- `FIELDS = frozenset({"permissions.allow", "enableAllProjectMcpServers",
  "enabledMcpjsonServers", "disabledMcpjsonServers"})` — the exact 4 top-level schema fields
  confirmed live in `investigation.md`'s Current Behavior section (lines 32-42 of that file: "the
  file's real top-level schema is exactly 4 fields").
- `load_registry(root=None) -> dict[tuple[str, object], dict]`: keyed by `(field, value)` tuple
  (not by `value` alone, so a `permissions.allow` string can never collide with an
  `enabledMcpjsonServers` name that happens to be spelled the same). One JSON object per line:
  `{"field": ..., "value": ..., "added_date": ..., "reviewed": ..., "note": ...}`. `reviewed` is a
  typed `bool` field — the durable, queryable fact of whether this `(field, value)` entry was
  individually reviewed (via `add_entry`) or bulk-seeded and never individually reviewed (via
  `seed_registry`). This is a **typed field**, not something recovered by string-matching `note`'s
  prose — `note` stays supplementary human-readable context only (see Step 2's seeded-`note` text
  below, which remains, but is no longer the sole carrier of the reviewed/unreviewed distinction).
  Raises `ValueError` on a duplicate `(field, value)` key found on disk — mirrors
  `tag_registry.py:156-179`'s duplicate-key invariant exactly, adapted to a 2-part key.
- `add_entry(field, value, note="", reviewed=True, root=None) -> dict`: raises `ValueError` if
  `field not in FIELDS`, or if `(field, value)` is already registered (mirrors
  `tag_registry.py:199-245`'s `add_tag()` — refuses re-add, no update/delete command exists).
  Appends `{"field": field, "value": value, "added_date": <utc today>, "reviewed": reviewed,
  "note": note}` with `json.dumps(entry, sort_keys=True)`. `reviewed` defaults to `True` because a
  direct call to `add_entry` (via the CLI's `add` subcommand, Step 4) is by construction a single,
  deliberate, individually-reviewed governance addition — the default requires no caller to
  remember to pass it. `seed_registry` (Step 2) is the one caller that overrides it to `False`.
**Do NOT touch:** `tools/tag_registry.py`, `tools/layer_registry.py`,
`registries/tag_registry.jsonl`, `registries/layer_registry.jsonl` — read as the pattern template
only; never imported, never modified. `tools/agent-monitoring/manifest.py` — not imported; its
snapshot pattern was considered and rejected above, not reused.
**Verify:** `test_baseline_registry_rejects_or_governs_duplicate_or_conflicting_entries` (the
append-only-uniqueness half of that test);
`test_seeded_entries_marked_unreviewed_and_manual_adds_marked_reviewed` (the `add_entry` half —
asserts `reviewed=True` on direct add).

### Step 2 — Live-file parsing and bulk idempotent seed
**Files:** `tools/capability_envelope_baseline.py`
**Change:**
- `load_settings_local(path) -> dict | None`: returns the parsed JSON object, or `None` if `path`
  does not exist (never raises `FileNotFoundError`) — this is the direct, testable fix for the
  real condition confirmed in `investigation.md`'s Current Behavior section: "`.claude/
  settings.local.json` does NOT exist in this worktree" (confirmed via `ls`, "No such file or
  directory").
- `extract_entries(settings: dict) -> list[tuple[str, object]]`: flattens `settings["permissions"]
  ["allow"]` (list of strings, defaulting to `[]` if the key is absent — `investigation.md`
  confirms `permissions.deny`/`permissions.ask` are absent in the live file, so read defensively
  with `.get(...)`) into one `("permissions.allow", <string>)` tuple per entry; wraps
  `settings.get("enableAllProjectMcpServers")` as a single `("enableAllProjectMcpServers", <bool>)`
  tuple only if the key is present; flattens `enabledMcpjsonServers`/`disabledMcpjsonServers` (each
  a list of server-name strings) into one tuple per name for each field.
- `seed_registry(settings_path, root=None, note="") -> list[dict]`: calls
  `load_settings_local` + `extract_entries`, then calls `add_entry(field, value, note=note,
  reviewed=False, root=root)` for each tuple **but catches and swallows the `ValueError` that
  `add_entry` raises for an already-registered `(field, value)` pair** (returns only the entries
  actually appended). This is a deliberately different contract from `add_entry`'s raise-on-
  duplicate behavior: `add_entry` (called directly, `reviewed` defaults `True`) is for one
  deliberate, individually-reviewed governance addition (a mistake re-adding an existing key should
  be loud), while `seed_registry` is a bulk bootstrap/re-sync operation where hitting
  already-registered entries on a re-run is the expected, common case, not an error — document this
  distinction in both functions' docstrings so a future reader does not "fix" one to match the
  other. `seed_registry`'s explicit `reviewed=False` override is the typed, automatic population of
  the reviewed/unreviewed distinction (see Step 1) — every entry `seed_registry` writes is
  `reviewed: false` on disk, regardless of what `note` says.
**Do NOT touch:** No other file writes `registries/capability_envelope_registry.jsonl` — this is a
brand-new file with exactly one writer path in the whole repo (`add_entry`/`seed_registry` in this
module, invoked only by a human/implementer running the CLI; never by an automated hook, unlike
`agent-monitoring/data/*/tools.jsonl`'s `PostToolUse`-hook writer). There is therefore no
concurrent-writer race to reconcile for this step.
**Verify:** `test_baseline_schema_covers_all_four_settings_local_fields` (via a synthetic
`settings` dict covering all 4 fields, asserting `extract_entries` returns a tuple for each);
`test_seeded_entries_marked_unreviewed_and_manual_adds_marked_reviewed` (the `seed_registry` half —
asserts `reviewed=False` on every seeded entry).

### Step 3 — Diff/report logic
**Files:** `tools/capability_envelope_baseline.py`
**Change:**
- `compute_diff(live_settings: dict | None, registry: dict) -> dict`: if `live_settings is None`,
  return `{"status": "no_local_file", "fields": {}}` (the graceful missing-file report,
  see Step 2). Otherwise, for each `field in FIELDS`: compute `live_values` as the same flattening
  `extract_entries` uses for that one field (reuse `extract_entries` internally rather than
  duplicating the flattening logic — call it on `live_settings` and filter by field), compute
  `baseline_values = {value for (f, value), _ in registry.items() if f == field}`, and report
  `{"in_envelope": sorted(live ∩ baseline, key=str), "out_of_envelope": sorted(live - baseline,
  key=str)}` per field. This treats every field uniformly, including the two scalar-shaped fields
  (`enableAllProjectMcpServers` as a one-element live/baseline set) — so a flipped boolean is
  reported as an `out_of_envelope` entry the same way a new permission string would be, with no
  special-cased comparison branch.
- `build_report(settings_path, root=None) -> dict`: calls `load_settings_local(settings_path)` +
  `load_registry(root)`, calls `compute_diff`, and adds a top-level
  `"audit_only_disclaimer"` string field with fixed text, e.g. `"AUDIT-ONLY REPORT: this diff has
  no runtime-enforcement effect. It is evidence for human review, not a security control. See
  docs/ai/capability_envelope_baseline.md."` — satisfies AC3 directly in the report payload (not
  only in the module docstring, so every printed report is self-disclosing even out of context).
**Do NOT touch:** `compute_diff`/`build_report` perform no writes anywhere — pure read-and-report
functions over already-loaded in-memory data.
**Verify:** `test_diff_script_handles_missing_settings_local_json_gracefully`,
`test_diff_script_output_states_audit_only_no_enforcement`,
`test_clean_baseline_input_produces_empty_result`,
`test_out_of_envelope_entry_produces_flagged_result`.

## Anti-Drift Notes

- **Never hardcode 114 or 48 anywhere in `tools/capability_envelope_baseline.py`.** Both numbers
  are already-confirmed-live as of this planning session but will drift, exactly as the same-day
  sibling ticket's own investigation found its cited corpus numbers stale one day later. Only test
  assertions may compare against a live-recomputed count.
- **The reviewed/unreviewed distinction is carried by the typed `reviewed: bool` field (Step 1),
  not by `note`'s prose.** `seed_registry` writes `reviewed=False` and `add_entry` writes
  `reviewed=True` (Step 1/2) — a future consumer that needs to query or branch on "was this entry
  individually reviewed" reads the typed field, never string-matches `note`. The registry's `note`
  field on every seeded entry should still say it is a grandfathered snapshot, not an
  individually-reviewed approval — this remains useful, disclosed human-readable context for
  Resolved Design Question 2's tradeoff (seeding from an unreviewed live file) — but it is now
  supplementary, not load-bearing: do not implement any logic (in `compute_diff`, docs, or tests)
  that recovers the reviewed/unreviewed fact by parsing or matching `note`'s text.
- **`enableAllProjectMcpServers` is a scalar, not a list — `compute_diff` must treat it as a
  one-element set for comparison, not a special-cased boolean branch.** This keeps all 4 fields
  going through one uniform diff code path (Step 3), which is easier to test and reason about than
  a per-field-type special case.
- **This worktree has no `.claude/settings.local.json`.** Both the real-corpus test (Step 6, test
  2) and the seed step (Step 5) must reference the main checkout's absolute path
  (`/home/u24desktop/Working/rpg-based-simulation/.claude/settings.local.json`), not a relative
  path assumed to exist in this worktree — confirmed absent by direct `ls` in investigation.md.
- **`add_entry` (raise-on-duplicate) and `seed_registry` (swallow-duplicate) are deliberately
  different contracts on purpose** — do not unify them into one behavior; a future reader might
  otherwise "fix" the apparent inconsistency and break either manual-add's mistake-detection or
  seed's idempotent-rerun property.
- **`registries/capability_envelope_registry.jsonl` has exactly one writer in the whole repo**
  (this module's own `add_entry`/`seed_registry`, run only by a human via the CLI) — there is no
  hook-driven concurrent writer analogous to `agent-monitoring/data/*/tools.jsonl`'s
  `PostToolUse` hook, so no ordering/race reasoning is needed for this file, unlike that other
  registry-shaped file elsewhere in the repo.
- **Parity ledger subsystem fit (Step 8) is a judgment call, not a certainty** — proactively
  included per the sibling ticket's own corrected precedent, but if the Parity phase disagrees,
  record the reversal in this ticket's Deviations section rather than silently dropping the entry
  or silently keeping it unexamined.
