# Investigation — TCK-20260713-MONITORING-SQLITE-INDEX

## Current Behavior

**Source files (measured live, 2026-07-28):** `agent-monitoring/runs.jsonl` (715 lines), `agent-monitoring/events.jsonl` (3,773 lines), `agent-monitoring/tools.jsonl` (67,763 lines) — larger than the idea doc's 2026-07-11 snapshot (582/2,724/46,984), confirming continuous append growth. All three remain plain, hook/CLI-written, append-only JSONL — no change needed or proposed to that write path.

**`tools/agent-monitoring/query.py`** (121 lines) — `load_jsonl()` (24-27) does a full read + `json.loads` per line, no caching. `main()` (80-120) applies argparse filters as list comprehensions directly against raw dict keys — e.g. line 98 reads `r.get("final_status")` with **no fallback to legacy `status`**, so `--status` filtering on runs silently misses every legacy-schema record. No normalization layer exists here at all. Zero test coverage confirmed — `tests/tools/test_query.py` does not exist (verified via directory listing of `tests/tools/`).

**`tools/agent-monitoring/generate_retro.py`** (816 lines) — already contains the normalization logic the idea doc wants centralized:
- `_resolve_status()` (88-96): `r.get("final_status") or r.get("status")` — deliberately does **not** normalize casing/spelling variants (`"success"`/`"done"` stay distinct from `"DONE"`).
- `_is_legacy_event()` (99-104): `e.get("agent") is None` — events.jsonl's legacy-schema discriminator (free-text `event`/`detail` shape vs. current `summary`/`agent` shape).
- `_is_gate_fail()` (107-112): single source of truth for "did not reach a terminal state."
- `_canonicalize()`/`_normalize_phase()`/`_normalize_agent()` (115-153): casefold canonicalization against `vocabulary.py`'s sets, read-time only (never written back).
- `compute_retro_metrics()` (269-518): the single computation entrypoint — consumed by both this module's own CLI `main()` **and** by `src/api/agent_ops_dashboard/ingest.py::get_agent_monitoring_stats()` (confirmed by parity ledger entry INFRA-274, `TCK-20260718-AGENTOPS-STATS-API`). **This is a 5th live consumer of the raw JSONL normalization logic, not named in the idea doc's "4 independent consumers" framing** — worth flagging for awareness even though it is untouched by this ticket.

**`tools/agent-monitoring/validate.py`** (286 lines) — `LEGACY_COMPLETION_FIELDS` (31): `("end_ts", "finished_at", "completed_at", "ts_end")`. `LEGACY_TERMINAL_STATUS_VALUES` (37-41): an 11-value set (`DONE`, `done`, `complete`, `completed`, `success`, `EPIC_SCOPED`, `ALL_SCOPED`, `DOD_BLOCKED`, `NEEDS_HUMAN_INPUT`, `GATE_FAIL`, `STOPPED_BY_USER`). `_record_is_complete()` (44-51) is exactly the completeness check AC4 requires cross-verifying against. `compute_drift_report()` (61-121), `compute_tool_count_drift_report()` (124-167 — groups `tools.jsonl` by `(run_id, seq)`, the same join key the new `tools` table must support efficiently), `compute_multi_invocation_collision_report()` (170-193 — detects duplicate `phase="Scope", seq=1` per `run_id`, the exact signature `TCK-20260728-MONITORING-PAUSE-RESUME-SEQ-COLLISION` fixed).

**`tools/agent-monitoring/vocabulary.py`** (95 lines) — `CANONICAL_TIERS`, `WORKFLOW_PHASES`, `WORKFLOW_AGENTS`, `WORKFLOW_AGENT_PREFIXES`, `infer_workflow()`, `is_known_agent()`. Already the single source of truth imported by both `validate.py` and `generate_retro.py`; its own docstring (lines 4-7) states "Do not duplicate these sets elsewhere," enforced by `tests/tools/test_validate_agent_monitoring.py::test_canonical_vocabulary_single_sourced`. `build_index.py` must import from here too.

**`tools/knowledge_search.py`** (the named structural precedent) — `cmd_build()` (622-745): unconditional full rebuild (`if db_path.exists(): db_path.unlink()` at 675-676, fresh `sqlite3.connect()`, `CREATE TABLE`, bulk `INSERT`, single `conn.commit()`/`close()`). `cmd_build_incremental()` (748-937) exists for this module but the idea doc explicitly says **not** to copy that machinery for `build_index.py` (see Anti-Drift Hazards). `Makefile:282-286` (`knowledge-index:` target) resolves the Python interpreter across both known dev machines via a shell fallback chain (`.venv/bin/python3`, `/home/vboxuser/Work/venv/bin/python3`, `python3`) before invoking the build — `build_index.py`'s new Make target should follow the identical interpreter-fallback shape for portability. `.gitignore:264` (`knowledge-index/`) ignores a whole directory, not a single file inside a tracked directory — this is the pattern to mirror, not a bespoke single-file ignore inside the tracked `agent-monitoring/` dir.

**Live data-shape audit (performed directly against this checkout, not assumed from docs):**
- `runs.jsonl`: 715 lines, **60 distinct top-level key-sets** — materially more than schema.md's "5+ historical schema generations" framing suggests literally, though most of the 60 are additive/optional-field variants (`files_changed`, `notes`, `summary`, `phases_completed`, etc.) layered on top of the same small number of *terminal-status* vocabularies `_resolve_status()`/`LEGACY_COMPLETION_FIELDS` already normalize. The load-bearing dimension is which key carries the terminal signal (`end_ts` / `final_status` / `status` / `finished_at` / `completed_at` / `ts_end` / bespoke pairs like `ts_start`/`ts_end`/`result`), not the full 60-way key-set cross-product.
- `events.jsonl`: 3,773 lines, 39 distinct key-sets — dominated by the 6 current-schema shapes (with/without `tool_call_count`/`cost_proxy_score`/`reason_code`) plus a legacy `event`+`detail` shape (`_is_legacy_event()`'s target).
- `tools.jsonl`: 67,763 lines, only 6 distinct key-sets — but **3 of those 6 are singleton (count=1) records that are not real per-tool-call records at all**:
  - `{"tool":"implement-epic","last_run":"2026-06-28T04:10:00Z","result":"DONE 1/6; ...","tickets":[...]}`
  - `{"run_id":"TCK-20260628-SIMQ-E1-FOUNDATION","ts":"...","tools_used":["Read","Write","Edit","Bash"],"files_written":20,"files_modified":1,"tests_run":54,"tests_passed":54}`
  - `{"session_id":"...","run_id":"TCK-20260716-SIMQ-URBAN-POLITICAL-FULL-PILLAR-SWEEP","seq":4,"ts":"2026-07-16T12:06:04"}` (no `tool` key at all)

  These are off-schema artifacts (plausibly a manual/legacy write path, not the current `post_tool_hook.py`) that will break any strict `tool` `NOT NULL` column or a normalizer that assumes `tool` is always a real tool name. This is a **new finding, not previously documented** in `docs/agent-monitoring/schema.md`'s Known Limitations section and not covered by any existing test.

## Mechanics / Engine Constraints

This is not simulation-mechanics work. `docs/agent-monitoring/README.md:13` states the scope explicitly: "Claude Code agents only ... Not the RPG simulation engine's Grafana/Loki/Prometheus stack." No `docs/mechanics/` chapter or `docs/engine/` contract applies to `tools/agent-monitoring/`.

The one binding constraint is CLAUDE.md's Hard Rule: *"Every implement-ticket workflow run ... must record a run entry and at least one event entry to `agent-monitoring/`. Monitoring write failure must never fail the workflow."* The idea doc's own design (`docs/plans/agent_infrastructure/idea_agent_monitoring_derived_index.md:40`) is built explicitly around never touching the write path (`pre_tool_hook.py`/`post_tool_hook.py`/`writeSidecar`/`writeMonitoring`) for exactly this reason — a DB write/lock is harder to guarantee "never blocks the workflow" for than a bare file append. The ticket's Out of Scope section already encodes this; the investigation confirms no file in the ticket's Related Code Areas touches the write path, and `build_index.py` must not add any such coupling.

## Risks and Open Questions

1. **DB file location is undecided** — no existing code or doc names one, and it is not listed among the ticket's own "Assumptions/Open Questions." Recommend mirroring `knowledge-index/knowledge.db`'s whole-directory gitignore pattern (a new top-level `agent-monitoring-index/` directory, e.g. `agent-monitoring-index/monitoring.db`) rather than a single gitignored file inside the tracked `agent-monitoring/` directory — this is the only existing derived-index precedent in the repo. Left as a Plan-phase decision, not resolved here.
2. `resolved_status` as a build-time SQL column/view vs. a Python helper run once at build time (idea doc's own first Open Question) — still unresolved; Plan's call, not blocking Investigation.
3. Make target vs. CLI subcommand (idea doc's second Open Question) — **already resolved for this specific ticket**: Scope explicitly says "Add a single new Make target `agent-monitoring-index`," even though the idea doc leaves the general question open.
4. AC2 ("byte-identical before/after, verified by hash comparison") requires `build_index.py` to open all 3 JSONL files strictly read-only and never re-serialize/write back to them — including for the 3 off-schema `tools.jsonl` records found above. Those must be skipped/logged, never "corrected in place."
5. AC5 ("byte-identical or row-count-identical ... both times") — SQLite files produced from identical logical content are **not guaranteed byte-identical** across separate writes (page ordering/freelist bookkeeping can differ even with `VACUUM` unless a deterministic write order and no incidental metadata like build timestamps are used). Recommend the test assert **row-count-identical** per table (the weaker, always-achievable form AC5 itself offers as an alternative), not byte-identical file hashes, unless `build_index.py` is deliberately written to guarantee deterministic page layout (extra design cost not currently justified).
6. The 3 off-schema `tools.jsonl` records are a genuinely new finding (not in `schema.md`'s Known Limitations, no existing test). Plan should decide: silently skip-and-count vs. surface a build-time warning (mirrors `validate.py`'s existing `WARNING:`-to-stderr convention at `validate.py:207` for malformed JSON lines).
7. Whether the `events` table needs a surrogate primary key (`rowid`) instead of `(run_id, seq)` as a natural/unique key, given the pause/resume collision precedent above proves `(run_id, seq)` duplication exists in live historical data.
8. `runs.jsonl`'s newer `provider`/`execution_id`/`ticket_id`/`identity_provenance` fields (added at the dashboard API/Pydantic layer per INFRA-274/parity entry for `TCK-20260721-MONITORING-WRITER-UNIFICATION`) are **not yet present in any live `runs.jsonl` record** (`grep -c '"execution_id"' agent-monitoring/runs.jsonl` → 0 of 715). No `runs` table column is required for them yet, but Plan should note the schema may need forward-compatible columns once writer.py starts emitting them (out of scope now — flagged for awareness only).

## Anti-Drift Hazards

- Do not re-derive phase/agent/tier vocabulary inline — `vocabulary.py` is already the single source of truth with its own anti-drift test (`test_canonical_vocabulary_single_sourced`); `build_index.py` must import from it exactly like `validate.py`/`generate_retro.py` do.
- Do not silently "fix," reorder, or drop-and-rewrite the 3 off-schema `tools.jsonl` records in place — the source JSONL files must remain byte-identical (AC2); any normalization/exclusion happens only in the SQLite output, never the source.
- Do not implement incremental-build logic — the idea doc explicitly rejects this as introducing "a second surface for exactly the kind of subtle staleness bug this session's two tickets were both about." Full rebuild only, every time, per the ticket's own Scope.
- Do not add a hook-triggered or automatic build — the idea doc's last Open Question frames this as "should stay strictly on-demand," and the ticket's Out of Scope explicitly excludes "Automatic or hook-triggered index builds."
- Do not migrate `query.py`/`validate.py`/`generate_retro.py` to consume the new index in this ticket — three sibling tickets exist specifically for that (`TCK-20260713-MONITORING-QUERY-INDEX-MIGRATE` / `-VALIDATE-INDEX-MIGRATE` / `-RETRO-INDEX-MIGRATE`), each explicitly blocked on this one per `tickets/todos/agent-monitoring-derived-index/SEQUENCE.md`.
- Do not change `record_run.py`/`record_events.py`/`pre_tool_hook.py`/`post_tool_hook.py`/`writer.py` — the write path is explicitly frozen by this ticket's Out of Scope and by CLAUDE.md's monitoring-write-never-fails hard rule.
- Do not invent new terminal-status normalization beyond what `validate.py`'s `LEGACY_TERMINAL_STATUS_VALUES` already encodes (e.g. further casing/spelling folding) — `schema.md`'s Historical Corrections section documents that casing drift was already deliberately, narrowly, one-time-fixed by `TCK-20260718-STATUS-DRIFT-REPAIR`; `resolved_status` should reuse the existing allowlist as-is, per AC3/AC4's own wording ("agrees with ... existing `_resolve_status()` output," "consistent with ... existing allowlists" — not "improves on").
