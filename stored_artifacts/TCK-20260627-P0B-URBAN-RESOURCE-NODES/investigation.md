# Investigation — TCK-20260627-P0B-URBAN-RESOURCE-NODES

## Root Cause

`urban_political` compiles to `resource_node_count: 0` because none of the four modules
it references (`frontier_village_core`, `trading_company_hub`, `bandit_road_trade_pressure`,
`hero_adventurers`) declare any `resource_recipes`.

Confirmed via `data/worlds/urban_political/world_compile_report.json`:
```json
{"resource_node_count": 0}
```

And `data/worlds/urban_political/resolved/world.resolved.yaml` contains:
```yaml
resources: []
```

## Two Compilation Paths

The `urban_political` world uses `schema_version: worldcomposition.v1`. There are TWO
separate files:

| File | Used by |
|---|---|
| `data/worlds/urban_political/world.yaml` | `make world-resolve` / `make world-compile` |
| `data/content/world_compositions/urban_political.yaml` | Integration tests (live-assemble) |

The CLI path (`make world-compile WORLD=urban_political`) reads from
`data/worlds/urban_political/resolved/world.resolved.yaml`, which was generated by
`make world-resolve`. Tests assemble `data/content/world_compositions/urban_political.yaml`
directly via `WorldAssemblyResolver`.

## Resource Assembly Pipeline

Resources flow through the WorldAssemblyResolver in two ways per module:

1. **`resource_recipes: List[ResourceRecipeSpec]`** (v1, explicit) — each entry has
   `resource_type`, `count`, `region`. Resolver applies namespace prefix to region.
   Validates resource type against catalog via `ResourceResolver.resolve(res.resource_type)`.

2. **`resources: Dict[str, int]`** (count-map) — uses the module's first region as
   `default_region`. Resolves each entry by catalog ID.

The WorldAssemblyValidator validates each module in isolation via a `dummy_spec` containing
only that module's declared regions. The rule "resource node region doesn't exist"
(line 111–130, `validator.py`) is ERROR-level and blocks assembly if a resource recipe
references a region not in the same module. Therefore, resource_recipes must reference
regions declared by the **same module**.

## Valid Catalog Resource IDs

From `data/content/world/resources.yaml` (indexed by `id`):

| Catalog ID | resource_type field | Preferred Biomes |
|---|---|---|
| `wood_node` | `wood` | frontier_village, near_forest |
| `herb_patch` | `herb` | near_forest, sunken_swamp |
| `iron_vein` | `iron_ore` | old_mine |

Resource catalog IDs (not `resource_type` values) must be used in module `resource_type`
fields when going through the resolver path. This is confirmed by `dungeon_crawl` resolved
output: `resource_type: iron_vein` (catalog ID).

## Module–Region Mapping

| Module | Namespace in urban_political | Regions Defined | Assembled Region ID |
|---|---|---|---|
| `frontier_village_core` | (none) | `hometown` | `hometown` |
| `trading_company_hub` | `trading` | `hometown` | `trading_hometown` |
| `bandit_road_trade_pressure` | (none) | `bandit_road` | `bandit_road` |
| `hero_adventurers` | (none) | (none) | — |

## Chosen Fix

Add `resource_recipes` to two existing modules that define their own regions:

- **`frontier_village_core`**: `wood_node` (8 charges, hometown) + `herb_patch` (5 charges, hometown)
- **`trading_company_hub`**: `iron_vein` (6 charges, hometown → prefixed to `trading_hometown`)

This gives ≥3 resource nodes for urban_political after resolve+compile.

Side effect: other compositions using `frontier_village_core` (`frontier_extended`,
`frontier_living_world`, `generated_frontier_3_42`, `swamp_border_world`) will also
gain wood/herb nodes. No existing test asserts `resource_node_count == 0` for those
worlds; the "zero resource nodes" rule is a WARNING not an ERROR — adding resources
is strictly an improvement.
