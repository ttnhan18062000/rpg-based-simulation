# Implementation Plan — TCK-20260814-KGMCP-MEASUREMENT-BASELINE

## Summary

This ticket delivers Knowledge Gateway MCP Phase 0's final three §20 checklist bullets: a fixed,
versioned representative-query corpus with a real recorded direct-tool baseline, a 5-point latency
instrumentation contract, and baseline-derived promotion thresholds — plus §18.1's repeated-demand
design. Per the Design Decision below, this is **not** pure-documentation like the two sibling
KGMCP tickets: it adds two small, real, testable Python artifacts under
`tools/agent-monitoring/` (a corpus-definition module and a one-time corpus-runner script) because
AC3 ("recorded from a real run, not an estimate") and AC7 ("tests mirror
`test_retrieval_baseline_metrics.py`'s never-silent, derivation-string convention") are both
code-level requirements that cannot be satisfied by prose alone. The corpus itself is minimal by
design — exactly 7 queries, one per §8 routing shape, with 5 of the 7 also carrying one of the 5
§22 use-case tags — so no query is padding and every AC2 coverage requirement is met with the
smallest defensible corpus. Everything downstream (the instrumentation contract, the threshold
predeclaration, the repeated-demand design) is a `docs/engine/contracts/knowledge_gateway_mcp/`
prose artifact, matching the sibling tickets' contract-doc shape, but each numeric claim in it must
trace back to a field in the Step 2 fixture — never a free-floating number.

**Correction to `investigation.md`:** investigation.md's §3 cites `tools/agent-monitoring/
manifest.py` as "the existing, proven pattern" for `time.perf_counter()`-based latency
instrumentation. Direct read of `manifest.py` during Plan found **zero** occurrences of
`perf_counter`, `latency_ms`, or a "Wrapper" class/pattern — that citation is wrong. The real,
verified, and far more directly relevant precedent is `tools/retrieval_events.py`, which already
implements three live (if not-yet-wired-in) `time.perf_counter()`-timed Wrapper functions —
`wrap_hybrid_retrieval()` (`:154-212`, timing at `:175/177`), `wrap_retrieval_cache_check()`
(`:223-288`, timing at `:259/261`), and `wrap_context_packet_assembly()` (`:299-352`, timing at
`:324/326`) — each emitting a real `latency_ms` field into `agent-monitoring/events.jsonl` via
`emit_retrieval_event()`. Per this ticket's own Fact-Verification Requirements, Step 3 below cites
`retrieval_events.py`, not `manifest.py`.

## Design Decision

**Code + docs, not docs-only.** Concretely:

- `tools/agent-monitoring/kgmcp_baseline_corpus.py` — real, importable Python module. Defines the
  corpus as data (7 entries) plus the `kgmcp_char_heuristic_v1_token_count()` helper (a pure
  function implementing the already-frozen formula from
  `docs/engine/contracts/knowledge_gateway_mcp/redaction_retention_policy.md:147-149`). No live
  tool calls happen inside this module — it is fast, deterministic, and safe to import in every
  test run.
- `tools/agent-monitoring/kgmcp_baseline_runner.py` — a real script, run **once** during
  Implementation (not part of the fast pytest loop, not wired into `generate_retro.py`'s recurring
  cadence), that makes real `tools/search_mcp.py::_run_search()` calls and real `graphify query`
  subprocess calls against each of the 7 corpus queries, times each with `time.perf_counter()`
  (mirroring `retrieval_events.py`'s exact pattern), computes a token estimate via
  `kgmcp_char_heuristic_v1_token_count()`, and writes the result to a **committed** fixture file,
  `tests/tools/fixtures/kgmcp_measurement_baseline_corpus_results.json`. This fixture — not a
  re-run of live calls on every CI invocation — is the "recorded direct-tool baseline... from a
  real run" artifact AC3 requires. It is pinned (git-committed), not regenerated by the test suite.
- Tests read the committed fixture structurally (mirroring
  `test_retrieval_baseline_metrics.py`'s never-silent/derivation-string/real-corpus-plausibility
  conventions) plus **exactly one** live re-invocation of a single corpus query, matching
  `test_plan.md`'s own guidance to scope live re-runs to "whichever queries are safe/cheap enough"
  rather than re-running all 7 on every `pytest` invocation (which would be slow and reintroduce
  embedding-model nondeterminism risk into CI).
- The 5-latency-point contract, the threshold predeclaration, and the repeated-demand design remain
  pure `docs/engine/contracts/knowledge_gateway_mcp/` prose — exactly the sibling tickets' shape —
  because §20's own wording is "define separate measurement," not "measure them" (no gateway exists
  to attach live instrumentation to yet; investigation.md §3, confirmed above).

**Consequence for the parity ledger:** because this ticket adds real code under
`tools/agent-monitoring/` (unlike the two sibling KGMCP tickets, which added zero code), the
`INFRA-281`-through-`INFRA-333` "agent-tooling-infrastructure precedent for ledgering this class of
change" (`docs/parity_ledger/infrastructure.yaml:6355`, `INFRA-292`'s own text) applies here too.
Step 7 adds a new entry, `INFRA-334` (the next free ID — `infrastructure.yaml`'s highest existing ID
is `INFRA-333`, confirmed by direct grep during Plan).

No `## Unresolved Questions` section follows — every open question investigation.md raised is
resolved above or within its owning step.

### Step 2 — Corpus-runner script and real recorded baseline (the "real run")
**Files:** `tools/agent-monitoring/kgmcp_baseline_runner.py` (new),
`tests/tools/fixtures/kgmcp_measurement_baseline_corpus_results.json` (new, generated by running
the script once)

**Change:** Create a script that imports `CORPUS` and `kgmcp_char_heuristic_v1_token_count` from
Step 1's module, and for each of the 7 entries:
1. Calls `tools/search_mcp.py::_run_search(query_text, top_k=8)` directly (verified callable,
   `tools/search_mcp.py:82-84`; returns `list[dict]` of `{doc_id, title, heading, source_path,
   section, score, semantic_score, keyword_score, excerpt}` per `:129-141`, or an error dict per
   `:86`/`:96`), wrapped in `start = time.perf_counter(); ...; latency_ms = (time.perf_counter() -
   start) * 1000` — the exact pattern at `tools/retrieval_events.py:175-177`. Records
   `context_search.latency_ms`, `context_search.tool_call_count = 1`,
   `context_search.results_count`, `context_search.sources_recalled` (the `doc_id` list).
2. Shells out to `graphify query "<query_text>"` via `subprocess.run`, timed the same way. Graphify
   is confirmed CLI-shelled with no in-process adapter
   (`docs/engine/contracts/knowledge_gateway_mcp_contract.md:33-38`, Design Decision D1). Records
   `graphify.latency_ms`, `graphify.tool_call_count = 1`, `graphify.raw_stdout_bytes`.
3. Computes `combined.wall_time_ms = context_search.latency_ms + graphify.latency_ms`,
   `combined.tool_call_count = 2`, and
   `combined.serialized_tokens_estimate = kgmcp_char_heuristic_v1_token_count(json.dumps(context_search_results) + graphify_raw_stdout)`.
4. On entry `Q3_requirement_completeness`, adds a `notes` field disclosing that §8's row 3 lists
   Parity Ledger as primary provider but no callable Parity Ledger adapter exists yet
   (`docs/plans/knowledge-gateway-mcp-proposal.md` §20's own Phase-4 gating: "Parity Ledger is not
   required until Phase 4"), so this entry's direct-tool baseline is Context Search + Graphify
   only — an honest substitution, not a silent omission.
5. Every per-entry record and the top-level report carry a `derivation` string, matching the
   never-silent convention (`build_search_count_section`'s own `derivation` field,
   `generate_retro.py:364-374`, is the pattern to mirror).
6. Writes `{"corpus_version": 1, "recorded_at_utc": <ISO8601>, "entries": [...]}` to
   `tests/tools/fixtures/kgmcp_measurement_baseline_corpus_results.json`.
7. **Other writers to consider:** this script writes to a brand-new fixture path under
   `tests/tools/fixtures/` — no other code in this repo writes to that specific file today (grep
   during Plan confirmed no existing reference to `kgmcp_measurement_baseline_corpus_results.json`).
   It must **not** write into `agent-monitoring/runs.jsonl`/`events.jsonl`/`tools.jsonl` — `_run_search`
   is called directly (not through `wrap_hybrid_retrieval`/`wrap_retrieval_cache_check`, which are
   the only functions in this repo that call `emit_retrieval_event()`), so no event-writer path is
   invoked; the `graphify` subprocess call is a plain CLI invocation with no monitoring side effect.
   The implementer must run `git status --porcelain -- agent-monitoring/` before and after running
   this script once by hand and confirm the diff is empty, before committing the fixture.

**Do NOT touch:** `tools/retrieval_events.py`, `tools/retrieval_cache.py`,
`tools/hybrid_retrieval.py`, `tools/context_packet_assembler.py`, `tools/search_mcp.py` — all are
read/imported/subprocessed, never edited (Out of Scope: "no wiring into a live gateway").

**Verify:** `test_corpus_baseline_entries_have_real_measured_fields_never_estimated`,
`test_corpus_baseline_wall_time_and_tool_call_count_are_plausible`,
`test_zero_mutation_of_real_agent_monitoring_corpus`.

### Step 3 — Measurement-point instrumentation contract
**Files:** `docs/engine/contracts/knowledge_gateway_mcp/measurement_baseline_contract.md` (new,
§1–§3 in this step)

**Change:** Write §1 (corpus summary, referencing Step 1's module by name/path, not duplicating the
query text as a second source of truth) and §2 (the 5 latency measurement points). For each of
lookup, evidence-validation, provider-fallback, packet-assembly, end-to-end, document: meaning,
unit (ms), attachment point, and live-precedent status:
- **Lookup latency** — attaches where a future gateway's cache-lookup step would sit; closest real
  precedent today is `wrap_retrieval_cache_check()` (`tools/retrieval_events.py:223-288`, timing at
  `:259-261`), which already times `check_index_cache`/`check_query_cache`/`check_packet_cache`
  (`tools/retrieval_cache.py:204`, `:266`, `:335`). **Caveat, cited from
  `evidence_cache_identity_contract.md:100-121`'s Non-collapse rule:** that existing wrapper's
  single `latency_ms` blends lookup and any incidental validity bookkeeping the `check_*_cache`
  functions do internally — once a real evidence-validity step exists (§2 below), lookup latency
  must be re-measured as lookup-only, not reused verbatim from this wrapper's current number.
- **Evidence-validation latency** — no existing wrapper in this repo performs a validity check
  disjoint from lookup (confirmed: none of `check_index_cache`/`check_query_cache`/
  `check_packet_cache` returns a `freshness`/`verification` field,
  `evidence_cache_identity_contract.md:112-118`). This measurement point is a pure definition today
  — no live number exists, and none is fabricated.
- **Provider-fallback latency** — no existing wrapper; the concept (falling back to
  `PROVIDER_GENERATION`, `evidence_cache_identity_contract.md:124-139`) has no timed call site yet.
  Pure definition.
- **Packet-assembly latency** — direct precedent: `wrap_context_packet_assembly()`
  (`tools/retrieval_events.py:299-352`, timing at `:324-326`), which already times
  `assemble_context_packet()` end to end.
- **End-to-end latency** — defined as the sum of whichever of the above four actually execute for a
  given request (a cache-hit path skips provider-fallback; a cache-miss path includes it) — never a
  6th independently-measured number. State this reconciliation rule explicitly, since §18 lists it
  as one of 7 total metrics without stating the composition rule itself.

Also add a subsection explicitly distinguishing the Step 2 fixture's `combined.wall_time_ms` (real,
direct-tool, no-gateway-exists baseline) from this §2's future gateway "end-to-end latency"
measurement point — they are not the same number and must never be presented as if they were
(the anti-drift hazard investigation.md's Risk #4 and Anti-Drift Hazards section both name).

**Do NOT touch:** `docs/engine/contracts/knowledge_gateway_mcp/evidence_cache_identity_contract.md`
or `shared_enums.schema.json` — reference their frozen freshness/verification enums and Non-collapse
rule by citation only, never redefine them (mirrors that document's own §2 "Enum cross-reference,
not redefinition" rule).

**Verify:** `test_measurement_baseline_contract_defines_all_5_latency_points`.

### Step 4 — Baseline-derived promotion thresholds
**Files:** `docs/engine/contracts/knowledge_gateway_mcp/measurement_baseline_contract.md` (§4, this
step; appended after Step 3's §1-3 and after Step 2's fixture exists)

**Change:** Write §4, "Predeclared Promotion Thresholds." Each threshold must be a formula
referencing a named field from the Step 2 fixture (`tests/tools/fixtures/
kgmcp_measurement_baseline_corpus_results.json`) — **never a literal number invented independently
of that fixture**, per investigation.md Risk #4 and §20's explicit "does not invent numeric
thresholds before the baseline exists" instruction. At minimum:
- **Minimum latency threshold:** the future gateway's warm-hit end-to-end latency (§3's
  measurement-point definition) must not exceed some fraction (e.g. 50%) of the corpus-wide average
  of `combined.wall_time_ms` across all 7 fixture entries — state the fraction as a policy choice,
  and compute the actual millisecond figure directly from the fixture once it exists, citing the
  fixture path and the specific averaged value, not a number typed by hand.
- **Minimum token-reduction threshold:** the future gateway's packet token count (via
  `kgmcp_char_heuristic_v1`) must be some fraction lower than the corpus-wide average of
  `combined.serialized_tokens_estimate` — same sourcing rule.
- **No-regression-recall threshold:** the future gateway's `sources_recalled` set for a given query
  must be a superset of (or equal to) the fixture's `context_search.sources_recalled` +
  `graphify` sources for that same query — recall must never regress below the direct-tool
  baseline's own recall, per query, not only in aggregate.

Because this step's numeric thresholds are literally computed from Step 2's fixture, this step
cannot be written correctly until Step 2's fixture is committed (see Dependency Map).

**Do NOT touch:** No numeric threshold may reference `docs/plans/knowledge-gateway-mcp-proposal.md`
§21's Phase 3 pilot acceptance criteria as if it were this baseline — §21 is a separate, later-phase
acceptance bar this document only cross-references, never restates as its own threshold.

## Deviations (recorded during Implementation)

1. **Step 6's `test_zero_mutation_of_real_agent_monitoring_corpus` calls `run_corpus()` in-process,
   not `main()` via subprocess**, contrary to this plan's literal wording ("git-porcelain
   before/after running `kgmcp_baseline_runner.py`'s `main()` once"). Reason: `main()` overwrites
   the committed fixture with fresh `latency_ms`/`wall_time_ms` figures on every invocation — this
   is unavoidable, since real network/CPU call timing is not reproducible — which directly
   contradicts this same plan's Step 2 point 6 ("It is pinned (git-committed), not regenerated by
   the test suite"). Confirmed empirically during Implementation: running `main()` a second time
   changed the fixture's corpus-wide average `combined.wall_time_ms` from 1956.161 ms to 1741.182
   ms, which would have made any test asserting an exact literal number against the doc's §4 text
   flaky by construction. `run_corpus()` (a function Step 2's own script design already separates
   from `main()`'s file-write step) exercises the identical live `_run_context_search`/
   `_run_graphify` call path against all 7 corpus entries, so the zero-agent-monitoring-mutation
   proof this test exists to make is unaffected — only the fixture-file-write side effect (which
   this specific test does not need to exercise) is skipped. The one-time-by-hand fixture recording
   this plan's Step 2 describes was still performed exactly as written, twice, with
   `git status --porcelain -- agent-monitoring/` confirmed identical before/after each run.

2. **`test_predeclared_thresholds_cite_recorded_baseline_numbers` was scoped down to this plan's
   AC5 spec** (assert the literal fixture path string is present in §4's prose) rather than an
   exact-numeric-match assertion the implementer initially over-specified. The over-specified
   version was itself broken by Deviation 1's same non-reproducible-timing property (the doc's
   hand-typed average would drift out of sync with whatever `run_corpus()` last computed
   in-memory during a test run) — reverting to the plan's actual literal spec fixed this and better
   matches AC5's own stated purpose ("structural proof the section is fixture-derived, not
   free-floating"), not a numeric-equality proof.

Neither deviation changes what the contract doc's §4 thresholds mean or how they are computed —
both are test-methodology corrections responding to the same underlying, previously-unstated fact
(real recorded timing is not exactly reproducible across runs), discovered only once the runner
script was actually executed more than once during Implementation.
