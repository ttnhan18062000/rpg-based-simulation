Three `PreToolUse` matchers and three `PostToolUse` matchers, all wired to shell commands:

- `PreToolUse` `Bash` → inline case-statement on `$CMD` for `grep|rg|find|fd|ack|ag` → emits `additionalContext` only (the context-scan nudge, explicitly Out of Scope for this ticket).

- `PostToolUse` `*` → `tools/agent-monitoring/retro_nudge_hook.py` (advisory nudge to run the retro skill after 5+ DONE runs since the last dated retro; read in full — never blocks, `sys.exit(0)` on cooldown, wrapped in `except Exception: pass`).

**None of these six hook entries implement, or have any code path capable of implementing, either of the two cases this ticket must hard-block** (missing agent-monitoring write at Finalize; missing parity-ledger touch on a mapped `src/` change). This confirms the ticket's own framing that literally reading `.claude/settings.json` shows only advisory nudges — but see the critical correction below: **the actual mechanism for cases (a) and (b) does not live in `.claude/settings.json` hooks at all.** It lives in the `implement-ticket.js` orchestrator, which computes the relevant checks already but currently discards or defers their results. `.claude/settings.json` is therefore not the primary file to change — it was listed in the ticket's Related Code Areas but the real leverage point is `.claude/workflows/implement-ticket.js`, which is **not** listed there. This is the single most important correction from this investigation.

### Case (b) — parity cross-reference — ALREADY COMPUTED, DELIBERATELY NOT ENFORCED
`tools/gate_checks/parity_updater_static.py::cross_reference_touched` (lines 81-119) already implements the exact check this ticket's Scope item (b) asks for: given `files_changed` and the `git status --porcelain -- docs/parity_ledger/` output, it returns `PASS`/`FAIL`/`NA` per `src/` file against its expected ledger subsystem(s) (ANY-of-candidates semantics).

It is already wired into `implement-ticket.js`'s Parity phase (lines 829-847): `crossRefOutput` is computed via `bash()` immediately after the `parity-updater` agent call returns, `parityCrossRefFailures` is derived — **and then discarded**. Line 849-854:
```js
const parityEvidence = (parityCrossRef === null || parityCrossRefFailures.length > 0)
  ? (parity.summary || 'Parity ledger updated').slice(0, 150) + ' | cross-ref: ' + (...)
  : (parity.summary || 'Parity ledger updated')
pushEvent('Parity', 'parity-updater', 'ok', parityEvidence, parity.ts)
```
The `pushEvent` status is the **hardcoded literal `'ok'`** regardless of `parityCrossRefFailures.length`. A `FAIL` result only changes the *text* of the evidence string; it never changes control flow, never returns early, and the phase has no verdict enum at all today.

**This is not an oversight — it was an explicit, architecture-review-confirmed design decision** in the sibling ticket `TCK-20260705-GATE-DET-PARITY-UPDATER` (`stored_artifacts/TCK-20260705-GATE-DET-PARITY-UPDATER/plan.md` lines 41, 222-227, 319-320, 376-377): *"No new blocking status for Parity... a flagged miss is visibility-only, never a pipeline halt... Do not add a new blocking verdict/status enum to Parity — no AC asks for a new gate."* This ticket's Scope item (b) directly asks to reverse that decision. That reversal is in-scope per this ticket's own text (Related Tickets explicitly names `GATE-DET-PARITY-UPDATER` as prior art to build on, not a decision to leave standing), but the Plan phase must treat it as **overturning a documented prior decision**, not just "finishing" unstarted work — cite this investigation's finding when doing so, so a future reader doesn't think the reversal was accidental.

### Case (a) — agent-monitoring write verification — DOES NOT EXIST AT ALL
No static check anywhere verifies that `agent-monitoring/runs.jsonl` / `events.jsonl` actually received an entry for the finalizing ticket. The relevant code path in `implement-ticket.js`:
- `writeMonitoring(finalStatus)` (lines 189-239) is an `agent()` call — the monitoring write is itself performed by an LLM agent turn running `record_events.py`/`record_run.py`. If that agent call returns `null`, the orchestrator only logs `'WARNING: agent-monitoring write agent returned null (non-fatal)'` (line 237) and continues.
- `writeMonitoring('DONE')` is called at line 1099, **after** the Finalize agent call has already moved the ticket file to `tickets/done/` and after Part B's `run_finalize_selfcheck` (lines 1050-1096, from `done_checker_static.py::run_finalize_selfcheck`) has already passed and the workflow has already committed to *not* returning `FINALIZE_INCOMPLETE`.
- The subsequent `return { status: 'DONE', ... }` (line 1101) happens unconditionally after `writeMonitoring('DONE')` — its result is never inspected.

**Structural consequence for Plan phase:** by the time a monitoring-write verification could run, the ticket has *already* moved to `tickets/done/` and staging artifacts have *already* migrated to `stored_artifacts/`. A "hard block" here cannot prevent the finalize-file-move the way `FINALIZE_INCOMPLETE` currently prevents it (Part B's self-check runs *before* the move is deemed complete-and-final in the return path). Closing this gap correctly requires re-ordering: either (1) call `writeMonitoring` *before* Part B's self-check and add a 4th Part-B-style check that verifies the write landed (`runs.jsonl` has a row with `run_id == tid` and matching `final_status`; `events.jsonl` has at least one row with `run_id == tid`), gating the existing `FINALIZE_INCOMPLETE` return on it too — or (2) accept and explicitly document that this particular hard block is necessarily post-hoc (ticket already in `tickets/done/`, remediation-only) and pick a status accordingly. This is a genuine open question for Plan, not a detail to improvise during Implement — flagged below.

Also note the Hard Rule in `CLAUDE.md`: *"Monitoring write failure must never fail the workflow."* The verification check described above does **not** conflict with this rule if scoped correctly: the *write attempt* itself must stay resilient/non-fatal (mirrors `writeMonitoring`'s own `WARNING ... non-fatal` framing), but a **separate, subsequent static verification** that the write's *effect* landed is a different thing — the same pattern `run_finalize_selfcheck` already uses for the Finalize agent's file-move steps (the move itself isn't "made fatal"; a downstream self-check inspects whether it worked). Plan must state this distinction explicitly so Implement doesn't mistakenly make the `writeMonitoring` agent call itself raise/block, which would violate the Hard Rule.

## Risks and Open Questions

1. **[BLOCKS PLAN] Failure-vocabulary decision for case (b) is not free — it reverses an architecture-reviewed decision.** The ticket AC says "no new status string introduced unless Investigate finds concrete evidence that's wrong" — this investigation finds exactly that: Parity currently has **no verdict enum of any kind** (unlike done-checker/architecture-reviewer, which already had `DOD_BLOCKED`/`NEEDS_CHANGES`/`BLOCKED` to reuse before their static backstops existed). Reusing an existing status here means borrowing one from a different phase (e.g. reusing `DOD_BLOCKED` even though Parity ≠ Verify), or introducing a new one following the `FINALIZE_INCOMPLETE` precedent (a phase-specific new status justified because that phase had none before). Plan must decide and justify explicitly — do not silently default to either option.

2. **[BLOCKS PLAN] Case (a)'s hard block cannot fire before the ticket already moved to `tickets/done/`, given current phase ordering.** See Current Behavior above. Plan must either reorder `writeMonitoring` to run before Part B's self-check (larger, riskier change touching an already-shipped, tested code path) or explicitly accept/document a post-hoc remediation-only block. Silently picking one without stating the tradeoff would contradict this ticket's own AC wording ("hard-blocked, not just nudged" implies preventing something, which is structurally harder for case (a) than case (b)).

3. **Does the Claude Code harness's `PreToolUse`/`PostToolUse` hook mechanism actually support blocking a tool call (vs. only injecting `additionalContext`)?** This investigation found **zero precedent anywhere in this repo** for a hook that denies/blocks (no `permissionDecision`, no documented exit-code-2 blocking pattern in any existing hook script or doc). This matters only if Plan chooses to implement either hard block as a literal `.claude/settings.json` hook (intercepting the `mv .../tickets/done/` Bash call, for instance) rather than as an orchestrator-level check inside `implement-ticket.js` (which is how every existing gate — `DOD_BLOCKED`, `FINALIZE_INCOMPLETE` — is actually implemented, via `return {status: ...}` early-exits, not via `.claude/settings.json` hook denial). Given that both existing precedents block via the JS orchestrator's own control flow, not via `.claude/settings.json`, Plan should default to that same mechanism unless there's a concrete reason both cases must fire outside `implement-ticket.js`-driven runs (e.g., a raw manual `git commit` outside the workflow) — flag this as a scoping question: does "hard block" need to catch manual/out-of-workflow commits too, or only implement-ticket.js-orchestrated runs? The ticket's Scope wording ("a commit touching...", "a ticket finalizing...") reads ambiguously between the two.

4. **`implement-epic.js` batch-loop compatibility.** `FINALIZE_INCOMPLETE` was previously confirmed (GATE-DET-DONE-CHECKER plan.md) to already work correctly with `implement-epic.js`'s `result.status !== 'DONE'` stop condition with zero code changes. If case (b)'s new/reused status is anything other than exactly `FINALIZE_INCOMPLETE`/`DOD_BLOCKED`, Plan should explicitly re-confirm (not assume) that `implement-epic.js`'s stop condition still catches it — likely trivially true since the condition is `!== 'DONE'`, but state it rather than silently relying on the prior ticket's confirmation for a different status string.

5. **Hotfix tier still runs Finalize** (per CLAUDE.md's tier-routing table: hotfix = "Scope → Implement → Test → Parity → Verify → Finalize"). Confirm both new hard blocks apply correctly under hotfix tier too (no staging-artifacts requirement, but `run_finalize_selfcheck`'s `tier == "hotfix"` branch already special-cases `check_migration_complete` to `NA` — a new monitoring-write check must decide independently whether it applies identically regardless of tier, since agent-monitoring write is mandatory "including hotfix" per CLAUDE.md's own Hard Rules).
