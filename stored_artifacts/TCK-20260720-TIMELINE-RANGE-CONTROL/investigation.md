### `src/api/agent_ops_dashboard/main.py` / `ingest.py` — real current `until` behavior (confirmed)
- `GET /api/runs` (`main.py:66-74`): params are `limit, offset, status, workflow, since` — **no `until` param, at the route level or in `DashboardCache.get_runs()`** (`ingest.py:630-665`, confirmed by full read — only a `since` lower-bound filter at line 654: `if since is not None and (summary.start_ts is None or summary.start_ts < since): continue`).
- `GET /api/runs/timeline` (`main.py:77-84`): params are `limit, offset, since, until` — **both bounds exist**, delegating to `DashboardCache.get_bulk_timeline(since=since, until=until, limit=limit, offset=offset)` (`ingest.py:737-770`).
- `get_bulk_timeline`'s exact lexical-comparison behavior (`ingest.py:757-760`):
  ```python
  if since is not None and (summary.start_ts is None or summary.start_ts < since):
      continue
  if until is not None and (summary.start_ts is None or summary.start_ts > until):
      continue
  ```
  Both bounds are pure string comparisons (`<` / `>`) against `summary.start_ts` — never parsed to `datetime`. A run with `start_ts is None` is excluded whenever *either* bound is set (short-circuit convention, symmetric between `since` and `until`). This is the exact convention the custom picker's ISO strings must be lexically compatible with (zero-padded `YYYY-MM-DDTHH:MM:SS.sssZ` or equivalent — see next section).
  The method's own docstring (`ingest.py:745-748`) explicitly says it deliberately duplicates `get_runs()`'s selection logic rather than calling it, because `get_runs()`'s `[offset:offset+limit]` slice happens before any `until` bound could be applied.
- **`GET /api/runs` has no `until` param today, full stop.** This is real, verified, not a documentation gap — `ingest.py:630-665`'s `get_runs()` method has no `until` parameter, no filter branch for it, nothing. Adding one would be new backend work.

### ISO 8601 / zero-padding convention (confirmed across both layers)
- Backend: `_coerce_ts()` (`ingest.py:212-219`) only normalizes legacy epoch-number values to `str(value)` — it does **not** reformat or re-derive ISO strings; whatever is already in `runs.jsonl`/`events.jsonl` (`start_ts`, `ts`, etc.) passes through as-is. The bounding comparison is purely lexical string comparison against whatever this produces.
- Frontend: every existing `sinceIso`/`nowIso` value in the codebase is produced via `new Date(...).toISOString()` (`ProgressTimelineView.tsx:20,21,27`; `mergeAndSortRuns`'s comparator at `api.ts:401-405` also does `.localeCompare()` on the same shape). `Date.prototype.toISOString()` always emits the canonical zero-padded `YYYY-MM-DDTHH:mm:ss.sssZ` form — this is the established, already-proven-compatible convention. Test fixtures (`useRunTimelinesPolling.test.ts:12`, `useRunsPolling.test.ts:30`) use the same shape (`'2026-07-16T10:00:00Z'`, `.padStart(2, '0')` for manual minute construction), confirming lexical-comparison compatibility is already relied on elsewhere.
- **Implication for the custom `<input type="datetime-local">` picker**: `datetime-local`'s value is *not* ISO-8601-with-timezone — it's `YYYY-MM-DDTHH:mm` (no seconds unless `step` is set, no `Z`/offset, and it represents the browser's *local* time, not UTC). Converting it to a UTC ISO string requires `new Date(inputValue).toISOString()` (browser interprets the naive local-time string in local timezone, then `.toISOString()` re-renders it as UTC with zero-padding) — this is a real conversion step the implementation must get right, not a pass-through. This is a genuine implementation detail Plan must specify explicitly (see Anti-Drift Hazards).

## Risks and Open Questions

1. **`useRunTimelinesPolling` signature change — confirmed necessary, shape not yet decided.** Current: `useRunTimelinesPolling(sinceIso: string, intervalMs = 5000)`. It must gain `until` support to satisfy AC #2. Options, none pre-selected by any doc read:
   - (a) Insert `untilIso` as a new 2nd positional param, shifting `intervalMs` to 3rd: `useRunTimelinesPolling(sinceIso, untilIso, intervalMs = 5000)`. Breaks every existing call site positionally (`ProgressTimelineView.tsx:23`, and both call sites in `useRunTimelinesPolling.test.ts` that pass `intervalMs` as the 2nd arg: `useRunTimelinesPolling('2026-07-15T00:00:00Z', 999_999_999)` — these would silently become `(sinceIso, untilIso=999999999_as_string...)` if not updated, a real regression hazard if any call site is missed).
   - (b) Accept an options object: `useRunTimelinesPolling(sinceIso, { untilIso, intervalMs })`. Cleaner but a bigger diff (touches call sites' shape, not just an inserted arg) and diverges from `useRunsPolling`'s existing plain-positional convention.
   - (c) Optional 3rd param after `intervalMs`, i.e. `useRunTimelinesPolling(sinceIso, intervalMs = 5000, untilIso?: string)` — preserves existing 2-arg call sites' behavior unchanged but puts an optional parameter after a defaulted one, which is legal in TS/JS but reads awkwardly and is inconsistent with `fetchRunTimelines`'s own params-object convention one layer down.
   This is a concrete decision Plan must make explicitly — flagging per this investigation's brief, not assuming an answer. Whichever shape is chosen must be applied **identically** to `useRunsPolling` if `useRunsPolling` is also extended (see next point), for consistency between the two sibling hooks.

2. **`useRunsPolling` / `GET /api/runs` has no `until` support at all today — this is a real scope decision, not a given.** The ticket's Scope explicitly only mentions wiring `sinceIso`/`untilIso` into `useRunTimelinesPolling` (bulk timeline fetch) and says nothing about `useRunsPolling` (drives `runs`, i.e. which run rows exist as y-axis categories). Consequences of leaving `useRunsPolling` `until`-unbounded:
   - `runs` (the y-axis category list) would be fetched with only a `sinceIso` lower bound and no upper bound, while `entriesByRun` (the segments) would be bounded to `[sinceIso, untilIso]`. For the *default* (no user interaction) case this is harmless since `untilIso` defaults to "now" and there's nothing later than "now" anyway. But for a **custom picker with `untilIso` in the past** (e.g., "show me last Tuesday"), `useRunsPolling` would still fetch runs all the way up to "now" — including runs that started *after* the selected `untilIso` window — while `entriesByRun` would have no data for those runs' segments (since bulk-timeline is bounded). Net effect: the chart would show y-axis rows for runs with no visible segments in the selected window, a real UX inconsistency.
   - Extending `useRunsPolling`/`GET /api/runs` with `until` is **not listed in this ticket's Scope or Related Code Areas**, and adding an `until` param to `GET /api/runs` is backend work `main.py`/`ingest.py`'s `get_runs()` currently has zero support for (confirmed above — no route param, no filter branch). This is arguably new backend scope beyond "wire the range-control into the fetch," which the ticket's own Out-of-Scope explicitly excludes ("Implementing the bulk endpoint's `until` param itself — this ticket only consumes it once available" — implying by extension that implementing a *new* `until` param on a *different* endpoint is equally out of scope, not implicitly included).
   - **Flagging as blocking for Plan, not assuming an answer**: either (i) extend `useRunsPolling`/`GET /api/runs` with `until` too, in scope, accepting it's backend + frontend work beyond the ticket's literal Related Code Areas list, or (ii) leave `useRunsPolling` `sinceIso`-only and accept the minor y-axis-row inconsistency described above as a known, documented limitation (candidate for `docs/guidelines/intentional_divergences.md` if so). This is exactly the kind of "vague lead stays vague until evidence narrows it" case the Uncertainty Rule covers — evidence narrows it to "there IS a real inconsistency risk," but not to which fix Plan should choose.

## Anti-Drift Hazards

- **Do not let the range-control's `sinceIso`/`untilIso` state influence or be influenced by `dataZoom`.** Both the ticket's Scope and this investigation confirm these are two independently-verified-separate layers today (`dataZoom` is 100% client-side, no `onEvents` handler exists for it). Any implementation that reads `dataZoom`'s current range to seed `untilIso`, or resets `dataZoom` when `sinceIso`/`untilIso` changes, is scope creep into "Any change to the chart's own client-side dataZoom behavior" (explicitly Out of Scope).
- **Do not touch `toChartOption.ts` or its `nowIso` parameter.** It's confirmed unrelated (drives only the live-segment trailing edge). A tempting-but-wrong move would be renaming/repurposing `nowIso` to also serve as a default `untilIso` — keep them as separate, independently-sourced values even if they'd often be equal.
- **Do not modify `RecentActivityGantt.tsx`/`TimeAxis.tsx`/`GanttBar.tsx`.** They are deleted; the ticket's own stale Related Code Areas list must not send an implementer looking for them.
- **Do not silently add an `until` param to `GET /api/runs`/`get_runs()`/`useRunsPolling` "just to be safe"** without an explicit Plan decision (see Open Question 2) — this is real backend scope beyond what's declared, and doing it unannounced would violate the "no important decision is undocumented" Definition-of-Done item.
- **Preserve the exact default-mount behavior**: `sinceIso = now - 24h`, `untilIso = now` — AC #3 requires bit-for-bit equivalent default windowing to today's `SINCE_WINDOW_MS = 24h` hardcode. A common drift risk here is computing the default preset duration inconsistently between the "1h/6h/24h/7d" preset button labeled "24h" and the initial-mount default — they must use the same constant/computation, not two independently-typed `24 * 60 * 60 * 1000` literals that could silently diverge.
- **Lexical string comparison, not `Date` comparison, governs backend bounding.** Any client-side pre-filtering or validation logic (e.g., "custom start must be before custom end") should not assume the backend does date-aware comparison — it's pure string `<`/`>`. As long as both bounds are well-formed zero-padded ISO-UTC strings (guaranteed by `.toISOString()`), lexical and chronological ordering coincide, but this is a fragile invariant worth a one-line test/comment, not silent trust.
