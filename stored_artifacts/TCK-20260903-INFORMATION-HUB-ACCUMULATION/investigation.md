### `InformationProviderState` (`src/domains/information/providers.py:36-74`)
Frozen, slotted dataclass: `entity_id: int`, `archetype: InformationProviderArchetype`
(`MERCHANT`/`GUILD_MASTER`/`ELDER`), `reliability_score: float = 1.0`,
`knowledge_domains: Tuple[str, ...] = ()`, `knowledge_age: int = 0`. No accumulation field exists.
Registered on `AuthoritativeState.information_providers: Dict[int, InformationProviderState]`
(`src/core/state.py:1237`).

**New finding, more severe than the ticket's own pre-verified facts assumed**: grepping all of
`src/` (excluding tests) for `InformationProviderState(` and `information_providers[` returns
**zero construction/assignment sites**. `AuthoritativeState.information_providers` is never
populated anywhere in production code — not in `V2EntityBuilder`, not in any content/scenario
loader, not in `src/worldbuilding/`. The only two production readers are
`PaidInformationTransactionSystem.enforce()` (`src/engine/pipeline_phases/paid_information.py:89-91`,
which early-returns `update` unchanged when `providers` is empty — i.e. always, in any real
content-driven run) and `LeadContradictionSystem.enforce()` (which only *decrements* an existing
provider's `reliability_score`, a no-op when the dict is empty). The entire `InformationProviderState`
mechanism is exercised only by unit tests (`tests/unit/cognition/test_information_seeking.py`'s
`._make_provider()` helper) — it has **zero live instances in any real corpus world today**. This
means "give Guides a real knowledge-accumulation mechanism" is not extending a live NPC system; it
is extending a typed shape with no seeding path at all. See "Risks and Open Questions" — this
changes the ticket's effective scope size.

### Quest-completion / "report back" hook (Scope item 1 — grep for the real event/callback point)
- `src/town/guild.py:16` `GuildAction.visit()` is the only code path that constructs a real
  `QuestState` via `QuestGenerator.generate_quests()`. Confirmed (`tickets/done/
  TCK-20260807-QUEST-GUILDACTION-DEAD-WIRING.md`) it is now live-wired via a dedicated
  `GuildVisitPhase` pipeline phase (`src/engine/pipeline_phases/guild_visit.py`), gated behind
  `ENABLE_GUILD_QUEST_GENERATION` (currently `OFF`).
- **Leads generated by `GuildAction.visit()` are explicitly `source_entity_id=None  # GUILD`**
  (`src/town/guild.py:38`) — deliberately hub-sourced, not entity-sourced. There is no NPC entity
  behind the Guild hub in the live path; `town_hall` (a `BuildingState`, not an `EntityState`) is
  reused as the guild location because "no world in the real content corpus ever declares a
  dedicated guild building" (per the dead-wiring ticket's own finding). This is a structural
  mismatch with the ticket's framing: `InformationProviderState.entity_id` is keyed to an
  `EntityState`, but the real hub that hands out quests is a `BuildingState` with no entity
  identity — there is no live "Guide" NPC to attach an `InformationProviderState` record to today.
- `QuestState` (`src/core/models/quests.py:36-59`) has **both** `source_building_id: Optional[int]`
  and `source_entity_id: Optional[int]` fields already declared. Only `source_building_id` is ever
  populated (`src/quests/generator.py:230`, `q.replace(source_building_id=building_id)`) —
  `source_entity_id` is a dead/unpopulated field on `QuestState` today, not a missing field. This
  is a much cheaper attribution path than adding a new field, *if* Plan decides to populate it —
  but it still requires deciding what to populate it with, since the hub has no entity today.
- The real "report back" hook point, confirmed by direct read: `QuestResolutionSystem.enforce()`
  (`src/engine/quests.py:154-253`), called from `QuestRewardPhase.resolve()`
  (`src/engine/pipeline_phases/quests.py:13-28`, itself called from `AuthoritativeApplyPipeline.refine()`,
  `src/engine/pipeline.py:500-501`). Its `is_newly_completed` branch (`src/engine/quests.py:197`,
  `updated_quest.quest_status == COMPLETED and project.quest_status == ACTIVE`) is the exact
  moment a quest transitions from active to reported-back; it already does one side-effect keyed
  off `quest_kind` there (`ESCORT` → `ReputationUpdateService.process_witnessed_event(...)`,
  lines 221-235) — a directly analogous, already-proven pattern for "quest completion triggers a
  typed side-effect via `StateUpdate`," not a novel shape to invent.
- **However**, real end-to-end quest completion is itself narrow today.
  `TCK-20260807-QUEST-EVALUATOR-GATHER-BOUNTY-LIBERATE-GAP` (DONE) found `QuestGenerator.generate()`
  never populates `QuestState.metadata` at all, so no progress evaluator could ever match a real
  generated quest; it fixed **only** the EXPLORE path (deterministic `target_pos`). HUNT was
  explicitly deferred to a new follow-up (no template field for target identity); GATHER/BOUNTY/
  LIBERATE remain unfixed. So even once `ENABLE_GUILD_QUEST_GENERATION` is flipped ON, only
  EXPLORE quests can realistically reach `COMPLETED`/`REWARD_PENDING` in a real run today.

**Conclusion for Scope item 1**: the hook point (`QuestResolutionSystem.enforce()`'s
`is_newly_completed` branch) is real and precedented. But "a quest a Guide assigned is reported
back" cannot be built as a live-entity-to-live-entity flow today — the Guide is a building-level
hub with no entity identity in the live path, `QuestState.source_entity_id` is a dead field, and
`InformationProviderState` has zero live instances. This is a genuinely bigger gap than the
ticket's own scope line ("Trigger accumulation on a concrete event") implies; it is flagged as an
open question below, not silently resolved.

### Faction territory/diplomatic propagation precedent (Scope item 2)
- `FactionState` (`src/core/state.py:639-676`): `territory: Tuple[str, ...]` (region_ids
  controlled), `diplomatic_relations: Dict[str, DiplomaticState]`. No "City"/"Country" typed
  concept exists anywhere in `src/` — confirmed via grep of `docs/mechanics/regional_sovereignty.md`
  and `src/core/enums.py`. The atlas's "City"/"Country" language (idea 41's own title) maps onto
  existing vocabulary as: **City ≈ `region_id`** (an element of `FactionState.territory`),
  **Country ≈ `Faction`/`FactionState`** itself. This mapping should be made explicit in the plan
  rather than inventing new terms.
- **Real, already-proven precedent for walking `territory` to propagate a signal**:
  `FactionAwarenessService.compute_tension_updates()` (`src/engine/faction_decision.py:174-208`)
  reads `state.recent_world_events` (bounded, one-tick-lagged window populated via
  `StateUpdate.world_events_add` → `AuthoritativeState.recent_world_events`,
  `src/core/state.py:1234`), filters by `WorldEventCategory.RESOURCE_DEPLETED`, and for each event
  whose `region_id` is in `fs.territory`, emits `FactionUpdate(tension_delta=0.1)`. This exact
  pattern was reused again, just landed on this branch, by `TCK-20260903-ECONOMIC-VACANCY-SIGNAL`
  (`stored_artifacts/TCK-20260903-ECONOMIC-VACANCY-SIGNAL/investigation.md`) — confirming it is a
  standing, reusable convention for "walk faction territory against a bounded recent-events
  window," not a one-off. It is the recommended mechanism to reuse for City-to-City propagation
  (all regions in the same faction's `territory`) rather than inventing a new topology walk.
- **No existing precedent walks `diplomatic_relations` for signal propagation** (as opposed to
  diplomatic-state transitions themselves). `diplomatic_relations` is actively read elsewhere
  (`src/domains/faction/diplomatic_state_machine.py`, `src/engine/military_conflict.py:59,201`,
  `src/domains/adventure/scoring.py:147`) via the established
  `fs.diplomatic_relations.get(other_fid, DiplomaticState.NEUTRAL)` idiom — that idiom is the
  correct one to reuse for City-to-Country (cross-faction) propagation, gated on relation (e.g.
  propagate to `ALLIED`/`NEUTRAL`, not `HOSTILE`/`WAR` — an explicit Plan-phase decision, not
  assumed here).
- `WorldEventCategory` (`src/domains/world_emergence/schema.py:15-45`) already declares
  `RUMOR_CONFIRMED`/`RUMOR_CONTRADICTED` members — confirmed via grep these are **never emitted or
  consumed anywhere in `src/`** (dead enum members). They read as a plausible category to reuse or
  extend for "critical information" propagation events, but are not currently wired to anything —
  flagged as a candidate, not a working mechanism.

## Risks and Open Questions
1. **(Blocking, requires a Plan-phase decision, do not assume)** `InformationProviderState` has
   zero live production instances (no seeding path anywhere in `src/`). Building an accumulation
   mechanism on a record that never exists in a real run is scaffolding, not observable behavior,
   until something also seeds at least one `InformationProviderState`. Options for Plan to weigh:
   (a) scope this ticket to *also* seed a minimal `InformationProviderState` (e.g. one per
   `GUILD_MASTER`-archetype building/entity) — expands scope meaningfully; (b) scope this ticket to
   build the accumulation mechanism and typed update path only, verified via direct unit-level
   `StateUpdate`/`AuthoritativeState` construction (matching how `PaidInformationTransactionSystem`/
   `LeadContradictionSystem` are themselves tested — via `_make_provider()`-style fixtures, not a
   real corpus world), and file the seeding gap as an explicit separate follow-up ticket. This
   investigation does not resolve which option Plan should take.
2. **(Blocking, requires a Plan-phase decision)** The Guild hub has no entity identity in the live
   path (`source_entity_id=None # GUILD`, `BuildingState` not `EntityState`). "A quest a Guide
   assigned is reported back" as literally scoped implies a specific NPC entity assigned the
   quest — that does not exist today. Plan must decide whether to (a) redefine the trigger as
   building-keyed (requires either a new field on `InformationProviderState` or a
   `source_building_id` for the trigger instead of `entity_id`), or (b) treat any
   `GUILD_MASTER`-archetype provider co-located at the same building as the completing quest's
   `source_building_id` as the accumulation target (requires a building→provider lookup that does
   not exist), or (c) narrow scope to only entity-sourced quests (which do not exist in the live
   path either, since peer-sourced quest-giving needs Conversation, confirmed out of scope).
3. Real quest completion is narrow: only EXPLORE quests can reach `COMPLETED` today (confirmed via
   `TCK-20260807-QUEST-EVALUATOR-GATHER-BOUNTY-LIBERATE-GAP`). Any test claiming "before/after
   state assertion... when a quest a Guide assigned is reported back" (AC #1) should either use
   EXPLORE (the only kind that reliably completes) or drive the scenario at the unit level via
   direct `QuestResolutionSystem.enforce()` calls rather than a full corpus-world run, to avoid
   silently depending on the unfixed HUNT/GATHER/BOUNTY/LIBERATE paths.
4. `ENABLE_GUILD_QUEST_GENERATION` is itself OFF by default — any test exercising the live
   `GuildVisitPhase`→`GuildAction.visit()` path must explicitly enable it via
   `FeatureFlagManager` overrides, matching that ticket's own test pattern
   (`tests/unit/engine/test_guild_visit_phase.py`).
5. "City"/"Country" have no typed representation — Plan must state explicitly that City = a
   `region_id` in `FactionState.territory` and Country = the owning `FactionState`/`Faction`, not
   invent new topology types (the ticket's own Scope already states "no new topology type," this
   just makes the mapping concrete).
6. Neither `WorldEvent.severity` nor `SimulationEvent.severity` is currently used as a propagation
   gate anywhere — "critical" needs an explicit, stated threshold/definition in Plan, not an
   implicit one.

## Anti-Drift Hazards
- Do not build a `Conversation`/entity-dialogue system as a side effect of solving Guide-to-Guide
  exchange — explicitly out of scope; the atlas's own idea 33 text says Guide-to-Guide "needs no
  new mechanism at all — it's the same Conversation system," which does not exist, so this must be
  reframed at the state level (e.g., a direct `StateUpdate.information_providers_update` merge
  between two provider records) or explicitly deferred, not silently built as a mini-dialogue
  system.
- Do not add a new topology field to `FactionState` for propagation — Scope explicitly requires
  reusing `territory`/`diplomatic_relations` as they exist today.
- Do not conflate this ticket's new accumulation write path with `LeadContradictionSystem`'s
  existing decrement path in a way that changes decrement behavior or its floor
  (`_RELIABILITY_FLOOR = 0.1`) — both must coexist as independent branches merging into the same
  `information_providers_update` dict via `StateUpdate.merge()`.
- Do not silently "fix" the unpopulated `QuestState.metadata`/`source_entity_id` gaps for
  HUNT/GATHER/BOUNTY/LIBERATE quest kinds as a side effect — those are separately scoped,
  pre-existing, already-disclosed gaps (see Prior Work) with their own follow-up tickets; touching
  them here would be uncontrolled scope creep.
- Do not flip `ENABLE_GUILD_QUEST_GENERATION` ON as a side effect of making this ticket's own
  tests pass against a real corpus world — that is a separate rollout decision outside this
  ticket's scope; tests should enable it locally via `FeatureFlagManager` overrides only.
- Do not silently redefine "reliability_score" itself as the accumulation metric — Scope explicitly
  asks for a "real accumulation mechanism," implying a new/distinct field or concept
  (e.g. cumulative knowledge count, freshness bump), not just letting `reliability_score` increase
  in the opposite direction of `LeadContradictionSystem`'s decrement (that would risk colliding
  semantics — "trustworthiness" vs "how much knowledge accumulated" are different concepts even
  though both live on the same record).
