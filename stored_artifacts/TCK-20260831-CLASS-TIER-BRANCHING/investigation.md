## Current Behavior

**1. `CLASS_REGISTRY` (`src/core/classes.py:1-51`) — confirmed real current shape.**
```python
@dataclass(frozen=True)
class ClassDefinition:
    id: str
    name: str
    base_hp: int
    base_atk: int
    base_def: int
    starting_skills: List[str] = field(default_factory=list)
    starting_gear: Dict[str, str] = field(default_factory=dict)  # SlotID -> ItemID

CLASS_REGISTRY: Dict[str, ClassDefinition] = {"NOVICE": ..., "WARRIOR": ..., "MAGE": ..., "ROGUE": ...}
```
Only 4 entries. **No `RANGER` entry exists**, despite `docs/core/attributes_and_classes.md` §5 documenting Ranger as one of 4 base "Tier 1" classes (see finding #4). `ClassDefinition` has **no attribute-bonus field, no cap-bonus field, no tier field, no next-tier/breakthrough-requirement field** — only `base_hp`/`base_atk`/`base_def`/`starting_skills`/`starting_gear`. This is a flat, single-tier registry today; there is no existing "next tier" concept anywhere in code.

**2. `class_id` already exists as durable state, spawn-only.** `IdentityComponent.class_id: str = "NOVICE"` (`src/core/state.py:482`), included in `to_canonical_dict()` (line 500), copied through `ApplyPath._fast_replace_identity` (`src/engine/apply.py:524`) and the canonical/frozen conversion (`src/core/state.py:868`). `V2EntityBuilder.identity(class_id=...)` (`src/core/builder.py:176,198`) stores it at spawn only — confirmed by the already-existing test `tests/unit/core/test_class_registry.py::test_builder_stores_class_id_without_hidden_registry_application`: "the clean builder only stores class_id... does not automatically apply class registry stats, skills, or gear." **Nothing in `src/` ever writes `class_id` after spawn** — grep for `class_id` across `src/` returns only the 4 sites above (definition, builder param, 2 canonical-dict copies), no assignment inside any `*Update`/`*Patch` apply-path file. This is PROG-108's spawn-only law (see Mechanics/Engine Constraints).

**3. `IdentityUpdate` (`src/core/updates.py:220-267`) has no `class_id_set` field today.** Its 15 fields (`role_set`, `faction_set`, `recipes_learned`, `craft_target`, `evolution_level_set`, `life_stage_set`, `evolution_points_delta`, `veterancy_points_delta`, `breakthroughs_add`, `unspent_ap_delta`, `unspent_ap_set`, `learned_skills`, `traits_add`, `traits_remove`, `cooldown_updates`) cover every other identity-durable field except `class_id`. `is_noop()` (239-246) and `merge()` (248-267) would both need a new `class_id_set` branch, following the exact pattern already used for `evolution_level_set`/`life_stage_set` (both simple `Optional[...]` "last-write-wins" fields, not accumulating deltas).

**4. `EvolutionSystem.kind_set` — the real precedent this ticket must generalize, exact apply-path trace.**
- `EvolutionSystem.evaluate()` (`src/engine/evolution.py:20-154`) computes `new_kind` via `_get_evolved_kind(entity.kind)` (156-169), a **hardcoded, linear, single-target mapping**: `{"GOBLIN": "GOBLIN_WARRIOR", "GOBLIN_WARRIOR": "ORC_SCOUT", "WOLF": "DIRE_WOLF", "HERO": "LEGEND_HERO"}`, plus a numeric-suffix increment rule (`goblin_0` → `goblin_1` → `goblin_2`...). **This is exactly the "single linear chain" the ticket's Request Summary says not to copy** — one input kind maps to exactly one output kind, no branch choice.
- The chosen `new_kind` is written onto `update.entity_updates[e_id] = replace(ent_upd, kind_set=new_kind, ...)` (evolution.py:136-152) — `EntityUpdate.kind_set: Optional[str]` (`src/core/updates.py:631`).
- **Apply-path mechanism for `kind_set` (the pattern `class_id_set` must mirror):** `extract_patches()` (`src/engine/patches.py:683-729`) checks `if update.kind_set is not None: patches.append(KindPatch(entity_id, kind_set=update.kind_set))` (line 689-690). `KindPatch` (patches.py:38-52) is a `ComponentPatch` subclass: `is_noop()` returns `kind_set is None`; `merge()` prefers the newer non-`None` value (last-write-wins); `apply(entity, changes)` does `if self.kind_set is not None and self.kind_set != entity.kind: changes["kind"] = self.kind_set` (patches.py:50-52). `ApplyPath._fast_replace_entity` (`src/engine/apply.py:568-576`) then does `object.__setattr__(res, "kind", changes.get("kind", entity.kind))` to materialize it into the new frozen `EntityState`.
- `EvolutionSystem` also emits accompanying `EquipmentUpdate`/`AttributeUpdate`/`CombatUpdate` in the **same** `EntityUpdate` when it evolves (evolution.py:100-134), which is what actually makes the transformation observable in combat stats — see finding #6 below for why a bare `kind_set`/`class_id_set` alone would not be.

**5. `IdentityPatch.apply()` (`src/engine/patches.py:170-228`) is the sibling patch that would carry a new `class_id_set` branch.** It currently reads every other `IdentityUpdate` "_set" field (`role_set`, `faction_set`, `evolution_level_set`, `life_stage_set`, `unspent_ap_set`) into local vars and writes the reconstructed `IdentityComponent` via `replace(new_id, role=rl, faction=fac, ..., group_id=gid, properties=..., latest_intent_results=...)` (223-228) — `class_id` is not among the kwargs passed to this `replace()` call, so today it always survives unchanged (dataclass `replace` preserves unlisted fields). Adding `class_id_set` here requires: (a) reading `new_id.class_id` into a local `cls_id` var, (b) `if u_id.class_id_set is not None: cls_id = u_id.class_id_set`, (c) adding `class_id=cls_id` to the final `replace(...)` call. This is the concrete apply-path hook point — the same file/class as `KindPatch`, but a different patch (`IdentityPatch`, not a new dedicated patch type), consistent with `class_id` being an `IdentityComponent` field, not an `EntityState`-top-level field like `kind`.

**6. Confirmed pre-existing gap that directly threatens whether any tier's stat bonuses stay observable: the only live call site of `get_effective_stats()` never passes class base stats.** `grep -rn "get_effective_stats(" src/` (excluding the definition) returns exactly one call site: `src/engine/apply.py:481-487`, inside the `stats_dirty` branch of `_apply_entity_update_to_dict`:
  ```python
  derived = SkillScalingService.get_effective_stats(
      new_att, new_eq,
      wounds=new_com.wounds, scars=new_com.scars,
      learned_skills=new_id.learned_skills, traits=new_id.traits,
      current_role=new_com.tactical_role, active_breakthroughs=new_id.active_breakthroughs
  )
  ```
  This never passes `base_hp`/`base_atk`/`base_def`/`base_evasion`, so `SkillScalingService.get_effective_stats` (`src/engine/rpg_depth.py:342-354`) falls back to its own defaults (`base_hp=100, base_atk=10, base_def=5, base_evasion=0.05` — the `NOVICE` values, not the entity's actual class). The return fully **replaces** `combat.max_hp`/`atk`/`def_stat`/`evasion` (`apply.py:490-497`, `replace(new_com, max_hp=derived["max_hp"], ...)` — not additive). **Concretely: a `WARRIOR` (base_hp=150) that triggers *any* `stats_dirty` event post-spawn (a level-up, a breakthrough grant, an AP spend, equipment change, a wound) has its effective `max_hp` recomputed from the generic `100` default, not `150`.** This is a pre-existing bug, independent of this ticket, but directly load-bearing for AC #4 ("a tier's stat bonuses do not decrease average combat win-rate") — if tier bonuses are meant to persist as an ongoing combat advantage (not just a one-tick snapshot at the milestone moment), they must be threaded through this same `base_hp`/`base_atk`/`base_def` parameter chain, or they will be silently wiped the next time `stats_dirty` fires for any unrelated reason. See Risks and Anti-Drift Hazards.

**7. `docs/core/attributes_and_classes.md` §5 already documents a *different*, non-branching "Hero Classes" tier tree — a major pre-existing design/doc artifact, entirely unimplemented in code.** It defines "Base Classes (Tier 1)" (Warrior/Ranger/Mage/Rogue, each with Primary Scaling grades, attribute Bonuses, Cap Bonuses), "Breakthrough Classes (Tier 2)" (Champion/Sharpshooter/Archmage/Assassin, each keyed to exactly **one** Tier-1 "From" class), and "Transcendence Classes (Tier 3)" (Warlord/Storm Caller/Ghost Stalker/Nightshade). The doc's own mermaid diagram is **strictly linear per base class** — `Warrior → Champion → Warlord`, `Ranger → Sharpshooter → (unlabeled edge target 'F')`, `Mage → Archmage → Ghost Stalker` (note: this contradicts the doc's own prose table, which says Ghost Stalker's "From" is Sharpshooter, not Archmage — a pre-existing internal inconsistency in this doc, out of this ticket's scope to fix but worth flagging to Plan), `Rogue → Assassin → Nightshade`. **None of Champion/Sharpshooter/Archmage/Assassin/Warlord/Storm Caller/Ghost Stalker/Nightshade/Ranger exist anywhere in `CLASS_REGISTRY` or any other code** — confirmed via `grep -rn "Champion\|Archmage\|Sharpshooter\|Assassin\|Warlord\|Storm Caller\|Ghost Stalker\|Nightshade" src/` returning zero hits outside comments/strings unrelated to classes. This doc content is 100% aspirational/undocumented-as-implemented. **Critically, it is also NOT a branching design** — each Tier-1 class has exactly one named Tier-2 destination, the opposite of this ticket's AC #1 ("≥2 mutually-exclusive next-tier options per base class, not a single linear chain"). See Risks — Plan must decide how the new registry relates to this existing (but unimplemented) doc content.

## Risks and Open Questions

1. **Exact registry shape/location is a genuine Plan-phase decision, not settled by this investigation — but the evidence points toward a new, separate structure rather than extending `ClassDefinition`.** Two real options: (a) extend `src/core/classes.py`'s existing `ClassDefinition`/`CLASS_REGISTRY` with a `next_tiers: List[TierOption]` field (keeps everything in one file, one import site, matches the "base class → tier options" framing directly), or (b) a new sibling structure (e.g. `CLASS_TIER_REGISTRY: Dict[str, List[TierOption]]` in a new `src/progression/class_tiers.py`, mirroring `BreakthroughService`'s own module-per-mechanism placement in `src/progression/`). **Recommendation, not a decision**: option (b) — `src/progression/class_tiers.py` — fits the codebase's existing convention better: `BreakthroughService` (perks), `LevelingService` (XP/level), `VeterancyService` (veterancy) are each a separate `src/progression/` module with their own registry, none of them living inside `src/core/classes.py`; `CLASS_REGISTRY` itself is a `src/core/` primitive (base identity data, imported by the builder), while tier-branching is progression *logic* (milestone-gated, choice-bearing), matching the existing `src/core/` (data) vs `src/progression/` (logic/services) split this repo already draws. Each `TierOption` entry should minimally carry: a stable `id` (the new `class_id` value, e.g. `"WARRIOR_BERSERKER"`), a `from_class_id` (which base class it branches from), a human `name`, and `attribute_bonuses: Dict[str, int]` (mirroring `BreakthroughService.REGISTRY`'s existing `attribute_bonuses` shape exactly, for consistency and because `apply_bonuses`'s established pattern already knows how to consume that shape if Plan chooses to reuse it rather than invent a second bonus-application mechanism).
2. **How the new registry relates to the pre-existing, unimplemented `docs/core/attributes_and_classes.md` §5 tier tree is unresolved and must not be silently ignored (see Current Behavior #7).** That doc already claims a specific (linear, not branching) Tier1→Tier2→Tier3 design with named classes (Champion, Archmage, etc.) that exist nowhere in code. Plan has three real options: (a) treat §5 as stale/aspirational and build something new and different (branching), updating §5 to describe the new reality, replacing the old tree; (b) reuse §5's named tiers but reshape them to be branching (e.g. give `WARRIOR` two Tier-2 options instead of just `Champion`) — requires inventing a second option per class not in the current doc; (c) build the new mechanism as fully independent/parallel terminology (different class_id namespace) and leave §5 as documenting a distinct, still-unimplemented aspirational track. **This blocks a clean Plan** if not explicitly decided — recommend Plan pick (a) or (b) rather than (c), since (c) would leave two competing, confusing "class advancement" doc sections both under `docs/core/` and `docs/mechanics/`-adjacent authority.
3. **The stats_dirty / base-stat-sourcing gap (Current Behavior #6) is not named in this ticket's Scope or Out of Scope, but directly determines whether AC #4 is even testable in a meaningful way.** If tier stat bonuses are applied only via a one-time `AttributeUpdate`/`CombatUpdate` bundled in the same tick as `class_id_set` (mirroring how `EvolutionSystem` bundles its own updates), the bonus lands in `entity.attributes`/`entity.combat` directly and *does* survive subsequent `stats_dirty` recomputes for the `strength`/`vitality`/`endurance`/`agility` portion (since those flow through `AttributeComponent`, which — unlike `combat.max_hp`/`atk`/`def_stat` — is not reset to a generic default). This means: **tier bonuses expressed as `AttributeUpdate` deltas (matching `BreakthroughService`'s `attribute_bonuses` shape) are safe from the base-stat-reset bug; tier bonuses expressed as direct `CombatUpdate` (`max_hp_delta`/`atk_delta`) deltas are not**, because the very next `stats_dirty` event fully replaces `combat.max_hp`/`atk`/`def_stat` from `get_effective_stats()`'s generic-default-sourced return, discarding any prior delta-based combat bonus that wasn't re-derived from attributes. **Recommendation: Plan should design tier bonuses exclusively as attribute-level bonuses (like `BreakthroughService.REGISTRY`'s `attribute_bonuses`), not combat-stat deltas**, to sidestep this pre-existing bug entirely rather than needing to fix it as an unscoped dependency. Flagging as a hard constraint on the implementation shape, not merely an FYI.
4. **AC #4's "metamorphic-style comparison" verifying win-rate has no existing lightweight harness to reuse.** `src/lab/metamorphic.py` (`MetamorphicRuleEngine`/`MetamorphicComparisonResult`) exists but is built for full simulation-run comparison (`src/lab/`, used by the `investigate-simulation-result`/`propose-simulation-enhancements` workflows), not a targeted "run N isolated combats, compare win rate" unit/integration test. No `win_rate`-named test exists anywhere in `tests/` today (`grep -rln "win_rate\|win rate" tests/ src/` returns zero source/test hits). This is genuinely new test infrastructure — a small helper that runs `CombatResolutionSystem`/`src/engine/combat.py` head-to-head N times with a fixed seed sweep, comparing win totals with vs. without the tier bonus applied, is the natural shape, but it does not yet exist and Plan must scope its size explicitly (this is not "reuse `src/lab/metamorphic.py`" — that module's `MutationSpec`/scenario-file-driven design is a much heavier fit than what a single AC needs).

## Anti-Drift Hazards

- **Do not implement tier stat bonuses as `CombatUpdate` deltas (`max_hp_delta`/`atk_delta`).** They will be silently discarded by the very next `stats_dirty` recompute due to the pre-existing base-stat-sourcing gap (Current Behavior #6 / Risk #3). Use `AttributeUpdate`-shaped or `BreakthroughService.REGISTRY`-shaped attribute bonuses instead.
- **Do not silently fix the `get_effective_stats()` base_hp/atk/def sourcing gap (Current Behavior #6) as a drive-by.** It is a real, confirmed, pre-existing bug that predates this ticket and affects every class (not just new tiers) — fixing it is a materially larger, separately-scoped change (it would also change spawn-time `WARRIOR`/`MAGE`/`ROGUE` base-stat persistence across level-ups, a behavior change well beyond "add class-tier branching") and needs its own ticket/decision doc, not an incidental fix buried inside this one.
- **Do not build the new registry inside `BreakthroughService.REGISTRY` itself, and do not conflate "tier branch" with "breakthrough."** The ticket's Out of Scope is explicit: breakthroughs remain always-additive, non-exclusive perks — a separate concept. Even though the recommended `attribute_bonuses` *shape* is the same (Risk #1), the registry, the field (`class_id_set` vs `breakthroughs_add`), and the mutual-exclusivity semantics must stay entirely separate mechanisms.
- **Do not silently redefine or delete `docs/core/attributes_and_classes.md` §5's existing content without an explicit Plan-phase call** (Risk #2) — it is `authority: P0`, `status: authoritative`, and describes the same subject area; overwriting it without reconciling is exactly the kind of undocumented mechanics change the Authoritative Mechanics Rule forbids.
- **Do not let the new `class_id_set` field bypass `is_noop()`/`merge()` on `IdentityUpdate`.** Every existing `*_set` field on this dataclass is included in both methods (updates.py:239-246, 248-267); a new field omitted from either would silently break update-merging across ticks/phases (the same class of bug the `stats_dirty` omission already demonstrates for other fields).
- **Do not construct a live AI/decision producer for branch selection as part of this ticket unless Plan explicitly re-scopes it in.** The ticket's Scope only requires the registry + typed field + apply-path wiring + the two required tests; per Prior Work (TCK-20260808-TRAIT-EXPRESSED-PRODUCER-INVESTIGATION), landing a fully-wired-but-uninvoked-in-production mechanism is an accepted, precedented end state for this codebase, not a defect to "complete" by inventing an unscoped goal/decision system.
