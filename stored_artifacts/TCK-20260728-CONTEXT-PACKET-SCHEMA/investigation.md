## Risks and Open Questions

- **Open Decision 3 itself is the crux of this ticket** and must be resolved, not deferred. The
  cleanest resolution consistent with the ticket's own instruction ("build on
  docs/REGISTRY.yaml's existing status/authority enums rather than inventing a parallel system")
  is: a packet's `authority` field is populated directly from REGISTRY.yaml's `authority`
  (`P0`/`P1`/`P2`) for any doc-source, and `freshness` is derived from `status` +
  `last_verified` (e.g. `authoritative` + recent `last_verified` = freshest; `historical`/`archive`
  = stale by construction) rather than a new numeric score. This investigation recommends that
  resolution but does **not** pre-write the planner's exact prose — the planner/implementer should
  treat this as the primary design decision to finalize, citing this investigation's field-mapping
  evidence.
- **Sources with no REGISTRY.yaml entry** (code symbols, test files, Graphify nodes,
  `docs/parity_ledger/` entries, ticket bodies in `tickets/inprogress/`) have no `status`/
  `authority` triple at all. The doc must state an explicit fallback (e.g., "non-doc sources carry
  `authority: null` / a documented default, and this is itself a flagged gap") rather than silently
  implying every `included[]` entry always has a real REGISTRY-backed authority value. Confirmed:
  `tools/generate_registry.py` only indexes `docs/` (minus skipped subdirs) and `tickets/done/` —
  never `src/`, `tests/`, `tickets/inprogress/`, or `docs/parity_ledger/`.
- **"Conflicting active documents" has no existing representation** to build on — this is a genuine
  gap the ticket's own Assumptions/Open Questions section already anticipates ("the doc must
  propose a doc-only resolution or explicitly flag this as an unresolved gap rather than silently
  inventing new registry machinery"). The safest resolution is to document a doc-only tie-break
  rule (e.g., "when two `status: active`/`authoritative` docs conflict on the same subject, the
  packet includes both, ranks by `authority` then `last_verified` recency, and flags the
  lower-ranked one via `inclusion_reason`") explicitly framed as advisory documentation guidance,
  not a new registry field/schema change — since Out of Scope explicitly forbids "Replacing or
  modifying docs/REGISTRY.yaml's existing status/authority enum values."
- Tier is `standard`, meaning this ticket is architecture-review-worthy per its own Assumptions
  note. There is no `src/`/`tools/` diff for an architecture-reviewer to check against durable-state
  rules, so the review will necessarily focus on doc-schema-shape correctness and whether Open
  Decision 3 is honestly resolved (not overclaimed) — flag this so the implementer doesn't skip
  requesting review on the theory that "it's just a doc."

  construction/serialization code. The doc must read as a specification for a *future* Phase 3
