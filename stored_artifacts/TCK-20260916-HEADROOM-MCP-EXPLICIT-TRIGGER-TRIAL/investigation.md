# Investigation — TCK-20260916-HEADROOM-MCP-EXPLICIT-TRIGGER-TRIAL

This ticket ran in two passes: an earlier registration + smoke test (recorded directly in the
ticket, folded into PR #228), and this pass — the systematic paired measurement that is the
ticket's own actual substance.

## Payload selection

Used exactly the 4 payload types the ticket's own Scope names, one real file each, no
substitution or tuning:

- `docs/REGISTRY.yaml` — the real, current file (1.6MB).
- A real junit XML: generated by running `pytest tests/tools/ -m "not slow and not extra_slow"
  --junit-xml=...` (2767 real test results, 427KB) rather than inventing one, since none existed
  locally under `reports/junit/` at the time.
- A real `agent-monitoring/data/2026-W36/tools.jsonl` shard (15MB) — one of the larger real
  shards, matching the ticket's own named `agent-monitoring/data/**/*.jsonl` target.
- `graphify-out/graph.json` (54MB) — the exact file the ticket names, at its real current size.

Every file was copied to a scratch temp directory before measurement; none was compressed in
place.

## Real MCP client, not a bypass

Reused the same approach as the prior smoke test: the `mcp` Python SDK's own
`stdio_client`/`ClientSession`, launched via `tools/start_headroom_mcp.sh` (the same launcher a
real Claude Code session would use), speaking the real MCP protocol — never a direct Python
import of Headroom's internal compression functions, which would not have exercised the actual
registered integration.

## Findings, not assumed from the smoke test

The smoke test's own small-payload results (0%, 0%, 7.5%) did **not** reliably predict this
trial's real results — a completely new transform, `inflation_guard:reverted`, appeared on the
real 15MB `tools.jsonl` shard (the smoke test's largest payload was only 66KB), and a real
20-second content-analysis timeout appeared on the 54MB `graph.json` (far larger than anything the
smoke test tried). Both were investigated by reading the real warning lines the CLI itself
printed, not guessed at:

- `"Optimization inflated tokens (4283819 -> 4293204); reverting to original messages"` —
  `inflation_guard:reverted` is Headroom's own safety mechanism against a net-harmful transform.
- `"ContentRouter single-cache-miss compression exceeded 20.0s; failing open via PASSTHROUGH"` —
  a real, previously-undocumented operational limit on large-file content analysis.

`docs/REGISTRY.yaml`'s 99.5% result was cross-checked against `headroom_stats`'s own per-event log
(`strategy: "router:mixed:0.01"`) to confirm the number wasn't an artifact of the reporting layer.

## The `headroom_stats` aggregate discrepancy, checked rather than assumed

`headroom_stats` after this trial reported `combined.total_compressions: 7`, not the 4 this trial
itself made. Rather than reporting this as unexplained or assuming a concurrent session was
interfering, read `session_stats.jsonl` directly — every extra compress/retrieve pair carries a
PID from this same ticket's own earlier smoke-test script invocations (different subprocess PIDs
per separate script run, all from this same session, all earlier the same day). `headroom_stats`
is a cumulative view over the isolated store's full history, not a per-invocation report — a real
behavioral property of the tool, not a bug or an isolation failure, recorded as a finding so a
future reader of `headroom_stats` doesn't misread it the same way on first glance.
