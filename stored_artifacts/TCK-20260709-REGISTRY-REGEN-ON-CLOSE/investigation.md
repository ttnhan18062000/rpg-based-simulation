**Established orchestrator-verified self-check pattern** (the two precedents the ticket asks to mirror):

- **`run_finalize_selfcheck`** (`tools/gate_checks/done_checker_static.py:404-414`): aggregates 3 post-Finalize conditions (`check_migration_complete`, `check_ticket_finalized`, `check_working_log_exactly_one_row`). Invoked via `bash()` from the orchestrator **after** the Finalize `agent()` call returns (`implement-ticket.js:1072-1080`, `finalizeCheckOutput`), using the `MARKER:json` + `indexOf` + `try/catch JSON.parse` idiom (lines 1082-1095). Any `FAIL` in the result **blocks**: pushes a `failed` event, calls `writeMonitoring('FINALIZE_INCOMPLETE')`, and returns `status: 'FINALIZE_INCOMPLETE'` (lines 1108-1118) — the ticket is not considered closed.
- **`check_monitoring_write_recorded`** (`done_checker_static.py:372-401`): a *separate*, deliberately **non-blocking** check, invoked via its own `bash()` call (`monitoringCheckOutput`, lines 1130-1145) **after** `writeMonitoring('DONE')` has already run and `status: 'DONE'` is locked in. A `FAIL` here only sets `monitoringWarning` and surfaces a `WARNING:` message in the final return payload (lines 1146-1164) — it can never flip `status` away from `'DONE'`, per CLAUDE.md's Hard Rule ("monitoring write failure must never fail the workflow").
- **`clean_data_runs_early`** (`done_checker_static.py:159-207`): a third pattern — invoked via `bash()` between Test and Parity phases (`implement-ticket.js:711-719`, `cleanupOutput`), not agent-prompt text. Its own failure (deletion error) **is** escalated to a new blocking status, `DATA_RUNS_CLEAN_FAILED` (lines 724-734) — showing that "orchestrator bash() checkpoint" does not by itself imply non-blocking; blocking vs. non-blocking is a separate design choice made per-checkpoint.

All three are triggered from `bash()` calls the orchestrator runs directly (never from inside an `agent()` prompt), using individually-quoted argv elements or JSON-marker-prefixed stdout — never a JSON blob embedded inside a `python3 -c "..."` string (the `p0ScanOutput` comment at `implement-ticket.js:759-763` documents why: unescaped nested quotes corrupt the script and silently fail open).

**Critical ordering constraint for this ticket:** `collect_tickets()` (`generate_registry.py:239`) only walks `tickets/done/*.md`, and `join_artifact_files()` (line 98) only reads `stored_artifacts/{ticket_id}/`. The Finalize agent's own steps 2 (move to `tickets/done/`) and 5 (migrate `staging_artifacts/` → `stored_artifacts/`) happen **inside** the Finalize `agent()` call (lines 1035, 1058-1059). Therefore any regen/self-check call must run **after** the Finalize `agent()` call returns (i.e., in the same orchestrator region as `finalizeCheckOutput`/`monitoringCheckOutput`, lines 1069+) — running it any earlier (e.g., as a Finalize agent-prompt step, or a Post-Test-style checkpoint like `clean_data_runs_early`) would regenerate against a registry that still has the ticket in `tickets/inprogress/` and would always fail the "entry exists" self-check.

## Risks and Open Questions

1. **Blocking vs. non-blocking for the "entry exists" self-check is genuinely unresolved by the ticket text — flagging, not assuming.** AC #3 says the self-check must confirm the entry "before Finalize completes," which reads as a gate (matching `run_finalize_selfcheck`'s existing blocking 3 conditions → `FINALIZE_INCOMPLETE`). But AC #2 says a nonzero *tool* exit is explicitly non-blocking (matching `check_monitoring_write_recorded`'s pattern). These are two different failure modes of two different things (the regen tool's own exit code vs. a downstream self-check reading its output) and the ticket does not say whether the self-check itself blocks. Concretely: does a missing registry entry for `tid` (post-regen) produce `FINALIZE_INCOMPLETE` (extend `run_finalize_selfcheck` to 4 conditions, breaking the existing `len(results) == 3` test — an update, not a break, but must be done deliberately), or a `monitoringWarning`-style non-blocking message? **This must be decided at Plan/Review, not assumed by Implement.**
2. **`bash()`'s exit-code semantics on a non-zero subprocess are not verifiable from repo inspection.** `bash()` is part of the Claude Code workflow-DSL harness, not defined anywhere in this repo (confirmed: no `function bash`/`const bash` definition found under `.claude/`). Every existing `bash()` call in `implement-ticket.js` that reads a result invokes a `python3 -c "..."` one-liner that always prints a `MARKER:json` and (as far as can be determined from the Python source) exits 0 on the success path even when the *check itself* reports FAIL — the FAIL is conveyed in the printed JSON, not the process exit code. Directly running `python3 tools/generate_registry.py` (which can legitimately `sys.exit(1)` on unrelated doc-frontmatter errors elsewhere in the repo, per `generate_registry.py:441`) breaks this pattern: if `bash()` throws/halts the workflow on a non-zero exit code, AC #2's "non-blocking warning" requirement cannot be satisfied by a bare `await bash('python3 tools/generate_registry.py')` call — the invocation must suppress/capture the exit code explicitly (e.g. `python3 tools/generate_registry.py; echo "EXIT:$?"` or wrapping the call from a `python3 -c` one-liner that imports `generate_registry()` directly and catches the return value, matching every other check in this file). **Flag for planner/implementer**: verify `bash()`'s actual non-zero-exit behavior (or default to the safe wrapped form) before assuming a bare invocation is safe.
3. **Unrelated pre-existing doc-frontmatter gaps could make the "non-blocking warning" branch fire on nearly every run.** `generate_registry.py` exits 1 if *any* doc under `docs/` (not just docs this ticket touches) is missing frontmatter — a repo-wide condition, not scoped to the closing ticket. If such gaps exist today (not confirmed either way in this investigation — not checked, out of scope to fix per this ticket's Out of Scope), every ticket close would log the same warning, becoming noise. This is explicitly called out as an assumption in the ticket itself ("Non-fatal handling must tolerate a pre-existing, unrelated frontmatter gap elsewhere in the repo without becoming a recurring false FINALIZE_INCOMPLETE signal") — confirms the AC's intent is for this warning path to be low-noise, not that it's currently gap-free.
4. **Placement ambiguity: Finalize agent-prompt step vs. post-agent orchestrator `bash()`.** As established in Current Behavior, the regen call *must* run after the Finalize `agent()` returns (ordering constraint on `tickets/done/` + `stored_artifacts/`). The ticket's own Scope text offers both options ("Finalize phase (or a Post-Finalize orchestrator bash() checkpoint...)") — but only the orchestrator `bash()` placement (after the Finalize `agent()` call, alongside `finalizeCheckOutput`) is ordering-correct; an agent-prompt step *inside* Finalize's numbered list (before step 2 has necessarily executed, since agent step ordering is prose-enforced, not language-enforced) is unsafe. This is not fully open — the evidence strongly favors post-agent `bash()` — but the ticket's own wording leaves it phrased as a choice.
5. **Concurrent-session interleaving**: if two `implement-ticket` runs finalize different tickets close together, a `docs/REGISTRY.yaml` regen at Finalize for run A could race a regen for run B (last-write-wins on a shared file, no session partitioning) — same class of accepted residual risk already documented for `clean_data_runs_early` ("Residual Risk: Concurrent-Session Overlap Window"). Not a blocker; should be noted as an accepted tradeoff if raised.

- **Do not implement the `--check`/CI drift-detection gate** — that is `TCK-20260709-REGISTRY-DRIFT-CHECK-GATE`, explicitly out of scope here and already scoped as a separate standard-tier ticket.
- **Do not fix pre-existing frontmatterless docs/tickets** to make the tool's exit code cleaner — that's `TCK-20260709-DOCSITE-TICKETS-FRONTMATTER-BACKFILL`'s territory (already done for the 3 known cases) and any *new* gaps found are out of scope per this ticket's own Out of Scope section.
- **Do not silently pick blocking vs. non-blocking for the self-check** (Risk #1) — this is a real design fork with a regression-test consequence (`len(results) == 3` in `test_run_finalize_selfcheck_all_pass`) either way; deciding it implicitly during Implement would violate the "no important decision undocumented" Definition-of-Done rule.
- **Do not touch `run_static_precheck`'s 5 conditions (Part A, pre-Finalize)** — this ticket's self-check is inherently a *post*-Finalize check (registry entry can only exist after the ticket is in `tickets/done/`), so it belongs in Part B (`run_finalize_selfcheck`'s family) or a wholly new sibling function, never Part A.
- **Do not let the regen call run before the Finalize `agent()`'s own move/migrate steps** (Risk #4) — this would make the self-check permanently fail (or worse, silently pass against a stale registry if the self-check is checking the wrong thing).
- **`Makefile`'s `docs-registry` target itself needs no change** — it already does exactly `python3 tools/generate_registry.py`; the new orchestrator call can literally reuse the same invocation string, not a copy/fork of the logic.
- **CLAUDE.md's "After Work" edit (AC #4) must stay a documentation-only change** — do not use it as a place to sneak in new *behavioral* rules beyond what's actually implemented in `implement-ticket.js`; the doc must describe what the code now does, matching this repo's Parity discipline principle (docs and code in sync) even though this ticket is workflow-tooling, not a Mechanics Bible chapter.
